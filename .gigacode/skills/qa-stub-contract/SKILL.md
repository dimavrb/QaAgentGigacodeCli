# Контракт и наблюдение заглушки

Кандидат для измерения: польза для живого GIGACODE пока не установлена. Читай в [STUBS.md](../../../docs/STUBS.md) короткий порядок и раздел выбранного транспорта, затем формат текущего этапа. Переданный снимок стандарта повторно читать не нужно.

Для каждой зависимости свяжи источник поведения → значимое условие matcher → положительный запрос → отрицательное отличие → ожидаемое наблюдение. Не переносить фактический ответ в expected: если широкое правило перехватывает оба запроса, успешный positive не доказывает контракт. Сохрани конфликт и конкретные затронутые сценарии; чужое правило нельзя изменять без назначенного target ID.

Различай три факта: запись создана, конфигурация перечитана, поведение проверено. `configure_only` заканчивается `stubs_configured`; он не разрешает публикацию или выдачу execution-ready. Без назначения допустим черновик и discovery. При `verify` оцени все зависимости каждого сценария: общий непроверенный stub блокирует все связанные сценарии, сохраняя независимую готовую часть.

Для Kafka проверь, что наблюдение относится к текущей корреляции и позиции после актуального readback. Отсутствие сообщения до конца назначенного окна — незавершённая negative-проба, а старое сообщение не подтверждает новую positive. Недоступный механизм capture остаётся ограничением, не выдуманной гарантией доставки. Поздняя правка требует новых наблюдений затронутых зависимостей; очистка ждёт их последнего использования.

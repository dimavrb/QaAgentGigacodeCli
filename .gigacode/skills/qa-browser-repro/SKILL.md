# Воспроизведение через Playwright MCP

## Сессия и наблюдение

1. Проверь доступность MCP и схемы нужных инструментов. При отсутствии сервера верни технический блокер, продолжая анализ материалов. Подключение описано в `docs/BROWSER_MCP.md`.
2. Получи URL стенда, сборку, роль, данные, шаги, ожидание и общий абсолютный browser_pool_path с доступным scripts/manage_browser_pool.py. По docs/BROWSER_PROFILES.md займи один свободный сервер непосредственно перед UI; используй возвращённые server/lease_id и фактический GIGACODE owner_task_id. Перед каждой короткой серией продли heartbeat; при отказе прекрати UI. Без реестра/при отсутствии свободных ресурсов верни техническую потребность, не обходи пул соседним сервером. Вкладки контекста разделяют storage; зависимые действия последовательны.
3. Сохраняй авторизацию только внутри короткого совместимого UI-набора. Между попытками проверь исходное состояние: URL не сбрасывает данные/storage. Перед анализом кода, отчётом, ожиданием вопроса/данных/ревью освободи профиль; для продолжения возьми новый lease и восстанови условия. Не закрывай после каждого клика, не резервируй профиль на всё расследование. Смена пользователя/окружения требует отдельного подтверждённого контекста. После закрытия isolated авторизация теряется.
4. После первого перехода прочитай snapshot. В проектном профиле автоматические снимки отключены: для поиска используй `browser_find`, для изучения состояния — `browser_snapshot` нужного контейнера с подходящей глубиной, если схема поддерживает это. Полный снимок нужен при неизвестной структуре. Не дублируй достаточное наблюдение. Скриншот нужен для визуального дефекта или доказательства.

## Действия

- Бери refs из свежего наблюдения; после навигации, смены вкладки или перестроения формы найди элементы снова. Для кода используй локаторы по role/name, label или test id, подтверждённые наблюдением. Не угадывай селекторы и не выбирай первый элемент из неоднозначного списка.
- Независимые поля заполняй через `browser_fill_form`. Зависимые поля разделяй контрольной точкой. Для дефекта клавиатуры сохрани нужную последовательность ввода вместо массового заполнения.
- Изученный стабильный участок можно выполнить короткой функцией через доступный `browser_run_code` или `browser_run_code_unsafe`. В версии проекта доступен второй вариант, исполняющий код в процессе сервера. Используй его для действий с `page` и краткого результата, без shell-команд, чтения посторонних файлов или установки пакетов. Пример — в `docs/BROWSER_MCP.md`.
- Завершай серию на неизвестном экране, условной ветке, диалоге, ошибке или критическом изменении данных. Верни выполненные шаги, URL и наблюдаемый результат; при исключении — последний завершённый шаг и ошибку. Не скрывай сбой и не продолжай после него.
- Используй auto-wait локаторов и ожидание конкретного состояния/текста. Фиксированная пауза допустима, когда требуется сценарием. Не меняй тайминги, события ввода, viewport, кэш или сеть ради ускорения, если они могут определять дефект.
- После timeout/разрыва связи сначала проверь UI и относящийся ответ API: операция могла завершиться. Повторяй только после подтверждения отсутствия результата и восстановления условий. При повторном одинаковом техническом сбое без новой гипотезы останови попытку с блокером. Автоматический повтор не считается независимым воспроизведением.
- `browser_evaluate` применяй для компактного чтения состояния. DOM-click, изменение storage и прямой API-запрос не заменяют пользовательские шаги подтверждения UI-дефекта.

## Доказательства

Создай папку `artifacts/browser/<task_id>/<request_id>/attempt-<n>/` с безопасными компонентами пути. При сохранении snapshot, screenshot, console и network указывай путь явно: `outputDir` относится только к автоматически названным файлам. Сохраняй диагностику до следующей навигации, связывая её со временем и попыткой. Читай сначала список запросов без успешной статики, затем конкретный относящийся запрос. Перед передачей проверь отсутствие секретов в копии доказательств.

В журнале попытки укажи исходные условия и восстановление, сборку, роль, шаги, ожидаемое поведение с источником, факт, время, ограничения и пути к существующим доказательствам. Для сбоя нужны состояние UI и относящиеся console/network либо объяснение их отсутствия. Ошибка console сама по себе не устанавливает причину дефекта.

Верни результат своей роли по `docs/CONTRACT.md`. Журнал и метрики передай ссылками в `artifacts`, доказательства — по полям события. Запиши число MCP-вызовов, snapshot, screenshot и восстановлений, длительность владения/ожидания, MCP-версию и usage при наличии. Недоступные счётчики помечай `unknown`, не оценивай по памяти.

## Освобождение при любом исходе

После доказательств выполняй cleanup как finally на success/failed/blocked/отмене/ошибке: begin-close → фактическое закрытие контекста/профиля того же сервера → первичный результат с lease_id/close_id → finish-close --evidence. Одной закрытой вкладки недостаточно; семантику browser_close проверь по установленной версии. Не проверяй свободу вызовом, заново открывающим браузер. При timeout/неясном результате — quarantine, один инцидент и передача координатору; TTL не освобождает профиль. В artifacts сохрани жизненный цикл, состояние освобождения и доказательство. При прерывании владельца cleanup принимает координатор. Восстановление только выделенного сервера после остановки прежних клиентов; не удаляй общий профиль/locks и не закрывай чужие процессы. Команды — нужный раздел docs/BROWSER_PROFILES.md.

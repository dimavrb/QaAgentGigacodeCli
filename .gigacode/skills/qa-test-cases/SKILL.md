В режиме GIGACODE extension пути `docs/`, `scripts/`, `examples/` и `.gigacode/` относятся к установленному `package_root`, а продуктовые файлы и артефакты — к `project_root`. Получи оба абсолютных корня и версию из назначения координатора; при их отсутствии восстанови привязку по `docs/EXTENSION_RUNTIME.md` до работы. Скрипты запускай по абсолютному пути из рабочей директории проекта; передавай явно назначенные пути данных и состояния.

# Тест-кейсы QA

1. Прочитай `docs/TEST_CASE_SELECTION.md` и `docs/TEST_CASE_STYLE.md`. Для содержательного отбора применяй `qa-check-quality`; если skill недоступен, прочитай `.gigacode/skills/qa-check-quality/SKILL.md` от корня пакета. Используй уже переданные инструкции без повторного чтения. Определи `test_type` (`api` или `ui`) по назначению или способу проверки; уточни только при неоднозначности. Для смешанной задачи выдели API- и UI-группы.
2. Получи источники поведения, существующее покрытие и нужные разделы проектного `.qa-agent/APP_CONTEXT.md`: роли, подготовка данных/состояний, ограничения выбранного канала и способы наблюдения. Следуй ссылкам только для существенных неизвестных условий. Контекст и реализация могут подтверждать техническую возможность, но не устанавливают новое бизнес-требование. Не угадывай доступы, API, SQL, тексты ошибок и способ внедрения сбоя.
3. До подробных шагов выбери сценарии. Свяжи кандидат с правилом/риском, возможной ошибкой, достижимым условием и различающим наблюдением; сопоставь с существующим покрытием. Решение: отдельный кейс, встроить проверку, предусловие, вопрос или исключение с основанием. Для ясного случая достаточно строки в карте покрытия; не составляй отдельный отчёт для каждого шага. Редкость и отсутствие доступа не доказывают невозможность. Сохрани обязательные критерии, границы и права; неизвестный способ проверки — вопрос planning, известный способ с недоступными ресурсами — зависимость execution.
4. После отбора для текущей группы прочитай только `examples/test-cases/<test_type>/INDEX.md` и один подходящий JSON-пример. Дополнительный пример нужен для существенного аспекта, не показанного первым. Примеры учебные: не переноси их HTTP-коды, диапазоны, тексты, URL, права или данные в реальные кейсы без подтверждённого источника. Не загружай всю библиотеку или эталон оценки навыка ради оформления.
5. Напиши инструкции для исполнителя, который не участвовал в обсуждении: как получить предусловия и данные, какое действие выполнить и где увидеть различающий результат. API-шаг задаёт метод, путь, существенные заголовки/body; UI-шаг — действие пользователя и видимый результат. Используй конкретные данные либо воспроизводимый способ их выбора, а не случайный пример из учебного каталога. Секреты обозначай способом получения доступа. Не дополняй неизвестное выдуманными подробностями ради завершённого текста.
6. Сохрани `scenario_id`, если поведение не изменилось. JSON-каталог остаётся единственным местом для предусловий, шагов и ожиданий. В плане оставь карту покрытия, решения отбора, зависимости подготовки и вопросы по `docs/TEST_PLAN.md`; новый обязательный JSON-формат не нужен. Для объединения укажи прежние ID → сохраняемый ID и сохранённое покрытие. Отсутствие ресурсов не превращает спроектированный кейс в выполненный или готовый к запуску.
7. Запусти `python3 scripts/validate_test_cases.py --input <путь-к-каталогу>` по абсолютному пути скрипта. Затем проверь содержание: сможет ли новый исполнитель выполнить инструкции без догадок; обнаружит ли ожидание предполагаемую ошибку; подтверждены ли существенные детали. Успешный валидатор не отвечает на эти вопросы. Для неизвестного поведения/способа проверки оставь вопрос и пробел покрытия, без готового кейса; продолжай независимую часть.
8. Передай координатору пути к плану и каталогу, ревизию, изменённые ID и нерешённые условия для независимого принятия. Не копируй подробные шаги в сообщение. Подготовка каталога не разрешает запуск продукта или публикацию в TMS; при назначенной публикации проверь представление действий/ожиданий по `docs/TESTOPS_JENKINS.md`.

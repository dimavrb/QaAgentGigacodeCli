В режиме GIGACODE extension пути `docs/`, `scripts/`, `examples/` и `.gigacode/` относятся к установленному `package_root`, а продуктовые файлы и артефакты — к `project_root`. Получи оба абсолютных корня и версию из назначения координатора; при их отсутствии восстанови привязку по `docs/EXTENSION_RUNTIME.md` до работы. Скрипты запускай по абсолютному пути из рабочей директории проекта; передавай явно назначенные пути данных и состояния.

# Тест-кейсы QA

1. Прочитай `docs/TEST_CASE_SELECTION.md` и `docs/TEST_CASE_STYLE.md`. Для содержательного отбора применяй `qa-check-quality`; если skill недоступен, прочитай `.gigacode/skills/qa-check-quality/SKILL.md` от корня пакета. Используй уже переданные инструкции без повторного чтения. Определи `test_type` (`api`, `ui` или `kafka`) по назначению или способу проверки; уточни только при неоднозначности. Для смешанной задачи выдели группы по способу проверки.
2. Получи источники поведения, существующее покрытие и нужные разделы проектного `.qa-agent/APP_CONTEXT.md`: роли, подготовка данных/состояний, ограничения выбранного канала и способы наблюдения. Следуй ссылкам только для существенных неизвестных условий. Контекст и реализация могут подтверждать техническую возможность, но не устанавливают новое бизнес-требование. Не угадывай доступы, API, SQL, тексты ошибок и способ внедрения сбоя.
3. До подробных шагов выбери сценарии. Свяжи кандидат с правилом/риском, возможной ошибкой, достижимым условием и различающим наблюдением; сопоставь с существующим покрытием. Решение: отдельный кейс, встроить проверку, предусловие, вопрос или исключение с основанием. Для ясного случая достаточно строки в карте покрытия; не составляй отдельный отчёт для каждого шага. Редкость и отсутствие доступа не доказывают невозможность. Сохрани обязательные критерии, границы и права; неизвестный способ проверки — вопрос planning, известный способ с недоступными ресурсами — зависимость execution.
4. После отбора для текущей группы прочитай только `examples/test-cases/<test_type>/INDEX.md` и один подходящий JSON-пример. В managed/bare используй уже переданные индекс и JSON целиком по `docs/TEST_CASE_REVIEW.md`; если нужного примера нет в контексте, запроси его у координатора, не утверждай, что прочитал ссылку. Дополнительный пример нужен для существенного аспекта, не показанного первым. Примеры учебные: не переноси их HTTP-коды, топики, таблицы БД, лимиты времени, тексты, права или данные в реальные кейсы без подтверждённого источника. Не загружай всю библиотеку или эталон оценки навыка ради оформления.
5. Напиши инструкции для исполнителя, который не участвовал в обсуждении: как получить предусловия и данные, какое действие выполнить и где увидеть различающий результат. Для API, UI и Kafka стандарт представления — «Шаг — Ожидаемый результат — Тест-дата»; по запросу человекочитаемого кейса показывай эту таблицу. Для API оставь короткое `name` и отдельный конкретный `expected_result`; метод/путь, обязательные headers и body храни в `request`, а подтверждённый статус, нужные headers ответа и JSON-пример — в `response` по API-разделу `docs/TEST_CASE_STYLE.md`. Эти блоки составляют колонку «Тест-дата» автоматически; не копируй их в текстовый test_data. Последнее поле используй только для дополнительных данных, SQL или инструкции. Не пропускай тело ответа, когда проверяешь его поля. Явно отличай отсутствие тела от JSON null; обязательные заголовки определяй по контракту, включая намеренные пропуски в негативном сценарии. Для JSON-ответа обозначай fragment/exact и запиши конкретные проверяемые значения в `expected_result`: пример не заменяет проверку. У таймаута может не быть HTTP-ответа; не выдумывай статус. Отправка и сверка её HTTP-ответа могут оставаться одним шагом; наблюдение отдельного бизнес-эффекта — отдельное действие, если оно требуется контрактом. Не делай отдельный кейс или шаг для каждого JSON-поля и не считай HTTP 200 доказательством сохранения состояния. Используй конкретные данные либо воспроизводимый способ их выбора. Токены/секреты — обозначения с доступным способом получения и подстановки в предусловиях, без реальных значений. Не дополняй неизвестное выдуманными подробностями ради завершённого текста.
   Для UI применяй раздел «UI: Шаг — Ожидаемый результат — Тест-дата»: name — действие с видимым объектом, expected_result — конкретное состояние экрана, необязательный test_data — значения полей/фильтров, выбранные ID, URL и ожидаемые строки/тексты. Связанные поля формы можно заполнить одним шагом, если промежуточное состояние не проверяется; отправку и наблюдение отдельного эффекта оставляй отдельными действиями. У динамического объекта сохрани фактический ID и используй его при поиске результата. Доступность кнопки и значения формы входят в сценарий; самостоятельный кейс нужен при отдельном правиле. Не добавляй к чистому UI-шагу HTTP-коды, JSON-ответы, селекторы или SQL без назначенного отдельного наблюдения и источника.
   Для Kafka применяй раздел «Kafka: Шаг — Ожидаемый результат — Тест-дата» того же стандарта. Показывай таблицу этих трёх колонок, когда запрошен человекочитаемый кейс. В JSON оставь короткое `name`, конкретный `expected_result` и необязательный текстовый `test_data` с topic/key/headers/телом сообщения, SQL и ожидаемым сообщением или записью БД, когда они нужны шагу. Не используй HTTP-блоки request/response для Kafka. Объединяй технически единое действие, например сохранение offsets и запуск чтения с этих позиций; отделяй публикацию, ожидание бизнес-эффекта и сверку его содержимого. Не добавляй выдуманную «панель завершения пробы» или контрольные сообщения без необходимости и подтверждённого способа. Подтверждение брокера не доказывает запись в БД.
6. Сохрани `scenario_id`, если поведение не изменилось. JSON-каталог остаётся единственным местом для предусловий, шагов, API-деталей, тестовых данных и ожиданий; `schema_version: 1` и прежние обязательные поля сохраняются. Старые кейсы без request/response/test_data работают; не переписывай незатронутое покрытие. В плане оставь карту покрытия, решения отбора, зависимости подготовки и вопросы по `docs/TEST_PLAN.md`. Для объединения укажи прежние ID → сохраняемый ID и сохранённое покрытие. Отсутствие ресурсов не превращает спроектированный кейс в выполненный или готовый к запуску.
7. Проверь сохранённый каталог по `docs/TEST_CASE_REVIEW.md`: при разрешённом локальном запуске используй `python3 scripts/validate_test_cases.py --input <путь-к-каталогу>` по абсолютному пути скрипта. В bare сверь `catalog_validations` текущего входа с его путём/хешем. Для нового выходного файла запроси проверку координатора после сохранения; проверка входа не подтверждает новую ревизию. Не приписывай runtime-вызов себе и не обходи ограничения tools. Затем проверь содержание: сможет ли новый исполнитель выполнить инструкции без догадок; обнаружит ли ожидание предполагаемую ошибку; подтверждены ли существенные детали. Успешный валидатор не отвечает на эти вопросы. Для неизвестного поведения/способа проверки оставь вопрос и пробел покрытия, без готового кейса; продолжай независимую часть.
8. Передай координатору пути к плану и каталогу, ревизию, изменённые ID и нерешённые условия для независимого принятия. Не копируй подробные шаги в сообщение. Подготовка каталога не разрешает запуск продукта или публикацию в TMS; при назначенной публикации проверь представление действий/ожиданий по `docs/TESTOPS_JENKINS.md`.

Для итогового HTML-плана применяй `docs/TEST_PLAN_HTML.md`: сохраняй связи ID кейсов с требованиями в requirement_coverage, точные source и доступные локальные снимки до ревью. Представление формируется после принятия; HTML не заменяет исходный каталог.

Для большого объёма следуй `docs/TEST_PLAN_PARTITION.md`: общие решения отбора принимаются до распределения, причинно связанный кейс имеет одного автора. При plan_partition деталируй только назначенные ID, используй проверенный контекст группы и общие ограничения; новые ID/источники/исключения требуют решения координатора и новой базы. Итоговый владелец проверяет объединённое покрытие и межгрупповые зависимости отдельно.

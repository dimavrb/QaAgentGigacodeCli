В проектной установке `package_root` — `<project_root>/.qa-agent/package`; в исходном репозитории — корень QA-пакета. Пути `docs/`, `scripts/`, `examples/` и `.gigacode/` относятся к `package_root`, а продуктовые файлы и артефакты — к `project_root`. Получи оба абсолютных корня и версию из назначения координатора; при их отсутствии восстанови привязку по `docs/EXTENSION_RUNTIME.md` до работы. Скрипты запускай по абсолютному пути из рабочей директории проекта; передавай явно назначенные пути данных и состояния.

# Качество проверки

Работай в пределах назначения. Получи критерий/риск, источник ожидания, кандидат
проверки, известное покрытие и доступные условия. Отсутствующие сведения обозначай
явно. Для простого подтверждённого сценария достаточно одной строки; углубляй
анализ при высокой цене ошибки, неизвестном ожидании или сложном наблюдении.

До детализации либо принятия существенной проверки:

1. Свяжи её с источником и конкретной возможной ошибкой. Реализация и учебный
   пример не устанавливают новое бизнес-требование. Уточни противоречие источников.
2. Назови наблюдение, отличающее правильное поведение от ошибочного. Проверь
   контрпример: какая существенная неправильная реализация всё ещё пройдёт?
   Если по источнику ожидается объект, исключи ложный успех на пустом результате.
3. Сверь способ подготовки и наблюдения с реальными данными, правами и средствами.
   Не угадывай API, SQL, возможность остановить сервис, изменить часы или внедрить
   ошибку. Успех команды, заглушки или discovery подтверждает только своё условие.
4. Сопоставь с существующими проверками: какую ошибку/класс условий добавляешь и
   оправдана ли цена риском? Объединяй эквивалентные проверки с сохранением покрытия.

Сохрани решение: **сохранить**, **переработать**, **объединить/исключить** либо
**вне области**. Для исключения обязательного риска нужна подтверждённая
неприменимость или согласованное изменение scope; отсутствие доступа не достаточно.

При ручном каталоге применяй docs/TEST_CASE_REVIEW.md: сверь выбранный пример и структурную проверку текущего каталога по пути/хешу, отдельно оцени смысл. Пример задаёт оформление, не требования продукта. Уточняй решение по docs/TEST_CASE_SELECTION.md: отдельный кейс,
встроенная проверка, предусловие, вопрос либо исключение с основанием. Достижимость
относится к выбранному каналу: ограничение UI не отменяет применимый негативный
вход API. Неизвестный способ подготовки/наблюдения — planning; известный способ с
недоступным ресурсом — execution. Не подменяй полезное наблюдение отдельным кейсом,
если оно уже надёжно входит в существующий сценарий.

Отдельно укажи две готовности:

- Проектирование: ожидание/способ проверки подтверждены либо нужен вопрос planning.
- Исполнение: условия фактически готовы либо нужна конкретная предпосылка execution.

Полезный кейс с известным ожиданием можно спроектировать без готового стенда.
При неизвестном ожидании сохраняй риск и вопрос, не готовый кейс с выдуманным
результатом. При недоступном условии сохраняй кейс, затронутые ID, нужную
предпосылку и способ подтвердить готовность. Продолжай независимую часть.

Альтернативному наблюдению приписывай ровно доказанное свойство: UI-сообщение не
подтверждает внутренний rollback, mock-ответ — реальную интеграцию. Существенный
остаточный риск остаётся явным. В плане не запускай продукт ради подтверждения.

Для критичного assert оцени необходимость контролируемой ошибки. Если она выбрана,
используй безопасную воспроизводимую изоляцию по docs/AUTOTEST_QUALITY.md: правильный ответ → целевое
падение на assert → восстановление. Setup/timeout/skip не считаются обнаружением.
Прямого сравнения с подтверждённым источником или независимого наблюдения может
быть достаточно; искусственное внедрение ошибки не обязательно для каждого assert.
Мысленный контрпример и выполненный эксперимент обозначай раздельно.

Сохрани краткий вывод в существующей карте или quality-артефакте: ID, критерий и
source, ошибка → наблюдение, решение, две готовности/вопрос, добавленное покрытие,
предел доказательности. Не дублируй шаги каталога или все восемь критериев оценки.
Ссылку передай через artifacts и существующие checks/limitations/self_review.role.
Reviewer самостоятельно сверяет источник, существенный контрпример и ревизию.

При комбинациях используй docs/TEST_DESIGN.md: каждый фактор становится конкретным
условием/параметром кейса, каждое применимое правило — различающим наблюдением.
Один TC-ID без этой связи не добавляет покрытие. Параметризованный кейс сохраняет
отдельные наборы значений и ожиданий; независимое ревью отражает каждую связь через
combination_checks. Математическое покрытие и проектирование не доказывают выполнение.

Для спорного случая читай [references/examples.md](references/examples.md).
Оформление — qa-test-cases; UI — qa-browser-repro; подготовка данных —
docs/TEST_DATA_CHECKLIST.md; статусы и приёмка — docs/CONTRACT.md и TASK_ACCEPTANCE.md.
Пути к стандартам разрешай относительно переданного корня QA-пакета.

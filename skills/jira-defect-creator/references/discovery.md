# Разведка конкретного проекта

Настраивай профиль чтением. Никаких проб create/update/link для выяснения схемы
без согласованного тестового плана, каждой операции и способа отката.
Профиль песочницы не доказывает формат/права/опции промышленного проекта.

## Входные параметры

Одним пакетом запроси недостающее: HTTPS URL Jira (включая context path, если
есть), ключ проекта, тип дефекта, разрешённые критичности, поля среды/этапа/
экспертизы и default экспертизы, секретность, правило выбора релиза/истории,
тип связи, эталон описания или «эталонов нет», клиент и каталог навыков,
абсолютный приватный `state_dir`, TTL и доступный коннектор.
Для необязательных возможностей допустимо явное «не используется».
Названия заказчика — пожелания для проверки, а не измеренные идентификаторы.
Секреты не запрашивай в чате: используй установленное подключение.

## Набор замеров

1. **Инструменты.** По реестру получи фактические имена и input schema.
   Проверь наличие аналогов search/get issue, metadata/fields, types, users,
   link types и требуемых write. Для get_createmeta сначала проверь реестр:
   недоступное имя не вызывай. Различай absent, forbidden, untested, verified;
   объявленная схема не доказывает права. jira-zephyr и Atlassian оценивай
   отдельно; не переноси из задания утверждение, что один канал всегда read-only.
2. **Проект и типы.** Получи реальные project key/id и типы. Раздельно сохрани
   идентификатор/имя для create и проверенный операнд JQL issuetype.
   Метаданные инструмента и чтение задач могут дать косвенное подтверждение
   формата create, но не называй это успешной записью.
3. **Поля.** Получи get_fields или аналог один раз на обновление кеша;
   используй контекстные metadata, если доступны. Прочитай 3–5 существующих
   дефектов, фиксируя фактически заполненные поля. Заполненность в примерах
   не доказывает обязательность. Required из точных create metadata — прямой
   источник; иначе required остаётся unknown/indirect. Не проводи негативную
   пробу в production. Песочница подтверждает только свою схему.
4. **Опции.** Предпочти полный список из контекстных metadata, включая
   пагинацию. JQL-пробы и существующие задачи дают только наблюдаемые значения;
   ноль результатов не означает недопустимую опцию, непустой ответ не доказывает
   полноту списка или возможность её записи. Сохрани exact label/id и форму
   значения без нормализации пробелов, дефисов, регистра, O/0. Пользователю можно
   показать неполный проверенный набор с явным ограничением. Непроверенное
   выбранное значение блокирует запись; не утверждай, что известны все опции.
5. **Формат запроса.** Для каждого передаваемого поля свяжи путь в input schema,
   JSON-тип, допустимые значения, required, AUTO/response-only. Поля, которые
   Jira вычисляет, не передавай. Формат ответа не является форматом запроса.
   Разрешённый create + отдельный readback подтверждает фактическое сохранение;
   без него указывай точный источник и границы уверенности. Не выбирай между
   строкой, объектом и массивом по виду `get_issue`.
6. **Поиск.** Проверь кириллические имена полей и отдельно заведомо встречающееся
   слово в summary. Учти токенизацию: full-text не всегда ищет подстроки.
   Сохрани запрос, известную задачу, результат и пагинацию. При отказе используй
   обзор 50–100 последних дефектов, сравнивая заголовки и читая кандидатов;
   назови это ограниченным обзором. Расширяй выборку/фильтры, если возможно.
   Отсутствие совпадения в обзоре не доказывает отсутствия дублей; для managed
   публикации обеспечь полный согласованный охват или верни blocked.
7. **Секретность и назначение.** Получи уровень и формат из metadata, проверь
   фактические значения. Автоматическое применение и оставление без назначения
   проверяются readback разрешённой записи; до этого AUTO — гипотеза. Если
   требуемую секретность нельзя гарантировать до создания, запись блокируется:
   readback не отменяет уже случившееся раскрытие.
8. **Связи.** Получи name/id/inward/outward из link types и прочитай raw
   `issuelinks` существующих задач. Инструмент с потерей направления не годится
   как доказательство. Создание тестовой связи и чтение обеих сторон допустимы
   лишь по согласованному плану. Не меняй стороны вслепую при 401/403: проверь
   аргументы, тип, канал, auth и права. Другое направление меняет смысл связи
   и требует исправленного согласованного плана. Без достоверной ориентации
   связь не создавай.
9. **Цель привязки.** Построй проектный JQL из согласованного правила; проверь
   тип/статус/сортировку/пагинацию и прочитай результат. Непустой список не
   доказывает актуальность цели; сохрани основание и запроси выбор при неоднозначности.
10. **Описание.** Прочитай эталон. Без эталона используй четыре секции из SKILL.
    Определи plain text/wiki/ADF по реальному контракту. Тест рендеринга требует
    отдельного разрешения; сырой readback доказывает сохранение, визуальный
    просмотр — рендеринг. Не объявляй второе по первому.

## Готовность профиля

Сохрани идентичность, TTL, подтверждённые факты и unresolved по
[profile.md](profile.md). Выполни dry-run на тексте заказчика до чек-листа.
Если исходного дефекта нет, пройди явно синтетический сценарий и перечисли,
какие живые проверки остаются; он проверяет переносимый процесс, не проект.
Отчёт содержит результаты get_createmeta, кириллического поиска, возможностей
каждого канала, raw issuelinks/направления либо причину, почему проба недоступна.
После разрешённых тестов покажи ключи, созданные link id и фактический откат.
При отсутствии права/инструмента удаления не обещай полного отката: согласуй
остаточные объекты до теста. Не трогай чужие объекты, даже ради уборки.

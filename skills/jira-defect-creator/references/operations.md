# Операции, восстановление и журнал

## Согласование и запись

Сохрани неизменный план конкретных вызовов с порядком, целями, аргументами и
хешами вложений. Передай пользователю содержание и результат прединспекции.
Явное «ок» относится к этому плану, а не ко всем последующим операциям в Jira.
При создании ключ ещё неизвестен: согласуй зависимые вызовы с единственной
подстановкой ключа из проверенного create/readback; остальные аргументы фиксированы.
Перед зависимым вызовом повтори прединспекцию с фактическим ключом. Любое иное
изменение требует нового подтверждения. В managed-create зависимых write нет,
если их не разрешает отдельное назначение и политика шлюза.

Для update перечитай задачу непосредственно перед записью. Покажи diff,
не перезаписывай описание ответом get_issue или неполным снимком. Комментарий
и вложение являются отдельными write. Если инструмент комментариев отсутствует,
не имитируй его заменой описания. Проверь файл и его SHA-256 перед upload;
повторный upload после unknown может создать второй файл.

## Ограниченные повторы

Для **read** — максимум три попытки всего: исходная и два повтора через 5 и
10 секунд. При 429 жди `Retry-After`, а если его нет — 60 секунд; это также
считается попыткой. Не делай лишнюю четвёртую попытку ради интервала 20 секунд.
Повторяй сетевые временные ошибки и 5xx, остальные 4xx не повторяй вслепую.
Если ожидание превышает время исполнения, сохрани продолжение и сообщи блокер.

Для **write** общий retry read не применяется. Перед вызовом сохрани intent и
идентификатор операции, после — ответ/ошибку и ключ/id объекта, если известен.
Timeout, потеря соединения и 5xx оставляют unknown: мог сохраниться объект.
Восстанови результат через согласованное чтение/поддерживаемый idempotency key;
не добавляй произвольный idempotency-параметр в MCP. Подтверждённый объект
переиспользуй. Только авторитетное доказательство not_applied и заранее
согласованная политика могут разрешить повтор; без них спроси о новой конкретной
операции после восстановления исхода. 429 на write также не является
универсальным доказательством not_applied для любого прокси/коннектора.
В QA-пакете действует более строгий предел: один create / одна попытка, даже
после not_applied. Не меняй gateway, step_id или request_id ради обхода лимита.

Если create успешен, но update/link/upload/readback не выполнен, сохрани
частичный результат с ключом и отдельным состоянием каждого шага.
Сбой локального журнала после create не разрешает второй create.

## Черновики и журнал

Используй приватный `state_dir` (права каталога 0700, файлов 0600). Не сохраняй
секреты; при необходимости оставь ссылку на исходный защищённый источник.
Не используй общее фиксированное имя `/tmp/jira-defect-creator-draft.json`:
разные проекты/операции могут перезаписать друг друга. Если нужен временный
каталог, создай его безопасным tempfile API с уникальным именем и правами.

Черновик: версия формата, operation_id, инстанс/проект/коннектор, исходный
очищенный материал, точный план и его хеш, хеш профиля, согласование, состояния
шагов (`planned`, `started`, `verified`, `not_applied`, `unknown`, `failed`),
ключ/id, ошибка без секретов и следующий безопасный шаг. Записывай атомарно.
После ошибки/исчерпания read-попыток сохрани черновик и покажи его абсолютный путь.
При следующем запуске предложи восстановление, сверь профиль и согласование.
Восстановление unknown начинается с чтения. Старое согласие не разрешает
изменённый payload. Другой проект/операция не наследует согласие.

Append-only журнал JSONL: время с зоной, operation_id, хеш плана, инстанс/проект,
действие, состояние, число попыток, ключ/id/URL, пути и хеши доказательств,
ошибка без credentials. Отмечай созданное отдельно от проверенного и частичного.
Метрики (число подтверждений, кандидатов, попыток и исход) выводи из журнала;
не выдавай локальные dry-run за скорость/качество живой модели.

## Каталог ошибок и self-heal

Накопительный `errors.jsonl` веди в state_dir. У случая есть incident_id,
инстанс/проект/версия коннектора, очищенный симптом, observation, гипотеза
причины, проверка, доказанное исправление либо unknown, дата и применимость.
В QA-пакете передай существенный сбой координатору для общего failure journal,
сохранив incident_id. Совпадение сообщения не доказывает одинаковую причину.

| Симптом (пример, не факт об инстансе) | Что проверить | Действие |
| --- | --- | --- |
| `Option id 'null' is not valid` | Контекст поля, exact label/id, JSON-форма | Обновить замер, показать правку, согласовать новый payload |
| `must match a schema in anyOf` | Реальный input schema, response-only и неверные типы | Исправить локальный план, повторить прединспекцию и подтверждение |
| `No issue link type with name ... found` | Name/id типа и inward/outward из metadata | Использовать измеренный идентификатор после согласования |
| `401` / `403` / `No Link Issue Permission` | Auth, проект, права, канал, стороны и существующие связи | Остановить write; не менять стороны вслепую |
| Ноль результатов по кириллице | Известное слово, токенизация, охват и пагинация | Обзор с ограничением; при недостаточном охвате blocked |
| Timeout/5xx после create | Состояние исходной операции и результат чтения | Reconciliation, сохранить ключ, не создавать дубль |
| Поле отличается при readback | Default/AUTO, преобразование коннектора, другая схема | Частичный результат, обновить замер; правка только с согласием |

Self-heal не переписывает SKILL, правила разрешений или чужую конфигурацию.
Предложи минимальную правку профиля с причиной, diff и доказательством; получи
подтверждение перед её применением, сохрани новую ревизию и прежнюю историю.
Обычное обновление истёкшего кеша чтением допустимо в рамках настройки, но любое
изменение согласованных аргументов отменяет прежнее подтверждение записи.

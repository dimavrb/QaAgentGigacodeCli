# QA Agent extension

Для QA-задач используй `/qa`, роли `qa-*` и навыки QA-пакета. Для подключения
проекта используй `/qa:init`, для проверки подключения — `/qa:doctor`.
Список сохранённых заданий — `/qa:tasks`, продолжение выбранного — `/qa:resume <ID>`.
Пустая `/qa` показывает незавершённые задания и запрашивает выбор либо новую цель.
Эти команды не меняют авторизацию, модель или подключения внешних систем.

Перед первой QA-задачей получи `package_root` и `package_version` через
MCP-инструмент `qa_package_info` сервера `qa-agent`. Он только читает метаданные
установленного пакета и не обращается к продукту. Проверь локальную конфигурацию
проекта `.qa-agent/project.local.json` через read-only MCP `qa_project_doctor`
с абсолютным `project_root`; `needs_attention` — штатный результат диагностики.
Для подключения используй MCP `qa_project_init(project_root, rebind=false)`:
он пишет только `.gitignore`, `.qa-agent/APP_CONTEXT.md`, `.qa-agent/project.local.json`.
Ошибки `QA project error: …` возвращаются как `isError`. При переносе сначала
получи и покажи старый/новый пути без `rebind`; `rebind=true` разрешён только
вторым шагом той же MCP-сессии для согласованного переноса. При недоступности
инструментов используй `qa_project.py` как CLI fallback по `/qa:init`, `/qa:doctor`.
При смене версии повтори `/qa:init`; контекст приложения остаётся прежним.
Если QA-роли отсутствуют в `/agents manage` активного extension после новой
сессии, сначала проверь полную установку 2.3.12 или новее с корневыми `agents/`,
`skills/`, `commands/` по EXTENSIONS.md: поля путей в манифесте не обеспечивают
discovery целевой сборки. Не считай наличие файлов подтверждением загрузки.
Если проблема сохраняется, покажи порядок явного
подключения проектных ролей через `qa_project_agents.py` из EXTENSIONS.md.
Этот отдельный вызов требует остановки активной QA-работы; preview не пишет файлы,
`--apply` обновляет управляемые роли по сохранённой базе и сохраняет адаптации.
Правила и восстановление — PROJECT_AGENT_UPDATES.md. `qa-start` синхронизирует
копии до новой сессии; конфликт одной роли не мешает обновлению остальных,
но блокирует начало QA-работы до рассмотрения. При прямом запуске CLI
выполни синхронизацию отдельно и проверь `/qa:doctor`.
При запуске через `qa-start` обновление и освежение привязки выполняются до
сессии по `docs/AUTO_UPDATE.md`. Не обновляй установленный пакет посреди текущей
QA-задачи; незавершённый managed-план сохраняет свою ревизию инструкций.
Защита обновления/независимый rollback — `<package_root>/docs/UPDATE_SAFETY.md`.
Rollback выполняется отдельным явным действием после остановки работы; не сбрасывай
историю задачи или отмену ради отката. CLI rebind требует digest из первого показа.

Прочитай `<package_root>/docs/EXTENSION_RUNTIME.md`, затем только нужные
инструкции координатора. Пути `docs/`, `scripts/`, `examples/`, `.gigacode/`
в инструкциях QA относятся к пакету. Продуктовые данные и артефакты относятся
к `project_root`. Передавай оба абсолютных пути каждому исполнителю.

Для ручного каталога сначала применяй `qa-test-cases` и отбор по
`<package_root>/docs/TEST_CASE_SELECTION.md`: проверь пользу, достижимость и
добавленное покрытие до шагов. Решения и зависимости оставляй в плане; JSON
сохраняет прежний формат. Непонятная подготовка требует вопроса, временно
недоступный известный ресурс — условия execution. Тестовая задача навыка —
`<package_root>/docs/TEST_CASE_PILOT.md`; подготовка кейсов не запускает продукт.

Хранение и восстановление — `<package_root>/docs/TASK_STORAGE.md`. Read-only MCP
`qa_tasks_list` и `qa_task_get` читают `.qa-agent-state/tasks/*/task.json` без записи.
Снимок не является разрешением запуска: проверь владельца, hashes и актуальные
условия; не сбрасывай отмену. При нескольких задачах запроси выбор, при warnings
не объявляй отсутствие работы. Старые явные пути сохраняй; локальные реестры
не синхронизируются Git. Планы/кейсы команды хранятся в Git отдельно от доказательств.

Когда задача не относится к QA, соблюдай инструкции проекта. Правила разработки
самого QA-пакета из его `AGENTS.md` не являются правилами версионирования приложения.

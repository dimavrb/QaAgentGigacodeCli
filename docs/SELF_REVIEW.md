# Самопроверка перед передачей результата

Каждый исполнитель проверяет свой окончательный результат перед возвратом, включая `blocked`, `needs_*` и частичные события. Координатор делает такую же короткую проверку перед назначением следующего этапа и итоговым сообщением: нет ли пропущенных обязательных условий, непринятых источников или более сильного вывода, чем доказательства позволяют. Самопроверка автора не заменяет независимое содержательное принятие и роль `qa-autotest-reviewer`.

## Порядок

1. Сверь сохранённый результат с каждым критерием назначения и всем назначенным набором ID. Для каждого критерия должен быть результат либо конкретное недостающее условие. Не оценивай только последний изменённый фрагмент.
2. Проверь доказательства утверждений: источник ожидания, выполненные действия, актуальная версия, доступность файлов. Найди самое слабое существенное утверждение и проверь, не опровергает ли его источник или пропущенный контрпример. Успешный валидатор подтверждает структуру, а не смысл.
3. Устрани найденные ошибки, которые можно исправить в пределах назначения. Для существенных изменений обнови затронутые доказательства и самопроверку. Не запускай проверки продукта, записи во внешнюю систему или дополнительного агента, если они не разрешены назначением.
4. Сохрани короткий `self_review` окончательного JSON-отчёта, затем проверь весь отчёт валидатором. Не меняй его после `submit`: реестр связывает самопроверку и результат одними контрольными суммами. Последующие изменения получают новое назначение и ревью.

Обычно достаточно одного прохода. Повтор нужен после исправления, меняющего проверяемый вывод; повторять «подумай ещё» без новой информации не нужно. Если существенная неопределённость остаётся, передай её координатору существующим частичным/блокирующим событием или запросом, продолжив независимую часть. Самопроверка не является основанием расширять задачу.

## Четыре проверки

| ID | Что проверять |
| --- | --- |
| `scope` | Каждый критерий приёмки, назначенные ID, пределы действий и условие остановки. В зарегистрированном назначении ссылка `assignment:/acceptance_criteria` обязательна. |
| `evidence` | Факты отделены от гипотез; существенные выводы подтверждены актуальными источниками или явно ограничены. |
| `consistency` | Событие, summary, payload, файлы и ограничения согласованы; непроверенное не названо успешным. |
| `role` | Применимый риск роли из таблицы ниже, включая существенный пропущенный контрпример. |

| Роль | Минимальная предметная проверка |
| --- | --- |
| `qa-result-reviewer` | Все назначенные критерии проверены по источникам и точному target; решение автора не использовано как доказательство; unknown не назван passed. |
| `qa-conclusion-reviewer` | Все утверждения назначенных полей проверены по первичным снимкам; числа, причины и область вывода не усилены; цитаты объясняют вывод, неизвестное не названо подтверждённым. |
| `qa-analyst` | Не превратил ли предположение в подтверждённое ожидание; какие риски/неизвестные не покрыты вопросами? |
| `qa-impact-analyst` | Полная поставка и каталог отражены; косвенные зависимости и обязательные/новые/ранее падавшие тесты сохранены; неизвестные связи не стали основанием исключения? |
| `qa-test-plan-writer` | Покрыты ли обязательные критерии, отрицательные/граничные случаи; готовый кейс не зависит от открытого вопроса? |
| `qa-test-env-configurator` | Готовность подтверждена фактическими возможностями нужной версии, а не наличием конфигурации? |
| `qa-test-data-builder` | Свойства и связи каждой нужной записи проверены; изоляция, повторяемость и очистка предусмотрены? |
| `qa-stub-builder` | Не изменены ли ожидания назначения; настройка не выдана за проверенную готовность или реальную интеграцию? |
| `qa-defect-investigator` | Доказано ли нарушение конкретного требования; причина не выведена только из воспроизведения? |
| `qa-feature-tester` | Все назначенные ID отражены; фактические шаги и доказательства есть, не запущенное не прошло? |
| `qa-test-automation` | Assert обнаруживает нужную ошибку; данные, discovery, запуск, названия/Allure и версия для ревью подтверждены либо ограничены? |
| `qa-autotest-reviewer` | Прочитана ли проверяемая версия независимо от вывода автора; замечания и решение следуют из собственных проверок? |
| `qa-jira-defect-creator` | Дефект и дубли проверены; запись и поля подтверждены чтением, неоднозначная запись не повторена? |
| `qa-test-report-writer` | Итоги следуют из первичных результатов; неизвестные условия сохранены, готовый документ не объявляет фичу проверенной? |

## Формат

`self_review` — дополнительное поле верхнего уровня рабочего QA-отчёта. `schema_version: 1`, ровно четыре объекта `checks` с уникальными ID из таблицы. Каждый содержит `status: passed|limited`, короткую конкретную `note` и непустой массив `evidence`. `passed` означает, что автор проверил качество представления результата; это не утверждение об отсутствии дефектов продукта. `limited` означает, что проверку качества полностью подтвердить не удалось. Причина и влияние обязательны в `remaining_risks`. В `fixes` сохраняй только реально выполненные исправления. Пустые списки допустимы; не придумывай исправления ради заполнения.

Ссылки в `evidence` — JSON Pointer в окончательном отчёте (`report:/payload/run_result`, `report:/artifacts/0`, `report:/blockers`) или назначении (`assignment:/acceptance_criteria`, `assignment:/inputs/0`). Для `/` и `~` в ключах используй `~1` и `~0`. Ссылки на собственный `self_review` не разрешены. Указатель связывает вывод с проверяемым материалом, но сам по себе не доказывает его истинность. Файлы доказательств объявляй в `artifacts`; в реестре они проверяются и получают контрольные суммы. Контекст назначения разрешается по независимому заданию координатора, не по заявлению автора.

Пример находится в `examples/task-exchange/result.json`; он подтверждает только учебный протокол. Если запуск недоступен, проверка `evidence` может быть такой:

```json
{"id":"evidence","status":"limited","note":"Код сопоставлен с требованием; запуск недоступен без учётной записи стенда.","evidence":["report:/payload/limitations","report:/artifacts/0"]}
```

Тогда `remaining_risks` содержит «Поведение на стенде не проверено; обязательный запуск требует доступа». Это ограничение также отражается в существующих `payload.limitations`, `blockers` или вопросах согласно контракту роли. Не прячь обязательное условие только в самопроверке.

Храни выводы и ссылки, а не внутренний ход рассуждений, длинные логи или процент уверенности. Обычно это несколько коротких предложений. Пользователю координатор сообщает значимые исправления и оставшиеся риски, не весь чек-лист.

Существенную ошибку процесса и её исправление передай координатору для FAILURE_JOURNAL.md, включая фактические условия, неудачные попытки и проверку результата. Используя подобранный прошлый случай, сверяй его применимость к текущему назначению и отмечай реально выполненное исправление в fixes. Старое решение и собственная самопроверка не подтверждают причину нового сбоя.

## Проверка и совместимость

Новые назначения через `manage_task.py assign` получают `self_review_required: true`; отключить его нельзя. Передача через `prepare` включает доступный абсолютный путь к этому документу. `submit` проверяет наличие/формат самопроверки и разрешимость ссылок в отчёте и назначении. Недостающая или невалидная самопроверка не создаёт `result_ready`. Корректно описанный `limited` допускается к содержательному ревью: координатор оценивает, допустим ли частичный результат; незакрытый обязательный критерий не принимается как полностью готовый этап. Авторское `passed` не выполняет `review` автоматически.

Отдельный `run_test_automation.py` передаёт абсолютный путь и требует `self_review` также без общего реестра. Старые сохранённые отчёты и уже зарегистрированные назначения без флага совместимы: обычный валидатор не требует нового поля, но проверяет его, если оно есть. Проверка вне реестра:

```bash
python3 scripts/validate_qa_result.py --input result.json --task-id QA-1 --request-id QA-1-auto-1 --agent qa-test-automation --require-self-review --self-review-assignment assignment.json
```

Для standalone текстового задания опусти `--self-review-assignment`; ссылки на критерии описывай по содержимому задания и отчёта. Без JSON-назначения валидатор не подтверждает его ссылки. Измеряй эффект на одинаковых реальных задачах: ошибки/возвраты ревью, пропуски ограничений, время и токены. Наличие четырёх строк само по себе не доказывает улучшения качества.

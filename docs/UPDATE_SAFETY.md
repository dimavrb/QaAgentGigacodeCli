# Проверка выпуска, восстановление и откат

Для проектной установки 2.3.13 используйте [PROJECT_INSTALLATION.md](PROJECT_INSTALLATION.md).
Ниже описан прежний native-update механизм; он не обслуживает install.json.


Начиная с 2.3.0 автообновление проверяет точный commit до смены исходников:

1. Чистый main, разрешённый origin, fast-forward и новая согласованная версия.
2. Для штатного GitHub-источника — последний push-run `ci.yml` этого SHA на main
   должен быть completed/success. Нет подтверждения, сеть/API недоступны или
   лимит запросов исчерпан — `release_not_verified`, запуск остаётся на старой версии.
3. Git archive точного commit распаковывается в отдельный временный каталог.
   Проверяются безопасные пути, отсутствие symlinks/submodules, обязательные
   ресурсы, Python-синтаксис, локальные зависимости launcher/MCP и полный ZIP manifest.
4. Новый код проверяется свежим изолированным интерпретатором: импорты,
   launcher --help, MCP initialize и metadata. Продукт и его внешние системы не запускаются.
5. До fast-forward создаются независимый recovery zipapp, архив установки,
   hashes/права файлов и сохранённое намерение. После native update повторяются
   readback/probes и fsync установленного содержимого; лишь затем очищается pending.

GitHub CI выполняет тесты на двух платформах и сохраняет ZIP/checksum как
артефакты, привязанные к SHA. Проверка run использует официальный
[REST API](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-workflow).
Это доверие к CI указанного репозитория, а не криптографическая подпись автора
или запрет администратору изменить workflow. Защита main и права публикации
настраиваются администраторами отдельно. Пакет не меняет их автоматически.

## Независимый инструмент

Перед первым защищённым обновлением сохраняется
`~/.gigacode/qa-agent-updates/qa-recover.pyz`. Он содержит собственные копии
qa_recover/qa_files, использует стандартную библиотеку и не импортирует checkout
или установленное расширение. В следующих обновлениях этот helper не заменяется;
проверяется его записанный hash. Для другого `--state-dir` используйте тот же профиль.

```bash
python3 "$HOME/.gigacode/qa-agent-updates/qa-recover.pyz" \
  --state-dir "$HOME/.gigacode/qa-agent-updates" status
python3 "$HOME/.gigacode/qa-agent-updates/qa-recover.pyz" \
  --state-dir "$HOME/.gigacode/qa-agent-updates" rollback
```

Rollback — отдельное явное действие пользователя после остановки сессий,
назначений и managed execution. Он проверяет блокировку, процессы, журнал,
backup hashes, identity/HEAD/чистоту Git и отсутствие посторонних изменений установки.
Проектные контекст, кейсы, реестры, доказательства и auth не откатываются.

Откатывается только записанный fast-forward `commit → base_commit` через
`git reset --hard` после проверок. Произвольный SHA, чужие коммиты, другая ветка,
другой origin и dirty source запрещены. Установка восстанавливается из backup
с правами файлов через подготовленный каталог и проверяемое переключение.
Прерванное переключение имеет phase=restoring; повторите тот же helper rollback.
Не открывайте CLI между прерыванием и восстановлением.

Вытесненная установка сохраняется ZIP-архивом в том же recovery-профиле, затем
удаляется только её временный каталог. Рядом с extensions не остаётся второй
manifest, который менеджер мог бы ошибочно обнаружить. Снимки/RECOVERY.json
сохраняются для аудита; пакет не вводит их автоматическое удаление.
Повтор того же выполненного rollback идемпотентен. Откаченный commit не применяется
автоматически снова: нужен следующий проверенный выпуск.

## Границы восстановления

- Требуются локальная POSIX-файловая система, рабочие flock/link/rename/fsync
  и Git 2.36+ (`core.fsync=all` для Git-операций). Возможности описаны в
  [Git config](https://git-scm.com/docs/git-config#Documentation/git-config.txt-corefsync).
- fsync применяется к данным и каталогам перед completion markers. Проверены
  инъекции отказов и прерывания на границах операций; это не физическое отключение
  питания и не доказательство гарантий контроллера диска/NFS.
- Повреждённые backup/helper, посторонние правки и неясное состояние блокируют
  откат. Журнал не является разрешением уничтожить новые данные. Повреждение самого
  Git repository/index требует отдельного ручного восстановления; helper не чинит его вслепую.
- Внешний registry менеджера GIGACODE не редактируется. Rollback подтверждает
  локальные файлы/HEAD; соответствие registry и видимость компонентов после
  восстановления проверяются на живом CLI и при необходимости штатным менеджером.
- До 2.3.0 snapshots/helper не создавались. Старый pending без backup автоматически
  не мигрирует: сначала согласуйте/завершите прежнюю активацию по старой инструкции.

## Проектная конфигурация

Init и configure используют общую блокировку inode каталога проекта, без нового
lock-файла в приложении. APP_CONTEXT публикуется атомарным link без замены уже
существующего файла, даже если его создал внешний редактор между проверкой и записью.
Другие файловые операции выполняются через directory descriptors с O_NOFOLLOW;
локальный JSON читается только из regular files, с лимитом 8 MiB и защитой от FIFO.

Перепривязка требует показанного полного binding. MCP хранит preview в своей
сессии, а initialize сравнивает его и пишет новый binding под одной блокировкой.
Изменение любого поля требует нового показа. CLI fallback получает digest из
первой ошибки: `--rebind --expected-binding-sha256 <показанный SHA-256>`.
Слепой rebind через CLI/библиотеку отклоняется. Блокировка согласует инструменты
пакета; произвольные сторонние редакторы .gitignore должны согласовывать свои записи.

Stdio MCP ограничивает входную строку 65536 символами, возвращает ошибку для
слишком глубокого/длинного JSON и продолжает обслуживать следующие сообщения.
Экранирование envelope защищает stdout даже при некорректном Unicode ID.

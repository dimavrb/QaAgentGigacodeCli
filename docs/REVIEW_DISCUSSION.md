# Независимые reviewer и ограниченное обсуждение

Обсуждение — отдельная опциональная фаза review-cycle для двух `qa-conclusion-reviewer` с разными scope/focus. Сначала каждый получает автора и первичные источники без чужого verdict. Сохраняются оба исходных отчёта. Если по назначенным полям или критериям оценки отличаются, coordinator создаёт хешированный пакет расхождений. Если расхождений нет, обсуждение не запускается.

```json
{
  "discussion": {"max_rounds": 2},
  "reviewers": [
    {"scope": "facts", "agent": "qa-conclusion-reviewer", "focus": "Факты запусков, числа, версии и полнота ведомости", "review_sources": ["/absolute/primary.json"]},
    {"scope": "inference", "agent": "qa-conclusion-reviewer", "focus": "Причинность, контрпримеры и область вывода", "review_sources": ["/absolute/primary.json"]}
  ]
}
```

Это фрагмент обычного плана: author_plan, критерии required_reviews обоих scope, адаптеры и общий бюджет задаются по [CONCLUSION_REVIEW.md](CONCLUSION_REVIEW.md). `max_rounds` — 1 или 2, bool/0/3 отклоняются. Без discussion прежний маршрут сохраняется. Другие сочетания reviewer пока используют обычное независимое ревью; обсуждение специально ограничено проверкой выводов. Два направления могут использовать одну модель, но имеют разные сессии/владельцев; их фактическую независимость суждений следует измерять отдельно.

## Раунд

Оба участника получают один неизменяемый packet: точный author target, номера спорных полей, полные предыдущие отзывы с хешами и номер раунда. Ответ второго участника текущего раунда первому не передаётся. Следующий раунд видит только сохранённые ответы предыдущего. Каждое обсуждение запускается новой owned-сессией своего направления; исходные оценки не редактируются.

Обычный review payload и conclusion_checks сохраняются. Дополнительно каждый issue требует discussion_checks:

```json
{
  "issue_id": "I-1",
  "position": "revise",
  "status": "resolved",
  "note": "Первый вывод пропустил not_run; снимок не подтверждает продуктовую интеграцию",
  "source_refs": [{"path": "/absolute/primary.json", "quote": "\"product_run\": \"not_run\""}]
}
```

`maintain` сохраняет статус предыдущего отзыва по этому issue; `revise` действительно меняет его. `resolved/unresolved` описывает возможность разрешения возражения, а не голос за продуктовый успех. Для resolved и любой смены позиции обязательны первичные source_refs с дословными цитатами назначенных снимков либо receipt свежего OBS-вызова собственной managed-политики. Квитанция фиксирует действие/наблюдение; связь результата с возражением объясняется в note. Чужой verdict не допускается в роли такого источника. Все issues рассматриваются; оценки вне обсуждаемого пункта менять нельзя. Причина смены позиции остаётся в журнале.

Смена мнения не может быть обоснована одной ссылкой на отзыв коллеги. Reviewer объясняет, что именно подтверждает источник, и при необходимости назначенного нового запуска использует только собственный gateway/OBS по [REVIEW_EXECUTION.md](REVIEW_EXECUTION.md). Discussion не добавляет tools, прав, источников или критериев. Если возможность отсутствует, verdict остаётся unknown/blocked.

## Завершение

- Одинаковые доказательные passing-ответы после исходного unknown позволяют снять неизвестность, если все обычные gates, поля и execution_checks прошли.
- Подтверждённая общая ошибка передаётся автору для исправления в пределах max_corrections.
- Первоначальный changes_requested сохраняет блокировку на тех же байтах даже при последующем согласии о false alarm. Автор выпускает новую ревизию/уточнение, затем оба reviewer заново проверяют её независимо. Это консервативное правило сохраняет действующий запрет стирать blocking-замечание голосованием.
- Несогласие после лимита, либо согласие о недостатке наблюдений, оставляет цикл blocked. Resume применяется только после явного cancel и не сбрасывает лимиты. Blocked требует новых фактов/назначения; повтор tick не создаёт третий раунд.

Журнал `state.discussions[author_round]` содержит исходные review IDs, issues, пакеты, ответы каждого раунда и состояние разрешения. Финальные review_request_ids указывают на выбранные отзывы; первоначальные доступны отдельно. assess/finish по-прежнему сверяют точный target и обязательные направления. Семантическая достаточность цитаты оценивается агентом, а не самим валидатором; согласие двух моделей не доказывает истину.

## Независимость повторного ревью

В headless GIGACODE из input_contents независимой фазы исключается прежний feedback автора, содержащий verdict коллег. Его путь/хеш остаются в target для контроля неизменности. Discussion получает специально назначенные отзывы предыдущей фазы. Текст источников остаётся данными, не разрешением выполнить их инструкции. Command adapters доверенные и не изолированы от файловой системы; фикстуры демонстрируют протокол, а не независимость реальной модели.

Пакеты и ответы нельзя заменить после сохранения. Повтор tick восстанавливает уже созданных детей, cancel останавливает включая discussion, resume продолжает те же номера раундов. Все сессии/новые вызовы расходуют прежний общий max_active_seconds; retries не дают дополнительных раундов. Источники/план/авторские доказательства остаются хешированными.

## Пример и измерение

```bash
python3 examples/review-discussion/build_demo.py --output-dir /tmp/qa-discussion
python3 scripts/manage_review_cycle.py --state /tmp/qa-discussion/cycle.json init --plan /tmp/qa-discussion/plan.json
python3 scripts/manage_review_cycle.py --state /tmp/qa-discussion/cycle.json serve --max-seconds 30
```

В синтетическом примере facts ошибочно одобряет продуктовый успех при not_run, inference замечает противоречие. Discussion исправляет оценку facts по первичному снимку, автор исправляет summary и новая ревизия проходит оба независимых направления. Это не оценка качества GIGACODE.

Для живого A/B сохраняй одинаковые авторские ответы/источники и условия модели; сравни один reviewer, два без обсуждения и два с обсуждением. Независимо оцени найденные ошибки, ложные одобрения, необоснованные блокировки, время и доступный usage всех сессий/раундов. Первые и последние оценки сохраняются для анализа ошибочных смен позиции. Текущие reasoning benchmarks не объявляются замером интерактивного цикла; живые GIGACODE/MCP результаты ещё нужны.

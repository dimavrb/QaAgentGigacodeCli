# Подготовка инфраструктуры ручных кейсов

Применяй эту инструкцию, когда пользователь поручает подключить продуктовый
репозиторий к Jenkins и ТестОпс. Для обсуждения архитектуры или адаптации
переносимого шаблона реальные URL, ID проектов и credentials не нужны.
Рабочий шаблон и ограничения формата — в `examples/testops-jenkins/README.md`.

## Сбор параметров при подготовке инфраструктуры

Сначала прочитай назначение и доступную конфигурацию. Уже подтверждённые данные
не спрашивай повторно. Когда переходишь к настройке реальных систем, собери
недостающие параметры одним пакетом вопросов:

- URL целевого продуктового репозитория GitVerse и точные owner/repository;
- основная ветка (`main`, `master` либо указанная пользователем), каталог ручных
  JSON-кейсов и стабильный namespace;
- URL Jenkins, целевые имена двух джоб, метки агентов, существующие версии
  Pipeline/Git/Generic Webhook Trigger/плагина ТестОпс;
- URL и точная сборка ТестОпс, ID пилотного и рабочего проектов;
- ID уже созданных Jenkins Credentials для чтения Git, токенов вебхуков и
  публикации в ТестОпс; serverId настроенного сервера плагина;
- область разрешённых изменений: какие репозитории, джобы, вебхуки, проекты
  можно создавать или менять, и какие действующие процессы нельзя прерывать;
- доступность Jenkins из GitVerse и доступность ТестОпс с агента Jenkins.

Токены и пароли не запрашивай в сообщениях или артефактах репозитория. Пользователь
или администратор создаёт Jenkins Credentials; для настройки используются их ID.
Если назначение уже разрешает настройку и нужный доступ имеется, дополнительное
подтверждение каждого шага не требуется. Отсутствие ответа не разрешает выбирать
рабочий проект, ветку или credentials самостоятельно.

Пока ответы ожидаются, готовь независимые шаблоны, локально проверяй генератор и
документируй недостающие условия. Не объявляй подключение настроенным на основании
готового Jenkinsfile или локального Allure JSON.

## Выполнение и проверка

1. Сохрани исходную конфигурацию и способ восстановления. Проверяй применимость
   официальной инструкции Jenkins к установленным версиям и сетевым условиям.
2. Отдели preview без доступа к публикации от джобы публикации. Pipeline обеих
   джоб читается из защищённой основной ветки; репозиторий из payload не исполняется.
3. Подготовь catalogs/ID-карту, проверь дубли, namespace, инстанс и проект. Для
   существующих карточек прочитай их ID в целевом проекте; не подставляй примеры.
4. Получи тестовую доставку GitVerse, зафиксируй фактическую схему payload и
   проверь JSONPath/regex через dry-run. Не объявляй `$.ref` и
   `$.repository.full_name` подтверждёнными до этой проверки.
5. Проверь подготовку каталога с выключенной публикацией. Потом в назначенном
   пилотном проекте выполни чек-лист `examples/testops-jenkins/README.md`:
   тип Manual, полные шаги, статусы без ложного Passed, изменение и переименование
   без новых карточек, обработка повторного вебхука и ошибки сети.
6. Согласуй процесс закрытия ручных запусков. Allure-импорт создаёт запуск и
   не равен обновлению карточек через API; не закрывай непройденный запуск ради
   зелёной сборки. При необходимости чистой синхронизации карточек выбери API/MCP.
7. В пределах назначения включи публикацию только основной ветки. Проверь, что
   событие рабочей ветки запускает preview, а публикацию не запускает. Сохрани
   SHA каталога, URL Jenkins build/ТестОпс launch и подтверждённые TestOps ID.
8. При неопределённом исходе внешней записи сначала прочитай состояние сервера;
   повторная загрузка может создать дополнительный запуск. Отсутствующий файл
   не является командой удаления кейса; удаления обрабатываются отдельно.

В результате отдели подготовленные файлы, созданную конфигурацию и реально
проверенное подключение. `environment_ready` возможно только при выполнении
критериев назначенной инфраструктурной задачи. При недоступных системах укажи
частичную готовность/блокер по действующему контракту и сохрани локальную работу.

# Подключение QA-пакета к проекту приложения

Для нового подключения предпочтителен [extension](EXTENSIONS.md): установите
пакет и выполните `/qa:init` в проекте. Роли/skills не копируются в приложение,
контекст хранится в `.qa-agent/APP_CONTEXT.md`. Ниже сохранён альтернативный
порядок подключения исходной копии и миграции существующих адаптаций.
Для native extension начиная с 2.3.12 нужны корневые `agents/`, `skills/`,
`commands/`; прежняя поставка только `.gigacode/…` не обнаруживалась целевой
сборкой CLI. Сначала обновите полный пакет по [EXTENSIONS.md](EXTENSIONS.md).
Если после этого в `/agents manage` не видны только его роли, используйте более узкое
[явное подключение ролей](EXTENSIONS.md#если-агенты-extension-отсутствуют-в-agents-manage)
через `qa_project_agents.py`. Полное копирование и адаптация пакета ниже для
этого случая не требуются.

## Подключение только в одном проекте

Чтобы QA-компоненты подключались в одном выбранном проекте, используйте проектные
`.gigacode/agents/`, `.gigacode/skills/`, `.gigacode/commands/` и импорт в его
`GIGACODE.md` по порядку ниже. Эти уровни описаны в официальных документах:
[агенты](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/subagents),
[skills](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/skills),
[команды](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/commands).
Это проектное подключение файлов пакета; native extension manager для него
не вызывается. Манифест extension сам по себе не устанавливает область проекта.

Разместите полную проверенную копию в `<project>/qa-agent/`, а адаптированные
роли, навыки и `/qa` — в `<project>/.gigacode/`. Сохраняйте существующие файлы
приложения, исправьте пути по шагам ниже. Запускайте GIGACODE из корня проекта.
Не копируйте QA-компоненты в `~/.gigacode/`. Новое подключение применяется
в следующей сессии; открытая сессия не становится проектной переустановкой.

Если `qa-agent` ранее установлен native-менеджером и активен в других проектах,
проектные файлы не отключат ту копию. Сначала сохраните её и настройки, завершите
активную работу, затем используйте штатное отключение/удаление по `--help`
целевой сборки. Не редактируйте внутренний registry. Проверьте `/memory`:
личные/родительские инструкции могут наследоваться и при локальном подключении.

В этом режиме `/qa:init`, `/qa:doctor` и `qa-start` из native extension
не являются установщиком проектных ролей. Используйте `/qa` и проверку загрузки
из шага 9. Обновляйте исходную копию и адаптированные подключения вместе по
этому документу; цикл native uninstall/install к ним не применяется.

Если требуется именно native extension с видимостью только в проекте, сначала
снимите `gigacode extensions install --help`, `enable --help`, `disable --help`.
Различайте место хранения пакета и область его включения. Наличие workspace
enable/disable ещё не подтверждает отдельную версию пакета для каждого проекта.
Без этих данных проектную область native extension не заявляйте.
Образец native project activation из исходников Qwen Code разобран в
[EXTENSIONS.md](EXTENSIONS.md#проектная-область-как-это-устроено-в-qwen-code).
Он отделяет пользовательское хранение пакета от включения в текущем workspace;
совместимость GIGACODE с этими командами остаётся отдельной проверкой.

Приёмка: в целевом проекте видны QA-компоненты; в отдельном соседнем проекте
без QA-подключения они отсутствуют. Проверяйте в новых сессиях, включая роли,
skills, `/qa`, память и MCP. Такой пилот требует реального CLI.

Исходный пакет храните отдельным подкаталогом `qa-agent/` либо в отдельной рабочей
копии. Для новой установки GIGACODE нужен весь пакет 2.3.12 с `docs`, `scripts`,
`examples`, `.gigacode`, корневыми `agents`, `skills`, `commands`, `GIGACODE.md`
и `qa-runtime.json`.

## Порядок переноса

1. Прочитайте правила приложения и существующий `GIGACODE.md`/`AGENTS.md`.
   Зафиксируйте локальные изменения и доступные инструменты.
2. Проверьте commit или ZIP с checksum/manifest. Исходную копию держите отдельно
   от адаптируемых подключений. Не копируйте README/.gitignore в корень приложения.
3. Скопируйте QA-роли в `.gigacode/agents`, навыки в `.gigacode/skills`, `qa.md`
   в `.gigacode/commands`, сохраняя другие файлы приложения. При совпадении имени
   сравните обе версии; локальные требования не теряйте.
4. Создайте `qa-agent/APP_COORDINATOR.md` из `qa-agent/docs/COORDINATOR.md`.
   Адаптируйте ссылки к `qa-agent/docs`, `qa-agent/scripts`, `qa-agent/examples`,
   и подключённым `.gigacode/skills` в корне приложения. Сохраните исходник отдельно.
5. Добавьте в существующий `GIGACODE.md` приложения импорт
   `@qa-agent/APP_COORDINATOR.md`. Полный набор стандартов постоянно не импортируйте.
6. В скопированных ролях и skills адаптируйте ссылки на документы/утилиты с учётом
   нового расположения. Относительные ссылки Markdown разрешаются от файла skill;
   команды Python запускаются из явно указанного корня приложения/пакета.
7. Настройки Playwright MCP объедините отдельно. Путь к config теперь
   `qa-agent/.gigacode/playwright.config.json`; если MCP использует другой cwd,
   задайте фактический абсолютный путь. Существующие соединения и auth сохраняйте.
8. Добавьте игнорирование `.qa-agent-state`, рабочих artifacts и локальных секретов
   в .gitignore приложения, сохраняя прежние правила.
9. Откройте новую сессию GIGACODE из приложения. Проверьте `/memory`,
   `/agents manage`, `/skills`, `/help`, `/mcp` и одну задачу по требованиям.

## Контекст приложения

Заполните отдельный APP_CONTEXT.md по [шаблону](../examples/qa-only/APP_CONTEXT.template.md):
источники требований, бизнес-термины, стенды/сборки, роли, данные, доступные tools,
команды автотестов и ограничения действий. Не выдумывайте неизвестные параметры
и не добавляйте credentials. Для Jira используйте поставляемый jira-defect-creator,
настройте доступ и измеренный профиль проекта вне поставки.
Для UI задайте один общий browser_pool_path и фактический owner; cleanup и
карантин применяются по [BROWSER_PROFILES.md](BROWSER_PROFILES.md).

## Отдельный запуск автотестов

Runner передаёт тело роли, предметные стандарты и контракт в системный prompt.
Frontmatter роли сам по себе не ограничивает отдельную CLI-сессию в другом
репозитории: её tools определяются настройками целевого проекта. Используйте
его отдельную рабочую копию; task/state храните вне неё. CLI-совместимость
проверяется до задания по [RUNTIMES.md](RUNTIMES.md).

## Приёмка подключения

Сохраните INSTALL_REPORT.md: версия/commit, изменённые пути, проверки, доступные
инструменты и остающиеся блокеры. Проверка загрузки файлов не означает
продуктового исполнения или измеренного качества GIGACODE. Для нового managed-
плана фиксируйте фактические версии/tools/gateway scope и независимое ревью.

# Подтверждённая публикация дефекта в Jira

Новые назначения qa-jira-defect-creator получают jira_checks_required=true.
Без согласованного jira_assignment допустим только blocked с подготовленными
материалами. Пакет поставляет универсальный
[jira-defect-creator](../.gigacode/skills/jira-defect-creator/SKILL.md).
Подключение Jira и измеренный профиль конкретного проекта настраиваются отдельно;
валидатор пакета не создаёт задачи. Локальный check_payload.py из навыка проверяет
структуру плана, но не заменяет назначение, gateway или доказательства публикации.
Перед внешними действиями прочитай установленный навык и соблюдай его порядок,
поля и ограничения; при отсутствии навыка, проекта или доступа верни blocked.

Встроенный навык поддерживает также самостоятельные дополнения/вложения/связи,
но managed-create не получает эти write автоматически. Для них нужны отдельные
согласованные назначения/политики. Retry чтения из навыка не меняет предел
одного create/одной попытки. Ограниченный обзор последних задач не удовлетворяет
требованию complete поиска; неизвестный охват оставляет blocked.

## До внешних действий

Координатор принимает state-backed investigation_complete с outcome=defect_confirmed.
Назначение Jira включает этот request_id как явную ready-зависимость. Другой
вердикт, непринятый источник, изменённые доказательства и blocking-ревью исключают
передачу. Подтверждение причины не требуется для регистрации подтверждённого
нарушения; неизвестную причину не превращай в установленную.

В assignment.jira_assignment передай независимый локальный JSON:

- schema_version=1, task_id, investigation_request_id, investigation_sha256 —
  точный SHA-256 принятого отчёта; created_at с временной зоной;
- jira_base_url — согласованный HTTPS-корень без завершающего слеша;
  project_key — ключ проекта;
- expected_fields — нормализованные project_key, issue_type, summary, description
  и остальные обязательные поля проекта. Для созданной задачи все эти значения
  должны совпасть при чтении. Это представление для сравнения, не универсальный
  формат Jira API. Адаптер согласует его с реальными полями/шаблоном навыка;
- skill: path/sha256 установленного jira-defect-creator;
- gateway: state_path, policy_path, step_id, create_tool, create_arguments
  (точные согласованные аргументы записи), issue_key_pointer (JSON Pointer
  ключа задачи в MCP-ответе, включая ответ reconciliation).

Scope, файл навыка и policy автоматически замораживаются как inputs. Registry
задаётся пакетом через jira_task_state, исполнитель не подменяет его другим.
Описание сохраняет источник ожидания, фактическое нарушение, условия/сборку,
шаги/диагностику, первичные доказательства и ограничения. Исключи секреты и
персональные данные; координатор содержательно проверяет полноту и допустимость.

Для управляемой записи используй ACTION_GATEWAY.md: только согласованный
create_tool имеет effect=write, ограничения охватывают проект и аргументы,
max_write_actions=1, max_action_attempts=1. Поиск и чтение доступны как разрешённые
read. Перед вызовом запиши точный scope; штатный managed-runner проверяет приёмку
зависимостей до запуска исполнителя. Прикладной сервер/адаптер и реальные MCP
названия настраиваются под доступный Jira-сервис; учебный адаптер не рабочий Jira.

До создания поищи дубли по симптому, версии и компоненту, прочитай каждого
кандидата. Сохрани reason для same_defect/different. Неопределённый кандидат,
неполная пагинация или недоступный поиск требуют blocked. Подходящий дубль
возвращается без создания новой задачи. Координатор проверяет смысл сравнения,
включая применимость старой/закрытой задачи к текущему нарушению.

## Неоднозначный исход

Gateway сохраняет started **до** записи. Timeout/разрыв оставляет unknown;
это блокирует любую следующую запись шага, включая изменённые аргументы.
Не перезапускай создание под другим request_id, step_id или файлом gateway.
Для того же принятого дефекта, Jira и проекта реестр требует повторно использовать
исходный gateway и step_id, включая исправление отчёта после blocked.

Выполни согласованное qa_reconcile_action/чтение по ACTION_GATEWAY.md. Только
подтверждённый объект даёт verified и квитанцию, после чего отдельно прочитай
его поля. Отсутствие объекта в неполном поиске не означает неуспешное создание.
Одна попытка создания на эту операцию — консервативный предел: автоматического
повтора нет даже после not_applied. Если нужна новая операция, координатор
сначала разбирает исход и отдельно согласует её; не обнуляй журнал. Между
разными реестрами семантическое совпадение контролирует координатор.

## Артефакты результата

Новые jira_defect_created и jira_duplicate_found содержат issue_key, issue_url,
duplicate_check, evidence (локальные первичные доказательства принятого расследования),
jira_assignment_sha256 и publication_artifact. Issue URL точно соответствует
`<jira_base_url>/browse/<issue_key>`, ключ относится к назначенному проекту.
При blocked без публикации publication_artifact можно опустить.

publication_artifact — отдельный JSON: schema_version=1, task_id, request_id,
search_artifact и readback_artifact (для созданной задачи). Все относительные
ссылки разрешаются по artifact_base назначения, для отдельного CLI — по каталогу
результата либо --jira-evidence-base. Все вложенные материалы хешируются реестром.

search_artifact — сохранённое наблюдение: observed_at, jira_base_url, project_key,
query, complete=true, candidates. В каждом кандидате issue_key, issue_url,
assessment=same_defect|different, содержательный reason и readback_artifact.
Непрочитанный/неоценённый кандидат не позволяет завершить публикацию. Чтение
кандидата содержит observed_at, jira_base_url, issue_key, issue_url и fields
как минимум с непустыми summary/description. Для duplicate_found выбранный
ключ должен быть среди same_defect, а gateway не должен содержать записей.

Для jira_defect_created нужен отдельный readback_artifact с observed_at,
jira_base_url, issue_key, issue_url и fields. Чтение выполняется после начала
создания, совпадает с ожидаемыми полями. Поиск и чтение всех кандидатов должны предшествовать созданию,
все наблюдения — быть не старше scope и не из будущего. Gateway содержит ровно
одну verified-попытку с точными аргументами и неизменной квитанцией того же ключа.
Успешный ответ create без чтения фактически сохранённых полей недостаточен.

Снимки должны фиксировать реальные ответы и их контекст, при необходимости
сохраняй первичные ответы рядом через artifacts. Пакет проверяет связи,
неизменность, порядок и объявленные значения. Он не обращается к Jira при
валидации, не удостоверяет происхождение вручную записанного файла и не
заменяет независимое чтение координатором. Не создавай фиктивные «доказательства».

После принятия координатор возвращает ссылку на созданную задачу либо на дубль
и короткое обоснование. При неопределённой записи возвращает blocked и причину.
Переход, verified-критерий, finish и checkpoint повторно проверяют публикацию;
сам по себе jira_* не означает, что дефект исправлен или продукт готов.

## Проверка и совместимость

```bash
python3 scripts/validate_qa_result.py --input /absolute/jira-result.json \
  --task-id QA-FIXTURE --request-id jira-1 --agent qa-jira-defect-creator \
  --jira-assignment /absolute/jira-assignment.json \
  --jira-task-state /absolute/task.json --require-jira-checks
```

Старые отчёты и хеши не мигрируются. Обычный CLI без scope сохраняет структурный
аудит истории; новый ready-переход/verified/finish/checkpoint требует подтверждения
публикации. Для диагностики старый отчёт можно передать как context. Исправленный
отчёт получает новый request_id/result_path, сохраняя gateway той же операции.
Синтетический пример — [jira-publication](../examples/jira-publication/README.md).

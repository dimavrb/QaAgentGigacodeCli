# Проверка подозрения на дефект

## Когда включать

При наблюдаемом расхождении с требованием или подозрении пользователя координатор сам назначает `qa-defect-investigator` в рамках текущей задачи. Отдельная просьба «сделай ретест» не нужна. Падение инструмента/фикстуры без продуктового наблюдения сначала требует диагностики теста или окружения. Один симптом в тех же условиях ведётся в одном расследовании; независимые сценарии продолжаются.

Координатор создаёт состояние по INVESTIGATION.md с `verification_required: true`, передаёт относящиеся ID сценариев, источник правила, первичное наблюдение, сборку и условия, доступный путь к **коду приложения** и его ревизию (если известны). Передаёт доступный путь к этому документу только участникам расследования. Не загружай весь репозиторий или историю. Внешний автоматизатор сообщает подозрение своему координатору через результат; он не запускает отсутствующие в его сессии роли.

## Порядок работы

1. **Правило и факт.** Назови бизнес-действие, предусловия и ожидаемый эффект по актуальному источнику. Код объясняет реализацию, но не задаёт ожидаемое поведение. Если правило не определено, запроси анализ, сохрани наблюдение; не называй его дефектом.
2. **Имеющиеся доказательства.** Прочитай относящиеся ответы API, логи, trace, состояние данных и первичные шаги. Проверь роль, набор данных, сборку, тогглы и их эффективные значения. Достаточный сохранённый запуск повторять не нужно. При импорте первичного запуска сохраняй его автора, исходную ссылку, время и условия в observations/описании доказательства; не выдавай его за собственный новый запуск. Чтение кода не является выполненной попыткой проверки продукта.
3. **Путь по коду.** Ищи точку входа по действию, запросу или событию. Проследи относящиеся проверки прав/условий/тогглов до ответа, изменения данных или события. Сохрани короткие фрагменты с путём, строкой и ревизией; проверь кеш/асинхронность только если они относятся к симптому. Свяжи ревизию с фактически развёрнутой сборкой через наблюдаемые метаданные. Совпадение названия ветки или локальный HEAD не доказывает этого. Исходники теста в trace не заменяют код приложения. При недоступном коде зафиксируй ограничение, продолжи проверку факта.
4. **Недостающий факт.** Сформулируй один вопрос и самое дешёвое наблюдение, которое его решит: прочитать уже имеющийся ответ, проверить эффективный тоггл, запись/событие, выполнить адресный запрос или сценарий. Для асинхронного результата используй ограниченное ожидание по условию. Повтор требует ссылки на прошлую попытку, причины и критерия остановки; без новой информации не повторяй весь набор. Соблюдай лимит циклов CONTRACT.md.
5. **Вывод и независимое принятие.** Сохрани verification.json, передай координатору. Он читает правило и первичные материалы и оценивает пять проверок из INVESTIGATION.md. Подтверждение нарушения и подтверждение причины — разные решения. Для причины в коде нужны применимая ревизия и наблюдение фактически сработавшего механизма; достижимость ветки по исходникам недостаточна. Не исправляй продукт и не ослабляй тест в рамках проверки подозрения.

Критерий остановки: доказательств достаточно для ограниченного вердикта, обнаружен конкретный блокер либо исчерпан лимит адресных уточнений. Не ищи полную первопричину как условие регистрации уже подтверждённого нарушения. Исследование причины может остаться отдельной следующей работой.

## Артефакт и проверка

Используй `schema_version: 1`. Все поля из таблицы обязательны; пустые списки и null указываются явно. Пример с разбором учебного обработчика: `examples/investigations/verification/verification.json`; вариант с недоступным кодом описан в соседнем README.md.

| Поле | Содержание |
| --- | --- |
| `task_id`, `request_id`, `outcome` | Совпадают с текущим investigation_complete |
| `business_rule` | `source` совпадает с expected_source; `expected_result` описывает бизнес-эффект; `relation`: violated для defect_confirmed, matches для expected_behavior, undetermined для остальных |
| `observation` | `actual_result` совпадает с payload; `runtime_evidence_ids` — первичные наблюдения выполненных попыток в текущем context |
| `code_path` | `status`: traced/unavailable/not_needed; `repository`, `revision`: строки для traced, иначе null; `deployment_match`: matched/mismatch/unknown; `deployment_evidence_ids`; `steps`; `assessment` объясняет путь, неопределённость или причину отсутствия разбора |
| `code_path.steps[]` | `file` относительно репозитория, `line` от 1, `behavior` — конкретная проверка/эффект, `evidence_ids` — сохранённые фрагменты исходников; для traced хотя бы один шаг |
| `cause` | `status`: unknown/suspected/confirmed; `scope`: application/test/environment; `statement`; `evidence_ids`. Для unknown — null scope/statement и пустой список |
| `next_check` | `action`: none/inspect_evidence/targeted_check/retest/blocked; `goal`: defect_confirmation/cause_analysis; `gap` — конкретный недостающий факт; `reason`; `repeat_of` — ID прежней попытки, обязателен для retest. Для none — null goal/gap/repeat_of и причина остановки |
| `limitations` | Совпадают с payload.limitations; ограничения области вывода, доступности кода/сборки/тогглов |

Все evidence_ids относятся к реестру **названных в отчёте попыток**. Исходники и verification.json не могут служить runtime-доказательством. Для matched требуется отдельное наблюдение развёрнутой ревизии в текущих условиях. Для confirmed причины application нужны matched, трассировка и поддерживающие причину исходники и runtime-доказательства. Для причин теста/окружения необходимы фактические наблюдения; смысл этих связей проверяет координатор. Не называй гипотезу причиной только потому, что заполнены поля.

verification.json зарегистрируй как локальное доказательство с SHA-256 в состоянии, привязав к попытке, материалы которой он оценивает. Добавь путь в `payload.verification_artifact`, `payload.evidence` и `artifacts`; это артефакт анализа, не ещё один продуктовый запуск. Относительный путь разрешается **от каталога state.json**, как прочие доказательства. При разных каталогах результата и состояния используй абсолютные пути. После любого изменения обновляются SHA и содержательная оценка, а не только fingerprints.

Проверяй результат обычным `scripts/validate_qa_result.py` с `--investigation-state` по INVESTIGATION.md. Без этого параметра результат с verification_artifact отклоняется. Скрипт проверяет структуру, ссылки, неизменность локальных файлов и совместимость заявлений; он не устанавливает истинность логов, бизнес-правила, классификации доказательств или выполнения ветки кода. Эти вопросы явно отрази в заметках ревью.

Старые состояния без verification_required и отчёты без verification_artifact остаются совместимыми. Для всех новых подозрений флаг обязателен; при продолжении старого расследования координатор включает его и сбрасывает прежнее ревью. События и статусы сценариев сохраняются: failed не превращается в passed после чтения кода, исторический запуск не переписывается.

## Короткое сообщение пользователю

После принятия координатором, например:

> **Дефект подтверждён: покупатель получает список пользователей.** По правилу R-1 доступ должен быть запрещён; на fixture-1 API вернул 200 и список. Причина пока не установлена: код развёрнутой версии недоступен. Повтор не нужен для подтверждения нарушения. Доказательства и область вывода — в артефакте проверки.

Это учебный пример, не результат проверки приложения. При неподтверждённом подозрении назови недостающий факт и следующую адресную проверку. Не перечисляй весь путь по коду в сообщении — он остаётся в артефакте.

## Подключение изменения к установленному агенту

Обновляй весь текущий пакет по SETUP_AND_UPDATE.md и UPDATE.md; проверяй версию и SHA-256 исходного ZIP. При переносе обнови вместе GIGACODE.md/подключённый APP_COORDINATOR.md, роли координатора (главная сессия), qa-feature-tester, qa-test-automation, qa-defect-investigator, новые defect_verification.py и DEFECT_VERIFICATION.md, investigation_state.py, validate_qa_result.py и связанные документы. Сохрани локальные tools, пути, ограничения приложения и незавершённое состояние. Для подключённых копий адаптируй ссылки к qa-agent/docs/ и qa-agent/scripts/. Полный стандарт не импортируй в постоянный GIGACODE-контекст. Начни новую сессию и проверь на одном разрешённом случае: маршрутизацию подозрения, использование первичного наблюдения, конкретность следующего вопроса и короткий вердикт. Успех тестов пакета не заменяет эту проверку живой моделью.

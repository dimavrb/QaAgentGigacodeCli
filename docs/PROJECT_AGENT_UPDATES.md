# Установка и обновление проектных QA-ролей

Для проектной установки с install.json обновляйте весь комплект через qa_install.py
по [PROJECT_INSTALLATION.md](PROJECT_INSTALLATION.md). Следующая процедура
сохранена для прежних отдельно управляемых копий ролей.

`qa_project_agents.py` размещает роли в `<project_root>/.gigacode/agents/`.
Исходник — установленный `package_root` из `qa_project.py info`, совпадающий
с `.qa-agent/project.local.json`. Init сохраняет контракт трёх файлов;
первое подключение ролей выполняется отдельной явной командой.

## Первое подключение и ручная синхронизация

Завершите активные QA-назначения и закройте GIGACODE. Выполняйте команды
из обычного терминала; подставьте абсолютные пути своей установки и проекта:

```bash
python3 /absolute/path/to/installed/qa-agent/scripts/qa_project.py init --project-root /absolute/path/to/app
python3 /absolute/path/to/installed/qa-agent/scripts/qa_project_agents.py --project-root /absolute/path/to/app
python3 /absolute/path/to/installed/qa-agent/scripts/qa_project_agents.py --project-root /absolute/path/to/app --apply
```

Без `--apply` — план без записи, в том числе при незавершённой операции.
С `--apply` — применение безопасных изменений каждой роли. В этом режиме код
выхода 0 означает согласованную синхронизацию файлов. Preview с кодом 0 означает
валидный план, который ещё не применён. Код 1 — `needs_attention`, 2 — ошибка.
При активной сессии или незавершённом назначении применение отклоняется.
CLI использует тот же lock-профиль `~/.gigacode/qa-agent-updates`, что и
`qa-start`; при собственном профиле передавайте одинаковый `--state-dir`.
Launcher передаёт уже удерживаемую блокировку дочернему синхронизатору.
Работу с исходным пакетом и другими редакторами на время синхронизации остановите.

Наличие файлов не подтверждает живую загрузку: `live_agents_verified=false`.
После применения откройте новую сессию из проекта, проверьте `/agents manage`,
вызов роли и возврат координатору. Не приписывайте файловой проверке качество модели.

## Правила обновления

Для каждой управляемой роли сравниваются предыдущий исходник поставки, текущий
проектный файл и новый исходник поставки.

| Состояние | Действие |
| --- | --- |
| Проектный файл не менялся локально | Автоматически заменить новой версией |
| Проектный файл уже совпадает с новым | Принять новый исходник в историю без перезаписи |
| Есть локальные правки, исходник поставки не менялся | Сохранить адаптацию |
| Изменились и проектный файл, и исходник поставки | Сохранить файл, сообщить `both_changed` |
| Новая роль отсутствует в проекте | Добавить независимо от конфликтов других ролей |
| Управляемую роль удалили в проекте | Сообщить `deleted_locally`, не восстанавливать молча |
| Роль убрана из пакета, проектный файл не менялся | Сохранить резервную копию и удалить из каталога обнаружения |
| Убранная из пакета роль адаптирована | Сохранить её и сообщить конфликт |

Конфликт одной роли не останавливает обновление остальных. Общий статус остаётся
`needs_attention`, завершённая версия реестра не повышается до разрешения всех
конфликтов. Базовые версии отдельных успешно обработанных ролей сохраняются.
Чужие роли, которых нет в реестре и новой поставке, не меняются.

## Разрешение конфликтов

В `conflict_details` указаны причина, имя, хеши и пути предыдущего/нового
исходников. Сравните их с текущим файлом и объедините изменения адресно.
Если заменить проектную роль точной новой версией, следующий `--apply` примет её
автоматически. Чтобы сохранить рассмотренную адаптацию, выполните новый preview
и передайте **его актуальные** хеши:

```bash
python3 /absolute/path/to/installed/qa-agent/scripts/qa_project_agents.py \
  --project-root /absolute/path/to/app --apply \
  --accept-local 'qa-analyst.md:LOCAL_SHA256:INCOMING_SHA256'
```

`--accept-local` не переписывает адаптацию, а принимает новый исходник поставки
как базу для следующих сравнений. Изменение любого из двух хешей отклоняет решение.
Автоматического текстового merge и режима force нет. Удалённую локально роль
восстанавливают отдельно с `--apply --restore qa-analyst.md`.
Адаптированную роль, убранную из пакета, сохраните вне `.gigacode/agents/`, затем
повторите синхронизацию: её запись будет снята с управления.

## История и восстановление

Локальные файлы игнорируются Git после init:

- `.qa-agent/agents.local.json` — базовые хеши/версии ролей и незавершённая операция;
- `.qa-agent/agent-updates/blobs/` — исходники с проверяемыми SHA-256;
- `.qa-agent/agent-updates/backups/<ID>/` — файлы перед изменением;
- `.qa-agent/agent-updates/transactions/` — неизменяемые журналы намерений.

Снимки и pending сохраняются до замены ролей. Записи публикуются атомарно
по файлам под общей блокировкой проекта; набор ролей не переключается одной
операцией. После прерывания повторите `--apply`: уже применённые файлы будут
распознаны, оставшиеся продолжены. Новые посторонние правки сохраняются как
конфликт. Блокировка согласует утилиты пакета, но не произвольные внешние редакторы.
Журнал намерения сам по себе не подтверждает завершение: текущее состояние —
в реестре и файлах. Не удаляйте и не редактируйте историю ради обхода конфликта;
повреждение baseline/реестра останавливает запись.

Копии из 2.3.10 не имеют истории. Первый явный `--apply` принимает совпадающие
с текущим пакетом файлы, добавляет отсутствующие и сохраняет отличающиеся
как `unknown_baseline`. Старые файлы нельзя объявлять неизменёнными только
по совпадению имени: их нужно сравнить и принять отдельно.

## Автоматический запуск

После обновления native-пакета `qa-start` освежает binding, вызывает синхронизацию
из установленного пакета и только затем открывает GIGACODE. `--no-update`
отключает Git-проверку, но не обходит нерешённые конфликты проектных ролей.
При общей блокировке активных сессий launcher делает только preview; требующие
записи изменения откладываются до завершения сессий. `--update-only` также
синхронизирует управляемые роли и не открывает модельную сессию.

Проект без реестра и без проектных QA-копий не подключается автоматически.
Старые копии без реестра требуют первого явного `--apply`. Doctor читает историю
без записи: принятые адаптации к неизменившейся базе допустимы, pending,
конфликты и требующаяся синхронизация отражаются в `project_agent_copies`.
Прямой запуск `gigacode` не вызывает эту утилиту; перед ним нужна ручная
синхронизация. Непроверенные native hooks не используются.

Изменённые инструкции требуют нового managed-плана. При откате между выпусками,
поддерживающими эту историю, выполните ту же синхронизацию: неизменённые роли
вернутся к исходникам выбранного выпуска, адаптированные потребуют рассмотрения.
Для отката до 2.3.10 и ниже нужен согласованный снимок пакета, проектных ролей и
состояния до включения нового механизма; текущую историю сохраните отдельно.
Старая утилита не умеет продолжать новую транзакцию. Runtime, доказательства
и исторические хеши задач не переписываются.

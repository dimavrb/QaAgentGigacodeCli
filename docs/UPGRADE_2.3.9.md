# Обновление до 2.3.9

Для установки только в один проект выберите проектное подключение по
[IMPORT_INTO_APP.md](IMPORT_INTO_APP.md#подключение-только-в-одном-проекте)
и обновляйте локальную копию вместе с адаптированными `.gigacode`-файлами.
Ниже — порядок для native extension. Проектная область native manager требует
подтверждения по `--help` вашей сборки; флаги других CLI не переносите.

1. Сохраните предыдущий пакет/commit, локальные адаптации и настройки расширения
   вне заменяемого каталога. Закройте все сессии GIGACODE и завершите активные
   назначения. Контекст приложения, задачи, auth/MCP и доказательства храните
   отдельно от пакета; исторические hashes не пересчитывайте.
2. Следуйте [EXTENSIONS.md](EXTENSIONS.md). Если `extensions update qa-agent`
   требует сначала uninstall, используйте ручную переустановку: после подготовки
   исходного clone выполните `gigacode extensions uninstall qa-agent`, затем
   `gigacode extensions install /absolute/path/to/qa-agent`. При ошибке команды
   остановитесь; не правьте внутренний registry CLI.
3. Если прежний `qa-start` уже оставил pending, не делайте новый pull: используйте
   подготовленный commit из журнала. Сохраните pending/recovery и резервную копию.
   После установки в прежний путь выполните `qa-start --update-only` для сверки
   и завершения активации. При другом пути или частичной установке сначала
   восстановите согласованное состояние по [UPDATE_SAFETY.md](UPDATE_SAFETY.md).
   Не удаляйте журнал и не обходите pending через `--no-update`.
4. Сверьте VERSION и gigacode-extension.json: 2.3.9. Если pending был подготовлен
   для прежней версии, сначала завершите ту активацию, затем обновляйте до 2.3.9.
   Откройте новую сессию из приложения, проверьте `qa_package_info`, `/qa:init`,
   `/qa:doctor`, 14 ролей, 6 skills, команды и MCP. Изменённые инструкции требуют
   нового managed-плана. Сохранность настроек менеджера проверьте отдельно.
5. Выполните локальные проверки из [RELEASE_2.3.9.md](RELEASE_2.3.9.md).
   Отказ с требованием uninstall теперь показывает исходный ответ CLI и порядок
   продолжения; автоматическое удаление расширения не выполняется.

Для отката используйте предыдущую проверенную поставку и штатный менеджер,
сверьте registry и привязку проекта. Файловый rollback не удостоверяет состояние
менеджера. Runtime-артефакты и уже выполненные внешние действия сохраняются.

Для новых назначений qa-stub-builder передавайте независимый stub_assignment:
при assign проверяются роль/task/request/сценарии, scope автоматически замораживается.
Вложенные наблюдения входят в хеши результата; при отдельных каталогах задайте
artifact_base либо standalone --stub-evidence-base. Не переписывайте исторические
timestamps/hashes; новый request_id требует соответствующего назначения.
Подробности — [проверка передачи заглушек](STUBS_HANDOFF_REVIEW.md).

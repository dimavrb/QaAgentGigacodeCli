# Отбор ручных сценариев до написания шагов

Применяй при создании или существенном изменении ручного каталога вместе с
`qa-test-cases`, `qa-check-quality` и [TEST_PLAN.md](TEST_PLAN.md). Цель — полезное
покрытие с понятными инструкциями. Число кейсов и длина текста не являются
критериями качества. Принятые кейсы без затронутого поведения массово не переписывай.

## Основание и возможности

Для кандидата установи правило/риск и источник ожидания, конкретную возможную
ошибку, способ получить исходное условие, различающее наблюдение и отличие от
существующего покрытия. Используй требования, согласованную область, архитектурные
риски и известные дефекты; гипотеза ошибки не означает найденный дефект.
Отсутствие прошлых дефектов само по себе не оправдывает исключение.

Прочитай только относящиеся к задаче разделы `.qa-agent/APP_CONTEXT.md` и указанные
инструкции. Подтверди канал проверки (UI/API/импорт/интеграция), роли, создание
данных/состояний, разрешённую имитацию ошибок и доступные наблюдения. Ссылка на
средство не означает, что оно подключено или разрешено к запуску. Планирование
не разрешает эксперимент с продуктом. Неизвестные сведения сохраняй как вопросы.

Реализация может показать ограничение ввода или доступный наблюдатель, но не
определяет правильное бизнес-поведение вместо требования. При противоречии
уточняй источник; не принимай текущее поведение за норму, чтобы исключить тест.

## Достижимость и готовность

| Условие | Решение |
| --- | --- |
| Подтверждённо недостижимо через выбранный канал | Исключить этот способ с источником основания; проверить, остаётся ли нужное покрытие через другой канал |
| Запрещено правилом, но технически подаётся как вход | Сохранить применимый негативный сценарий; запрет не делает вход недостижимым |
| Способ подготовки и ожидание известны, но нет данных/доступа/стенда | Спроектировать кейс; указать зависимость `blocks=execution` и способ подтвердить её готовность |
| Неизвестны достижимость, способ подготовки/наблюдения либо ожидание | Сохранить риск и вопрос `blocks=planning`; не включать выдуманный готовый кейс в каталог |
| Событие редкое, последствия существенны | Оценить риск и доступную изоляцию; редкость не равна невозможности |

Пример: UI не позволяет установить количество `0`. Не описывай отправку формы
с `0` через этот экран, если нет подтверждённого способа. Доступность сохранения
может быть UI-проверкой; серверный запрет через API — отдельным контрактом с
собственной подготовкой и ожиданием. Скрытая кнопка не доказывает серверный отказ.

Для исключения обязательного критерия нужна подтверждённая неприменимость либо
согласованное изменение области. Если способ проверки непригоден, сохраняй
критерий как пробел до выбора альтернативы. Мок подтверждает только поведение
при заданном ответе; UI-сообщение само по себе не подтверждает внутренний rollback.

## Проверка и самостоятельный кейс

До детализации выбери различающие данные. Для существенной возможной ошибки
сопоставь результат по требованию и результат ошибочной реализации: на выбранном
наборе они должны отличаться. Например, для чтения сохранённого идентификатора
сохраняемое значение отличается от независимого расчёта по текущим данным.
Случайная строка/маркер не подходят, если нарушают предусловие проверяемой ветки.
Сравнивай на уровне требуемого свойства с учётом контрактной нормализации:
различие полных значений не подменяй косвенным отсутствием подстроки. Проверка
подстроки/фрагмента уместна, когда такое условие задано самим контрактом.
Не вычисляй эталон тем же проверяемым методом.

Заранее определи силу наблюдения: подтверждение команды, содержимое ответа,
изменение состояния или отсутствие попытки действия — разные свойства.
Неизменность значения не исключает попытку записи, отсутствие строки лога
без полного наблюдения не доказывает отсутствие действия. Если требование
касается именно попытки, выбери источник, позволяющий её увидеть; неизвестный
способ — planning, известный временно недоступный — execution. Если требование
касается только внешнего результата, не добавляй запрет внутренних действий
или обязательный аудит без отдельного основания.

Единица покрытия — правило в конкретном условии с наблюдением, обнаруживающим
существенную ошибку. Кейс организует исполнение одной или нескольких связанных
проверок. Для кандидата выбери решение:

- **Отдельный кейс:** иной класс условий, правило или ошибка требует независимой
  подготовки/исполнения; укажи, что существующие сценарии пропускают.
- **Встроить проверку:** общий сценарий уже создаёт нужные условия и позволяет
  наблюдать эффект; укажи сохраняемый ID и место наблюдения.
- **Предусловие:** действие только готовит сценарий и само не проверяет отдельное
  обязательное правило. Перенос не должен скрывать проверку этого правила.
- **Вопрос:** нужен источник или подтверждение способа; свяжи с требованием и ID.
- **Исключить:** нет добавленного покрытия, кандидат вне согласованной области
  или подтверждённо неприменим; запиши основание и сохранённое покрытие/пробел.

«Кнопка видна» обычно входит в успешное выполнение действия. Если доступность
зависит от роли, это отдельное правило, которое надо сохранить. Короткий сценарий
не становится тривиальным только из-за одного шага; длинный не становится полезным
из-за подробного оформления.

Объединяй при совместимой подготовке, действиях и наблюдениях. Разные права,
границы, состояния и уровни проверки не эквивалентны только из-за похожих шагов.
Не делай длинную цепочку независимых сценариев: ранний отказ или необратимое
действие может скрыть остальные проверки. Для сравнения условий допустимы
параметры по TEST_DESIGN.md, с отдельными наборами и ожиданиями; не добавляй
параметры в публикуемый каталог, если его потребитель их не поддерживает.

## Компактная запись и принятие

Сохраняй обоснования рядом с существующей картой покрытия, без новых обязательных
полей каталога или payload. Для ясного случая достаточно строки, например:
`C-02 → встроить в TC-EXPORT: тот же набор и запуск; скачивание наблюдается в шаге 2;
R-EXPORT сохраняется`. Для исключения укажи источник; для объединения — прежние
ID → сохраняемый ID; для зависимости — существующий вопрос и способ её закрыть.
Ссылки на готовый анализ заменяют повторение. Не копируй туда шаги каталога.

Координатор независимо сверяет существенные решения с источниками и покрытиями:
не исчезли ли критерии, не принята ли неизвестность за невозможность, действительно
ли объединение сохраняет наблюдения. Для простого ясного случая отдельный раунд
или новая роль не нужны. Замечание относится к конкретному ID и ревизии, а не
к требованию увеличить число кейсов.

Используй существующие `requirement_coverage`, `open_questions` и `plan_revision`
по TEST_PLAN.md. Готовность проектирования и исполнения различается. Каталог с
известным способом подготовки можно принять при зависимости execution; она
должна оставаться видимой в плане/назначении, а не скрываться общей фразой в кейсе.
Если всё покрытие заблокировано planning, готовый каталог не создаётся.

При назначенной публикации отдельно проверь перенос действий и ожиданий в TMS:
генератор JSON → Allure использует вложенный шаг для ожидаемого результата.
Содержательное принятие и готовность к исполнению не устанавливаются генератором.
Первая итерация не вводит автоматический барьер публикации или новые TMS-поля.

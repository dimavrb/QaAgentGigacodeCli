# Разделение написания кейсов и проверка общего покрытия

Для небольшой ясной задачи достаточно одного автора и независимого ревью.
Несколько авторов нужны, когда связные группы поведения требуют разных источников
или полный контекст/объём детализации становится чрезмерным. Количество кейсов
не является квотой. Размеры context-metrics и CLI usage учитывай по
CONTEXT_ASSEMBLY.md; лимит символов не доказывает качество живой модели.

## Общая карта до разделения

Координатор сохраняет одного владельца итогового плана. Этот владелец составляет
общую карту и проходит раннее содержательное принятие: стабильные ID требований,
рисков и выбранных сценариев, источники/приоритеты, решения отбора, исключения,
вопросы и общие зависимости. Исходный результат — принятый coverage_ready,
plan_partial либо существующий plan_ready. Он становится неизменяемой базой.

Дели по поведению и зависимостям. Причинно связанный кейс, включая отказ и сверку
сохранения состояния, целиком принадлежит одному автору. Требование может иметь
сценарии в разных группах. Не раздавай позитивную и негативную часть одного кейса
разным авторам. Общие права, лимиты, состояния, подготовка и наблюдения имеют
подтверждённые источники; нужные общие условия получают все зависимые группы.

Координатор распределяет выбранные scenario_ids без пересечений и пропусков,
назначает разные request_id, stages и директории результатов. Дополнительный автор
не получает право менять чужую группу, общую карту или добавлять новые ID.
Предложение нового/исключённого сценария возвращается координатору; изменение
области требует новой базы и снимка разделения. Редкость/недоступность не снимают риск.

## Снимок и назначение групп

Сохрани JSON выбора групп, например:

```json
{
  "schema_version": 1,
  "plan_revision": "v2",
  "integration_request_id": "plan-integrated",
  "shared_context_paths": ["shared-constraints.md"],
  "groups": [
    {"group_id":"create","request_id":"plan-create","test_type":"api",
     "scenario_ids":["TC-001"],"context_paths":[],"depends_on":[]},
    {"group_id":"permissions","request_id":"plan-permissions","test_type":"api",
     "scenario_ids":["TC-002"],"context_paths":[],"depends_on":[]}
  ]
}
```

Контекстные файлы и локальные источники требований должны входить в принятую
базу через inputs/artifacts. Подготовь их до раннего ревью. Для большого документа
source указывает точный Markdown-якорь или диапазон строк по TEST_PLAN_HTML.md.
Внешняя ссылка сама по себе не даёт bare-автору текст: передай подтверждённый
снимок через context_paths либо сохрани needs_analysis. Полные истории/библиотеки
примеров всем авторам не передаются. Нужные общие условия не сокращай ради размера.

```bash
python3 /absolute/package_root/scripts/partition_test_plan.py build \
  --state /absolute/project_root/.qa-agent-state/tasks/QA-123/task.json \
  --baseline-request-id plan-scope \
  --groups /absolute/project_root/group-selection.json \
  --output-dir /absolute/project_root/.qa-agent/artifacts/QA-123/planning/v2
```

Получаются partition.json, <group>/context.json и assignment.json каждой группы,
а также integration/assignment-template.json. В context.json находятся выбранные
строки карты, точные фрагменты требований, относящиеся вопросы и явно переданные
общие/групповые условия. Это именованная проекция с хешами целых первичных файлов;
исходники остаются доступными для аудита. Сборщик проверяет соответствие проекции.

Назначения содержат plan_partition (path, sha256, mode=group, group_id),
scenario_ids, base_revision/plan_revision и test_type. Используй обычный маршрут
assign → prepare → запуск → submit → независимое review в общем реестре.
Выбранный пример передай через instruction_paths execution-шагов по TEST_CASE_REVIEW.md.
По умолчанию criterion_ids группы пусты; при необходимости координатор задаёт
отдельные критерии группы и required_reviews до build. integration_criterion_ids
может добавить зарегистрированные глобальные критерии; критерии исходной базы
не удаляются. Их определения и назначение базы фиксируются хешами. Глобальные критерии задачи
принадлежат интеграции, их нельзя считать выполненными по одному фрагменту.

Для параллельных групп нужны отдельные сессии/владельцы. depends_on в конфигурации
содержит ID групп, чьи принятые результаты действительно нужны следующей группе;
циклы запрещены. Назначение автора не может удалить такую зависимость или заменить
её посторонним request ID. Можно явно выбрать принятую исправленную ревизию
той же группы (`.revision-N`); её готовность проверяется обычным маршрутом передачи.
Каждый review_cycle содержит одного автора и его reviewer.
Инструмент разделения создаёт файлы и проверяет их, не запускает модель или джобы.

## Работа автора и reviewer

Автор деталирует только назначенные ID и связи. В отчёте сохраняет base_revision
из снимка и общую plan_revision. plan_ready означает готовность его группы.
Не меняй подтверждённые source/priority общей карты. Объяснения способа проверки
и доказательств могут уточняться в пределах подтверждённого правила. Неизвестное
ожидание — вопрос planning; недоступный известный ресурс — execution.
Общий вопрос не разрешается локально: решение вносится в новую общую базу.
Новые вопросы получают ID Q-<group_id>-<положительное число>.

Reviewer получает ту же привязку к снимку и ограниченный контекст, стандарт и
выбранный пример. Проверяет источник, пользу, достижимость, данные и различающие
ожидания своей группы. Проверка структуры/хешей не заменяет содержательное ревью.
Приёмка проверяет scope через submit/review автоматически; bare получает правила
в замороженном профиле. Группы не публикуются как итоговый HTML-план или в TMS.

Исправления review_cycle используют новые request_id с .revision-N и отдельный
JSON-отчёт, сохраняя группу. После исправления координатор явно выбирает принятый
result_request_id; предыдущий verdict/хеш не переносится на новую ревизию.
Изменённые общие источники или область требуют нового разделения. Не пересчитывай
исторические хеши и не перезаписывай принятые версии ради продолжения.

## Объединение и итоговая приёмка

```bash
python3 /absolute/package_root/scripts/partition_test_plan.py merge \
  --partition /absolute/project_root/.qa-agent/artifacts/QA-123/planning/v2/partition.json
```

Если выбираются исправленные результаты, добавь --group-results с JSON-картой
всех групп: {"create":"plan-create.revision-1","permissions":"plan-permissions"}.
Выбор не выполняется автоматически по времени. До merge все выбранные группы
должны быть приняты как plan_ready с применимым независимым ревью.

Merge проверяет неизменность базы/источников/контекстов, принадлежность результатов
снимку, версии, точное распределение ID, все связи требований и общий каталог.
Повторы ID/названий, пропуски, чужие сценарии, нерешённые общие planning-вопросы,
непринятый/частичный результат и несогласованное ревью останавливают сборку.
При успешной структуре получаются integration/catalog.json, payload.json,
partition-merge.json и assignment.json итогового владельца. Исходные каталоги
сохраняются; повтор с теми же данными безопасен. Новая сборка с изменёнными
данными требует новой директории/ревизии.

Итоговый владелец читает карту/доказательства и проверяет межгрупповые зависимости,
общие предусловия и смысловые дубли. Сохраняет plan.md, переносит проверенный payload
в обычный QA JSON-отчёт и выполняет самопроверку. Каталог и связи не переписывает
поверх результата merge. Для изменений кейсов сначала исправляется затронутая
группа, затем выполняются новая сборка и адресное ревью зависимых групп.

Финальный reviewer отдельно проверяет весь согласованный объём: критерий/риск
не потерян, разные группы не предполагают противоречивые роли/состояния/лимиты,
сквозной эффект имеет владельца и наблюдение, дубли не заменяют обязательное
покрытие. Он получает первичные источники и proof, а не только итог автора.
Merge подтверждает структуру, не исполнимость или качество всей модели.
Итоговый plan_ready обязан содержать partition_artifact; submit/review заново
проверяют proof, каталог и связи. Только после итогового принятия создаётся HTML
по TEST_PLAN_HTML.md. Результаты выполнения и публикация в TMS — отдельные этапы.

Проверка разделения без запуска: partition_test_plan.py check --partition <path>.
Код 0 означает успех указанной структурной операции, код 2 — конкретную ошибку;
он не подтверждает живой GIGACODE или выполнение продукта.

Учебный маршрут двух авторов и итогового HTML: `examples/test-plan-partition/build_demo.py`. Отзывы там являются fixture-проверкой, а не оценкой живого GIGACODE.

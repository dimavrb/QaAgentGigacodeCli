# HTML-представление принятого тест-плана

После итогового содержательного принятия plan_ready координатор показывает
самостоятельную HTML-страницу. В ней есть обзор и критерии задачи, область/риски
из Markdown-плана, тест-кейсы, требования, карта покрытия, вопросы/решения и
результат ревью. Поиск находит кейсы по ID, названию или ID требования.
Предусловия и таблица «Шаг — Ожидаемый результат — Тест-дата» раскрываются
у каждого кейса; API/UI/Kafka-данные сохраняются по TEST_CASE_STYLE.md.

## Ссылка от кейса к требованию

Связи берутся из payload.requirement_coverage: requirement_id, source и
scenario_ids. Один кейс может иметь несколько ссылок. requirement_source кейса
остаётся основанием ожиданий, но не заменяет общую карту покрытия.
Новые поля каталога для этой связи не нужны.

Для локального source используй путь к доступному Markdown/текстовому источнику,
относительно artifact_base назначения, и точный якорь, например
`requirements.md#r-1` для заголовка `## R-1`. Поддерживаются обычные ATX-заголовки
и диапазоны строк `#L10-L15`. Без якоря показывается весь указанный источник.
Генератор не угадывает отсутствующий якорь и не создаёт текст требования из кейса.
Для сложного документа/PDF подготовь подтверждённый текстовый снимок нужной
части с исходной ссылкой до ревью; не переноси в него предположения автора.

Файл источника должен входить в inputs автора или его зарегистрированные artifacts
до независимого ревью. Текст локального фрагмента встраивается в раздел
«Требования», и ссылка у кейса ведёт к нему одним кликом. Там есть обратные ссылки
на покрывающие кейсы. Поэтому файл можно открыть или передать без локального сервера.

HTTP(S)-source сохраняется целиком, включая якорь, и открывается из кейса напрямую.
Генератор не читает сеть; содержимое/версия внешнего требования остаются предметом
ревью по первичным источникам. Для неизменяемого офлайн-текста используй локальный
снимок. Доступ к внешней системе определяется правами читателя.

## После ревью

В разделённой задаче по TEST_PLAN_PARTITION.md групповой plan_ready не создаёт
итоговый HTML. Он появляется после проверенного объединения и принятия результата
интеграции; источники и связи берутся из полного каталога/карты. Прямой CLI-экспорт
также отклоняет групповой результат: обход автоматической публикации не разрешает
представлять отдельную группу как финальный план.

`manage_task.py review` автоматически вызывает генератор после сохранения
accepted + review.passed для qa-test-plan-writer/plan_ready. Review-cycle использует
тот же маршрут после прохождения объявленных направлений. Для plan_partial,
coverage_ready и changes_requested итоговая страница не создаётся.
Если у критериев есть required_reviews, все они должны быть приняты, независимы
и относиться к текущим хешам. Содержательное принятие не означает выполнение тестов.

По умолчанию HTML лежит рядом с JSON-результатом: `result.json` → `result.plan.html`.
Для новой раскладки это `.qa-agent/artifacts/<TASK_ID>/planning/<revision>/`.
Он дополняет Markdown-план и JSON-каталог как производное представление; не редактируй
HTML для изменения кейсов и не добавляй его в авторские artifact_hashes задним числом.

В реестре назначения сохраняется presentation: status, path, sha256,
plan_revision, source_hashes и review_request_ids. `manage_task.py show`,
`manage_review_cycle.py show` и `qa_tasks.py get` показывают ссылку/статус.
Read-only discovery показывает записанный снимок, не пересчитывает эти хеши.
При восстановлении сверяй текущие файлы; старый HTML относится к прежней ревизии.

Координатор после принятия читает presentation и открывает ready.path в доступном
браузере/панели, передаёт пользователю ссылку вместе с остальными артефактами.
В bare это действие координатора, дополнительных tools автору/reviewer не требуется.
При needs_attention покажи причину: план принят содержательно, но HTML не готов.
Отсутствующий/изменённый источник требует корректного назначения и ревью новой
ревизии. Не объявляй HTML готовым только по status=accepted плана.

## Повторная сборка и экспорт

```bash
python3 /absolute/package_root/scripts/build_test_plan_html.py \
  --state /absolute/project_root/.qa-agent-state/tasks/QA-123/task.json \
  --request-id QA-123-plan-3
```

Для отдельного экспорта добавь `--output /absolute/path/test-plan.html`.
Без изменения входов повтор безопасен. Другой существующий файл не перезаписывается;
выбери новый путь. Генератор проверяет источники/ревью/каталог и точное покрытие
перед записью, отвергает некорректные ссылки, изменённые хеши, FIFO и симлинки
конечных файлов. HTML/данные экранируются, допустимы только HTTP(S)-ссылки без
credentials. Скрипты, HTTP, Kafka и SQL из кейсов не выполняются.
Код 0 — ready, код 2 — ошибка или needs_attention; acceptance и исходники сохраняются.

Учебный пример: `examples/test-plan-html/build_demo.py`. Он создаёт отдельный
синтетический реестр и использует стандартный маршрут принятия. Это демонстрация
механики, а не живое ревью GIGACODE или выполнение продуктовых кейсов.

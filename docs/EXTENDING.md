# Как добавлять функции в QA-агентную систему

Добавляй правило в то место, где оно будет единым источником истины. Не создавай нового агента для каждой договорённости о формате: роль нужна, когда появляется самостоятельная работа с отдельным результатом и инструментами. Стандарт названий тест-кейсов — пример общего правила, которое применяют несколько существующих ролей.

## Порядок изменений

Для самопроверки изменяй вместе SELF_REVIEW.md, короткие правила всех ролей/координатора, self_review.py/qa_contract.py/validate_qa_result.py, task_exchange.py, runner, examples/task-exchange и тесты. Сохраняй короткие доказуемые выводы, обязательность в новых назначениях и совместимость архивных отчётов; не выдавай проверку формата за независимое ревью.

Для общего реестра и проверяемой передачи изменяй вместе TASK_EXCHANGE.md, task_exchange.py/manage_task.py, правила координатора/команды qa, CONTRACT.md/WORKFLOWS.md, интеграции questionnaire и runner, examples/task-exchange и tests/test_task_exchange.py/test_runner.py. Обязательны атомарность, защита ревизии, единственное резервирование передачи, полный валидатор, отдельное содержательное принятие, контроль неизменности источников и повторяемая доставка событий. Схемы прежних QA-событий не меняются; не обещай пробуждение завершённой сессии без поддержки среды.

Для интерфейса вопросов изменяй вместе QUESTIONS_UI.md, questionnaire.py/questionnaire.html, правило координатора, ссылки в MESSAGES.md/TEST_PLAN.md/CONTRACT.md, examples/questions и tests/test_questionnaire.py. Сохраняй стабильные ID, связь ответа с ревизией и различие answered/deferred; исходные QA-события не меняются. Самостоятельный HTML передаёт общий ответ через копирование или JSON, локальная форма — через файл.

Для Playwright-пула изменяй вместе BROWSER_PROFILES.md/BROWSER_MCP.md, browser_pool.py/manage_browser_pool.py, qa-browser-repro, короткие правила координатора/исполнителей и examples/browser-pool. Один общий runtime-реестр сохраняется вне заменяемого пакета. Проверяй конкурентные процессы и сбои/expiry без ложного free; схема QA-событий остаётся прежней. Реестр кооперативный, физическое закрытие и работу живого MCP оценивай отдельно.

1. **Определи границу функции.** Какие роли создают результат, какие его используют, кто проверяет и что делать при ошибке. Для названий кейсов автор — `qa-test-plan-writer`, потребители — `qa-feature-tester` и `qa-test-automation`, проверка — валидатор и координатор.
2. **Запиши правило один раз.** Создай документ в `docs/` с хорошими и плохими примерами. В файлах ролей оставь короткую ссылку и только действия конкретной роли. Не копируй весь стандарт в промпты всех ролей.
3. **Определи артефакт и контракт.** Укажи стабильные ID, обязательные поля и ссылку на артефакт в `docs/CONTRACT.md`. Сохраняй подробности в артефакте, а не в сообщении между ролями.
4. **Добавь проверку там, где правило проверяемо.** Скрипт в `scripts/` должен возвращать ненулевой код и понятные ошибки. Смысл и соответствие требованиям остаются предметной проверкой; не выдавай проверку формата за проверку качества.
5. **Подключи нужные роли и маршрут.** Координатор передаёт путь к стандарту, автор создаёт артефакт, исполнитель сохраняет ID и названия, ревьюер проверяет связь с требованием. Скрипт в другом репозитории получает краткое правило в назначении или доступный ему файл.
6. **Проверь изменение.** Добавь пример в `examples/`, тесты валидного и ошибочного результата в `tests/`, затем запусти `python3 -m unittest discover -s tests -v`. Оцени на реальных заданиях время, токены и число ошибок до и после изменения.

Для стандарта тест-кейсов источником правила служит `docs/TEST_CASE_STYLE.md`, точкой входа при создании кейсов — `.gigacode/skills/qa-test-cases/SKILL.md`, примерами — файлы, выбираемые по индексам `examples/test-cases/api/INDEX.md` и `examples/test-cases/ui/INDEX.md`, проверкой — `scripts/validate_test_cases.py`. Поле `plan_ready.payload.test_cases_artifact` передаёт каталог координатору. Изменяй эти части вместе, иначе роли и валидатор начнут принимать разные форматы.

Для процесса тест-плана изменяй вместе `docs/TEST_PLAN.md`, контракт событий, инструкции координатора и автора, `scripts/test_plan.py`, CLI-валидатор и примеры `examples/test-plan/`. Не смешивай проектирование, принятие и выполнение сценариев.

Для журнала сбоев изменяй вместе FAILURE_JOURNAL.md, failure_journal.py, manage_failure_journal.py, интеграцию runner и examples/failure-journal. Не добавляй отдельную роль для самой регистрации. Сохраняй различие симптома, причины и доказательства восстановления; новые поля не должны ломать прежние рабочие QA-события.

Для поиска прошлых решений также обновляй координатора, ссылки исполнителей и SELF_REVIEW.md, тесты фильтрации/контекста/неизменности доказательств. В выдаче только последнее подтверждённое восстановление с текущими доказательствами; повторное открытие отменяет использование старого решения. Неизвестные условия не считаются совпавшими, совпадение не разрешает действие. Формат истории JSONL сохраняется.

Для названий автотестов и Allure-шагов изменяй вместе AUTOTEST_NAMING.md, ссылки в AUTOTEST_QUALITY.md/TEST_CASE_STYLE.md, роли автоматизатора и ревьюера, передачу доступных путей в runner и examples/autotest-naming. Правила записаны один раз; структурный валидатор каталога не проверяет Allure или смысл assert.

Для подготовки данных изменяй вместе TEST_DATA_CHECKLIST.md, TEST_DATA.md, выбор разделов в read_test_data_guide.py, ссылки в AUTOTEST_QUALITY.md, роли автора данных/автоматизатора/ревьюера, передачу доступного пути в runner и examples/test-data. Заголовки выбираемых разделов — часть интерфейса селектора: при переименовании обнови карту. Таблица назначения записей расширяет существующий артефакт, не схему QA-событий. Смысл данных и готовность стенда остаются предметной проверкой; сокращение контекста оценивай на заданиях context-eval.

Для проверки подозрения изменяй вместе DEFECT_VERIFICATION.md, INVESTIGATION.md, маршруты координатора/исполнителей, defect_verification.py, включение проверки в investigation_state.py/validate_qa_result.py и examples/investigations/verification. Не создавай новую роль; сохраняй отдельные выводы о нарушении и причине. Валидатор проверяет связи и совместимость заявлений, координатор — содержимое доказательств. Новые подозрения используют verification_required=true; прежние архивные состояния остаются совместимыми.

Для заглушек изменяй вместе STUBS.md, qa-stub-builder, stub_contract.py/validate_stub_assignment.py, события/проверку в qa_contract.py и validate_qa_result.py, маршруты координатора и examples/stubs. Фактические REST/Kafka-схемы и tools обнаруживаются в MCP sbermock; определения учебного примера не являются API сервиса. Сохраняй отдельные состояния планирования, настройки, проверки и очистки, границы симуляции и блокировку всех зависимостей непроверенной заглушки. Артефакты v2 принимаются с независимым назначением координатора; не разрешай доказательству менять своё expected и не переносись через поздние мутации. configure_only не выполняет Kafka-публикации.

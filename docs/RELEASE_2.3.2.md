# QA-пакет 2.3.2 — кейсы, разделение работы и HTML-план

Для большого объёма добавлен [маршрут нескольких авторов](TEST_PLAN_PARTITION.md):
принятая общая карта, группы с отдельными ID/контекстами/файлами и проверяемая
сборка всего покрытия. Привязка plan_partition проверяется при передаче и приёмке;
непринятые группы, дубли, пропуски, изменённые критерии/хеши останавливают сборку.
Финальное содержательное ревью выполняется отдельно. Утилиты не запускают модель.
Обязательные зависимости группы нельзя удалить/подменить в назначении;
поддержан явный выбор принятой исправленной ревизии зависимой группы.

После итогового принятия plan_ready создаётся [HTML-план](TEST_PLAN_HTML.md)
с обзором, кейсами, требованиями, покрытием, вопросами и ревью. Ссылки у кейсов
ведут к встроенным локальным фрагментам требований либо напрямую к внешнему
HTTP(S)-источнику. Есть поиск и обратные ссылки; поддержаны несколько требований
у одного кейса. Обязательное ревью и текущие хеши проверяются до записи.
Статус/путь/хеш представления доступны в реестре, CLI и qa_task_get.
Запрет финального HTML для отдельной группы действует и при прямом CLI-экспорте.

Ручные API-, UI- и Kafka-кейсы используют «Шаг — Ожидаемый результат — Тест-дата».
У каждого действия конкретное наблюдение и нужные для него данные, включая
ожидаемое тело ответа или запись БД. Контракт — [TEST_CASE_STYLE.md](TEST_CASE_STYLE.md).
HTTP-колонка и вложенный шаг формируются из request/response, без второй копии
этих значений в текстовом test_data и без дублей API-разделов после таблицы.

UI-колонка содержит значения полей/фильтров, выбранные ID и ожидаемые строки или
тексты из test_data. Связанные поля можно заполнить одним действием; отправка
формы и наблюдение результата имеют собственные ожидания. Пять
[UI-примеров](../examples/test-cases/ui/INDEX.md) переписаны со стабильными ID,
поиском созданного объекта по фактическому номеру и конкретным составом фильтра.

Kafka-кейсы используют формат «Шаг — Ожидаемый результат — Тест-дата» и
необязательное текстовое поле `test_data`. Данные сообщения, SQL и ожидаемый
payload хранятся рядом с соответствующим действием. Allure сохраняет таблицу
трёх колонок в descriptionHtml и вложенный шаг «Тест-дата:»; нативное поле TestOps
не заявляется. Формат доступен через `test_type: kafka` и
[учебный пример сохранения сообщения в БД](../examples/test-cases/kafka/persistence.json).
Подтверждение публикации брокером отделено от сохранения и сверки payload.

- `request`: method, path, headers, body (none/json/text). Отсутствующее тело
  отличается от JSON null; повреждённый JSON можно описать как точный текст.
- `response`: подтверждённый HTTP-статус, нужные headers и JSON-пример с явным
  scope fragment/exact. Конкретные проверки остаются в expected_result;
  неизвестный HTTP-ответ при таймауте не выдумывается.
- Новые детали проверяются валидатором и сохраняются в Allure descriptionHtml
  в колонке данных соответствующей строки и во вложенном шаге. Данные экранируются, специальные символы отображаются
  однозначно. Названия действий, шаги ожиданий и stable scenario_id сохраняются.
- Шесть API-примеров переписаны по общему формату, включая [кейс отмены чужого заказа](../examples/test-cases/api/cancellation.json).
  Отказ и сохранение состояния остаются одним причинно связанным сценарием.

Это совместимое расширение schema_version: 1: старые шаги без request/response/test_data
продолжают работать. Для новых полей нужен обновлённый генератор вместе с
api_case_details.py. Произвольные метаданные и параметризованные каталоги
по-прежнему не публикуются без поддерживаемого преобразования.

## Проверка

Разделение проверено на непересекающихся ID/путях, точных фрагментах источников,
общих условиях, циклах, изменении критериев/версий/хешей, обязательном ревью,
пропусках/дублях и явном выборе исправленных результатов. Учебный маршрут двух
авторов собрал итоговый HTML после отдельных fixture-отзывов. Небольшие задачи
без привязки сохраняют прежний маршрут; качество живого GIGACODE не измерено.

HTML-план проверен на переходах к локальным и внешним требованиям, связях
многих требований с одним кейсом, обязательном независимом ревью, изменении
источников, безопасном повторе и сохранности данных. Отдельный локальный запуск
JavaScript проверил поиск и раскрытие кейса по обратной ссылке без браузера.
Визуальный просмотр во встроенном браузере недоступен: его политика запрещает
локальный file://. Учебный HTML доступен для просмотра в обычном браузере.

Маршрут примеров и проверки закреплён в [TEST_CASE_REVIEW.md](TEST_CASE_REVIEW.md).
Автор, исполнитель, автоматизатор и профильные reviewer получают стандарт,
индекс и выбранный JSON в замороженном контексте. Сборщик проверяет пример до
запуска, а входные каталоги — напрямую с SHA256 тех же байтов. Review-cycle
сохраняет test_type и выбранные примеры автора. Первичные требования передаются
явно; примеры не устанавливают бизнес-правила. Полномочия reviewer не расширены.

[CONTEXT_ASSEMBLY.md](CONTEXT_ASSEMBLY.md) сверён с текущими сборщиком и worker:
описаны замороженные источники, выбор примеров, полный набор входов reviewer,
контексты групп/интеграции и файлы попытки. Приведены команды просмотра сводки,
правила частичного usage и ограничения измерений. Runtime-телеметрия не вычисляет
качество кейсов и не объединяет независимые execution групп автоматически.

Локально прошли 804 теста полного набора, включая 24 проверки API-деталей,
11 проверок каталога/CLI, 28 проверок Allure-генератора, 23 проверки сборки
контекста, 14 регрессий передачи примеров/валидации, 20 проверок HTML-плана
и 34 проверки разделения/объединения. Проверены полный
текст примера, SHA256, выбор по типу, независимое ревью и диагностика некорректного
JSON без запуска кейсов. Валидатор QA-результата использует тот же строгий
JSON-reader для каталога: дубли ключей, NaN и чрезмерная вложенность отклоняются
с контролируемой диагностикой. Шесть учебных API-кейсов,
пять UI-кейсов и один Kafka-кейс собраны в таблицы; данные восстановлены из
HTML и вложенных шагов без потерь. У UI-шагов без данных колонка показывает `—`,
пустой вложенный шаг не создаётся. Skill прошёл quick_validate.

Проверки покрывают API-детали, каталог/CLI и Allure-генератор, включая сохранность
трёх колонок и тестовых данных API/UI/Kafka, HTML-экранирование, ошибки данных и
стабильность ID при изменении payload. Учебные API-, UI- и Kafka-кейсы собираются
в Allure без исполнения продукта. Предыдущая независимая проверка API-инструкций
с Codex на синтетической задаче сохранила один кейс отказа/состояния и не добавила
неподтверждённые HTTP-коды или headers; это не замер качества живого GIGACODE.

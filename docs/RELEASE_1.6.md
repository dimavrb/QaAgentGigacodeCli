# Обновлённая поставка QA-агента 1.6

Дата: 2026-10-07. Файлы: `qa-agent-1.6.zip`, `qa-agent-1.6.zip.sha256`. Состав, размеры и хеши файлов — в `qa-agent/PACKAGE_MANIFEST.json` внутри ZIP. Специализированных ролей — 10; новых ролей в этой версии нет.

## Проверка подозрения на дефект — 2026-10-07

- Координатор сам передаёт подозрение существующему qa-defect-investigator, не ожидая отдельной просьбы о ретесте. Ручной тестировщик и автоматизатор сохраняют первичный факт; независимые сценарии продолжаются.
- DEFECT_VERIFICATION.md: бизнес-правило → первичное наблюдение → относящийся код приложения и его применимость к сборке → только недостающий факт → независимое принятие. Причина оценивается отдельно от нарушения.
- verification.json регистрируется с SHA-256, связан с попытками и записанным ревью. Для новых подозрений verification_required=true; результат с verification_artifact проверяется только с --investigation-state.
- Валидатор проверяет совместимость заявлений и ссылки: исходники не заменяют runtime-доказательство, для confirmed причины приложения нужны traced и matched. Истинность материалов и выполнение механизма проверяет координатор. Недоступный код не блокирует подтверждение доказанного нарушения.
- Добавлены синтетический пример verification/ и 12 тестов границ нового протокола. Подробный стандарт загружается только для расследования, не в постоянный контекст всех ролей.

Предыдущая обновлённая сборка с SHA-256 d3223182967fdb4a11c70b31b079f573b07b50c8f599551388af3a9939903131 сохранена с инструкциями и протоколом в dist/backups/1.6-d3223182967f у сборщика. Для отката установленного агента нужна также резервная копия его локальных адаптаций.

## Что добавлено к первой сборке 1.6

- TEST_DATA.md: назначение каждой записи, минимальный набор с контрпримерами, повторяемый рецепт, проверка готовности, изоляция попыток и очистка частичного сбоя. Подключены автор данных, автоматизатор и независимый ревьюер.
- TEST_DATA_CHECKLIST.md и read_test_data_guide.py: обязательное ядро и начальные разделы по роли. Дополнительные разделы читаются по риску через --only-sections, без повтора ядра; полный справочник и примеры не загружаются без потребности.
- Runner передаёт ядро автоматически. test_data_context_characters/sections измеряют только исходный текст правил данных; поздние чтения, токены и контекст приложения сюда не входят.
- Учебный рецепт проверяет изоляцию, повтор, частичную очистку и ложный успех на пустой или неверно отфильтрованной выдаче. Для оценки ответов модели подготовлены три задания A/B и 12 критериев.

VERSION остаётся 1.6. Первая сборка с SHA-256 cfeb9f786a1eb7c245cecb656dda13c99d6a69da7d0af843ed95d4d4f72bd831 сохранена в dist/backups/1.6-cfeb9f786a1e у сборщика. Новую сборку определяйте по отдельному checksum рядом с ZIP; совпадение VERSION не означает совпадения поставки.

## Изменения первой сборки относительно 1.5

- Локальный журнал сбоев: симптом, влияние, гипотеза или подтверждённая причина, доказательства и восстановление. Уточнения одного инцидента не увеличивают число сбоев. История и текущая доступность доказательств проверяются отдельно; синтетические и рабочие записи разделяются.
- Runner регистрирует технические ошибки, timeout, невалидный ответ и blocked. Причину не угадывает; ошибка записи журнала сохраняет первоначальный результат и отражается в метриках. Другие маршруты регистрирует координатор.
- `AUTOTEST_NAMING.md` закрепляет названия тестов и Allure-шагов: условие и ожидаемый результат, реальные assert внутри проверочных шагов, различимость вариантов и связь с scenario_id. Автоматизатор проверяет свежие результаты, независимый ревьюер сопоставляет названия с источником и кодом; недоступное отображение остаётся ограничением.
- Внешний runner передаёт доступные абсолютные пути к стандартам качества, именования и тест-кейсов. Есть учебные примеры журнала и названий.

Отчётность по бизнес-кейсам, функционалу и тогглам версии 1.5 сохраняется.

## Установка и совместимость

Краткая инструкция — `UPGRADE_1.6.md`, полная — `UPDATE.md`, первая установка в приложение — `IMPORT_INTO_APP.md`, отдельная установка — `SETUP_AND_UPDATE.md`. Рядом с архивом поставляются копии `UPGRADE_1.6.md`, `UPDATE_1.6.md`, `INSTALL_1.6.md`, `SETUP_AND_UPDATE_1.6.md`, `RELEASE_1.6.md` и внешний протокол проверки `VALIDATION_1.6.json`.

Прежние QA-события, каталог `schema_version: 1`, отчётность 1.5 и архивные состояния расследований совместимы. Новые подозрения требуют verification_required=true и verification_artifact; при продолжении старого подозрения включайте флаг с новым назначением и сбрасывайте прежнее ревью. Журнал — отдельный JSONL-артефакт, его нельзя подменять QA-результатом. При обновлении сохраняются история, доказательства, `.qa-agent-state/`, локальные MCP/tools, контекст приложения и сокращённый QWEN.md. Массовое переименование тестов не требуется.

Python-скрипты используют стандартную библиотеку; Python 3.10+. Журнал и runner используют POSIX-блокировки: macOS/Linux или WSL, нативный Windows не проверен. Playwright MCP остаётся `0.0.83`. Рабочие журналы, артефакты, `.git`, `.idea`, dist и кеши Python не входят в архив; учебные примеры входят. Предыдущие архивы сохраняются.

## Проверки поставки

Из корня исходников и из распакованной копии:

```bash
python3 -m unittest discover -s tests
python3 scripts/validate_test_cases.py --input examples/test-cases.json
```

Ожидается 151 локальный тест. Они проверяют скрипты, контракты, передачу стандартов, протокол проверки подозрения и защиту файлов от перезаписи; не подтверждают ответы живой модели или отображение Allure в приложении.

Проверьте новый пример отдельно (учебные материалы, без приложения):

```bash
python3 scripts/validate_qa_result.py \
  --input examples/investigations/verification/result.json \
  --task-id QA-FIXTURE --request-id QA-FIXTURE-1 \
  --agent qa-defect-investigator \
  --investigation-state examples/investigations/verification/state.json
```

Ожидается код 0. Без --investigation-state тот же результат должен отклоняться с кодом 2. Изменение verification.json без нового SHA/ревью тоже отклоняется. Эти ограничения включены в тесты; живую маршрутизацию и качество расследования проверьте отдельно на разрешённом случае после новой Qwen-сессии, без запуска продукта ради установки.

Дополнительно проверьте учебный рецепт и выбор разделов (без приложения):

```bash
python3 -m unittest discover -s examples/test-data -v
python3 scripts/read_test_data_guide.py --role qa-test-data-builder
python3 scripts/read_test_data_guide.py --role qa-test-automation
python3 scripts/read_test_data_guide.py --role qa-autotest-reviewer
python3 scripts/read_test_data_guide.py --role qa-test-automation --only-sections --section cleanup
```

Ожидается один успешный учебный тест; каждый начальный вывод содержит чек-лист и только разделы своей роли, последний вывод — только cleanup без повтора ядра. Сравнение живой модели A/B по context-eval — отдельная проверка, в сборке не выполнялось.

Учебный журнал создавайте отдельно от рабочего:

```bash
QA_RELEASE_CHECK_DIR=$(mktemp -d)
python3 scripts/manage_failure_journal.py record --journal "$QA_RELEASE_CHECK_DIR/failures.jsonl" --entry examples/failure-journal/01-open.json
python3 scripts/manage_failure_journal.py record --journal "$QA_RELEASE_CHECK_DIR/failures.jsonl" --entry examples/failure-journal/02-recovered.json
python3 scripts/manage_failure_journal.py record --journal "$QA_RELEASE_CHECK_DIR/failures.jsonl" --entry examples/failure-journal/03-hypothesis.json
python3 scripts/manage_failure_journal.py check --journal "$QA_RELEASE_CHECK_DIR/failures.jsonl"
python3 scripts/manage_failure_journal.py summarize --journal "$QA_RELEASE_CHECK_DIR/failures.jsonl" --scope-kind synthetic --output-dir "$QA_RELEASE_CHECK_DIR/summary"
python3 scripts/build_test_report.py --scope examples/test-reporting/scope.json --runs examples/test-reporting/detailed-runs.json --revision install-check-1.6 --output-dir "$QA_RELEASE_CHECK_DIR/report"
python3 scripts/build_test_report.py --check "$QA_RELEASE_CHECK_DIR/report"
```

Ожидается 3 события / 2 инцидента: один восстановлен, один открыт. Рабочая сводка этого синтетического журнала пуста. В учебном отчёте выполнена 1 из 3 проверок; OFF не проверен, отмена заблокирована. Эти команды не выполняют действия в продукте.

Протокол конкретного ZIP отдельно фиксирует тесты исходников/распакованного пакета, проверки прежних валидаторов, базового/подробного отчётов, журнала, манифеста и checksum. Живой Qwen, браузер, CI приложения и реальное отображение Allure в рамках сборки не проверяются; экономия токенов неизвестна.

Регистрация инцидентов не даёт частоту ошибок без числа всех запусков. Хеши журнала проверяют связность сохранённой истории и доказательства, но не удостоверяют автора и не доказывают истинность причины.

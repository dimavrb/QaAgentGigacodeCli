# Выполнение без повторов одного блокера

Применяй при выполнении согласованных сценариев и продолжении частичной проверки. Это не разрешение выполнять продуктовые действия при задании только на тест-план. Матрица обязательна и при полной блокировке `qa-feature-tester`; миграция прежних отчётов описана в `docs/UPDATE.md`.

Для долговечных процессов и продолжения заранее заданного плана в текущих исходниках доступен [MANAGED_EXECUTION.md](MANAGED_EXECUTION.md). Эти механизмы контролируют запуск, отмену и повтор; применимость продуктовых результатов по правилам ниже по-прежнему оценивает координатор.

## Общее условие вместо повторных попыток

Перед запуском сгруппируй сценарии по обязательным условиям: доступ, сервис, роль, набор данных. Используй каталог и актуальные сведения стенда. Не создавай отдельное назначение ради этой группировки.

Если обязательное условие недоступно и это подтверждено проверкой, сохрани один блокер: ID, недостающее условие, затронутые сценарии, окружение/сборка, доказательство, нужное изменение. Причину сбоя не придумывай. Привяжи каждый зависимый сценарий к нему; не повторяй одинаковый заведомо невыполнимый шаг для каждого кейса.

Остальные сценарии продолжай только после проверки их собственных условий. Общий симптом не доказывает общую зависимость: недоступность оплаты сама по себе не блокирует фильтр заказов. Продуктовое расхождение в одном кейсе также не отменяет все последующие проверки. Останавливай только действия, чьи обязательные условия нарушены, либо продолжение которых исказит результаты.

В отчёте сохраняй каждый назначенный ID. Используй `blocked`, когда подтверждено отсутствие его обязательного условия, и `not_run`, когда проверку не начинали по другой причине, например из-за ограничения времени. В `actual_result` укажи причину и ID общего блокера. Для неисполненных действий не выдумывай шаги или доказательства выполнения. Доказательство проверки общего условия сохраняй отдельно; ссылка на него не означает, что продуктовый сценарий выполнен. Все `blocked` и `not_run` входят в `uncovered_scenarios`.

Пользователю сообщи блокер один раз с затронутыми ID и нужным действием. Подробная матрица результатов остаётся в артефакте. `feature_test_complete` означает отчёт о назначенном наборе, а не успешное прохождение всей фичи. Для смешанного набора (выполненные, заблокированные или не запущенные сценарии) возвращай `feature_test_complete` с полной матрицей. Возвращай `blocked` только если подтверждённые блокеры препятствуют выполнению всех назначенных сценариев; его `payload` также содержит `scenario_results`, `uncovered_scenarios`, `defects`, каждый назначенный ID имеет статус `blocked`. Ограничение времени само по себе не означает блокировку: используй `not_run` в `feature_test_complete`.

## Возобновление

Нехватка Playwright-профилей — общий ресурсный блокер по BROWSER_PROFILES.md. Пул один для всех обращающихся к этим ресурсам: активные владельцы продолжают, новые UI-наборы ожидают сигнала освобождения, независимый анализ продолжается. Карантин восстанавливается отдельно, не через ретест всех сценариев. Владелец закрывает контекст после доказательств до ожидания/отчёта, включая failed/blocked/ошибку; продуктовый passed не означает выполненную очистку.

Для итоговой отчётности фиксируй фактический контекст и значимые тогглы в момент исполнения по `docs/TEST_REPORTING.md`, отдельно от старой матрицы результатов. Координатор связывает их в runs.json с исходным назначением, временем и результатом. Сохраняй отдельные файлы каждого прогона; разные конфигурации и неизвестные условия не объединяются в одно подтверждённое покрытие.

Сохрани рядом с отчётом краткую запись: исходное назначение, текущие результаты, блокеры и связи с ID, версии требований и каталога, окружение/сборку и существенные свойства данных. Секреты не записывай. Перед продолжением прочитай запись и проверь текущие условия; не опирайся только на историю диалога.

1. Повторно проверь общее условие после сигнала о восстановлении, изменения условий либо согласованной попытки восстановления. Без нового основания не запускай все зависимые кейсы снова и не опрашивай стенд бесконечно. Неоднозначный результат внешнего действия сначала проверь по фактическому состоянию.
2. Сопоставь требования, каталог, окружение/сборку, роли и данные. При неизменных условиях назначай только заблокированные/неисполненные ID; ранее выполненные результаты сохраняй со ссылкой на их исходный отчёт. Пользователь может отдельно запросить повтор выполненных проверок.
3. При изменениях определи зависимые результаты и перепроверь их. Если область влияния неизвестна, расширь повторную проверку; не считай прежний успех доказательством на новой сборке. Устаревшие результаты сохраняй как историю с исходными условиями.
4. Передай новое назначение с новым `request_id`, выбранными ID, изменением условий и ссылками. Результат этого назначения содержит ровно назначенные ID; координатор обновляет общую матрицу по исходному набору. Не включай прежние `passed` в новый отчёт как будто они выполнены повторно.

Для каждого назначения запускай `validate_qa_result.py` с его ID сценариев. Итоговая матрица должна явно показывать, откуда взят каждый результат и применим ли он к текущим условиям; пропуски остаются видны.

## Учебный пример

TC-PAY-1 и TC-PAY-2 требуют одного платёжного сервиса. TC-FILTER использует только сервис заказов. Проверка доступности платежей подтвердила отсутствие подключения: B-1 блокирует TC-PAY-1 и TC-PAY-2. Исполнитель сохраняет одно доказательство B-1, не делает две одинаковые попытки оплаты и отдельно выполняет TC-FILTER при готовых условиях.

После восстановления платежей при той же сборке, требованиях и данных новое назначение содержит только TC-PAY-1 и TC-PAY-2. Результат TC-FILTER остаётся в прежнем отчёте. Если одновременно обновилась сборка и её влияние неизвестно, прежний TC-FILTER требует перепроверки; восстановления одного сервиса недостаточно для принятия старого результата на новой сборке.

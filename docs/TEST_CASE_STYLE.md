# Стандарт тест-кейсов и шагов

Новые общие каталоги хранятся в `test-cases/<feature>/*.json` по
[TASK_STORAGE.md](TASK_STORAGE.md); существующее расположение приложения
сохраняет приоритет. ID связывают кейс с планом, прогоном и расследованием;
результаты запусков и персональная конфигурация в каталог не включаются.

Этот стандарт применяй при создании или существенном изменении ручных тест-кейсов. Он хранится отдельно от ролей, чтобы одно правило использовали автор плана, тестировщик, автоматизатор и ревьюер. Не переименовывай существующие кейсы только ради этого документа. Если команда решит перейти на другой стандарт, одновременно обнови этот документ, пример и валидатор.

Для человекочитаемых названий исполняемых автотестов и Allure-шагов дополнительно применяй `AUTOTEST_NAMING.md`. Он разрешает отдельный проверочный шаг с реальным assert; структура и правила ручного каталога ниже сохраняются.

## Название кейса

Формат: **`<объект> — <условие или действие> — <ожидаемый результат>`**. Используй длинное тире с пробелами (` — `). Название отвечает на вопросы: что проверяем, при каком условии, что должно получиться. Идентификатор храни отдельно в `scenario_id`; не добавляй в название «Тест», «Проверка» или номер кейса.

Пример: `Список заказов — выбран статус «Оплачен» — показаны только оплаченные заказы`.

Негативный и граничный характер сценария показывай содержанием, а не словом «негативный» в начале: `Форма входа — введён неверный пароль — доступ отклонён`.

## Название шага

Имя шага — **одно конкретное действие с объектом**, с глагола в неопределённой форме: `Открыть список заказов`, `Выбрать статус «Оплачен»`, `Нажать «Применить»`. Не смешивай действие и ожидаемый результат в имени. Пиши ожидаемый результат отдельно: `В таблице остались только оплаченные заказы`. Избегай названий `Проверить, что всё работает`, `Шаг 1`, `Выполнить тест`.

Один шаг может иметь несколько наблюдаемых эффектов, но для разных пользовательских действий создай разные шаги. Если нужны конкретные данные, укажи их в названии или предусловиях, а не оставляй «ввести значение» без значения.

## Исполнимость инструкции

Пиши для тестировщика, который не участвовал в обсуждении задачи. Укажи исходную
роль/состояние и конкретные данные либо воспроизводимый способ их получить и
выбрать. «Есть подходящий заказ» и «подготовить ошибку» недостаточны без признаков
заказа или ссылки на доступную инструкцию. Ссылку на общий setup можно вынести
в предусловия; она должна быть доступна исполнителю из кейса, без поиска в чате.
Секреты не включай. Не выдумывай учётную запись, fixture, API или SQL ради полноты.

Шаг содержит объект действия и существенные параметры: поле и значение для UI,
метод/путь и нужные заголовки/body для API. Достаточно уровня детализации проекта:
не расписывай очевидную навигацию до каждого клика, если исполнитель однозначно
найдёт объект. Существенные особенности пути или состояния опиши явно.

Ожидание задаёт где и какой результат наблюдать, чтобы отличить правильное поведение
от предполагаемой ошибки. «Всё работает», «данные корректны» и «получена ошибка»
этого не определяют. Число строк или HTTP 200 не доказывают правильный состав
результата; видимое сообщение не доказывает внутреннее изменение состояния.
Точный текст, код, значение или допуск используй, когда он подтверждён источником.
Если правило не требует точной формулировки, проверяй подтверждённый смысл/эффект,
не придумывай дословное сообщение. У существенного неизвестного — вопрос planning.

Для синтетического требования «нулевое количество не сохраняется; поле показывает
ошибку диапазона» вместо «ввести неверное значение → ошибка» опиши ввод `0` в
поле «Количество», действие сохранения и наблюдение ошибки диапазона у этого поля.
Проверку отсутствия записи добавляй с подтверждённым способом её наблюдения.
В реальном приложении сперва подтверди, что выбранный канал позволяет такой ввод.

Отделяй подготовку от цели проверки: открытие страницы обычно подготавливает
действие; самостоятельный кейс нужен при отдельном критерии/риске открытия.
Связанные наблюдения оставляй при соответствующем действии, а независимые условия
не склеивай в один длинный сценарий. Проверь кейс «новыми глазами» и мысленным
контрпримером по qa-check-quality; это ревью проектирования, а не выполненный тест.

## Структурированный артефакт

Сохраняй кейсы в UTF-8 JSON с `schema_version: 1` и массивом `test_cases`. У каждого кейса обязательны `scenario_id`, `title`, `requirement_source`, `preconditions` (массив строк) и `steps` (непустой массив). У каждого шага обязательны `name` и `expected_result`. ID стабилен при редактуре названия и шагов; новый ID нужен для другого проверяемого поведения.

Примеры выбирай по `test_type` из назначения: для API используй `examples/test-cases/api/INDEX.md`, для UI — `examples/test-cases/ui/INDEX.md`. Прочитай только нужный индекс и подходящий JSON-пример. Учебные данные и контракты примеров не являются требованиями приложения. `test_type` — параметр назначения; он не меняет обязательную структуру JSON-каталога. Старый `examples/test-cases.json` сохранён для совместимости, его не нужно дополнительно читать при выборе нового примера. Проверь артефакт перед передачей координатору:

```bash
python3 scripts/validate_test_cases.py --input /absolute/path/to/test-cases.json
```

Валидатор проверяет структуру, уникальность ID и названий, три части заголовка и несколько явно неудачных формулировок. Он не доказывает соответствие требованиям или качество ожидаемого результата; эти вопросы остаются за автором и ревьюером.

## Польза сценария и дубли

До детализации используй [TEST_CASE_SELECTION.md](TEST_CASE_SELECTION.md) и правила выбора из `docs/TEST_PLAN.md`: у сценария должны быть критерий или риск, возможная обнаруживаемая ошибка и обоснованное отличие от других проверок. Проверяй эквивалентность условий и поведения, а не только названий. Объединение не должно терять обязательное покрытие; различия прав, границ, состояний и уровней UI/API могут требовать отдельных кейсов. Сохраняй обоснования в плане, не добавляй обязательные поля в JSON-каталог.

Если выбран модельный или комбинаторный подход, свяжи сценарии с правилами и строками комбинаций по `docs/TEST_DESIGN.md`. Подробные ожидания остаются в каталоге; у неизвестного правила готовый кейс не создаётся.

## Связь с тест-планом

JSON-каталог — единственное место с предусловиями, шагами и ожидаемыми результатами кейсов. В Markdown-плане оставляй стратегию проверки и компактную таблицу покрытия: источник критерия или риска, ID связанных кейсов, приоритет, способ проверки и нужное доказательство. Например:

| Критерий или риск | Кейсы | Приоритет | Проверка и доказательство |
| --- | --- | --- | --- |
| Критерий фильтрации заказов | `TC-001` | Высокий | Ручная проверка; скриншот списка после фильтрации |

Для непокрытого критерия укажи причину и открытый вопрос вместо ID. Проверь, что каждый ID готового покрытия есть в каталоге. В ранней карте `coverage_ready` допустимы ещё не детализированные ID; вопросы и готовность частей веди по `docs/TEST_PLAN.md`. В `plan_partial` не включай кейсы, заблокированные по planning, в каталог; известный способ с недоступными ресурсами относится к execution и не запрещает проектирование. Не копируй в план названия, предусловия, шаги и ожидаемые результаты из JSON; при передаче координатору укажи пути к обоим артефактам.

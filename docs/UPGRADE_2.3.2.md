# Обновление до 2.3.2

1. Завершите активные QA-сессии и обновите весь пакет штатным способом по
   [EXTENSIONS.md](EXTENSIONS.md). Проверьте VERSION и gigacode-extension.json:
   2.3.2. Локальную тестовую поставку можно установить из проверенного ZIP,
   распаковав его и передав менеджеру путь к папке с манифестом.
2. Откройте новую сессию, проверьте qa_package_info, повторите `/qa:init` и
   `/qa:doctor`. Контекст и старые каталоги не переписываются. При существенной
   редактуре API-кейса используйте формат «Шаг — Ожидаемый результат — Тест-дата»:
   HTTP-данные request/response автоматически составляют колонку таблицы.
   Текстовый test_data нужен только для дополнительных данных по TEST_CASE_STYLE.md.
   Для Kafka выберите test_type=kafka и формат «Шаг — Ожидаемый результат —
   Тест-дата», с необязательным текстовым test_data. Старые кейсы не переписывайте
   только ради оформления.
   Для UI выберите test_type=ui и тот же формат: значения полей/фильтров,
   выбранные ID и ожидаемые строки/тексты хранятся в test_data. Связанные поля
   можно заполнить одним логическим действием, сохраняя наблюдения по правилам UI.
3. В Jenkins/продуктовом репозитории обновите используемую копию scripts целиком,
   включая api_case_details.py, validate_test_cases.py и build_manual_allure.py.
   Старый генератор новые поля отвергнет; удалять их ради успешной публикации нельзя.
4. Передайте агенту контракт метода/пути, обязательных headers, тела и ответа;
   неизвестное обозначьте вопросом. Реальные секреты в каталог не добавляйте.
   Динамические ID и тестовые токены остаются обозначениями с инструкцией
   получения/подстановки в предусловиях, генератор их не разрешает.
   Для Kafka передайте реальные cluster/topic, сериализацию, key/headers/body,
   правило обработки, разрешённое наблюдение (выход/БД) и подтверждённый лимит
   ожидания. Таблица БД и SQL учебного примера не являются схемой вашего продукта.
   Для UI передайте реальные формы/маршруты, роли, допустимые данные, способ
   подготовки выбранных объектов и наблюдаемые результаты. Учебные кнопки,
   тексты ошибок и удаление из примеров не являются возможностями вашего UI.
5. Проверьте каталог и локальный Allure JSON. В назначенном пилотном проекте TMS
   отдельно проверьте таблицу API, номера шагов, JSON запроса/ответа, fragment/exact
   и вложенный шаг «Тест-дата:». Убедитесь, что правка request/response отображается
   сразу и не осталась старая текстовая копия.
   Для Kafka проверьте три колонки таблицы и вложенный шаг «Тест-дата:»;
   убедитесь, что тело входа, SQL и ожидаемый payload сохранились полностью.
   Для UI проверьте данные ввода, ожидаемые строки/тексты, динамические ID
   и `—` у шагов без данных; пустой вложенный шаг не должен появляться.
   Подготовка файлов не разрешает публикацию или выполнение продукта.

Создавайте новые managed-планы для изменённой ревизии инструкций; не обновляйте
старые хеши. Задавайте assignment.test_type и выбранный JSON-пример через
instruction_paths по [TEST_CASE_REVIEW.md](TEST_CASE_REVIEW.md); для прямого
reviewer каталога используйте scope=test_cases. Передавайте каталог и первичные
источники через inputs. Сверяйте catalog_validations с текущим хешем каталога:
успешная структурная проверка не означает содержательное принятие.

Сверьте явный контекст новой попытки по instructions.json, system.md и prompt.json,
а метрики — через manage_execution.py show или manage_review_cycle.py show.
Проверяйте complete_context/complete_usage перед сравнением итоговых сумм:
known_* показывает только доступные измерения. Границы контекстов групп и
интеграции, диагностика бюджета и точные поля описаны в
[CONTEXT_ASSEMBLY.md](CONTEXT_ASSEMBLY.md).

Старые кейсы без новых блоков, события и ID сохраняются.

Для HTML-плана после финального ревью передайте точные source в карте покрытия:
локальные Markdown/текстовые файлы с якорями включите в inputs/artifacts до ревью,
внешние документы укажите прямой HTTP(S)-ссылкой. Принятие нового plan_ready
соберёт result.plan.html автоматически. Уже принятый неизменённый план можно
обработать build_test_plan_html.py по TEST_PLAN_HTML.md; исторические хеши
не пересчитывайте. Ошибка представления показывается отдельно как needs_attention.
Защита обновления из 2.3.0 остаётся прежней; автообновление опубликованной версии
требует успешного CI точного commit.

Для нескольких авторов используйте TEST_PLAN_PARTITION.md и новые снимки
partition_test_plan.py build/check/merge. Сохранённые одиночные назначения
работают без новой привязки. При изменении источников/критериев/области готовьте
новую базу и директорию; старые хеши и принятые каталоги не переписывайте.
Сохраняйте обязательные depends_on из снимка при подготовке назначений групп;
для исправленного источника указывайте его принятый request ID с .revision-N.

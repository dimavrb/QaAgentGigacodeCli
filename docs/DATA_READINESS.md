# Проверенная готовность тестовых данных

Новые назначения qa-test-data-builder получают `data_checks_required: true`.
Координатор до подготовки фиксирует `assignment.data_assignment`: абсолютный
путь к независимому JSON со свойствами, связями, видимостью и допустимым сроком
использования. Файл и первичный источник автоматически входят в замороженные
inputs. Отключить проверку флагом исполнителя нельзя. Без назначения допустим
только `blocked` с запросом недостающих условий.

## Назначение координатора

JSON содержит schema_version=1, task_id, environment_id, product_version,
created_at и expires_at (ISO 8601 с зоной), непустой scenario_ids и
requirements_source: `{ "path": "requirements.txt", "sha256": "…" }`.
Путь источника разрешается относительно этого JSON; это локальный UTF-8 текст
с действующими правилами проекта. Срок устанавливает координатор с учётом
изменчивости данных и времени зависимого запуска, а не исполнитель задним числом.

Непустой requirements содержит для каждого обязательного условия:

- requirement_id — уникальный ID;
- kind — property, relation или visibility;
- quote — точную цитату из источника;
- expected_result — конкретный проверяемый результат;
- scenario_ids — затронутые сценарии. Отсутствие поля означает общий предусловный
  пункт для всех сценариев назначения. Пустой список недопустим.

Все назначенные сценарии должны иметь условия. Содержательно проверь полноту:
код проверяет объявленный список и ссылки, но не извлекает все бизнес-инварианты
из свободного текста. Включай обязательные свойства каждой записи, связи,
доступность для нужной роли/организации, изоляцию и важные ограничения профиля.
Неизвестное ожидание уточняется через QUESTIONS_UI.md, а не выдумывается.

## Отчёт и доказательства

Сохрани обязательные environment_id, data_ids или recipe, cleanup, scenario_ids.
Добавь product_version, data_assignment_sha256 и data_state:
`available`, `cleaned` или `unknown`. Непустые data_ids — уникальные строковые ID;
рецепт воспроизводит подготовку, но сам по себе не подтверждает её выполнение.

В новом протоколе verified_properties — объекты для **каждого** requirement_id
ровно один раз, включая невыполненные условия:

```json
{
  "requirement_id": "D-OWNER",
  "status": "passed",
  "actual_result": "Заказы O-1 и O-2 принадлежат тестовому владельцу U-1",
  "observed_at": "2026-10-15T12:00:00+03:00",
  "evidence": ["observations/order-owners.json"]
}
```

Статусы: passed, failed, blocked, not_run. Для всех нужны actual_result и массив
локальных evidence; для passed/failed — непустые файлы и время между created_at
и текущим моментом, внутри заданного окна. Доказательство содержит наблюдаемые
значения, контекст окружения и способ проверки. Снимок назначения, исходный текст
требования и сам отчёт не являются наблюдением свойств. Относительные evidence
разрешаются по artifact_base назначения, в standalone CLI — по каталогу отчёта
либо --data-evidence-base. Вложенные файлы автоматически получают хеши реестра.
Координатор проверяет содержание и соответствие наблюдаемого набора data_ids/recipe;
наличие JSON и локального файла не доказывает достоверность внешней системы.

`data_ready` допускается только при passed всех условий, data_state=available
и неистёкшем окне. `data_partial` возвращает ровно вычисленное подмножество
scenario_ids, чьи условия все passed, и остальные blocked_scenarios. Общий
непроверенный пункт блокирует все связанные сценарии. Если готовых сценариев
нет, используй blocked. Очищенный набор и неизвестное состояние не готовы.

cleanup остаётся строкой: назови созданные ресурсы/владельца, порядок удаления,
зависимые проверки, срок жизни и способ повторной подготовки. Регистрируй свои
ID сразу, при частичном сбое очищай только свои ресурсы; ошибку очистки сохраняй
отдельно. При принятом ready/partial удерживай данные до завершения зависимых
проверок; очистка после завершённого локального теста не оставляет готовый набор
для другого исполнителя. Код пакета не создаёт и не удаляет данные приложения.

## Переход к исполнению и совместимость

Принятие координатором обязательно. На ready-переходе реестр повторно проверяет
назначение, доказательства и срок, при partial — сценарии потребителя. Истёкшее
окно требует нового request_id с актуальными источниками и наблюдениями, а не
изменения принятого отчёта или продления старого expires_at.

Сохранённые старые отчёты и хеши не мигрируются. Обычный CLI без нового scope
сохраняет структурный аудит исторического формата, но новый ready-переход
по такому источнику запрещён; dependency_modes=context доступен для диагностики.
Истёкший новый отчёт также можно передать как context или проверить CLI с
--data-context-only; это не даёт готовности и не разрешает запуск.

```bash
python3 scripts/validate_qa_result.py --input /absolute/result.json \
  --task-id QA-DATA-DEMO --request-id data-1 --agent qa-test-data-builder \
  --data-assignment /absolute/data-assignment.json --require-data-checks \
  --scenario-id TC-1 --scenario-id TC-2
```

Свежий исполняемый пример — [data-readiness](../examples/data-readiness/README.md).
Его локальный файл и проверки — синтетика, не качество живой модели и не готовность
данных приложения. Общий предметный минимум — TEST_DATA_CHECKLIST.md; рецепт,
изоляция и очистка читаются выборочно через read_test_data_guide.py.

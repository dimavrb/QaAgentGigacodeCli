# Политика инструментов и журнал действий

`mcp_action_gateway.py` — единственная разрешённая MCP-точка управляемого GIGACODE-запуска. Политика фиксируется в плане шага и проверяется шлюзом перед вызовом. Модель не получает файл политики на запись и не выбирает иной backend. Пример структуры — [gateway-policy.json](../examples/execution/gateway-policy.json); это шаблон, его имя команды и схемы заменяются по фактическому серверу.

## Политика

`server_command` — явный массив argv существующего доверенного stdio MCP-сервера. `tools` содержит только разрешённые имена; у каждого `effect: read|write`, непустые `constraints` по JSON pointer и явный список верхних `allowed_arguments`. Ограничения сравниваются как JSON с учётом типов до передачи. Если требуемое поле ресурса отсутствует, вызов запрещён. Сложные вложенные поля также нужно ограничить под конкретную схему: разрешение корневого body разрешает его содержимое, кроме отдельно проверенных constraints.

У записи можно указать `idempotency_argument`: шлюз сам вставляет стабильный ID действия; модель не может назначить этот параметр. Один action_id соответствует task, step, имени инструмента и точным аргументам. Изменённые аргументы означают другое действие; семантические дубликаты должен исключать координатор. По умолчанию разрешено одно уникальное write-действие и не более двух подтверждённо допустимых попыток одного действия. `max_write_actions` и `max_action_attempts` задают общие пределы; `call_timeout_seconds` ограничивает ожидание ответа.

Шлюз скрывает остальные инструменты и параметр idempotency из tools/list. Он предоставляет два служебных инструмента: `qa_action_status` и `qa_reconcile_action`. Ресурсы, prompts, sampling/elicitation и другие RPC не проксируются; серверные запросы отклоняются. Пагинация ограничена. Поддерживается stdio JSON-RPC с JSON по одной строке, как в [MCP transport specification](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports). HTTP/SSE MCP в этом адаптере пока не поддерживаются.

## Неопределённый исход и readback

До внешней записи атомарно сохраняется `started`. Успешный ответ инструмента фиксируется как `verified`; для критичных операций фактическое бизнес-состояние дополнительно проверяется разрешённым чтением. Ошибка, timeout, разрыв соединения или авария между записью и фиксацией сохраняют `unknown`/`started`. Эти состояния блокируют **любую новую запись** шага, включая вызов с другим названием объекта. Сам по себе timeout не доказывает, что операция не выполнена.

`readback` задаёт разрешённый read-инструмент и аргументы, связанные с исходной записью: `literal`, `argument` (JSON pointer исходного аргумента), `action_key`. Его `presence_pointer` должен возвращать boolean. `true` подтверждает существующий объект и позволяет переиспользовать результат. `false` допускает повтор только при заранее заданном `authoritative_absence: true`. При eventual consistency, неполном поиске или неизвестной полноте задавайте false: отсутствие результата оставляет исход неизвестным. Сервер должен проверять именно действие/ресурс, а не наличие похожего объекта.

```bash
python3 scripts/manage_execution.py --state /absolute/path/execution.json reconcile-action --step-id jira-1 --action-id ACT-...
```

Команда выполняет только согласованное чтение, в том числе после отмены для диагностики. Она не снимает stop-флаг, не запускает модель и не объявляет задачу завершённой. После проверки координатор использует `retry` или явный `resume`. У действия без разрешённого readback нет автоматического способа подтвердить отсутствие; ручное редактирование журнала не заменяет доказательство.

## Подтверждения и конкуренция

Для managed reviewer со своей gateway_policy шлюз дополнительно записывает каждый
вызов в observations и выдаёт _meta.qa_review_execution_receipt. Read не кешируется;
повтор подтверждённого write остаётся fresh=false. Лимит max_review_calls общий
для всех попыток шага (по умолчанию 20). OBS связывается с точным target, политикой
и активной попыткой; старые/неопределённые результаты не закрывают runtime-критерий.
Перед стартом backend policy.json сверяется с замороженным планом. Формат —
[REVIEW_EXECUTION.md](REVIEW_EXECUTION.md). Прежний журнал actions/readback сохраняется.

Журнал `actions.json` общий для всех попыток шага; IO-lock сериализует обращения разных процессов. Перед вызовом после получения блокировки повторно проверяется stop-флаг и токен текущей попытки. Отмена не может отменить уже выполненную операцию на внешнем сервере: её фактический исход проверяется отдельно.

Подтверждённый write/readback сохраняет отдельный файл в `actions.json.receipts/` с task, step, action, исходными аргументами и наблюдаемым результатом. Имя включает SHA-256; существующий файл не перезаписывается. Шлюз возвращает `_meta.qa_action_receipt` с путём и хешем. Исполнитель может включить файл в QA artifacts. При повторном вызове сверяются сохранённый результат и подтверждение; изменённый файл не считается успехом. Это локальная запись наблюдения, а не доказательство корректности всех данных внешнего сервера.

Данные аргументов и ответов могут быть чувствительными: используйте сервер, который выдаёт необходимые поля, храните файлы локально и не передавайте секреты в аргументах инструмента; учётные данные задаются в конфигурации доверенного backend. Журнал не защищает от пользователя с полным доступом к workspace. Политика инструментов не изолирует сам MCP-сервер на уровне ОС.

# Примеры и проверка ручного каталога

Применяй, когда назначение создаёт, использует или проверяет JSON-каталог кейсов.
Общий формат — Шаг / Ожидаемый результат / Тест-дата по TEST_CASE_STYLE.md.
Примеры показывают оформление; их роли, пути, коды, лимиты и способы подготовки
не являются требованиями или возможностями продукта.

## Кто что проверяет

| Роль | Обязанность |
| --- | --- |
| Координатор | Задать тип/цель, выбрать пример, передать первичные требования и каталог, проверить структуру до передачи и назначить содержательное ревью |
| qa-test-plan-writer | Использовать подходящий пример, проверить сохранённый каталог валидатором, сверить покрытие/достижимость и исполнимость шагов |
| qa-feature-tester | Читать name, expected_result и все данные шага; подтверждать подготовку и использовать фактические значения/ID, не менять каталог во время прогона |
| qa-test-automation | Перенести подтверждённые действия/ожидания и данные в fixtures/assert, сохранив scenario_id; пример JSON не является готовым matcher |
| qa-result-reviewer | Проверить текущую структуру, источники, достижимость и различающие наблюдения независимо от автора; не исправлять его каталог |
| qa-autotest-reviewer | Сверить каталог и код: обязательные поля/условия не потеряны, fragment/exact и динамические ID перенесены правильно |
| Подготовка данных/окружения | При переданном каталоге учитывать его данные/условия; пример не разрешает новую внешнюю запись, публикацию Kafka или изменение БД |

## Выбор примера

Для API — examples/test-cases/api/INDEX.md, для UI — examples/test-cases/ui/INDEX.md,
для Kafka — examples/test-cases/kafka/INDEX.md. Прочитай индекс выбранного типа
и один подходящий JSON-файл. Второй файл нужен только для существенного аспекта,
не показанного первым. Не загружай всю библиотеку и не добавляй её сценарии в
покрытие продукта. При неизвестном типе/существенном способе проверки сохрани
вопрос; координатор должен выбрать пример до bare-запуска.

В обычной сессии используй доступное чтение от package_root. В managed-плане
координатор указывает assignment.test_type и выбранный JSON в instruction_paths:

```json
{
  "assignment": {"agent": "qa-result-reviewer", "test_type": "api"},
  "instruction_paths": ["examples/test-cases/api/cancellation.json"]
}
```

Это фрагмент шага, не полный execution-план. Для прямого ревью каталога используй
review_target.scope=test_cases; в review_cycle направление может иметь другой
scope, если авторский результат содержит test_cases_artifact. Первичные требования,
контекст возможностей проекта и сам продуктовый каталог передаются через inputs.
Авторский verdict, требования к модели и учебный пример не заменяют эти источники.

Сборщик передаёт индекс и выбранный пример целиком, фиксирует их SHA256 и
проверяет структуру примера перед запуском. Если assignment.test_type задан,
но пример не выбран, передаётся один базовый образец оформления: create.json
для API/UI, persistence.json для Kafka. Он не меняет цель задания; координатор
выбирает более подходящий файл через instruction_paths. Для смешанного каталога
явно передай по нужному примеру каждого типа. Review-cycle сохраняет выбранные
примеры и тип автора. Входы reviewer включают зарегистрированные target-файлы,
в том числе inputs автора; прочие первичные ссылки нужно предоставить явно.
Предыдущий feedback исключается из независимой оценки.

## Структурная проверка

При доступном разрешённом локальном запуске:

```bash
python3 /absolute/package_root/scripts/validate_test_cases.py --input /absolute/project_root/test-cases/catalog.json
```

Проверяй сохранённый файл, а не несохранённый текст ответа. При отсутствии у автора
разрешённого запуска координатор проверяет новый выходной файл после сохранения;
catalog_validations входа не подтверждает изменённую ревизию. Координатор и автор
сохраняют результат проверки текущей ревизии; успешный JSON/CLI не доказывает
качество или готовность исполнения. Публикация дополнительно требует генерации
Allure: она может отвергнуть метаданные/параметры, допустимые на стадии планирования.

Bare-контекст включает catalog_validations для каталогов, переданных через inputs:
путь, SHA256 именно прочитанных байтов, valid, case_count и errors. Это результат
реального вызова validate_catalog сборщиком, без subprocess, продуктовых действий
или новых tools. Некорректный JSON получает диагностику kind=json; её нельзя
выдавать за успешную проверку каталога. Требования и прочие JSON-источники без
test_cases не считаются каталогами.

Исполнитель/reviewer сверяет путь и SHA256 со своим текущим входом/target.
Отметь в checks, что структуру проверил runtime; не приписывай этот вызов себе
или живой модели. При отсутствии такого результата и разрешённого валидатора
запроси координаторскую проверку, сохрани unknown по этому условию. Не обходи
ограничения shell/gateway reviewer. Исторический лог проверки другого хеша
не доказывает текущую структуру. При ошибке каталога не принимай её как pass.

## Содержательное ревью

Независимо сверяй существенные решения по TEST_CASE_SELECTION.md и qa-check-quality:

- У действия свой конкретный наблюдаемый результат. Данные доступны из кейса,
  порядок действий/подготовка воспроизводимы, промежуточный обязательный эффект
  не потерян при объединении. Не требуй отдельный шаг/кейс для каждого поля.
- Краткость по TEST_CASE_STYLE не скрывает объект, порядок, условия и критерии.
  Подготовка/данные доступны из кейса без догадок, ожидание позволяет вынести
  pass/fail. Убирай повторы и рассуждения, но не требуй лимита слов, телеграфного
  языка или дробления единой операции ради длины. Длинная фраза сама по себе
  не дефект: замечание указывает потерянный смысл или конкретную избыточность.
- Данные удовлетворяют предусловию и отличают результат по требованию от
  существенной ошибочной реализации. Равенство полных значений не заменено
  косвенным совпадением/подстрокой; контрактный fragment/contains сохраняется.
  Эталон независим от проверяемого метода. Формула, нормализация и SLA имеют источник.
- Сила вывода соответствует наблюдению: приём команды, ответ, commit и попытка
  действия не смешаны. Изменение версии не объявлено причиной/изменением
  конкретного поля, неизменность не выдана за отсутствие попыток, неполный лог
  не доказывает отсутствие действия. Альтернативный наблюдатель подтверждает
  тот же критерий; непроверенный обязательный критерий не скрыт общим passed.
- Для сравнения до/после подготовка зафиксирована, снимок и чтение свежи,
  чужие изменения отделены, известны корреляция и границы ожидания. Есть
  исполнимые запросы/точные ссылки и происхождение переменных. Оговорены только
  применимые условия; необоснованные аудит/БД/проверки версий не навязаны.
- API: обязательные headers/body и пример ответа подтверждены источником;
  fragment/exact и конкретные проверки согласованы. Отсутствие тела отличается
  от null; неизвестный HTTP-статус не выдуман. Нет второй устаревшей копии HTTP-данных.
- UI: данные привязаны к полям/объектам, ожидается конкретное состояние экрана;
  пустой список не проходит проверку нужных строк. Динамический ID берётся из
  фактического действия, видимость не выдаётся за серверный запрет или запись БД.
- Kafka: key/headers/body, сериализация и наблюдение эффекта подтверждены;
  подтверждение брокера не заменяет проверку результата потребителя. Окно отсутствия
  ответа полно и свежо, повреждённая корреляция/неработающий наблюдатель не дают pass.
- Пример тела/строки не заменяет assert/expected_result. Нельзя принимать каталог
  только из-за сходства с учебным образцом или успешного валидатора. Неизвестный
  способ/ожидание блокирует проектирование; недоступный известный ресурс — исполнение.

Замечание связывается с scenario_id и текущей ревизией/хешем. Reviewer не переписывает
каталог автора. Содержательное принятие, исполнение и отображение в TMS — разные
проверки; подготовка файлов не разрешает запуск продукта или публикацию.

Для финального плана проверь ссылки requirement_coverage по [TEST_PLAN_HTML.md](TEST_PLAN_HTML.md): точный источник/якорь входит в ревизию либо задан прямой URL. HTML строится после содержательного принятия и не заменяет первичные данные.

Разделённая задача использует [TEST_PLAN_PARTITION.md](TEST_PLAN_PARTITION.md): проверяй назначенный набор своей группы, а в финальном ревью — полное объединение и межгрупповые риски. Передача примеров и проверки текущих хешей сохраняются.

# Импакт-анализ и выбор регресса

Штатные команды обновления карты по наблюдениям, сравнения двух фактических
прогонов, полного времени и плана с блокировками — в QA_IMPROVEMENTS.md.
При заданном improvement_plan приёмка пересчитывает отчёты и проверяет пороги.

qa-impact-analyst предлагает набор существующих сценариев для конкретного изменения. Роль дополняет qa-analyst (ожидания и риски) и qa-test-plan-writer (проектирование покрытия). Координатор принимает рекомендацию, qa-feature-tester либо штатный CI выполняет согласованный набор. Автоматического изменения CI или критериев задачи нет.

## Маршрут

1. Координатор фиксирует последнюю проверенную base_revision, target_revision всей поставки, полный каталог согласованной области, карту зависимостей и политику обязательных проверок. Границы каталога требуют обоснования: сокращённый вход не доказывает полноту регресса.
2. Создаёт неизменный impact_input и назначение с impact_input, полным scenario_ids каталога и критериями. Реестр автоматически включает первичные снимки в inputs, сохраняет хеши и проверяет их при продолжении. Без материалов агент возвращает blocked.
3. Агент исследует прямое/косвенное влияние и вызывает селектор. Дополнительные риски расширяют набор либо требуют новой карты координатора. Входы не переписываются ради исключений.
4. Для сокращения набора назначается qa-result-reviewer с review_scope=impact_selection, первичными снимками и точным review_target. Managed-профиль этого scope автоматически включает docs/IMPACT_ANALYSIS.md; в другом scope передайте документ через instruction_paths. Для критериев задачи используйте required_reviews с этим reviewer. Проверяются границы, общие механизмы, исключения и контрпример пропуска. Валидатор не подтверждает истинность карты.
5. После ревью координатор принимает артефакт и назначает run_scenario_ids исполнителям. ready-зависимость от impact_ready разрешает только эти ID, включая review_scenario_ids. Для чтения всех исключений нужна context-зависимость. Критерии scenario_execution всей задачи не меняются селектором. Пробелы передаются автору плана.

## Снимки входов

impact_input — JSON schema_version=1. Обязательные поля:

- base_revision и target_revision: фиксированные версии всей поставки. Для Git используйте разрешённые полные commit SHA.
- change_set и catalog: `{path, sha256}` с локальными снимками. Путь относительно impact_input либо абсолютный. Каталог соответствует TEST_CASE_STYLE.md.
- evidence_sources: список дополнительных `{path, sha256}` для требований, архитектуры, покрытия и истории. Evidence связей/политики/дополнений ссылается на эти локальные снимки либо change_set/catalog, с необязательным #locator. Сырые внешние ссылки требуют доступного снимка. Все первичные файлы включаются в хеши и реестр.
- completeness: boolean-поля dependencies, test_mapping, history. true означает подтверждённую полноту согласованной области, а не уверенность модели.
- components: component_id, depends_on, evidence. `A.depends_on=[B]` означает, что изменение B может затронуть A. Неизвестные ID и дубли отклоняются, циклы допустимы.
- change_components: change_id, component_ids, evidence. Неописанная/пустая связь изменения вызывает полный fallback. Учитывайте внешние требования, runtime-конфигурацию, миграции и контракты, отсутствующие в Git.
- tests: ровно одна запись на каждый scenario_id каталога. component_ids, mapping_status=confirmed|unknown, evidence, duration_seconds (число >=0 либо null). Новые ID нельзя изобретать в этой карте. Параметризованный кейс выбирается целиком.
- policy: mandatory_scenario_ids, new_scenario_ids, previously_failed_scenario_ids, force_full (boolean), evidence. Источник политики и истории обязателен. Пустая неподтверждённая история требует history=false.

change_set, schema_version=1: base_revision, target_revision, complete (boolean), source, changes. Каждое изменение: change_id, paths (относительные пути), evidence. status/diff можно хранить дополнительно. Полнота и смысл источника требуют ревью.

Снимок Git без изменения рабочей копии:

```bash
python3 scripts/capture_impact_changes.py --repo /path/to/app --base <previous-commit> --target <release-commit> --output /path/to/new-changes.json
```

Скрипт разрешает refs в commit SHA, сохраняет diff и оба пути переименованного файла. Читает только закоммиченные изменения. Внешние изменения и продуктовые ожидания этим снимком не подтверждаются. Недоступные источники обозначайте как неполноту, а не отсутствие влияния. Рабочую копию и секреты автоматически не собирает.

## Выбор и проверка

```bash
python3 scripts/select_regression.py --input /path/to/impact-input.json --output /path/to/new-selection.json
python3 scripts/validate_qa_result.py --input /path/to/result.json --task-id QA-123 --request-id QA-123-impact-1 --agent qa-impact-analyst --impact-input /path/to/impact-input.json --require-self-review
```

Селектор обходит зависимости в сторону потребителей, выбирает связанные тесты и обязательные/новые/ранее падавшие проверки. Неполные источники, неизвестное изменение, отсутствие подтверждённого тестового покрытия изменения или force_full дают полный регресс. Неизвестная связь отдельного теста сохраняет его в прогоне как review. Остальные решения: run/exclude. Все ID каталога отражаются ровно один раз, review_scenario_ids входят в run_scenario_ids. coverage_gaps сохраняются при fallback: запуск имеющихся тестов не закрывает отсутствующее покрытие.

Для расширения используйте --additional-scenarios с JSON-списком `{scenario_id, reason, evidence}`. Принимаются существующие ID, дополнения не меняют обязательный минимум. Выходные файлы создаются исключительно, существующие не перезаписываются.

impact_ready содержит impact_artifact, impact_input, input_sha256, base_revision, target_revision, run_scenario_ids, review_scenario_ids, excluded_scenario_ids, limitations и обычный self_review. Артефакт включает решения, причины, связанные change_ids/источники, fallback_reasons, coverage_gaps, additional_scenarios, хеши входов и estimated_serial_duration. Валидатор требует независимый --impact-input, пересчитывает артефакт и сверяет поля. Реестр проверяет источники/выходы до handoff, включая первичные файлы, пропущенные автором в artifacts.

Расчёт подтверждает согласованность представленной модели. Полноту реального diff, истинность связей и исключения подтверждает независимое ревью. Селектор не строит call graph и не инструментирует продукт автоматически. Карты первой версии собираются из кода, контрактов, архитектуры и фактического покрытия с указанием источников.

## Проверка пользы

Первый пилот сохраняет полный прогон и оценивает сокращённый набор на той же сборке и условиях. Сравнивайте подтверждённые дефекты, найденные только полным прогоном, и полное время: анализ, ревью, setup, исполнение, очередь и повторы. Flaky/setup-ошибки разбирайте отдельно. Включите прошлые дефекты и изменения общих механизмов в контрольные случаи. Синтетический пример не доказывает ускорение продукта.

estimated_serial_duration показывает сумму известных длительностей, missing_scenario_ids и total_seconds=null при неполных измерениях. Это не wall-clock параллельного CI и не затраты агента. Полный периодический регресс и условия force_full задаёт команда.

Пример — examples/impact-analysis/README.md. Исторический выпуск 2.0 сохраняется. Новый агент включён в поставку 2.1, без заявления о живом GIGACODE/CI-пилоте.

# Оценка эффективности QA-агента

Первый исполняемый baseline — scripts/run_agent_benchmark.py: пять учебных задач, повторные сессии GIGACODE, сохранённые инструкции/ответы и ведомости 20 независимых оценок. Запуск отделён от смыслового принятия; детали и пределы reasoning-профиля — examples/benchmark/README.md. Недоступный GIGACODE фиксируется как unavailable, а не успешная проверка. Для A/B инструкции self-review применяй on/off при одинаковых условиях.

TASK_ACCEPTANCE.md добавляет проверяемые критерии задачи и корреляцию передач всех ролей. export_task_trace.py экспортирует события реестра; runner сохраняет также успешные запуски и ошибки. Учитывай границы измерения: события передачи не заменяют расход фактического исполнителя и содержательную оценку. Интерактивный usage всех ролей и отдельные MCP-вызовы пока автоматически не собираются.

Сравнивайте изменения на одном наборе реальных или воспроизводимых задач. Для каждого маршрута (тест-план, проверка фичи, расследование, автотест) включите простые и сложные случаи. Сохраняйте одинаковые модель, инструменты, требования и окружение для сравниваемых запусков.

Для каждой задачи фиксируйте:

| Показатель | Как учитывать |
| --- | --- |
| Время | От назначения до проверяемого результата; ожидание пользователя отмечать отдельно |
| Токены | Из `reported_usage`, когда CLI их сообщает; иначе `unknown`, без пересчёта символов в токены |
| Назначения | Число вызовов ролей и повторных вызовов с причиной |
| Контракт | Доля результатов без ошибок валидации |
| Доказательства | Проверяющий вручную подтверждает, что вывод опирается на доступный источник и артефакты |
| Покрытие | Доля существенных критериев приёмки со сценарием и фактическим результатом |
| Дефекты | Для задач с известным дефектом: обнаружен ли он, корректны ли шаги и ожидаемое поведение |
| Ревью | Число возвратов, существенные замечания и был ли итог привязан к актуальной ревизии |

Считайте задачу качественно завершённой только после выполнения обязательных проверок из `CONTRACT.md`. Экономию токенов сравнивайте среди задач, сохранивших это качество. `artifact_count` в метриках отдельного запуска показывает наличие ссылок, но не доказывает пригодность доказательств.

## Постоянный контекст GIGACODE CLI

В новой интерактивной сессии из корня проекта выполните `/context detail` до работы с задачей. Зафиксируйте входные токены простого запроса без вызовов инструментов (*idle cost*) и строки для `GIGACODE.md`, списка навыков и схем инструментов. После изменения инструкций повторите измерение с той же моделью и настройками в новой сессии. Сравнивайте абсолютные токены, а не долю окна контекста. Отдельно выполните задачу с тест-кейсами и проверьте, что навык `qa-test-cases` доступен и применяется, а валидатор принимает созданный каталог. Отсутствие вызова навыка или ухудшение результата — повод пересмотреть описание навыка, даже если постоянный контекст стал меньше.

## Актуальные наборы и тесты пакета

[Карта Python-проверок](../tests/README.md) отделяет локальные контракты/процессы
от смысловой оценки модели. Полный discover обязателен после изменений пакета;
его успех не является eval качества ролей.

| Набор | Задачи / критерии на повтор | Назначение |
| --- | --- | --- |
| suite.json | 5 / 20 | Исходный контрольный набор |
| quality-suite.json | 9 / 36 | Общий навык качества и дополнительные контрпримеры |
| profile-suite.json | 15 / 60 | Кандидаты навыков данных/заглушек и holdout |
| regression-suite.json | 17 / 68 | Краткость/наблюдение, сбои координации и решения оставшихся ролей |

Пути относятся к examples/benchmark; первые три набора имеют общие задания,
поэтому их размеры не складываются в число уникальных случаев. В объединении
каждая из 14 зарегистрированных ролей представлена минимум одним заданием;
семантическая полнота роли этим не гарантируется. Подробности и команды нового
набора — [REGRESSION.md](../examples/benchmark/REGRESSION.md).

Для новых manual-case заданий явно задавай agent и test_type; runner передаёт
индекс и один валидный пример выбранного канала. Reasoning-контекст использует
применимые разделы; workflow координатора не включается всем ролям. instruction_paths добавляет
только нужные docs пакета; рубрика и ответы оценщика не передаются. Старые
запуски оценивай по сохранённым instructions.json/system.md, без обновления
исторических хешей. Добавление заданий требует новых сопоставимых запусков.
Программный CLI имеет measurement_kind=fixture и не доказывает качество модели;
отсутствующий живой runtime остаётся unavailable, не pass.

## Проверка качества отдельных ролей

Для выборочного контекста данных используй `examples/test-data/context-eval/README.md`: три одинаковых задания A/B, 12 критериев, независимая оценка и повторные запуски. Чек-лист/начальные разделы — автоматический минимум, дополнительные разделы читаются при соответствующем риске. `test_data_context_characters` в метриках runner измеряет только переданный текст ядра, не поздние чтения и не токены. Уменьшение символов не означает доказанную экономию usage или времени.

Готовый контрольный набор из пяти синтетических задач — `examples/benchmark/README.md`: выбор сценариев и дублей, неизвестные права, слабый assert, понятное сообщение о дефекте и общий блокер с продолжением. `suite.json` задаёт 20 критериев независимой ручной оценки. `scripts/check_benchmark_review.py` проверяет полноту ведомости и хеш сохранённого ответа; не оценивает смысл и не запускает модель. Используйте его до и после изменения инструкций, сохраняя одинаковые условия. Невыполненный набор не считается успешным релизным замером.

Для браузерной работы дополнительно фиксируйте версию MCP, число вызовов, явных snapshot, screenshot и восстановлений, время до проверяемого вывода и объём ответов инструментов. Сравнивайте исходный профиль и `.gigacode/playwright.config.json` на одинаковых сценариях с известным дефектом. Учитывайте только запуски с тем же качеством воспроизведения и доказательств; недоступные счётчики записывайте как `unknown`. Техническая smoke-проверка описана в `BROWSER_MCP.md` и не заменяет замер на реальном сценарии.

Для каждой роли подготовьте несколько задач с заранее проверенным результатом, включая неполные входные данные. Оценивайте не только заполнение JSON, но и правильность решения:

| Роль | Главная проверка качества |
| --- | --- |
| `qa-analyst` | Нашёл существенные противоречия и сценарии риска, не придумал ожидаемое поведение |
| `qa-test-plan-writer` | Покрыл критерии приёмки без лишних сценариев, расставил приоритеты по риску |
| `qa-test-env-configurator` | Подтвердил выполнение всех пунктов переданного админгайда для нужного стенда/версии; не пропустил пункт и не объявил частичный стенд полным |
| `qa-test-data-builder` | Проверил свойства и связи данных, сохранил повторяемость и очистку |
| `qa-defect-investigator` | Отделил наблюдение от причины, честно описал попытки и ограничения |
| `qa-feature-tester` | Не засчитал пропуски как успех, привязал фактические результаты к версии и доказательствам |
| `qa-test-automation` | Assert обнаруживает заданный дефект; тест устойчив и запущен адресно |
| `qa-autotest-reviewer` | Нашёл существенные слабые проверки и привязал замечания к нужной ревизии |
| `qa-jira-defect-creator` | Не создал дубль, сохранил обязательные поля и проверил запись после создания |
| `qa-test-report-writer` | Бизнес-кейсы и конфигурации соответствуют источникам; пропуски, неизвестные тогглы, конфликтующие повторы и pending review не превращены в успех |

В набор включите минимум один случай, где корректный ответ — `blocked` или `needs_*`. Сравнивайте долю правильных решений и ложных утверждений вместе с токенами и временем. Валидный контракт доказывает форму ответа, но не его фактическую истинность.

Состояние отдельного запуска хранится рядом с файлом задания в `.qa-agent-state/` либо по явно заданному `--state`. Для новых маршрутов координатор ведёт общий реестр по TASK_EXCHANGE.md; runner подключается через `--task-state`. В нём сохраняются назначения, владельцы, ревизии, принятие и события готовности. При возобновлении читайте эту запись и предметные состояния, проверяйте внешнее состояние перед повтором действия. В старых задачах прежняя краткая запись остаётся источником восстановления; перенос в реестр не запускает работу заново.

Для сравнения передачи до/после дополнительно фиксируйте долю неверных/устаревших результатов, остановленных до следующего назначения, повторы после потери уведомления и время от result_ready/answers_ready до обработки координатором. Тесты атомарности и доставки событий не заменяют замер живых агентов. Расход всех ролей и координатора учитывайте вместе; локальная запись файла сама по себе не сокращает токены чтения его содержимого.

## Состояние и доказательства расследования

Контрольные синтетические сцены и ожидаемые решения перечислены в `examples/investigations/INDEX.md`. Тесты проверяют продолжение, смену окружения/сборки/требований/данных, повторы без причины, недоступные или изменённые файлы и устаревшее ревью. Оценку координатора на реальных материалах проверяйте отдельно: найдёт ли он несовпадение факта и доказательства, вернёт ли адресный запрос и сохранит ли ограниченный вывод вместо ложного подтверждения. Сравнивайте число необоснованных повторов, размер передаваемого контекста и время до проверяемого результата. Локальное прохождение примеров не доказывает соблюдение протокола живой моделью.

## Ускорение подготовки тест-плана

Дополнительно оцени модель поведения и контрпримеры по TEST_DESIGN.md: верно ли связаны правила с источниками, сохранены ли неизвестные ожидания и обязательные риски, на какой конкретной проверке обнаруживается каждый существенный контрпример. Для большого набора факторов проверь реальные взаимодействия scripts/generate_combinations.py; успешная проверка сочетаний не заменяет оценку ожидаемых результатов. Учебный материал — examples/test-design/.

Сравнивайте прежний и новый маршруты на ясной задаче, задаче с локальным вопросом и задаче с изменением общей модели прав. Фиксируйте время до карты, до готовой независимой части и до принятого плана, ожидание ответов отдельно, число переделанных кейсов и полных повторных ревью. Контролируйте одинаковое покрытие существенных требований и рисков, число пропущенных ошибок и неподтверждённых ожиданий по независимой оценке. Ускорение считается подтверждённым только при сохранении качества; прохождение валидатора само по себе этого не доказывает.

## Качество автотестов

Для автотестов применяй AUTOTEST_QUALITY.md: фиксируй добавленное покрытие, повторяемость исходного состояния, включение нового теста в штатный прогон и результат контролируемой ошибки для критичного assert. Проверяй целевую причину падения и восстановление; ошибка инфраструктуры не засчитывается. При исправлении сопоставляй assert и источник до/после. Учебный механизм — examples/autotest-quality/, реальные интеграции оцениваются отдельно. Сравнивай затраты среди результатов, прошедших содержательное принятие.

## Краткость служебных сообщений

При сравнении стиля фиксируйте входные и выходные токены всего запуска, время и качество результата на одинаковых задачах. Проверьте отсутствие повторных пересказов задания и пояснений к каждому инструменту. Оцените, сохранены ли обязательные поля, условия, отрицания, блокеры, источники и доказательства, различается ли валидация и содержательное принятие. Краткие сообщения не оправдывают неполные артефакты. Инструкции стиля сами добавляют входные токены: экономия требует замера, а не оценки длины финального ответа.

## Понятность сообщений

Проверь сообщения на подтверждённом дефекте, неизвестном требовании, недоступном стенде, ошибке инструмента и успешной частичной проверке. По первым двум предложениям читатель должен понимать конкретное поведение или блокер. Из краткого сообщения должны быть ясны подтверждённое влияние, степень уверенности и нужное решение, если оно требуется. Не допускай выдуманных последствий, подмены гипотезы причиной, объявления ошибки инструмента дефектом продукта или пропусков успехом. Полные доказательства доступны по ссылке. Сравнивай число дополнительных вопросов «в чём проблема?»; одна лишь длина ответа не является показателем понятности.

## Инциденты как источник контрольных задач

Используй FAILURE_JOURNAL.md: группируй последние снимки по incident_id, отдельно учитывай наблюдаемые симптомы и причины с записанным подтверждением. Контрольное задание выбирай по конкретному подтверждённому сбою и проверяй содержательно, что оно обнаруживает ту же ошибку. Гипотезы, изменённые доказательства и рабочие/синтетические записи не смешивай. Количество зарегистрированных инцидентов не равно доле ошибочных запусков без полного знаменателя. Сравнение версий выполняй на одинаковых задачах с повторными независимыми запусками.

## Метрики управляемого цикла

Новые managed-попытки сохраняют context-metrics.json и metrics.json; сводки execution/review-cycle учитывают все попытки и доступный terminal CLI usage. Полный токенный итог остаётся null при любой неизмеренной попытке; known_* обозначает частичную сумму. Контекст считается в символах без внутренних инструкций CLI, tool schemas и последующей истории. Интерактивный координатор требует отдельного учёта. Протокол выборочной сборки и A/B — [CONTEXT_ASSEMBLY.md](CONTEXT_ASSEMBLY.md).

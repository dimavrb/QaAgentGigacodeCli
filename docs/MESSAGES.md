# Понятные сообщения о результатах QA

Сообщение пользователю помогает понять проблему и принять решение. Координатор преобразует отчёты исполнителей в краткий вывод; не вставляет JSON, журнал действий или длинный отчёт целиком. Полные данные сохраняются в предусмотренных контрактом артефактах. Эта инструкция не меняет JSON-схему и обязательные поля.

## Порядок сообщения

1. **Суть:** одно предложение с объектом, условием и конкретным результатом. Для дефекта назови расхождение, для блокера — недостающее условие, для успешной проверки — проверенное поведение.
2. **Влияние:** что не может сделать пользователь или какую часть QA нельзя завершить. Не выдумывай ущерб, охват и критичность. Если влияние не установлено, укажи это, когда оно нужно для решения.
3. **Подтверждение:** степень уверенности, существенные условия и краткая ссылка на доказательства. Для продуктового дефекта нужны фактический результат и ожидаемое поведение по источнику. Указывай окружение и сборку, если они известны и относятся к выводу.
4. **Нужное решение или следующий шаг:** конкретный вопрос, действие или рекомендация, только если они действительно нужны. Рекомендация создать дефект не является выполненным внешним действием.

Обычно достаточно одного абзаца и нескольких коротких строк. Не заполняй ненужные поля ради шаблона и не обрезай существенные ограничения ради длины. Подробные шаги, логи, ответы API, гипотезы и история попыток — по ссылке. По запросу объясняй подробнее.

## Различай ситуации

| Ситуация | Первая строка | Что необходимо для решения |
| --- | --- | --- |
| Подтверждённый дефект | Конкретное расхождение факта и требования | Влияние, фактическое и ожидаемое поведение, источник и доказательства |
| Возможный дефект | Наблюдаемый симптом и что ещё не подтверждено | Недостающая проверка; гипотеза не превращается в причину |
| Неясное требование | Какое поведение неизвестно | Затронутые сценарии и конкретный вопрос |
| Стенд или данные | Какое условие отсутствует | Что нельзя проверить и какая независимая часть остаётся доступной |
| Ошибка инструмента | Что не удалось выполнить | Какой результат не получен; продуктовый дефект не объявляется без оснований |
| Успешная проверка | Какое поведение проверено | Объём, версия и оставшиеся ограничения; пропуски не считаются успехом |
| Замечание ревью | В каком случае тест пропустит дефект или даст ложное падение | Последствие, файл/строка, нужное исправление и ревизия |

Слова «проблема», «некорректно», «ошибка в логике» без описания поведения недостаточны. Код ошибки сам по себе не объясняет нарушение требования. Не начинай пользовательское сообщение с перечня инструментов, ID назначения, пути лога или статуса события.

## Факт, причина и принятие

«После нажатия кнопки заказ не сохраняется; API вернул 500» — наблюдение. «Причина в базе данных» допустимо только при подтверждении. Иначе это отдельная гипотеза в артефакте, с явным статусом.

Различай «воспроизведено исполнителем» и «дефект принят координатором по доказательствам». Валидный JSON не подтверждает вывод. При `not_reproduced` не утверждай отсутствие дефекта; при `inconclusive` скажи, чего не хватает для вывода. При `expected_behavior` объясни, какое требование подтверждает наблюдение.

## Примеры

Все примеры учебные. Числа, источники, версия и статус в реальном сообщении должны соответствовать актуальным доказательствам.

### Дефект после содержательного принятия

> **Фильтр «Оплачен» оставляет в списке неоплаченные заказы.**
> После применения фильтра виден заказ со статусом «Новый»; по критерию R-1 должны остаться только оплаченные.
> **Влияние:** пользователь не получает список оплаченных заказов через этот фильтр.
> **Подтверждение:** стенд stage, сборка 42; вывод принят координатором. Шаги и скриншот — в артефакте TC-001, источник — R-1.
> **Дальше:** предлагаю оформить дефект.

### Неясное требование

Для вопросов, требующих ответа пользователя, координатор готовит HTML-форму по [QUESTIONS_UI.md](QUESTIONS_UI.md), даёт одну ссылку и кратко объясняет, что блокируется. Пользователь отвечает по пунктам и отправляет один пакет. Свободный текст и «Пока не знаю» доступны всегда; последний вариант не снимает блокер. В самостоятельном HTML общий ответ копируется в чат.

> **Не определено, может ли оператор удалять чужие заказы.**
> Вопрос Q-3 блокирует ожидаемые результаты TC-007 и TC-008. Остальные сценарии можно готовить независимо.
> **Нужно решить:** разрешено ли оператору удаление чужого заказа?

### Недоступное условие проверки

> **Нельзя проверить оплату: тестовый платёжный сервис недоступен.**
> TC-004 заблокирован; создание заказа и фильтрация проверены отдельно.
> **Подтверждение:** ошибка подключения сохранена в артефакте проверки стенда. Причина недоступности не установлена.
> **Нужно:** восстановить сервис либо предоставить согласованное окружение для TC-004.

### Ошибка инструмента

> **Проверка фильтра не выполнена: браузерная сессия не запустилась.**
> Результат TC-001 не получен, состояние продукта неизвестно.
> **Дальше:** восстановить подключение браузера и повторить сценарий после проверки предусловий.

### Успешная проверка с ограничением

> **Фильтр показывает только оплаченные заказы в проверенном наборе данных.**
> TC-001 выполнен на stage, сборка 42; доказательства сохранены в артефакте сценария.
> Проверка на большом объёме данных не выполнялась, поэтому вывод на неё не распространяется.

### Замечание ревью

> **Тест пройдёт, даже если фильтр вернёт неоплаченные заказы.**
> Он проверяет только число строк, а статусы заказов не сравнивает. Поэтому дефект фильтрации может остаться незамеченным.
> **Нужно исправить:** проверить статусы всех возвращённых заказов. Место — tests/filter_test.py:18, ревизия abc123.

## Несколько результатов и сообщения по ходу работы

Сначала покажи общий результат: сколько подтверждённых дефектов и какие обязательные проверки заблокированы, если эти числа помогают решению. Затем короткий список или таблицу «проблема → влияние → подтверждение». Не называй разные симптомы одной проблемы отдельными дефектами без оснований. При большом списке выдели наиболее важное, укажи полный объём и дай ссылку на остальное; не скрывай блокеры и ограничения.

По ходу работы сообщай новые существенные факты, изменение вывода или нужный ответ пользователя. Не пересказывай прежние сообщения и не комментируй каждое чтение файла. Если вывода пока нет, обозначь конкретную неопределённость вместо общих слов «ведётся анализ».

## summary исполнителя

Одна-две фразы с конкретным результатом или блокером; статус должен совпадать с payload и доказательствами. Например: «После фильтра “Оплачен” остаётся заказ “Новый”; воспроизведено на stage, сборка 42. Требование R-1 и скриншот переданы на оценку координатору». Остальные обязательные поля отчёта остаются полными; не заменяй ими понятное резюме.

## Применение в установленном проекте

Обнови инструкции подключённых ролей, APP_COORDINATOR.md и раздел сообщений в CONTRACT.md, сохранив локальные пути, tools и ограничения приложения. Для ссылок подключённых копий используй префикс qa-agent/docs/. Не заменяй сокращённый корневой GIGACODE.md большим файлом пакета: при необходимости добавь только короткую ссылку на правила сообщений. Начни новую сессию. Проверка реального вывода модели необходима отдельно от тестов валидаторов. Эти правила включены в пакет 1.3; прежние архивы 1.1 и 1.2 не изменены.

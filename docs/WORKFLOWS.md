# Маршруты и зависимости

Главная сессия GIGACODE CLI исполняет роль `qa-agent`. Роль выбирает маршрут по запросу и вызывает только нужных исполнителей. У каждого исполнителя собственный контекст. Результат передаётся через краткий отчёт и ссылки на артефакты.

Новые маршруты используют общий реестр и подготовленную передачу по `docs/TASK_EXCHANGE.md`: assign → prepare → фактический запуск/start → submit → содержательное review → зависимое назначение. Ожидание результата или ответов пользователя — через сохранённые события wait/ack при поддержке фонового ожидания; это не автоматический запуск завершённого чата. При продолжении сначала прочитай актуальный реестр и предметные артефакты.

Регистрация неожиданных сбоев процесса — по FAILURE_JOURNAL.md: координатор записывает симптом, влияние, назначение и доказательства, затем уточняет причину и восстановление тем же incident_id. Для автоматизации используй уже созданный runner failure_incident_id. Обычный вопрос и продуктовый дефект не дублируются как сбой агента.

## Обращение с прода

Исходное обращение → компактное состояние расследования по `docs/INVESTIGATION.md` → анализ ожидаемого поведения при необходимости → проверка нужных условий стенда и данных → `qa-defect-investigator` проверяет подозрение по DEFECT_VERIFICATION.md, используя первичные материалы и только необходимые новые наблюдения → координатор читает относящиеся доказательства и сохраняет оценку текущего отчёта → `qa-jira-defect-creator` оформляет подтверждённый дефект при наличии оснований. Задача автоматизации создаётся отдельно или выполняется в явно заданном объёме.

## Новая фича

Требования → `qa-analyst` при существенной неопределённости → `qa-test-plan-writer`, если нужен план → `qa-test-env-configurator` и `qa-test-data-builder` только для недостающих условий → `qa-feature-tester` выполняет готовые сценарии → координатор собирает покрытие и дефекты. При готовом сценарии можно сразу перейти к проверке. При подозрении на продуктовый дефект координатор сам передаёт его `qa-defect-investigator` по DEFECT_VERIFICATION.md: сохранённое наблюдение → бизнес-правило → относящийся код → только недостающая адресная проверка → независимое принятие. Отдельная просьба о ретесте не нужна; независимые сценарии продолжаются. Подготовка стенда и данных выполняется только там, где она требуется сценарию.

Для итогового или промежуточного отчёта после прогона координатор передаёт `qa-test-report-writer` область бизнес-кейсов и конфигураций, сохранённые результаты и оценки по `docs/TEST_REPORTING.md`. Итоговый документ отделяет выполнение от целевых условий и принятия; роль не выполняет дополнительные проверки продукта.

Для частичного выполнения и продолжения проверок используй `docs/EXECUTION.md`: группируй общие блокеры, сохраняй независимые результаты и проверяй их применимость после изменения условий. Это правило относится к маршруту проверки фичи, а не к разрешению автоматического выполнения плана.

## Импакт-анализ регресса

Изменения всей поставки и полный каталог согласованной области → независимый impact_input координатора по IMPACT_ANALYSIS.md → qa-impact-analyst связывает изменения и косвенные зависимости со сценариями → селектор создаёт impact_artifact → qa-result-reviewer проверяет источники и исключения → координатор принимает версию и назначает run_scenario_ids qa-feature-tester либо штатному CI в разрешённом объёме. Пробелы передаются qa-test-plan-writer. Неизвестные связи расширяют прогон. Аналитик требований не повторяет импакт-анализ, автор плана не переписывает каталог ради выбора существующих кейсов. Пилот сравнивает рекомендацию с полным регрессом.

## Автотесты

Для подготовки публикации ручных JSON-кейсов из GitVerse через вебхук и Jenkins
используй `qa-test-env-configurator`, `docs/TESTOPS_JENKINS.md` и
`examples/testops-jenkins/README.md`. Параметры реальных систем собираются при
подготовке инфраструктуры, а не при обсуждении или создании переносимого шаблона.
Передавай исполнителю обе инструкции и назначенный объём внешних изменений.

Сценарий и источник ожидаемого поведения → `qa-test-automation` изучает покрытие и реализует тест → адресный запуск → `qa-autotest-reviewer` проверяет текущую версию изменений → замечания возвращаются автоматизатору → повторное ревью изменённых участков. Исполнитель в отдельном репозитории запускается через `scripts/run_test_automation.py` либо другой настроенный способ. Правила целевого репозитория изучаются там. Подозрение на продуктовый дефект из run_result передаётся координатором расследователю по DEFECT_VERIFICATION.md; падение инструмента/фикстуры без продуктового наблюдения диагностируется как сбой теста/окружения. Сам внешний runner другие роли не запускает.

Качество автотеста проверяй по `docs/AUTOTEST_QUALITY.md`: подготовка, добавленная польза, адресный запуск, штатное обнаружение и доказательства для критичных assert. Ревьюер оценивает ограничения и сохранность исходного требования при исправлении. Автор и ревьюер обязательно используют `docs/AUTOTEST_NAMING.md`: проверяют имена по источнику и assert, шаги и различимость вариантов в свежем результате запуска либо сохраняют ограничение отображения. Данные проектируются и проверяются по ядру из `scripts/read_test_data_guide.py --role <роль>`; TEST_DATA.md дочитывается нужными разделами, уже переданное не повторяется. Координатор передаёт доступные пути к стандартам качества/названий и селектору данных, правила языка проекта и каталог при наличии.

## Заглушки через sbermock

Контракт/сценарии → при необходимости qa-stub-builder читает MCP-схемы и возвращает stubs_plan_ready без мутаций → координатор оценивает и фиксирует assignment.json → агент применяет намерение. configure_only возвращает stubs_configured без runtime-проб/Kafka-публикаций. verify проверяет назначенные пробы после всех мутаций и возвращает stubs_ready/stubs_partial либо конфигурацию с непроверенными зависимостями. Координатор проверяет материалы с --stub-assignment и полным --scenario-id; затем настройщик подтверждает подключение продукта и исполнитель использует готовые зависимости. stubs_configured не разрешает исполнение продукта. Повторное планирование не нужно при уже зафиксированном намерении.

Если заглушка нужна фиче/автотесту, её отсутствие передаётся как needs_environment с проектом, контрактом и зависимыми ID; координатор выбирает qa-stub-builder. На общем проекте один владелец изменения. После последнего зависимого прогона координатор отдельно назначает очистку по сохранённым ID/снимкам; чужие правила и топики не удаляются.

## Самостоятельные запросы

- Только тест-план: один `qa-test-plan-writer` готовит раннюю карту покрытия → координатор оценивает её при сложном объёме или существенной неопределённости → вопросы решаются одновременно с подготовкой независимых сценариев → автор возвращает `plan_partial` или `plan_ready` → валидатор проверяет структуру → координатор оценивает содержание. После ответов обновляются и ревьюятся затронутые сценарии и зависимости. Для ясной небольшой задачи отдельный возврат карты не нужен. `qa-analyst` подключается для существенных противоречий или исследования источников. Правила готовности, вопросов и ревизий — в `docs/TEST_PLAN.md`. Выполнение проверок не запускается автоматически.
- Только стенд: админгайд → `qa-test-env-configurator` → отчёт о фактической готовности.
- Только данные: предусловия → `qa-test-data-builder` с ядром данных и адресным чтением справочника → набор с обоснованием каждой записи и рецепт; выполненная подготовка дополнительно требует доказательств готовности. Не объявляй рецепт фактически готовыми данными.
- Только отчёт: согласованный scope и сохранённые прогоны/снимки/ревью → `qa-test-report-writer` → сборка и проверка report.json/report.md → содержательная оценка координатора. Пустой набор прогонов даёт непроверенную область; отсутствие данных не разрешает выполнить тесты.

## Изменения и восстановление

При продолжении расследования прочитай сохранённые попытки и нерешённые гипотезы, проверь свежий снимок условий и используй `scripts/validate_investigation_state.py`. Изменённые условия требуют перепроверки применимости результатов; повтор действий требует ссылки на прошлую попытку и причины. Передавай исполнителю только оставшийся вопрос, критерий остановки, ожидаемый артефакт и ссылки.

При изменении требований обновляй затронутые сценарии и отмечай устаревшие результаты. При изменении стенда перепроверяй зависимые условия. Перед повтором внешнего действия проверяй, не выполнилось ли оно уже. Для общих стендов и файлов назначай одного владельца изменений на время работы.

## Экономия контекста

Для UI исполнитель использует qa-browser-repro и общий browser_pool_path по нужному разделу docs/BROWSER_PROFILES.md. Один lease на короткий совместимый UI-набор; после доказательств освобождение до анализа/ожидания/отчёта, также при ошибке. Нет свободных — очередь, неясное закрытие — карантин и адресное восстановление координатором после остановки прежних клиентов. Независимые наборы используют отдельные контексты. Подключение — docs/BROWSER_MCP.md.

При переходе передавай краткое назначение и доступные исполнителю ссылки на первичные артефакты. Отчёт исполнителя содержит вывод, ограничения и ссылки; длинные логи, ответы API, планы и diff сохраняются отдельно. Для ревью передавай базовую и текущую ревизии, изменённые файлы и результат запуска; ревьюер читает нужный diff сам. Повторное назначение содержит только изменения после предыдущего `request_id`, открытые замечания и актуальную ревизию. Если артефакт недоступен, включи минимальный фрагмент, необходимый для решения.

## Самопроверка перед передачей

Каждый исполнитель проверяет окончательный результат по SELF_REVIEW.md и возвращает self_review, включая частичные события и запросы условий. В новых назначениях реестра это обязательно. Координатор оценивает содержание отдельно и сверяет обязательные условия перед следующим этапом и итогом; самостоятельная проверка автора не заменяет независимого ревью автотестов.

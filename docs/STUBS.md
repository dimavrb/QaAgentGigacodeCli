# REST- и Kafka-заглушки через MCP sbermock

## Короткий порядок

`qa-stub-builder` работает с отдельным приложением заглушек. Ожидаемое внешнее поведение задаётся контрактом, а формат записи — фактическими схемами MCP. В пакете нет универсального JSON API sbermock и выдуманных tools.

1. Если готового назначения нет, агент выполняет discovery/чтение и возвращает `stubs_plan_ready` с draft_assignment.json. Мутаций и публикаций ещё нет.
2. Координатор проверяет контракт, matcher/приоритеты, границы замены, проект и разрешённые действия. Фиксирует assignment.json отдельным новым назначением и передаёт доступный путь. Это рабочая оценка координатора; дополнительное подтверждение пользователя не требуется для уже разрешённой подготовки. Неясные правила/недоступные условия требуют конкретного вопроса, а не выдуманной конфигурации.
3. Исполнитель применяет зафиксированное намерение и немедленно сохраняет ID/состояние/очистку. При неизвестном результате сначала читает фактическое состояние, затем решает о повторе. Чужое правило не заменяется молча; update разрешён только для конкретного ID со снимком до изменения.
4. После **всех** мутаций/сверок записывает verification_started_at, заново читает каждую конфигурацию и выполняет только разрешённые пробы. При позднем изменении повторно проверяет затронутые зависимости; ранние доказательства через него не переносятся.
5. Координатор проверяет артефакты с независимым назначением и читает первичные материалы. Только подтверждённая готовность передаётся исполнителю продукта. Очистка — отдельная работа после последнего зависимого прогона.

Для запроса «напиши заглушки» по умолчанию используй `configure_only`: создать/переиспользовать и прочитать конфигурацию. `verify` задаётся для проверки поведения заглушек в разрешённых условиях, включая Kafka-трафик. Планирование тестов само по себе не разрешает создание или публикации.

## Подключение

Роль включена в поставку 1.7. При переносе обнови qa-stub-builder.md, STUBS.md, stub_contract.py, validate_stub_assignment.py, qa_contract.py, validate_qa_result.py и инструкции координатора/потребителей вместе. Сохрани настройки, credentials, локальные tools и ограничения; ссылки подключённых копий адаптируй к qa-agent/docs/scripts/examples по IMPORT_INTO_APP.md.

Используй существующий MCP sbermock в GIGACODE CLI. В этой копии пакета настроен только Playwright: неизвестный URL/transport не добавляется. Роль наследует инструменты; для установленного явного tools сохраняй ограничения и добавляй только подтверждённые имена из живого discovery. В новой сессии проверь подключение, чтение/список, запись и доступный способ пробы. Недоступная проба не отменяет факт создания, но исключает готовность к выполнению.

В APP_CONTEXT.md укажи действительные server alias/project/environment, источник REST/Kafka-схем, правила namespace, чтение результатов и подключение продукта к заглушкам. provider=sbermock — тип интеграции; mcp_server — **реальное имя подключения**, включая алиас. Не выбирай другой проект/сервер по сходству имени. Подробный стандарт не подключай постоянным @-импортом.

## REST

Назови method/path, значимые query/headers/body, приоритет, status/headers/body и согласованную задержку/ошибку. Включи в definition все поля, меняющие поведение, включая активность и порядок, если они есть в реальной схеме. Широкий matcher и безусловный 200 могут скрыть дефект. Перед изменением проверь пересечения с существующими правилами.

В verify положительная проба проверяет назначенный запрос и ответ. Отрицательная меняет значимое условие или явно заданные предусловия и проверяет отказ совпадения/альтернативу по контракту. План фиксируется **до** наблюдения. Expected не копируется из actual. Используй существующий MCP-способ проверки, не придумывай endpoint. Подготовка не доказывает продуктовый процесс или реальный внешний сервис.

## Kafka

Уточни фактический режим sbermock: реакция на вход, формирование ответа или явная публикация. Назови environment/cluster, входной/выходной topic, key/headers, сериализацию и версию схемы, payload и корреляцию. Не угадывай guarantees, порядок или допустимость дублей: они определяются контрактом/доступными наблюдениями.

В configure_only настройка правила не сопровождается тестовой публикацией. Если сама реальная MCP-операция создаёт запись **и** публикует сообщение, она не подходит этому режиму: найди поддерживаемый способ подготовки или верни блокер. В verify выполняй только назначенный input; положительная и отрицательная пробы используют разные correlation_id. Сохрани позицию начала/конца наблюдения (offsets/группа либо доступный серверный cursor) и время. Не выдавай старое событие за ответ нового запуска.

Отрицательный контроль отсутствия ответа требует полного назначенного window_ms. «Сообщения нет в окне» — ограниченный вывод. Если позиция/корреляция недоступна, не придумывай её; конфигурация может быть подготовлена, runtime-проверка остаётся неизвестной. Не сбрасывай offsets общей группы, не удаляй топики/сообщения и не делай безусловный resend при timeout. Пробы — только в разрешённых topic/namespace.

## Назначение и артефакты v2

Версия JSON-артефактов заглушек — **schema_version=2**; это не версия QA-событий/каталога/расследования. Относительные пути всех вложенных доказательств разрешаются от каталога результата назначения. При разных каталогах используй абсолютные пути. Сохраняй безопасные поля/фрагменты, без secrets и реальных персональных данных.

### assignment.json — зафиксированное намерение

| Поле | Содержание |
| --- | --- |
| `task_id`, `request_id`, `environment_id`, `provider`, `mcp_server`, `project_id`, `namespace` | Контекст задачи и конкретной цели; provider=sbermock, неизвестные значения недопустимы |
| `issued_at`, `mode`, `scenario_ids` | ISO-время с timezone; configure_only/verify; весь назначенный набор |
| `cases[]` | case_id, kind=REST/KAFKA, scenario_ids, requirement_source, purpose, definition, probes, allowed_operations, target_stub_id |
| `definition` | Непустой объект в **реальном формате провайдера**, значимые поля по контракту/схемам |
| `allowed_operations`, `target_stub_id` | Список created/reused/updated; для updated обязателен конкретный ID, иначе явный null или известный ID |
| `probes` | В configure_only допустим `{}`. Для verify — positive и negative с непустыми input/expected; при одинаковом input нужны различающиеся preconditions. Для Kafka дополнительно разные correlation_id и положительные целые window_ms |

Черновик подготавливает агент, зафиксированным файлом владеет координатор. Агент не редактирует собственные разрешения/ожидания. При изменении источника/схем координатор оценивает новый черновик и выдаёт новое назначение. Это протокол владения, а не криптографическая авторизация: локальные файлы не защищают от намеренного обхода.

Перед первой мутацией проверь зафиксированное назначение без обращения к MCP:

```bash
python3 scripts/validate_stub_assignment.py \
  --input /absolute/path/to/assignment.json --task-id QA-123 \
  --request-id QA-123-stubs-1 --scenario-id TC-REST --scenario-id TC-KAFKA
```

Код 0 проверяет структуру/ID, но не заменяет содержательную оценку координатора и не разрешает действие вне задания. Варианты дополнительных проб оформляются явно, неподдерживаемые ключи планов не игнорируются.

### profile.json — что было подготовлено

Содержит schema_version, семь полей контекста, assignment_sha256, prepared_at, verification_started_at, scenario_ids (весь набор), stubs. assignment_sha256 вычисляется `assignment_digest` из stub_contract.py: SHA-256 канонического JSON с sort_keys=True, ensure_ascii=False, allow_nan=False, без удаления полей. Изменение значимого назначения требует нового рассмотрения, а не механического обновления hash.

prepared_at — начало подготовки, не время последнего сохранения. verification_started_at — после всех мутаций/сверок; первичные readback и пробы не могут предшествовать ему. Для каждого stub:

- case_id и поля намерения kind/scenario_ids/requirement_source/purpose/definition/probes совпадают с назначением;
- stub_id — фактический ID, явный null допустим только для pending; operation=created/reused/updated/pending;
- resolved_at — время разрешения результата записи/переиспользования, после prepared_at и до verification_started_at; для pending — null;
- cleanup.action/reason: created→delete, reused→none, updated→restore, pending→inspect. Для updated обязательны previous_definition и before={artifact, sha256} со снимком до изменения; snapshot относится к тому же ID/контексту и времени до resolved_at.

### verification.json и первичные материалы

Содержит schema_version, семь полей контекста, assignment_sha256, profile_sha256 от точных байтов profile.json, limitations как в payload и checks по каждому case_id. Status:

- blocked: reason, готовность соответствующих зависимостей отсутствует;
- configured: readback={artifact,sha256}, reason — почему runtime не проверен;
- verified: readback, positive и negative как отдельные ссылки {artifact,sha256}. Для configure_only verified и пробные артефакты недопустимы.

Каждый первичный материал содержит schema_version=2, семь полей контекста, stub_id/kind и observed_at с timezone. Readback содержит действительно прочитанный definition. Все заданные **ветки** definition сравниваются целиком: лишнее условие внутри matcher/response не игнорируется. Дополнительные корневые метаданные провайдера допустимы; координатор проверяет, что не пропущено поле, влияющее на поведение.

Пробы содержат control=positive/negative, input/expected и при наличии preconditions из назначения, actual и passed=true только после наблюдения. Input/expected нельзя изменить внутри доказательства. Actual может иметь дополнительные объектные поля; проверяемые пустые объекты означают именно пустой объект, массивы сравниваются по длине/порядку. Если контракт допускает иной порядок, выбери подтверждённую нормализацию и опиши её по первичным материалам.

Kafka-проба дополнительно содержит capture={correlation_id, started_at, ended_at, position}. Позиция — непустой объект с фактическими offsets/cursor по доступному механизму, без выдуманных гарантий. Интервал после текущего readback, заканчивается не позднее observed_at; для negative длительность не меньше window_ms. Координатор проверяет фильтрацию по назначенной корреляции и нормализацию по безопасным фрагментам MCP/логов. Timestamp/hash сами по себе не доказывают свежесть или истинность.

## События и приёмка

| Событие | Значение и payload |
| --- | --- |
| `stubs_plan_ready` | Черновик без мутаций: контекст, assignment_artifact, scenario_ids (все), limitations; артефакт в artifacts |
| `stubs_configured` | Конфигурации прочитаны; контекст, profile_artifact, verification_artifact, configured_scenarios, blocked_scenarios, cleanup, limitations. Не содержит execution-ready scenario_ids |
| `stubs_ready` / `stubs_partial` | Готовность исполнения только для verify: тот же контекст/артефакты, scenario_ids (готовая часть), blocked_scenarios, cleanup, limitations |
| `blocked` | Полная блокировка: причина, попытки и уже созданные ID/доступные артефакты. Не потерять записи частичного сбоя |

Для configured непустая подготовленная часть вместе с заблокированной конфигурацией покрывает всё назначение. Для ready все заглушки всех сценариев verified; для partial непустые готовая/заблокированная части. Unverified-зависимость блокирует **все** связанные сценарии. Конфигурация и выполнение продукта учитываются отдельно.

```bash
python3 scripts/validate_qa_result.py \
  --input /absolute/path/to/result.json --task-id QA-123 \
  --request-id QA-123-stubs-1 --agent qa-stub-builder \
  --stub-assignment /absolute/path/to/coordinator-owned/assignment.json \
  --scenario-id TC-REST --scenario-id TC-KAFKA
```

Для plan-ready передаётся весь --scenario-id, но --stub-assignment не нужен: проверяется черновик из assignment_artifact, его успех не разрешает мутации. Для остальных новых событий внешний --stub-assignment обязателен: проверка по самому себе недопустима. Точные ID и цели сверяются с этим назначением, определения/пробы — с утверждёнными намерениями. JSON с повторяющимися ключами или нечисловыми/бесконечными значениями отклоняется.

CLI не вызывает MCP, не удостоверяет владельца, фактическую запись, бизнес-контракт, полноту matcher, delivery guarantees или содержательную правду логов. Координатор отвечает за эти оценки и за применимость к текущему запуску; результат проверки файлов не заменяет живую приёмку.

## Использование, очистка и миграция

Для запуска продукта передай профиль, namespace, ID и подтверждённое подключение интеграции. stubs_configured сам по себе не открывает выполнение: нужен verify либо явно иной согласованный способ подтверждения условий. Исполнитель фиксирует заменённый компонент и границы проверки в steps/actual_result/evidence; реальная интеграция не объявляется протестированной. Значимую конфигурацию включай в согласованную scope-карту отчёта, не подменяя прошлые условия текущими.

Очистку назначают после последнего зависимого прогона. Удаляются только created по сохранённым ID; reused сохраняются. Updated восстанавливаются по hash-проверенному снимку **после** проверки отсутствия новых чужих изменений и при доступном условном обновлении/защите от гонки. При конфликте сохраняй blocker, не восстанавливай поверх чужого изменения. Partial/pending требуют сверки всех уже созданных записей. План очистки не является её выполнением; сохраняй readback/остатки отдельно. Общий reset/удаление топиков/отключение MCP не используются.

Артефакты раннего v1 не принимаются как готовность новой схемой. Сохрани их историей, подготовь новое назначение v2 и перечитай фактические ID; не создавай заново только ради миграции. Повторные runtime-пробы — только для verify и конкретного недостающего факта. Версии каталога/остальных QA-событий не меняются. Поставка 1.7 включает новый протокол; ZIP 1.6 сохранён для отката.

Примеры: `examples/stubs/README.md` (проверка), `examples/stubs/configure-only/` (без проб), `examples/stubs/plan-result.json` (черновик). Все синтетические; определения не являются документацией sbermock. Результаты ревью и ограничения — STUBS_REVIEW.md.

# QA Agent как GIGACODE extension

Пакет 2.3.11 содержит `gigacode-extension.json`, отдельный контекст расширения,
14 ролей, 6 skills и команды `/qa`, `/qa:init`, `/qa:doctor`, `/qa:tasks`,
`/qa:resume`. Манифест подключает stdio MCP с пятью инструментами: read-only `qa_package_info` для обнаружения
абсолютного пути и версии, `qa_project_init` для подключения проекта и read-only
`qa_project_doctor` для диагностики, read-only `qa_tasks_list` и `qa_task_get`
для поиска/чтения задач. `/qa:init` и `/qa:doctor` используют MCP
в первую очередь; CLI остаётся fallback при недоступности соответствующего инструмента.
Внешние сервисы, Playwright, модель и авторизация настраиваются отдельно.

## Установка

Если QA нужен только одному проекту, сначала выберите область подключения по
[IMPORT_INTO_APP.md](IMPORT_INTO_APP.md#подключение-только-в-одном-проекте).
Локальный путь в `extensions install` задаёт источник пакета; запуск команды
из проекта сам по себе не задаёт проектную область установки.
Поддержка native project install или включения только в workspace должна быть
подтверждена `--help` вашей сборки. В текущей среде CLI отсутствует, такой режим
не проверен. Не добавляйте `--scope project` к командам GIGACODE без проверки
поддержки флага в его сборке.

Нужны Python 3.10+ в PATH и авторизованный GIGACODE CLI с поддержкой native
extensions, Markdown-команд, custom agents/skills paths и `${extensionPath}`
в аргументах MCP-сервера. Проверьте команды вашей сборки через `/help` и
`gigacode extensions --help`. CLI в среде разработки отсутствует: поддержка
всей комбинации функций целевой сборкой пока не подтверждена.

Установке передаётся локальная папка. Сначала клонируйте Git-репозиторий
отдельно от продуктового приложения, затем установите эту копию:

```bash
mkdir -p "$HOME/qa-tools"
git clone https://github.com/dimavrb/QaAgentGigacodeCli.git "$HOME/qa-tools/qa-agent"
gigacode extensions install "$HOME/qa-tools/qa-agent"
```

Прямую установку из Git URL целевая сборка не поддерживает. В интерактивном
менеджере также указывайте полный локальный путь, например:

```text
/extensions install /absolute/path/to/qa-agent
```

Точное имя команды менеджера сверяйте с `/help`. Для офлайн-установки распакуйте
проверенный ZIP и передайте путь к папке с `gigacode-extension.json`.
Автообновление требует сохранённого Git clone, зарегистрированного при install.

Для разработки `gigacode extensions link /absolute/path/to/qa-agent` применяется
только при наличии этой команды в установленной сборке. Не заменяйте native
установку ручной записью во внутренний registry CLI. Имя расширения — `qa-agent`.

Откройте GIGACODE в продуктовом проекте и выполните:

```text
/qa:init
/qa:doctor
/qa Составь тест-план по следующим требованиям: …
```

Если имена команд конфликтуют с проектными/пользовательскими, проверьте `/help`
и используйте имя команды расширения, показанное CLI. То же относится к
переопределённым ролям и навыкам. Изменение раскладки или `${extensionPath}`
не обходите выдуманными путями: зафиксируйте несовместимость конкретной сборки.

## Если агенты extension отсутствуют в /agents manage

В целевой установке пользователя глобальный `qa-agent` установлен, но QA-роли
не появляются в `/agents manage`. Это подтверждённое наблюдение для той сборки,
а не доказательство отсутствия extension agents во всех версиях GIGACODE.
В [официальной документации](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/subagents)
обнаружение ролей активного extension заявлено. В нашем манифесте уже есть
`agents: ".gigacode/agents"`; локальная проверка 14 файлов не подтверждает их загрузку CLI.

Сначала проверьте, что `qa-agent` активен в `/extensions`, метаданные
`qa_package_info` показывают ожидаемый установленный путь/версию, а проверка
выполняется в новой сессии. Если агенты по-прежнему отсутствуют, можно явно
разместить роли в проектной `.gigacode/agents/` при сохранении native-пакета
как источника общих документов, команд, skills и MCP.

Завершите активную QA-работу и закройте сессии GIGACODE. Из обычного терминала
используйте фактический `package_root` из `qa_package_info`, совпадающий с привязкой
проекта; не подставляйте вместо него исходный clone. Если проект ещё не подключён,
сначала выполните `qa_project.py init`. Для примерных абсолютных путей:

```bash
python3 /absolute/path/to/installed/qa-agent/scripts/qa_project.py init --project-root /absolute/path/to/app
python3 /absolute/path/to/installed/qa-agent/scripts/qa_project_agents.py --project-root /absolute/path/to/app
python3 /absolute/path/to/installed/qa-agent/scripts/qa_project_agents.py --project-root /absolute/path/to/app --apply
```

Второй вызов показывает план без записи. `--apply` устанавливает новые роли
и ведёт историю исходников. После обновления пакета неизменённые проектные
роли заменяются автоматически; локальные адаптации сохраняются. Если изменились
и адаптация, и исходник, конфликт одной роли не мешает обновлению остальных,
но общий статус остаётся `needs_attention` до рассмотрения.

`qa-start` синхронизирует управляемые роли до новой сессии и останавливает запуск
при нерешённых конфликтах. При прямом запуске `gigacode` синхронизация выполняется
явно. Копии из 2.3.10 без истории сначала принимаются отдельным `--apply`;
отличающиеся файлы без известной базы автоматически не заменяются.
Правила, хеши для принятия адаптаций, резервные копии и восстановление после
прерывания — [PROJECT_AGENT_UPDATES.md](PROJECT_AGENT_UPDATES.md).

В новой сессии из корня приложения проверьте `/agents manage`, вызов роли и
возврат координатору. Файловый статус `installed` не подтверждает загрузку CLI:
`live_agents_verified` остаётся false. Init пишет только три файла привязки/
контекста, синхронизация ролей выполняется отдельно. Настройки MCP и registry
GIGACODE утилита не меняет.

Этот способ подключает роли в конкретном проекте. Область активности остальных
компонентов глобального extension он не меняет. Для полного проектного
подключения используйте [IMPORT_INTO_APP.md](IMPORT_INTO_APP.md).

## Проектная область: как это устроено в Qwen Code

В Qwen Code документирована команда:

```bash
qwen extensions install /absolute/path/to/extension --scope project
```

`workspace` — синоним `project`, а без scope расширение включается на уровне
пользователя. Для уже установленного расширения доступны глобальное отключение
и включение в выбранном workspace:

```bash
qwen extensions disable extension-name
qwen extensions enable extension-name --scope workspace
```

Это команды Qwen Code; они не устанавливают наш GIGACODE-манифест и не являются
подтверждённым синтаксисом GIGACODE.
Источник — [документация Qwen](https://github.com/QwenLM/qwen-code/blob/main/docs/users/extension/introduction.md).

В [install.ts](https://github.com/QwenLM/qwen-code/blob/main/packages/cli/src/commands/extensions/install.ts)
`normalizeScope()` сводит project/workspace к project, `workspaceDir` получает
`process.cwd()`, а `installExtension()` получает initial activation с
`scope: 'workspace'` и `workspacePath: workspaceDir`. Установщик также сохраняет
предпочтение через `setExtensionScope()`.

Хранение пакета и область включения разделены: документация указывает
`~/.qwen/extensions`, а
[ExtensionStorage](https://github.com/QwenLM/qwen-code/blob/main/packages/core/src/extension/storage.ts)
строит каталог расширения через `getUserExtensionsDir()`.
В [extension-store.ts](https://github.com/QwenLM/qwen-code/blob/main/packages/core/src/extension/extension-store.ts)
есть `defaultActivation` и `workspaceOverrides`; пути workspace канонизируются.
Это механизм менеджера CLI, а не поле области в манифесте расширения.

Для нашей задачи подходящий образец — пакет в общем хранилище и включение
только в выбранном проекте. Отдельные версии на проект и изоляция обновлений
из этого не следуют. Перенос такого поведения в GIGACODE требует поддержки его
менеджером; файлы QA-пакета сами не добавляют ему новый флаг. Если такая поддержка
подтвердится, установка/переустановка должна сохранять выбранную область, а
приёмка — проверять отсутствие QA-компонентов в другом проекте.

## Файлы приложения

| Файл/каталог | Назначение | Обновление extension |
| --- | --- | --- |
| `.qa-agent/project.local.json` | Абсолютные корни и версия; игнорируется Git | Обновляется `/qa:init` |
| `.qa-agent/update.local.json` | Локальная Git-копия для `qa-start`; игнорируется Git | Сохраняется |
| `.qa-agent/APP_CONTEXT.md` | Подтверждённые сведения приложения; можно хранить в Git | Сохраняется |
| `.qa-agent/artifacts/` | Результаты и доказательства; игнорируются Git | Сохраняются |
| `.qa-agent-state/` | Managed-состояние; игнорируется Git | Сохраняется |
| Продуктовые кейсы/автотесты | Собственные каталоги приложения | Сохраняются |

Техническое подключение работает и без заполненного контекста. Неизвестные
данные не становятся подтверждёнными: уточняйте их для конкретной QA-задачи.
URL Jenkins/ТестОпс, ID проектов и credentials собираются при подготовке этой
инфраструктуры, а не при установке расширения.

MCP-вызовы требуют абсолютный `project_root` и вызывают `initialize()`/`doctor()`
напрямую, без запуска Python через subprocess:

```text
qa_project_init({"project_root":"/absolute/path/to/app"})
qa_project_doctor({"project_root":"/absolute/path/to/app"})
```

`qa_project_init` идемпотентен и пишет только `.gitignore`, `.qa-agent/APP_CONTEXT.md`,
`.qa-agent/project.local.json`, сохраняя существующий контекст. Для смены пути
первый вызов без `rebind` возвращает старый/новый пути: покажите их пользователю
и проверьте разрешение переноса. Только вторым вызовом той же MCP-сессии передайте
`rebind=true`; изменение путей или перезапуск сервера требует нового показа.
MCP проверяет наличие предшествующего ответа с путями, а показ пользователю
и разрешение переноса обеспечивает вызывающий агент.
Ошибки выполнения возвращаются как `isError` с текстом `QA project error: …`.
`needs_attention` у doctor — штатный результат с проверками, без `isError`.
Неверные аргументы, включая относительный путь, отклоняются до вызова функций.
Doctor не пишет файлы; единственный дочерний вызов — зонд `gigacode --version`.
Внешние системы и произвольные shell-команды инструменты не вызывают.

При недоступности MCP можно проверить локальную привязку вручную из любого cwd:

```bash
python3 /absolute/path/to/qa-agent/scripts/qa_project.py init --project-root /absolute/path/to/app
python3 /absolute/path/to/qa-agent/scripts/qa_project.py doctor --project-root /absolute/path/to/app
```

Диагностика возвращает 0 при готовности локальных файлов к проверке CLI,
1 при failed-проверках, 2 при ошибке структуры/чтения. Даже успешный результат
содержит `live_extension_verified=false`: видимость компонентов проверяется
в настоящей сессии. CLI `--rebind` требует того же предварительного показа
и разрешения переноса. Ошибку MCP не обходите переключением на CLI.

## Обновление и откат

Сохранённые задания: `/qa:tasks`, `/qa:resume QA-123` либо пустая `/qa` для выбора.
Стандартные пути, CLI fallback и проверки восстановления — [TASK_STORAGE.md](TASK_STORAGE.md).
Список читает реестры проекта; задачи не хранятся в package root и не выбираются
по памяти чата. Git не переносит игнорируемые локальные реестры другому пользователю.

Предпочтительный запуск — `qa-start`: перед новой сессией он проверяет Git,
выполняет fast-forward при повышенной версии, запускает штатное обновление
локальной установки и освежает привязку проекта. Контекст и доказательства
сохраняются. Активные сессии/managed-задачи откладывают замену пакета.
Настройка, отказы и пределы контроля — [AUTO_UPDATE.md](AUTO_UPDATE.md).

Для ручного обновления завершите активную работу и сохраните предыдущую
установленную копию/проверенный ZIP, commit и локальные адаптации вне пакета.
Обновите тот же локальный clone командой
`git -C /absolute/path/to/qa-agent pull --ff-only origin main`, затем выполните
`gigacode extensions update qa-agent`, если сборка поддерживает такое обновление.
Если CLI требует сначала `uninstall`, используйте переустановку ниже.
Менеджер получает содержимое из зарегистрированной локальной папки.
После успешной установки откройте новую сессию, повторите `/qa:init` и `/qa:doctor`.
При переносе пути проверьте расположение и разрешите rebind;
CLI требует `--expected-binding-sha256` из первого показанного ответа.
При изменении инструкций начните новый managed-план; старые hashes не пересчитывайте.

### Ручная переустановка, если update требует uninstall

В целевой установке получен отказ на `extensions update qa-agent` с требованием
сначала удалить расширение. Для такой сборки обновляйте через `uninstall` → `install`.
Это наблюдение пользователя; живой прогон этой сборки в репозитории не выполнен.

1. Закройте все сессии GIGACODE и завершите активные QA-назначения во всех проектах.
   Сохраните старый пакет, настройки расширения и локальные адаптации отдельно.
   Контекст приложения, auth/MCP, задачи, кейсы и доказательства должны находиться
   вне удаляемого каталога расширения. Исходный Git clone также храните отдельно.
2. Если автообновление ещё не начиналось, обновите исходный clone командой выше.
   Если `qa-start` уже оставил pending, сохраните его и recovery snapshot; используйте
   именно подготовленный clone с commit из pending, без нового pull или смены ветки.
3. Сверьте синтаксис через `gigacode extensions --help`. Выполните команды по очереди;
   после ошибки остановитесь. Для стандартного расположения clone:

   ```bash
   gigacode extensions uninstall qa-agent
   gigacode extensions install "$HOME/qa-tools/qa-agent"
   ```

   Install получает полный локальный путь к исходной папке с `gigacode-extension.json`,
   а не путь к удалённой установленной копии. Повторный update после uninstall не нужен.
4. Проверьте версию и фактический путь установки в менеджере. При сохранённом pending
   и прежнем пути установленной копии выполните `qa-start --update-only`: он сверит
   содержимое и завершит сохранённую активацию без повторного update. Не удаляйте
   вручную update-state.json/recovery.json и не обходите pending через `--no-update`.
   Если путь изменился либо install завершился частично, сначала восстановите
   согласованную установку по [UPDATE_SAFETY.md](UPDATE_SAFETY.md); не подменяйте binding.
5. В новой сессии из папки приложения выполните `qa_package_info`, `/qa:init`,
   `/qa:doctor`, проверьте роли, skills, команды и MCP. Сохранность настроек
   менеджера после uninstall/install требует проверки на вашей сборке.

`qa-start` не выполняет uninstall автоматически: при таком отказе он показывает
ответ CLI, сохраняет намерение и резервную копию и не открывает новую QA-сессию.
При неудачной переустановке верните предыдущую проверенную поставку штатным
менеджером и сверьте его registry и проектную привязку по UPDATE_SAFETY.md.

Для отката установите предыдущий проверенный extension и обновите локальную
привязку тем же порядком. До 2.1.4 native extension не поставлялся: откат на 2.1.3
требует прежнего способа подключения по `IMPORT_INTO_APP.md`.

## Пилот на целевой сборке

Защищённое обновление и независимый rollback — [UPDATE_SAFETY.md](UPDATE_SAFETY.md).
Проверьте CI gate, recovery helper/snapshot, остановку active work и native registry
после восстановления файлов. Эти проверки выполняйте в отдельном тестовом профиле.

Проверьте локальную установку в два отдельных проекта, видимость всех 14 ролей/6 skills
и пяти команд, список всех пяти MCP-инструментов, запуск `qa_package_info`
с правильным корнем, MCP-вызовы `/qa:init`,
`/qa:doctor`, список задач и `/qa:resume` после новой сессии, одну задачу `/qa`.
В проекте должны быть собственные `docs/` и
`scripts/`: QA-стандарты берутся из extension. Обновите тестовую поставку и
убедитесь, что `qa-start` получает новую версию, а контекст, кейсы, auth и результаты сохранены. Зафиксируйте сборку
CLI, version/commit пакета, реальные имена компонентов и ограничения tools.
Локальные тесты и ZIP manifest не заменяют этот пилот.

Поддержка extension agents/skills описана в официальных
[агентах](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/subagents)
и [skills](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/skills).
Примеры native-манифеста — [Sber ID Frontend](https://gitverse.ru/sber_id/frontend_sdd/content/master/gigacode-extension.json);
установки/link — [Gigadoc](https://github.com/travinov/gigadoc-extension).
Примеры являются источниками синтаксиса, а не подтверждением нашей live-приёмки.

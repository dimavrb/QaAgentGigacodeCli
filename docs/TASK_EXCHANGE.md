# Состояние задачи и проверяемая передача между агентами

Для новой QA-задачи координатор создаёт один реестр `.qa-agent-state/tasks/<task>/task.json` через `scripts/manage_task.py`. Он хранит этапы, назначения, владельцев, принятые результаты, ревизии, вопросы и события готовности. Реестр находится вне заменяемого пакета. В установленном приложении команды используют `qa-agent/scripts/`.

Изменения реестра выполняются под файловой блокировкой и публикуются атомарно. Команды координатора требуют `--expected-revision`: при конкурентном изменении нужно перечитать `show`, проверить применимость своего действия и повторить его с новой ревизией. Не редактируй реестр вручную и не повышай ревизию только ради обхода отказа. Ошибка проверки не публикует результат или передачу.

`show` по умолчанию выдаёт краткую сводку этапов, владельцев, путей результатов и вопросов. Полные назначения, контрольные суммы и история событий доступны через `show --full`; не загружай их в контекст на каждом шаге. Передача содержит выводы и ссылки на источники; подробные payload остаются в исходных отчётах.

## Назначение и результат

1. init --criteria создаёт реестр с ID, названием и согласованными критериями задачи по TASK_ACCEPTANCE.md. Повтор идентичного init читает существующее состояние; старый протокол требует явного --legacy-no-criteria.
2. Сохрани JSON назначения: `task_id`, новый `request_id`, `agent`, `stage`, `goal`, `acceptance_criteria` (непустой список), `stop_condition`, `expected_artifact`, `result_path`. `inputs` содержит пути неизменяемых исходных материалов, `depends_on` — ID принятых назначений. `scenario_ids` перечисляет весь назначенный набор, когда его требует QA-валидатор. Для расследования или заглушек укажи также `investigation_state` или `stub_assignment`. Пути назначения разрешаются относительно JSON назначения и сохраняются абсолютными.
3. `assign` регистрирует назначение. Один `request_id` и один `result_path` используются ровно одним назначением. Для уточнений, повторов и исправления уже зарегистрированного результата создай новый ID и отдельный файл; историю сохраняй. `stage` объединяет последовательные ревизии одного этапа, например `plan`.
4. `prepare` проверяет принятые источники, их зависимости и контрольные суммы входных файлов, затем резервирует единственную передачу (`dispatching`). Он возвращает краткое назначение, ссылки, выводы источников, ревизию и `delivery_id`. Сохрани этот вывод отдельным файлом и передай исполнителю его `result`. Повторный `prepare` для этого назначения запрещён.
5. Через механизм делегирования GIGACODE запусти исполнителя с подготовленным назначением. После получения фактического ID запиши его через `start --owner-task-id ... --delivery-id ...`. Для синхронного механизма без ID можно зарегистрировать готовый результат непосредственно из `dispatching`; не выдумывай ID GIGACODE. При потерянном подтверждении запуска сначала проверь существующего исполнителя. Резервирование не доказывает, что запуск состоялся.
6. Исполнитель сохраняет QA-отчёт в `result_path`; длинные материалы остаются отдельными файлами. Пути в `artifacts` разрешаются относительно `artifact_base`, по умолчанию — каталога отчёта. Для разных репозиториев лучше использовать абсолютные ссылки. Специализированные валидаторы сохраняют прежние правила разрешения своих ссылок относительно отчёта.
7. `submit` вызывает полный `validate_qa_result.py` с ID и дополнительными параметрами из назначения. Проверяются также доступность и SHA-256 локальных файлов, включая входы и изменённые файлы автоматизатора. Только после успеха появляется `result_ready` и статус `reported`. Повтор неизменённого результата не создаёт дубликат события. HTTP-ссылки сохраняются как `remote_artifacts`: их актуальность и доступность координатор проверяет отдельно.
8. Координатор читает доказательства и выполняет `review --decision "..."`; команда повторно проверяет результат и фиксирует содержательное принятие. `--changes-requested` сохраняет замечания. Принятие означает оценку именно этого результата; принятие `blocked` или `needs_*` не разрешает зависимое исполнение. Координатор выбирает подходящий маршрут и передаёт только готовую часть.
9. depends_on по умолчанию требует готовности. Для информации диагностики явно задают dependency_modes с context. Partial допускает только явно готовые scenario_ids потребителя. В обоих режимах проверяются принятие, неизменность и транзитивные зависимости. Координатор выполняет assess по критериям задачи; finish запрещён при непринятых обязательных критериях и прежних незавершённых условиях. ready_for_review требует независимого review_passed для точной ревизии автора. Смысл доказательств проверяет координатор.

`fail` записывает подтверждённый сбой запуска/работы и причину. Команда сама не останавливает агента: сначала убедись, что прежний исполнитель закончил или остановлен. `dispatching` после перезапуска не превращается автоматически в `queued`; неизвестный результат запуска нельзя повторять вслепую.

`depends_on` означает, что результат остаётся действующим основанием следующего шага. Для контекста исправления старого отчёта используй его неизменяемый JSON/diff в `inputs`; не объявляй устаревшую готовность зависимостью. Изменяемые журналы и файлы текущего кода сохраняй отдельными снимками по принятой ревизии, если они должны оставаться доказательствами прежнего результата. Для `investigation_state`/`stub_assignment` принятого отчёта также сохраняй проверяемую версию файла; следующая ревизия состояния не должна перезаписывать доказательство уже принятой ревизии. Реестр хранит ссылки и контрольные суммы, но не архивирует произвольные рабочие файлы автоматически.

Пример всех операций без настоящих агентов и внешних систем — [examples/task-exchange](../examples/task-exchange/README.md).

## События и ожидание

События хранятся в той же атомарной записи, что и состояние, и имеют монотонный `event_id`. Основные: `assignment_ready`, `handoff_prepared`, `assignment_started`, `result_ready`, `result_accepted`, `changes_requested`, `assignment_failed`, `questions_waiting`, `answers_ready`, `answers_applied`, `task_completed`.

```bash
python3 scripts/manage_task.py --state .qa-agent-state/tasks/QA-123/task.json wait --after 0 --timeout 60
```

`wait` проверяет реестр и возвращает неподтверждённые события, появившиеся после указанного ID. Таймаут от 0 до 60 секунд возвращает пустой список, а не ответ пользователя и не разрешение продолжить зависимую работу. Используй фоновое ожидание, если инструмент его поддерживает, и продолжай независимые проверки. После обработки события выполни `ack --event-id ... --expected-revision ...`. Подтверждение получения не принимает результат и не закрывает вопрос. После перезапуска неподтверждённые события можно получить снова; обработка должна учитывать ID и уже сохранённое состояние. Не сдвигай курсор через необработанные события.

Это локальная очередь готовности для работающего координатора. Она не вызывает инструменты GIGACODE вместо модели и не пробуждает завершённый чат. Среда с ожиданием фонового процесса может вернуть управление по событию; в среде без такой поддержки пользователь возобновляет чат одной короткой фразой.

## Вопросы пользователя

```bash
python3 scripts/questionnaire.py serve \
  --input artifacts/questions/QA-123/questions.json \
  --answers artifacts/questions/QA-123/answers.json \
  --task-state .qa-agent-state/tasks/QA-123/task.json \
  --expected-revision 5 --open --once
```

`--task-state` регистрирует пакет вопросов. `--expected-revision` обязателен для нового пакета; при перезапуске идентичного уже зарегистрированного пакета его можно не задавать. ID задачи должен совпадать с реестром. Отправка сначала атомарно сохраняет ответы, затем записывает `answers_ready`; интерфейс подтверждает успех только после обоих шагов. Если запись события не удалась, повтор безопасен. Перезапуск сервера с уже сохранённым ответом восстанавливает пропущенное уведомление без повторного ввода.

Для самостоятельного HTML: зарегистрируй пакет командой `questions`, затем сохрани скачанный ответ по зарегистрированному пути и вызови `notify-answers --input ... --answers ...`. Эта же команда восстанавливает уведомление вручную. Изменённый или чужой пакет не принимается.

`questionnaire.py wait --input ... --answers ... --task-state ...` ждёт конкретный
пакет до 1200 секунд с проверкой раз в 60 секунд. Уже сохранённые ответы возвращаются
сразу; пропущенное answers_ready восстанавливается автоматически. Таймаут не
закрывает вопросы и не выполняет apply-answers. Обычный manage_task.py wait сохраняет
прежний краткий режим ожидания любых событий; для формы используй новый waiter.

После `answers_ready` прочитай ответы и оцени решение, затем выполни `apply-answers --questionnaire-id ... --decision ...`. В следующем назначении укажи `questionnaire_ids` с ID применённых пакетов: prepare передаст проверенные ссылки на ответы, решение координатора и оставшиеся открытые ID. Файлы вопросов и ответов автоматически добавляются к неизменяемым входам этого назначения. Неприменённый или изменённый пакет не допускается к передаче.

Обновление плана/карты сохраняй новой ревизией в новых файлах. Не изменяй принятый отчёт, который использовался как источник вопросов: исходный пакет должен оставаться проверяемым. «Пока не знаю» сохраняет открытые ID. Новый раунд с теми же стабильными ID и новым ID пакета может уточнить прежние ответы; применение и источник решения сохраняются историей. Обработка событий не выбирает бизнес-ответ за пользователя.

## Отдельный репозиторий автотестов

Перед запуском зарегистрируй и подготовь назначение `qa-test-automation`. Его `result_path` совпадает с `--output`, `artifact_base` — с `--repo`. Передай `--task-state` в `run_test_automation.py`: runner проверяет подготовленное назначение до запуска GIGACODE, передаёт ему источники, записывает владельца `runner-pid:<PID>` и автоматически регистрирует проверенный результат или сбой. Это идентификатор процесса, а не ID для `send_message` GIGACODE. Содержательное принятие остаётся отдельным действием координатора.

Прежний `--state` runner сохраняет техническое состояние конкретного запуска и защиту от повторного request_id; investigation-state, browser-pool и другие специализированные файлы сохраняют свои предметные детали. Общий реестр связывает их путями и не дублирует журналы, каталог кейсов или большие отчёты. Без `--task-state` прежний standalone-режим runner и формы сохраняется; координатор нового маршрута обязан передавать этот параметр.

## Самопроверка автора

Новые assign получают self_review_required=true. prepare передаёт абсолютный self_review_guide; исполнитель сохраняет итог по SELF_REVIEW.md в окончательном отчёте. submit требует четыре проверки и действующие ссылки на отчёт/назначение. Формат не подтверждает смысл: limited допускает передачу честного частичного результата на review, но обязательная непроверенная готовность не принимается. Исправленный после submit результат требует нового назначения. Старые записи без флага совместимы.

# Модель поведения, комбинации и контрпримеры

Применяй для содержательного выбора и ревью сценариев в существующем маршруте TEST_PLAN.md. Аналитик или автор плана создаёт модель, координатор независимо оценивает источники и контрпримеры. Отдельная роль и дополнительный цикл не нужны. Простой критерий можно оставить одной строкой ранней карты.

## Компактная модель поведения

Выбирай только подходящее представление:

- Таблица решений: условия роли, владения, состояния → разрешённое действие и наблюдаемый результат.
- Состояния и переходы: исходное состояние, событие → новое состояние/отказ; отдельно важные запрещённые переходы.
- Обязательные свойства: что должно сохраняться при действии, например принадлежность результата пользователю или отсутствие повторного списания — только если это подтверждено источником.

Каждое правило получает стабильный rule_id, requirement_id, точный source, статус confirmed/inferred/unknown и связанные scenario_ids. Используй существующие ID анализа. Unknown имеет source и ожидаемое поведение null; inferred — ссылку на основание вывода. Для обоих нужен вопрос, блокирующий проектирование затронутого сценария. Модель не создаёт новые требования из поведения текущей реализации.

Модель хранится компактной таблицей в плане или отдельным связанным артефактом. Это правила продукта, не копия подробных шагов каталога. При изменении правила перепроверь зависимые сценарии и комбинации. Непокрытая строка остаётся явным пробелом; конфликт правил требует ответа, а не произвольного выбора. Не создавай сразу три модели для одной небольшой задачи.

## Проверяемые комбинации

Когда независимых параметров много, выдели конечные классы значений, ограничения реализуемости и обязательные комбинации. Источники классов и ограничений сохраняй рядом с моделью. Запрещённое продуктом действие обычно является допустимым негативным тестовым входом: не исключай его как «невозможное» ради сокращения набора.

Для независимых параметров используй pairwise (strength=2); известные риски взаимодействия трёх и более условий задавай через interaction_groups и отдельные обязательные seeds. Для последовательности событий используй модель переходов: попарные входные значения не проверяют порядок событий. Границы и критерии приёмки сохраняются независимо от попарного покрытия. Не обещай отсутствие дефектов или математически минимальное число кейсов.

Локальный инструмент scripts/generate_combinations.py строит детерминированный набор по конечной модели. Он перебирает допустимые полные назначения, сохраняет seeds и жадно добавляет строки, пока не покрыты требуемые взаимодействия. Ограничение размера защищает от чрезмерного перебора; при превышении раздели модель по реальным независимым областям либо используй специализированный генератор. Не уменьши strength или обязательные seeds молча.

```bash
python3 scripts/generate_combinations.py --model examples/test-design/combinations.json --output /tmp/combinations.json
python3 scripts/generate_combinations.py --model examples/test-design/combinations.json --check /tmp/combinations.json
```

Результат содержит combination_id, values и scenario_ids. Генерация создаёт проектные строки, не готовые тест-кейсы и не доказательства выполнения. Без --catalog проверяется только математика. Для готового набора --catalog теперь требует конкретные связи условий, правил и наблюдений, описанные ниже. Прежние отчёты с одними TC-ID нужно дополнить; обычные каталоги без комбинаций сохраняют прежний контракт. Не заявляй полноту планирования, когда проверена только математика комбинаций.

### Связь строки с проверкой

Добавь в конечную модель behavior_rules. Правило содержит rule_id, requirement_id,
source, status, conditions (частичное назначение факторов; {} — все строки) и
expected_result. Для ready применимы только confirmed с источником и непустым
ожиданием. Все правила согласованной области должны получить хотя бы одну строку,
а каждая строка — связи для всех применимых правил. Если pairwise не выбрал
условия существенного правила, добавь обязательный seed. Inferred/unknown оставляют
затронутое покрытие blocked и вопрос; конфликт ожиданий оценивает reviewer по источникам.

Каждая ready-строка сохраняет scenario_ids и непустые scenario_bindings:

```json
{
  "binding_id": "B-C-ACCESS-DENIED",
  "scenario_id": "TC-ACCESS",
  "parameter_set_id": "P-C-ACCESS-DENIED",
  "rule_id": "RULE-2",
  "factor_refs": {
    "role": "/preconditions/1",
    "owner": "/preconditions/2",
    "channel": "/preconditions/3",
    "browser": "/preconditions/3"
  },
  "expected_refs": ["/steps/0/expected_result"]
}
```

binding_id уникален во всём наборе и остаётся стабильным при адресном исправлении.
scenario_ids равен множеству реально связанных кейсов. factor_refs покрывает каждый
фактор JSON-указателем относительно выбранного кейса на preconditions[i] или
steps[i].name; ссылка на метаданные не является подготовкой. expected_refs указывает
на один или несколько steps[i].expected_result, которые наблюдают применимое правило.

Для отдельного статического кейса добавь combination_values, точно равный полному
назначению строки. Указанное значение должно присутствовать отдельным словом в
связанном условии/действии. Это проверяемый текстовый якорь, смысл проверяет reviewer.
Один статический кейс с фиксированными условиями не покрывает несовместимые строки.

Для общего параметризованного кейса вместо combination_values добавь parameter_sets:
каждый набор имеет уникальный parameter_set_id, полные values и необязательный
словарь дополнительных строковых parameters (например record_id и observation).
parameters не может переопределять факторы. В condition/action по factor_refs
должен реально использоваться {{имя_фактора}}. Остальные параметры также подставляются
как {{имя}}; неразрешённые подстановки в условиях, действиях и ожиданиях запрещены.
Связь обязательно выбирает точный набор. Ожидание может быть общей подтверждённой
строкой или {{observation}} с отдельным значением для набора; reviewer сверяет его
с правилом. Добавление значений в parameter_sets без их использования не даёт покрытия.

Код проверяет совпадение значений и указателей, применимость правил, полное покрытие
и отсутствие неразрешённых подстановок. Он не решает, верно ли естественным языком
описаны права, подготовка, конфликт правил и наблюдение. Для этого требуется
независимая оценка каждой связи, включая контрпример возможного ложного успеха.

### Проверяемая приёмка

Автор передаёт в payload.combination_coverage список ready-bundle:

```json
{"bundle_id":"access", "model_artifact":"combinations.json",
 "combinations_artifact":"ready-combinations.json", "catalog_artifact":"ready-cases.json"}
```

Пути разрешаются относительно QA-result. При наличии test_cases_artifact bundle
обязан использовать тот же файл каталога. Источники правил и scope_sources — локальные
текстовые снимки, пути относительно файла модели; URL оригинала можно сохранить внутри снимка.
validate_qa_result проверяет bundle; реестр автоматически фиксирует хеши модели,
строк, каталога и источников, даже без повторения вложенных ссылок в artifacts.
Проектные/заблокированные строки передавай обычными artifacts и картой вопросов,
без объявления их ready через combination_coverage.

До назначения зафиксируй критерий kind=combination_coverage, combination_bundle_id,
model_sha256 согласованной модели (generate_combinations.fingerprint) и required_reviews.
Пример — examples/test-design/coverage-criteria.json. Хеш не позволяет заменить
согласованную модель ослабленным strength, исключениями или удалёнными правилами.
Изменение scope требует решения и нового согласованного критерия, не правки автора.

Каждое обязательное независимое ревью точного author-target содержит checks критерия
и combination_checks: bundle_id, binding_id, status=passed|failed|unknown, note,
evidence. Reviewer объясняет соответствие условий, источника правила и различающего
наблюдения; общий verdict не заменяет строки. Все связи выбранного bundle должны
получить passed в каждом обязательном направлении. Неизвестное ожидание/подготовка
сохраняется явно; failed требует замечания, unknown — недоступного условия.
assess выбирает ровно один авторский bundle с заданным ID, все обязательные reviewers
и локальные доказательства. Частичный набор checks, другой target/владелец автора
или устаревшие хеши не подтверждают критерий. Автономный review-cycle применяет тот
же барьер перед принятием автора, finish повторно проверяет оценку и хеши.

Это приёмка проектирования. Подстановка параметров не создаёт реальные данные,
не запускает продукт и не доказывает выполнение каждой строки. Для исполнения
материализуй выбранные наборы в отдельные сценарии/наблюдения с устойчивыми ID
и используй отдельные критерии scenario_execution; одно наблюдение TC-ACCESS
не доказывает запуск девяти конфигураций. Простой кейс без многомерного риска
не требует этого bundle или дополнительного ревью комбинаций.

## Ревью через контрпримеры

При первом ревью или изменении поведения выбери несколько наиболее существенных возможных ошибок из требований, рисков и истории дефектов. Для каждой зафиксируй: описание неправильного поведения, rule/requirement_id, условия, scenario_id и точный наблюдаемый результат, который должен его обнаружить. Это гипотетические ошибки, не найденные дефекты.

Пример: «Список содержит свои оплаченные заказы и один чужой оплаченный. Какая проверка обнаружит именно чужого владельца?» Проверка только наличия своих записей или числа строк не отвечает на вопрос.

Если сценарий не обнаруживает контрпример, запиши пробел/замечание и адресное исправление. Если покрывает — укажи конкретную проверку, не только номер кейса. Для известного выполненного теста с доступной изоляцией можно перейти к контролируемой ошибке по AUTOTEST_QUALITY.md; запрос только на план не разрешает запуск продукта. Разбор контрпримера не подтверждает весь план: проверка критериев, источников и структуры сохраняется.

После локального ответа или правки ревьюй затронутые правила, комбинации и контрпримеры с зависимостями. Не переписывай принятую неизменившуюся часть. Сохрани ревизию и короткую таблицу замечаний рядом с планом; пользователю сообщай только существенный пробел и нужное решение.

# Приёмка задачи, готовность зависимостей и трассировка

Первый пакет добавляет машинные проверки полноты задачи и связей доказательств. Смысл результатов по-прежнему оценивает координатор. Контракт QA-отчёта сохраняется.

## Согласованные критерии

До первого назначения зафиксируй согласованный объём следующим объектом JSON:

```json
{
  "schema_version": 1,
  "criteria": [
    {"criterion_id": "C-FILTER", "description": "Согласованные сценарии фильтра проверены с доказательствами", "source": "requirements.md#R-1", "required": true},
    {"criterion_id": "C-AUTOTEST", "description": "Изменённый автотест проверен независимо", "source": "Согласованный объём", "required": true, "required_review_agent": "qa-autotest-reviewer"}
  ]
}
```

Для проектной установки используй локальный `scripts/qa_task_create.py --criteria`
по [TASK_STORAGE.md](TASK_STORAGE.md). Согласованные критерии передаются файлом;
реестр создаётся внутри проекта. Повтор идентичных параметров сохраняет прежние
назначения и ревизию; расхождение критериев требует отдельного рассмотрения.

```bash
python3 scripts/manage_task.py --state .qa-agent-state/tasks/QA-123/task.json init --task-id QA-123 --title "Проверка фильтра" --criteria /absolute/path/criteria.json
```

`required` — обязательный bool; ID не повторяются. `criterion_ids` назначения связывает работу с критериями задачи; неизвестный ID отклоняется. Прежний `acceptance_criteria` сохраняет конкретные условия исполнителя. `prepare` возвращает `task_criteria` и `trace_context`; передай их исполнителю. Доказательства сохраняются в обычном QA-отчёте.

`set-criteria --input ... --expected-revision ...` доступен до первого назначения. Изменение согласованного объёма после начала работы требует нового реестра с новой задачей и ссылками на применимые прежние результаты. Ограничение первого пакета защищает от удаления неудобного критерия перед finish.

## Готовность для исполнения и информационный контекст

Для обязательного исполнения используй типизированный критерий:

```json
{"criterion_id":"C-RUN","description":"Оба сценария выполнены","source":"Согласованный scope","required":true,"kind":"scenario_execution","scenario_ids":["TC-1","TC-2"],"execution_context":{"environment_id":"test","product_version":"42"}}
```

`kind` по умолчанию — `judgment` (прежняя содержательная оценка). `scenario_execution`
требует каждого ID со статусом passed/failed, согласованных environment_id и
product_version, а при заданном execution_context — точного совпадения. blocked/not_run
не подтверждают выполнение. Найденный продуктовый дефект подтверждает факт исполнения,
но не соответствие продукта требованиям. Такой критерий не заменяет отдельный
критерий соответствия и содержательное решение о qa_outcome.

При повторах assessment явно задаёт `scenario_sources`, например
`{"TC-1":"feature-1","TC-2":"feature-2"}`. Неоднозначные повторные записи не
выбираются автоматически. Старое наблюдение с другой сборки не переносится в
обязательный набор новой сборки. Вложенные scenario_results[].evidence и доступные
локальные expected_source входят в контрольные суммы реестра.

Для одного/двух содержательных направлений задавай `required_reviews` согласно
[CONTENT_REVIEW.md](CONTENT_REVIEW.md). Приёмка проверяет всех выбранных авторов,
точные targets и разные owner_task_id направлений, включая старую форму зависимости
qa-autotest-reviewer. Один автор не может принять собственный результат.

Для проверки сочетаний используй kind=combination_coverage с combination_bundle_id,
model_sha256 согласованной модели и обязательным required_reviews. Один выбранный
автор передаёт ready-bundle, каждое направление ревью подтверждает все binding_id
через combination_checks. Код перепроверяет условия, параметры, применимые правила,
наблюдения и хеши на assess/finish. Это критерий проектирования; исполнение остаётся
отдельным scenario_execution. Формат — [TEST_DESIGN.md](TEST_DESIGN.md).

Если направление ревью требует нового запуска, добавь required_reviews[].execution
по [REVIEW_EXECUTION.md](REVIEW_EXECUTION.md): check_id, tool, точные expected_arguments
и expected_result; для backend-job также run_started_pointer. Reviewer получает
собственный gateway и сохраняет execution_checks с первичными OBS-квитанциями.
assess/finish требуют всех свежих наблюдений именно этой попытки, владельца и target.
Старый лог автора и generic passed такой критерий не закрывают.

`depends_on` по умолчанию требует принятого, неизменённого и готового результата. Для диагностики назначение может явно задать:

```json
{"depends_on": ["QA-123-env-1"], "dependency_modes": {"QA-123-env-1": "context"}}
```

`context` позволяет прочитать принятый blocked/needs_*/раннюю карту/замечания как информацию. Это не подтверждает доступ и готовность среды. Содержательное принятие, хеши и транзитивные зависимости проверяются в обоих режимах на assign, prepare, start, submit и review.

Для environment/data/stubs partial обычная зависимость допустима только при непустом scenario_ids потребителя, полностью входящем в явно готовый набор. Для feature_test_complete выполненными считаются passed/failed; blocked/not_run не подтверждают выполнение. Найденный дефект может быть источником отчёта, но не становится успешной проверкой продукта.

ready_for_review готов для qa-autotest-reviewer; stubs_configured — для следующего шага qa-stub-builder. Произвольное зависимое исполнение эти события не разрешают. Для других диагностических маршрутов укажи context. Проверка готовности не заменяет согласование конкретной операции и условий среды.

## Оценка критериев

После принятия отчётов координатор сохраняет пакет:

```json
{"assessments": [{"criterion_id": "C-FILTER", "status": "verified", "decision": "Сопоставлены сценарии и фактические результаты", "request_ids": ["QA-123-feature-1"], "evidence": ["/absolute/path/feature-result.json", "/absolute/path/evidence.txt"]}]}
```

```bash
python3 scripts/manage_task.py --state .qa-agent-state/tasks/QA-123/task.json assess --input /absolute/path/assessments.json --expected-revision 8
```

Статусы: verified, failed, unknown, not_applicable. Для verified/not_applicable нужны принятое назначение с соответствующим criterion_ids, локальное доказательство из его проверенных артефактов и конкретное решение. CLI разрешает относительные пути evidence относительно файла assessments; библиотечному вызову передавай абсолютные пути. HTTP-ссылки не заменяют проверенное локальное доказательство.

Эти статусы доступны и для scenario_execution. failed/unknown можно сохранить
без результатов и доказательств, если исполнение не подтверждено; обязательный
критерий остаётся незакрытым. not_applicable требует принятого результата и
доказанного объяснения; finish повторно проверяет их хеши. Проверка фактических
статусов/контекста сценариев применяется при verified.

verified означает выполненность критерия задачи. Например, доказанное исследование может завершиться с qa_outcome=defect_confirmed. Ошибка продукта хранится в отчёте; она не означает невыполненность самого исследования. failed/unknown обязательного критерия запрещают завершение. not_applicable требует доказанного объяснения неприменимости и сохраняется в истории; это не успех продукта.

required_review_agent при verified требует результата автора и принятого результата нужной независимой роли, зависящего от автора. Для автотестов требуется review_passed именно для current_revision автора. Независимо от флага критерия, ready_for_review не позволяет finish без такого review.

Оценки публикуются атомарно: ошибка одной записи отклоняет весь пакет. Реестр сохраняет хеши результатов и доказательств; finish повторно проверяет их и все обязательные критерии. Координатор читает материалы: наличие ссылок само по себе не доказывает истинность вывода.

## Совместимость

Старые реестры без критериев продолжают работать и явно показывают acceptance_mode=legacy. Новый CLI требует --criteria либо --legacy-no-criteria. Последний предназначен для старого протокола; полноту задачи в нём контролирует координатор. Библиотечный init_task без criteria сохраняет прежнюю совместимость. Для обычных новых задач legacy не выбирают.

Готовность проверяется и для старых назначений: отсутствие dependency_modes означает ready. Ранее разрешённая передача blocked может теперь отклоняться. Зарегистрированное назначение не редактируют ради обхода; создают новое корректное назначение. Старую задачу с уже начатыми назначениями не переводят в режим критериев автоматически.

## Базовая трассировка

События реестра атомарно сохраняют trace_id, task_id, request_id, роль, этап, attempt_id, VERSION и хеш инструкций координатора. attempt_id появляется при резервировании передачи; queued не означает запуск. Новые поля не заменяют delivery_id и правила владения. При исходниках после релиза различай VERSION и хеш фактических инструкций.

```bash
python3 scripts/export_task_trace.py --state .qa-agent-state/tasks/QA-123/task.json --output /tmp/QA-123.trace.jsonl
```

Экспорт создаёт новый JSONL без токенов передачи и свободного текста решений. Для старых событий без метаданных версия инструкций и попытка неизвестны. run_test_automation.py сохраняет <output>.trace.jsonl: начало, окончание/прерывание, длительность, exit code, валидация, хеш ответа и доступный usage. С --task-state используются trace_id/attempt_id реестра. Успешные запуски записываются вместе с ошибками; недоступные версии модели/CLI не угадываются. Повреждённая трасса останавливает runner до вызова GIGACODE; ошибку записи после выполнения фиксируют отдельно, сохраняя исходный результат.

Трасса не содержит исходных промптов и скрытых рассуждений модели. Полные ответы и stderr benchmark остаются отдельными локальными артефактами. Первый пакет не инструментирует каждый MCP-вызов и не измеряет расход интерактивных ролей вне подключённого runner. События передачи наблюдаемы для всех ролей, но не доказывают запуск процесса или качество результата.

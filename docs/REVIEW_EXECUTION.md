# Новый запуск в независимом ревью

Когда для содержательного вывода нужны discovery, повтор продукта, проверка assert
или другое новое наблюдение, координатор выдаёт reviewer отдельную gateway_policy
в управляемом шаге либо в reviewers[] плана review-cycle. Область соответствует
заданию пользователя, фактическим инструментам, доступным данным и средствам
изоляции. Авторская политика не наследуется. Без нужной возможности reviewer
сохраняет unknown/blocked и требуемое условие.

Managed GIGACODE получает только этот scoped MCP-шлюз. Прямые shell, filesystem, web,
discovery/delegation bridges остаются отключёнными; входы передаются снимками.
Это позволяет задать существующий MCP-инструмент запуска тестов, адресного
наблюдения UI/API или подготовки изолированного эксперимента. Backend и семантику
его результатов выбирает координатор по фактической схеме, не по выдуманному имени.
Изолированный локальный пример использует доверенный stdio runner трёх запусков
synthetic unittest; новых операций на реальном продукте он не выполняет.

## Критерий запуска

До назначения зафиксируй required_reviews[].execution, например:

~~~json
{
  "scope": "runtime",
  "agent": "qa-autotest-reviewer",
  "execution": [{
    "check_id": "counterexample",
    "tool": "run_review_test",
    "run_started_pointer": "/structuredContent/started_epoch",
    "expected_arguments": {"/project": "SYNTHETIC", "/mode": "counterexample"},
    "expected_result": {
      "/structuredContent/exit_code": 1,
      "/structuredContent/assertion_failed": true
    }
  }]
}
~~~

check_id уникален внутри направления/критерия. expected_arguments и expected_result —
непустые карты JSON pointer → точное ожидаемое JSON-значение, включая тип. Применяй
реальную схему backend: exit=1 сам по себе не доказывает падение нужного assert,
exit=0 — выполнение нужного набора. Discovery/число реально выполненных тестов,
совпадение окружения/сборки, наблюдение эффекта и восстановление добавляются там,
где этого требует критерий. Успех команды не устанавливает бизнес-ожидание.

Для backend, возвращающего результаты отдельного job, задай run_started_pointer:
JSON pointer на фактическое время начала выполнения в секундах Unix. Оно должно
попадать в интервал нового вызова, иначе старый job/кеш не подтверждает новый запуск.
Backend должен предоставлять достоверное время в согласованной шкале; при его
отсутствии нужен подходящий observer/адаптер либо unknown. Локальный пример задаёт
этот pointer для каждого реального subprocess. Новое чтение старого лога не является
новым выполнением, даже если запрос к MCP сделан только что.

Политика reviewer содержит все назначенные tools с ресурсными constraints,
allowed_arguments, call_timeout_seconds и max_review_calls (1..100, по умолчанию 20).
Предел вызовов общий для попыток одного шага, включая ошибки; планируй его вместе
с лимитом retry. Новый раунд исправленного автора получает отдельный шаг ревью.
Критерий не выдаёт инструмент или полномочие сам по себе. Review-cycle отклоняет
отсутствующую runtime-политику до запуска автора. Для проверок без нового наблюдения
политика и execution необязательны; прежнее статическое ревью сохраняется.

Если потребность в запуске выявилась во время чтения, reviewer сначала использует
доступный согласованный инструмент в своей области. Если его нет, возвращает
конкретный blocked. Координатор готовит новое назначение/план с нужным инструментом
в рамках уже выданных полномочий; вопросы нужны только о реально отсутствующих
данных/доступе либо расширении области. Зарегистрированные назначения и согласованные
критерии не редактируются для обхода ограничений.

## Свежие доказательства

Supervisor выделяет review_execution с execution_state, step_id, attempt_token,
policy_sha256. Этот binding не принимается из плана: он принадлежит конкретной
управляемой попытке и владельцу managed-worker. Перед вызовом шлюз проверяет
замороженную политику, stop-флаг, актуальность попытки и хеши всех target-артефактов.
После ответа повторяет проверки. Изменившийся target не получает подтверждения.

Каждый reviewer-call сохраняет started в observations журнала шага до обращения
к backend. Подтверждённое наблюдение получает отдельный неизменяемый OBS-файл:
tool, arguments, result, task/step, точный review_target, попытку и время начала/окончания.
Ответ содержит _meta.qa_review_execution_receipt с path, sha256, observation_id, fresh.
Read-вызовы выполняются заново, даже при повторных аргументах. Кешированный write
помечается fresh=false и остаётся контекстом; новое ревью не требует повторять уже
подтверждённую внешнюю запись ради квитанции. Для нового наблюдения выбирай разрешённый
readback/прогон, сохраняя отдельные правила действий и неопределённых исходов.

Payload reviewer:

~~~json
{"execution_checks":[{
  "criterion_id":"C-ASSERT",
  "check_id":"counterexample",
  "status":"passed",
  "note":"Новый запуск упал на assert состава при контролируемой чужой записи",
  "receipt":"/absolute/path/actions.json.receipts/OBS-....json"
}]}
~~~

Статусы passed/failed/unknown. При отсутствии наблюдения unknown может быть без receipt;
review_passed требует всех declared checks passed. Ошибка инструмента/isError,
разрыв/timeout, отмена или авария оставляют started/unknown и не считаются наблюдением.
Продуктовый отказ/падение assert внутри успешного MCP-ответа — отдельный фактический
результат: в негативном эксперименте он может быть ожидаемым, в штатном — замечанием.
Нельзя выдавать мысленный контрпример или авторский лог за OBS-квитанцию.

Submit проверяет owner, попытку, scope, журнал и контрольную сумму receipt;
вложенные receipt автоматически входят в artifact_hashes. Каждый назначенный
check_id при assess и review-cycle сопоставляется с новым вызовом, фактическими
аргументами и наблюдением. Одна квитанция не заменяет несколько назначенных запусков.
Все checks направления обязательны; generic passed не закрывает runtime-критерий.
finish повторно проверяет доказательства и приёмку. Старый target, другой reviewer,
другая попытка, изменённое ожидание/квитанция не переносятся автоматически.

Если backend возвращает отдельные файлы/скриншоты, добавь первичные локальные
материалы также в checks[].evidence. Их хеши фиксируются реестром; одного имени
файла внутри tool-response недостаточно для содержательного вывода по изображению.

Supervisor и review-cycle сохраняют прежние пределы времени, число исправлений,
отмену и восстановление. Вызовы одного gateway сериализуются; общий IO-lock не
позволяет конкурентным вызовам выдать кешированную запись за новый запуск.
Политика ограничивает инструменты, но не изолирует доверенный MCP-backend/command
adapter на уровне ОС. Для реального эксперимента backend должен обеспечивать
согласованную изоляцию, наблюдение и cleanup; target-файлы автора менять нельзя.

## Локальный пример

~~~bash
python3 examples/review-execution/build_demo.py --output-dir /tmp/qa-runtime-review
python3 scripts/manage_review_cycle.py --state /tmp/qa-runtime-review/cycle.json init --plan /tmp/qa-runtime-review/plan.json
python3 scripts/manage_review_cycle.py --state /tmp/qa-runtime-review/cycle.json serve --max-seconds 60
~~~

Автор сначала создаёт слабый assert. Независимый runner выполняет normal,
counterexample, restored. Слабый тест пропускает ошибку и получает changes_requested.
После исправления новая ревизия проходит новый штатный запуск, падает на нужном
assert при ошибке и снова проходит после снятия ошибки. Все шесть вызовов — реальные
локальные subprocess/MCP-вызовы с квитанциями; это проверка механизма, не замер
GIGACODE и не испытание пользовательского продукта. Plan/registry/цикл сохраняются,
assess и finish задачи выполняются координатором отдельно.

## Исполнение benchmark-гейтов

Оценивающая роль benchmark запускается через run_benchmark_grader.py по BENCHMARK_EVIDENCE_GATES.md: только копии prompt/system/response и рубрика, пустой cwd, bare и запрет filesystem/shell/discovery/delegation. Адрес исходного прогона остаётся у координатора, Command-адаптер без изоляции не подтверждает эту границу. Сборка копий и сверка с оригиналами выполняются отдельной штатной командой каждая. accept_benchmark_review читает и валидирует файл до любых итогов. Сводные числа создаются build_benchmark_summary с независимой evidence_session_id назначения и проверяются при submit; незавершённый этап не получает готового события. Новый вызов OBS для продуктового ревью и командная квитанция benchmark имеют разные области и не подменяют друг друга.

# Состояние и принятие расследования

## Назначение и сохранение

Для расследования координатор создаёт `artifacts/investigations/<task_id>/state.json` и назначает одного владельца записи. Передаёт `task_id`, новый `request_id`, цель, `stop_condition`, `expected_artifact`, путь состояния, источник ожидаемого поведения и только нужные ссылки. Например: «Проверь отказ доступа покупателю; остановись при первом расхождении или отсутствии обязательных условий; сохрани попытку и наблюдение ответа API». Не делегируй весь предыдущий диалог.

До начала назначения запиши его ID в `used_request_ids`, установи текущий `request_id`, `execution_status=running` и сбрось устаревшее ревью. Даже назначение, прерванное до первой попытки, остаётся в истории ID. После каждой попытки и перед передачей управления обнови состояние. Пиши во временный файл рядом, затем замени `state.json` атомарным rename. Не перезаписывай предыдущие попытки и не меняй их ID. Не копируй длинные логи и диалоги; секреты и реальные токены в состоянии недопустимы.

Используется отдельная схема `schema_version: 1`, независимая от каталога тест-кейсов и состояния автотестового runner:

| Поле | Содержание |
| --- | --- |
| `task_id`, `request_id`, `used_request_ids` | Задача, текущее назначение и все использованные назначения |
| `updated_at`, `execution_status` | ISO-время с timezone; статусы из CONTRACT.md |
| `expected_source` | Доступная ссылка на подтверждённое требование |
| `context` | `environment_id`, `product_version`, `requirements_revision`, `data_revision` |
| `hypotheses` | Объекты с `hypothesis_id`, `statement`, `status`: `open`, `supported`, `refuted` |
| `attempts` | Записи конкретных выполненных или заблокированных попыток |
| `evidence` | Реестр ссылок с ID, владельцем-попыткой и кратким описанием |
| `blockers` | Конкретные нерешённые блокеры, отдельные от QA-вывода |
| `next_step` | `goal`, `stop_condition`, `expected_artifact` |
| `review` | Оценка координатора; отсутствует до оценки |
| `verification_required` | Для новых подозрений true; обязательный артефакт и проверка по DEFECT_VERIFICATION.md |

Попытка содержит `attempt_id`, `request_id`, `hypothesis_id`, `started_at`, снимок `context`, `preconditions`, `steps`, `observations`, `actual_result`, `status` (`executed` или `blocked`), `evidence_ids`. Для выполненной попытки условия, шаги и наблюдения не пусты. Для заблокированной попытки запиши факт технического отказа; не выдавай планируемые шаги за выполненные. При повторе добавь `repeat_of` и конкретный `repeat_reason`, например независимое подтверждение после восстановления данных. Timeout сначала требует проверки фактического результата внешнего действия.

Артефакт содержит `evidence_id`, `attempt_id`, `path`, `description`; для локального файла также `sha256` его содержимого. Пути относительны каталогу состояния или абсолютны. Локальные файлы проверяются на чтение и соответствие hash; HTTP(S)-ссылки координатор проверяет через доступный инструмент. SHA-256 показывает неизменность файла, а не истинность его содержимого. Для источников с изменяемыми URL сохраняй относящийся фрагмент/версию и фиксируй ревизию требований.

Пример структуры: `examples/investigations/not-reproduced/state.json`. Читай один относящийся пример из `examples/investigations/INDEX.md`, не все примеры сразу.

## Продолжение

1. Прочитай состояние и открытые гипотезы. До действий проверь фактические окружение, сборку, требования, данные и обязательные предусловия. Не считай запись из прошлого подтверждением текущего состояния.
2. Сохрани свежую проверку в `current-context.json`: объект `context` с четырьмя полями, `verified_at` с timezone и `verification_evidence` со ссылками на новые наблюдения. Пути к локальным доказательствам также разрешаются относительно каталога состояния. Ревизия данных — ID подготовленного набора или fingerprint значимых свойств; при изменении этих свойств обновляй её. Секреты в fingerprint не включай.
3. Подготовь продолжение:

```bash
python3 scripts/validate_investigation_state.py \
  --input artifacts/investigations/QA-123/state.json --task-id QA-123 \
  --current-context artifacts/investigations/QA-123/current-context.json \
  --request-id QA-123-investigate-2
```

Код 0 и `resume_ready` означают корректные записи и совпадение заявленных условий. Передай исполнителю нерешённый вопрос и `next_step`, сохранив ссылки на прошлые попытки. `do_not_repeat_without_reason` перечисляет попытки в тех же условиях. Список `previous_attempts` сохраняет также исторические попытки другой версии.

Код 3 и `revalidate_conditions` означают смену или неизвестность условий (значения `unknown`, `неизвестно`, `не настроено` не подтверждают совпадение): сначала восстанови/перепроверь условия и пересмотри применимость прежних результатов. Историю не удаляй; новый запуск в изменённом контексте не подтверждает автоматически прежний дефект. Код 2 — неверное состояние, недоступное доказательство или повтор использованного request_id; устрани указанную проблему до действий.

Скрипт не открывает браузер, не выполняет следующий шаг, не меняет состояние и не доказывает свежесть наблюдения по одному timestamp. Координатор отвечает за фактическую проверку. Если не хватает источника или данных, сохраняй блокер и продолжай только независимую работу. Ограничивай циклы доработки по CONTRACT.md, не повторяя расследование целиком.

## Принятие результата

Оболочка и обязательные поля `investigation_complete` сохраняются. При работе с состоянием добавляется `payload.attempt_ids`: уникальные ID попыток, на которых основан именно этот отчёт. `attempts` остаётся кратким описанием, `evidence` — ссылками из реестра соответствующих попыток. Путь состояния передай в `artifacts`; не включай всё состояние в сообщение.

Для новых подозрений применяй `docs/DEFECT_VERIFICATION.md`: сохраняй verification.json, регистрируй SHA-256 и добавляй payload.verification_artifact. В ревью оцени также бизнес-эффект, вид runtime-доказательств, применимость исходников к сборке и основание степени подтверждения причины.

Сначала запусти обычный `validate_qa_result.py` с `--investigation-state` для отчёта с verification_artifact (до записи ревью отказ о его отсутствии ожидаем). Его успех без `--investigation-state` проверяет только прежнюю структуру. Затем координатор читает относящиеся попытки, источник и доказательства и записывает пять проверок:

| Ключ в `review.checks` | Что координатор оценивает |
| --- | --- |
| `expected_source` | Источник доступен, актуален и действительно задаёт ожидаемое поведение |
| `actual_attempt` | Факт привязан к названной попытке с конкретными условиями и шагами |
| `evidence_support` | Содержание доказательства подтверждает факт и выбранный outcome; доступность проверена, включая удалённые ссылки |
| `observation_vs_cause` | Наблюдения отделены от гипотез; причина не объявлена установленной без основания |
| `limitations` | Ограничения и исходные материалы обращения учтены; невоспроизведение не означает отсутствие дефекта |

Каждая проверка — `{ "status": "passed|failed|unknown", "note": "конкретное обоснование" }`. Координатор записывает `review.request_id`, `outcome`, `decision` (`pending`, `changes_requested`, `passed`) и `follow_up` (список адресных запросов). Исполнитель не одобряет собственный отчёт. Эти поля не являются криптографическим удостоверением автора; это протокол работы координатора.

Для точной привязки оценки получи fingerprints:

```bash
python3 scripts/validate_investigation_state.py \
  --input artifacts/investigations/QA-123/state.json --task-id QA-123 \
  --result artifacts/investigations/QA-123/result.json
```

Запиши `review_digest` в `review.state_sha256`, `result_digest` — в `review.result_sha256`. Поле `review` исключено из fingerprint состояния. Сначала установи итоговый execution_status для принятого этапа, затем фиксируй fingerprints и оценку. Изменение остальных полей состояния или отчёта требует нового рассмотрения; не обновляй fingerprint только для обхода отказа. Затем проверь запись оценки:

```bash
python3 scripts/validate_qa_result.py \
  --input artifacts/investigations/QA-123/result.json \
  --task-id QA-123 --request-id QA-123-investigate-1 \
  --agent qa-defect-investigator \
  --investigation-state artifacts/investigations/QA-123/state.json
```

Непройденные/неизвестные проверки, отсутствующее ревью, изменённые файлы и неверные связи запрещают принятие вывода. Успех подтверждает только корректность записи оценки и локальных артефактов: содержательное решение всё равно принадлежит координатору. Скрипт не анализирует изображения/логи и не выставляет `passed` сам.

При недостатке доказательств верни конкретный запрос, например: «В A1 нет ответа API с HTTP 200; предоставь относящийся ответ либо исправь actual_result/outcome». Не поручай весь сценарий заново, если достаточно прочитать имеющийся запрос. `inconclusive` корректен, когда факт остаётся неоднозначным; координатор может принять этот ограниченный вывод, если он подтверждён материалами. Если обязательная проверка технически невозможна, используй `blocked`. Не переводить это в `defect_confirmed` и не оформлять Jira-дефект до достаточного подтверждения нарушения.

Для `not_reproduced` укажи число попыток, условия и пределы вывода. Для `expected_behavior` покажи совпадение факта с требованием. Для `defect_confirmed` нужны нарушение конкретного требования и относящееся доказательство; повторное воспроизведение не заменяет источник ожидаемого поведения.

## Контрольные примеры

В `examples/investigations/` пять прежних синтетических сцен: подтверждение дефекта, невоспроизведение, ожидаемое поведение, недоступный стенд и неподтверждённый вывод. Последняя сцена должна отклоняться; `blocked` корректен по форме, но не завершает обязательную проверку продукта. Дополнительная сцена `verification/` связывает правило, наблюдение, учебный код и развёрнутую ревизию. Эти примеры и локальные тесты проверяют протокол и программные ограничения. Они не являются запуском GIGACODE CLI или проверкой реального стенда.

# Поставка QA-агента 1.7

Дата: **2026-10-07**. Архив: `qa-agent-1.7.zip`, checksum: `qa-agent-1.7.zip.sha256`. Внутри `qa-agent/PACKAGE_MANIFEST.json` — версия, дата, размеры и SHA-256 файлов. Специализированных ролей — **11**; навыков — 2; команда — `/qa`.

## Что изменилось относительно 1.6

- Новый `qa-stub-builder` готовит REST/Kafka-заглушки в отдельном приложении через MCP sbermock. Реальные инструменты и формат определяются из подключённого сервера.
- Этапы разделены: черновик без изменений, настройка без runtime-проб (`configure_only`), проверка назначенных проб (`verify`). Настроенная заглушка сама по себе не объявляется готовой к выполнению теста.
- Намерение координатора v2 фиксирует ожидаемый контракт, пробные входы/ответы и разрешённые операции. Приёмка требует внешнего назначения и полного набора сценариев. Изменённые ожидания, лишние вложенные условия matcher и старые наблюдения отклоняются.
- Проверка начинается после завершения всех изменений. Kafka-пробы связаны разными корреляциями, позицией и временным окном; отрицательный контроль требует полного окна. Timeout записи сначала разбирается чтением состояния, без безусловного повтора.
- Для обновления существующего правила нужны назначенный ID и снимок до изменения. Очистка адресная: удалить созданное, сохранить переиспользованное, восстановить обновлённое после проверки конфликтов. План очистки не выдаётся за выполненную очистку.
- Добавлены короткая роль, стандарт по необходимости, структурные валидаторы, синтетические примеры и регрессии ревью. Остальные возможности 1.6 сохраняются.

Итоги ревью — `STUBS_REVIEW.md`, порядок работы — `STUBS.md`.

## Установка и совместимость

Обновление с 1.6 — `UPGRADE_1.7.md` и `UPDATE.md`. Первая установка в приложение — `IMPORT_INTO_APP.md`, в отдельный каталог — `SETUP_AND_UPDATE.md`. Рядом с ZIP поставляются копии `UPGRADE_1.7.md`, `UPDATE_1.7.md`, `INSTALL_1.7.md`, `SETUP_AND_UPDATE_1.7.md`, `RELEASE_1.7.md` и внешний протокол `VALIDATION_1.7.json`.

Сохраняйте локальный QWEN.md, APP_CONTEXT.md, MCP/settings/tools, credentials, состояния и рабочие артефакты. В приложении обновляйте также подключённые роли и APP_QWEN.md, адаптируя пути к вложенному qa-agent/. Сохраняйте исходный ZIP старой версии и резервную копию локальных адаптаций для отката.

Sbermock-соединение не включено в универсальный settings.json: адрес и transport неизвестны, их нельзя выдумать. Используется уже настроенный сервер и фактические REST/Kafka-схемы. Его доступность проверяется после установки отдельно, чтением без создания правил или публикаций.

Схема stub-артефактов — v2; ранние исходные v1 не принимаются как готовность. Они сохраняются историей; продолжение требует нового назначения и чтения фактических ID. Другие схемы QA-событий, каталог кейсов, отчётность, журнал и архивные расследования сохраняются. После отката 1.6 не принимает новые stub-события.

Python 3.10+, стандартная библиотека. Runner и журнал используют POSIX/macOS/Linux или WSL. Playwright MCP остаётся 0.0.83. Архив не содержит Git/IDE/cache, рабочих доказательств, runtime-состояния и dist. Прежние поставки не перезаписываются.

## Проверки поставки

Из корня распакованного пакета:

```bash
python3 -m unittest discover -s tests -v
python3 scripts/validate_test_cases.py --input examples/test-cases.json
python3 -m unittest discover -s examples/test-data -v
```

Ожидается **178 тестов пакета** и один отдельный учебный тест подготовки данных. Проверки используют синтетические материалы и подставной Qwen, без приложения.

Предварительная проверка намерения, без MCP:

```bash
python3 scripts/validate_stub_assignment.py \
  --input examples/stubs/assignment.json \
  --task-id QA-STUB-DEMO --request-id QA-STUB-DEMO-1 \
  --scenario-id TC-REST --scenario-id TC-KAFKA
```

Три учебных этапа:

```bash
python3 scripts/validate_qa_result.py \
  --input examples/stubs/plan-result.json \
  --task-id QA-STUB-DEMO --request-id QA-STUB-DEMO-1 \
  --agent qa-stub-builder --scenario-id TC-REST --scenario-id TC-KAFKA

python3 scripts/validate_qa_result.py \
  --input examples/stubs/configure-only/result.json \
  --task-id QA-STUB-CONFIG --request-id QA-STUB-CONFIG-1 \
  --agent qa-stub-builder --scenario-id TC-REST --scenario-id TC-KAFKA \
  --stub-assignment examples/stubs/configure-only/assignment.json

python3 scripts/validate_qa_result.py \
  --input examples/stubs/result.json \
  --task-id QA-STUB-DEMO --request-id QA-STUB-DEMO-1 \
  --agent qa-stub-builder --scenario-id TC-REST --scenario-id TC-KAFKA \
  --stub-assignment examples/stubs/assignment.json
```

Ожидаются соответственно stubs_plan_ready, stubs_configured, stubs_ready и код 0. Последняя команда без --stub-assignment или без полного набора ID должна отклоняться с кодом 2. Примеры независимые, MCP не вызывался; definition в них не является форматом sbermock.

Для проверки сохранённых возможностей выполните учебные команды отчётности, журнала, селектора данных и расследования из «Проверки поставки» `RELEASE_1.6.md`. Ожидаются частичный отчёт (1 из 3 проверок), журнал (3 события / 2 синтетических инцидента) и принятие расследования только с состоянием. Упомянутые там 151 тест относятся к исторической 1.6; текущий набор — 178.

Внешний протокол конкретного ZIP фиксирует проверки исходников и распакованного пакета, checksum/манифеста, состава и совпадения инструкций с архивом. Живой Qwen, MCP sbermock/Playwright, приложение, Allure и A/B модели при сборке не проверяются. Локальные hashes и времена не доказывают истинность наблюдений; координатор оценивает первичные материалы. Экономия токенов не измерена.

# Сборка контекста и метрики исполнения

Новые managed-планы используют `context_mode: compact`. Сборщик `scripts/context_builder.py` передаёт исходный документ роли, общий формат сообщения/частичного результата, события своей роли и самопроверку с её предметным риском. Протоколы других ролей, совместимость и инструкции координатора исключаются. Профильные стандарты включаются явно; полный QA-валидатор и условия приёмки сохраняются.

## Обязательные источники

`normalize_plan` фиксирует `context_profile`, полные SHA256 исходных документов и хеш сборщика. Worker сверяет их и сохраняет фактически переданные разделы в `instructions.json`. Отсутствующий/повторяющийся заголовок или изменённый документ останавливает запуск. Полный текст остаётся в исходниках; выбор разделов не редактирует первичное доказательство.

Стандартный профиль данных автоматически включает TEST_DATA_CHECKLIST и начальные разделы TEST_DATA: composition/profile для builder, recipe для automation, review для autotest-reviewer. `test_data_sections` добавляет предметные разделы по риску. Заглушки получают STUBS; расследование — INVESTIGATION/DEFECT_VERIFICATION; исполнение — EXECUTION; отчёт — TEST_REPORTING; автотесты — качество/названия/стиль. `test_type: ui` либо `browser_pool_path` добавляют правила браузера и пула. Новый runtime-review получает REVIEW_EXECUTION при собственной gateway_policy; discussion получает протокол обсуждения.

```json
{
  "step_id": "data",
  "context_mode": "compact",
  "max_context_characters": 200000,
  "test_data_sections": ["recipe", "isolation", "cleanup"],
  "instruction_paths": ["docs/AUTOTEST_QUALITY.md"],
  "assignment": {"agent": "qa-test-data-builder"}
}
```

Для reviewer-слота review-cycle доступны те же context_mode/max_context_characters/instruction_paths, а для autotest-reviewer также test_data_sections. Это фрагмент шага; остальные поля обычного execution-плана обязательны. Дополнительные `instruction_paths` сохраняются; для известных протоколов действует компактная проекция. `context_mode: full` передаёт полный текст всех выбранных документов для явного сравнения или случая, которому нужны остальные разделы. Внешний skill/документ нужно предоставить разрешённым способом; discovery в bare-режиме не включается.

Предметный риск, которого нет в начальном профиле, требует дополнительных инструкций в новом плане. Исполнитель не должен предполагать, что ссылка была прочитана: без доступного обязательного материала возвращается unknown/blocked. Сборщик не даёт новые tools, право записи или возможность самостоятельного filesystem-доступа.

## Входные материалы

Текстовые доказательства передаются полностью. Точные дубли `inputs` используют `input_ref` на первое содержимое; отчёты зависимостей и применённые ответы с тем же путём тоже ссылаются на `input_contents`. Сохраняются пути и хеши. Бинарный файл явно unavailable. Blind-feedback не раскрывается через ссылки зависимостей.

Авторское исправление получает компактную проекцию полного feedback: все findings исходной и текущей фазы, непрошедшие checks/conclusion_checks/execution_checks/combination_checks и ограничения. Дубли удаляются, исходные blocking сохраняются. Проекция явно помечена projection/content/source_sha256 и не выдаётся за полный текст. Полный feedback остаётся хешированным входным артефактом и содержит оба набора отзывов для аудита. Назначение связывает его через `correction_feedback`; это поле запрещено reviewer. Первичные review_sources и target не сокращаются.

`max_context_characters` — целое 1000..10000000, по умолчанию 200000. Оно ограничивает явно переданные system + сериализованный prompt в Unicode-символах, не токенах. При превышении сохраняются полный prompt и диагностика, запуск модели отклоняется. Автоматического обрезания нет: координатор пересматривает назначение, делает доступный проверяемый снимок или задаёт обоснованный бюджет в новом плане. Это не измерение лимита окна модели; схемы инструментов, внутренние инструкции CLI и последующая история сюда не входят.

## Телеметрия

В каждой попытке сохраняются:

- `context-metrics.json`: system/prompt, компоненты входа, документы, лимит и превышение; только размеры, без копии содержимого.
- `metrics.json`: backend, длительность попытки, exit/category, метрики контекста и фактический CLI usage/stats, когда доступны. Terminal result поддерживается в объекте и в списке событий. Отсутствующий/невалидный usage остаётся null; символы не пересчитываются в токены.

Сводки `manage_execution.py show` и `manage_review_cycle.py show` включают `metrics` всех зарезервированных попыток, включая сбои и незавершённые попытки. `known_input_tokens`/`known_output_tokens` — доступная частичная сумма. Итоговые `input_tokens`/`output_tokens` заполнены только при полном usage всех попыток; иначе null и `complete_usage: false`. Число измеренных попыток показано отдельно. Аналогично known_explicit_characters является частичной суммой; explicit_characters заполнено только при complete_context, иначе null. `measured_duration_seconds` — сумма доступных длительностей, не wall-clock всей задачи. Ожидание ответов/ревью не является запуском модели и отдельно видно в состоянии/trace.

Trusted command adapters получают метрики длительности/вывода, но не проходят сборку GIGACODE-промпта. Их неизвестный контекст/usage не засчитывается как нулевая стоимость. Fixture usage подтверждает только механику телеметрии. Координатор интерактивной GIGACODE-сессии и скрытые provider/cache расходы этой сводкой не измеряются; `/context detail` и фактические данные провайдера учитываются отдельно. Метрики диагностические, не условия содержательной приёмки.

## Совместимость и проверка пользы

Сохранённый execution без context_profile использует прежние полные instruction_hashes. Старые состояния не нормализуются и не переписываются автоматически. Новое назначение/новый план получают новую сборку; изменённый сборщик требует нового плана. Архив 1.9 остаётся замороженным.

Технические тесты проверяют все роли/события/обязательные поля, доступность предметных разделов, отсутствие утечки чужого feedback, дедупликацию, лимит без обрезки, сохранённые планы и полный учёт попыток. Реальный локальный fixture-процесс проверяет связку prompt → terminal usage → агрегат. Это не оценка качества живой модели.

Для A/B сохраняй одинаковые задания, доказательства, модель и условия. Сравни compact/full с независимой оценкой существенных ошибок, ложных одобрений и блокировок. Экономия символов подтверждает сокращение явного текста; пользу по токенам, времени и качеству можно подтвердить только живыми запусками.

# Сборка контекста и метрики исполнения

Документ описывает управляемый запуск через `execution_supervisor.py` и
`execution_worker.py`, включая review-cycle. Контекст собирается из назначения,
замороженных инструкций, явно переданных входов, принятых результатов зависимостей
и ответов на вопросы. Интерактивная сессия `/qa` не получает автоматически тот же
снимок и не входит в эту телеметрию.

Новые managed-планы используют `context_mode: compact`. Сборщик
`scripts/context_builder.py` выбирает инструкции по роли и предмету задания.
Компактный режим сокращает общие инструкции; текстовые входные доказательства
передаются полностью, кроме явно обозначенных проекций. Приёмка результата
по-прежнему использует полный QA-валидатор и назначенные условия
содержательного ревью.

## Фиксация контекста

При нормализации execution-плана фиксируются:

- `context_profile`: режим, роль и правила выбора документов/разделов;
- `instruction_hashes`: SHA256 полных исходных файлов инструкций;
- `context_builder_sha256`: SHA256 сборщика;
- `input_hashes`: SHA256 объявленных входных файлов;
- `max_context_characters`: бюджет явно переданного текста.

Перед запуском worker сверяет замороженные источники и сборщик. Хеш и текст
каждой инструкции берутся из одного чтения байтов. Даже изменение невыбранного
раздела меняет хеш исходного документа и требует нового плана. В компактной
проекции отсутствующий или повторяющийся обязательный заголовок вызывает ошибку.
Невалидный JSON-пример кейса отклоняется при подготовке профиля.

В каталоге попытки `<execution-state>.runs/<step_id>/attempt-N/` сохраняются
`handoff.json`, фактически выбранные инструкции в `instructions.json`,
`system.md` и `prompt.json`. По ним можно восстановить явный вход запуска.
Если подготовка остановилась раньше сборки, часть файлов может отсутствовать.
Артефакты попыток хранятся с runtime-состоянием вне поставки; их расположение
видно в `steps.<step_id>.run_dir` CLI-сводки.

Сборщик не даёт новых tools или прав доступа. В bare-режиме исполнитель использует
переданные материалы и разрешённый gateway. Ссылка на документ не означает,
что его содержимое прочитано. Недоступный обязательный материал требует
`unknown`/`blocked`, а не предположения о его содержимом.

## Инструкции по роли

Общий профиль включает полный документ `.gigacode/agents/<role>.md`,
проекции [CONTRACT.md](CONTRACT.md) и [SELF_REVIEW.md](SELF_REVIEW.md).
Из общего контракта выбираются оболочка сообщения, частичная готовность и события
своей роли; из самопроверки — общие проверки и предметный риск этой роли.
Предметные документы добавляются по назначению:

| Роль или условие | Дополнительный контекст |
| --- | --- |
| `qa-analyst`, `qa-test-plan-writer` | Маршрут плана, тест-дизайн, отбор сценариев и стандарт кейсов |
| `qa-test-plan-writer` | Навык `qa-test-cases`, правила разделения и итогового HTML-плана |
| Работа с каталогом кейсов | Протокол проверки, стандарт и выбранные примеры; условия ниже |
| `qa-test-automation`, `qa-autotest-reviewer` | Качество и названия автотестов, стандарт кейсов |
| `qa-test-data-builder` | TEST_DATA_CHECKLIST и разделы TEST_DATA `composition`, `profile` |
| `qa-test-automation` / `qa-autotest-reviewer` | TEST_DATA_CHECKLIST и соответственно `recipe` / `review` |
| `qa-stub-builder` | STUBS |
| `qa-impact-analyst` | IMPACT_ANALYSIS и QA_IMPROVEMENTS |
| `qa-defect-investigator` | Выбранные разделы INVESTIGATION и DEFECT_VERIFICATION |
| `qa-feature-tester` / `qa-test-report-writer` | Соответственно выбранные разделы EXECUTION / TEST_REPORTING |
| Reviewer | CONTENT_REVIEW; дополнительно предметный протокол по scope |
| Reviewer с собственной `gateway_policy` | Выбранные разделы REVIEW_EXECUTION |
| `review_discussion` | Протокол обсуждения расхождений |
| `test_type: ui` или `browser_pool_path` | Правила воспроизведения в браузере и браузерного пула |
| `plan_partition` | TEST_PLAN_PARTITION и проверка привязки к снимку |
| `improvement_plan` / `evidence_session_id` или scope `benchmark_evaluation` | Соответствующий протокол улучшений / проверки benchmark-доказательств |

Роли содержательной проверки также получают навык `qa-check-quality`.
Точный перечень документов и выбранных разделов хранится в `context_profile`;
таблица описывает условия выбора, а не обещает передачу всей библиотеки.

`test_data_sections` добавляет предметные разделы по риску для трёх ролей данных
из таблицы. `instruction_paths` позволяет явно добавить инструкции из пакета.
Для уже известных документов сохраняется их компактная проекция.
`context_mode: full` передаёт полный текст всех выбранных документов, сохраняя
проверку JSON-примеров. Он не подключает невыбранные документы, входы или tools.
Внешний документ/skill передаётся разрешённым способом; discovery в bare-режиме
не включается.

```json
{
  "step_id": "data",
  "context_mode": "compact",
  "max_context_characters": 200000,
  "test_data_sections": ["recipe", "isolation", "cleanup"],
  "instruction_paths": ["docs/AUTOTEST_QUALITY.md"],
  "assignment": {"agent": "qa-test-data-builder"}
}
```

Это фрагмент шага: остальные поля execution-плана обязательны. Для reviewer-слота
review-cycle доступны `context_mode`, `max_context_characters`, `instruction_paths`;
для `qa-autotest-reviewer` также `test_data_sections`. Новый предметный риск требует
явных дополнительных инструкций в новом плане.

## Кейсы и примеры API, UI, Kafka

Автор плана, исполнитель, автоматизатор и reviewer автотестов получают
[TEST_CASE_REVIEW.md](TEST_CASE_REVIEW.md) и [TEST_CASE_STYLE.md](TEST_CASE_STYLE.md).
Прямой reviewer получает этот контекст при `scope: test_cases`. Для остальных
читателей кейсов, включая аналитика, builder данных и configurator окружения,
его включают `assignment.test_type` или явно выбранный JSON-пример. Передача
TEST_CASE_STYLE через `instruction_paths` также включает протокол для reviewer.

`assignment.test_type` принимает `api`, `ui` или `kafka`. Для каждого нужного типа
передаётся его `INDEX.md` и один базовый JSON, если нет явного выбора:

| Тип | Базовый пример |
| --- | --- |
| `api` | `examples/test-cases/api/create.json` |
| `ui` | `examples/test-cases/ui/create.json` |
| `kafka` | `examples/test-cases/kafka/persistence.json` |

Например, фрагмент шага автора API-кейсов с явным образцом отказа:

```json
{
  "step_id": "cases-api",
  "context_mode": "compact",
  "max_context_characters": 200000,
  "instruction_paths": ["examples/test-cases/api/cancellation.json"],
  "assignment": {"agent": "qa-test-plan-writer", "test_type": "api"}
}
```

JSON-пути в `instruction_paths` заменяют базовый пример своего типа.
Можно явно выбрать несколько примеров, в том числе для смешанного каталога;
вся библиотека автоматически не загружается. Пример передаётся целиком,
валидируется и фиксируется хешем полного файла в обоих режимах контекста.
Образцы показывают формат «Шаг — Ожидаемый результат — Тест-дата»; их
синтетические API, SQL, UI и ожидания не устанавливают бизнес-правила проекта.

Если результат автора содержит `payload.test_cases_artifact`, review-cycle
передаёт reviewer протокол кейсов, тип и выбранные примеры автора. Первичные
требования, контекст приложения и доступные способы проверки нужно включить
в назначение явно. Пример не заменяет эти источники.

## Входы и независимое ревью

До заморозки плана координатор выполняет COORDINATION_SAFETY.md: inputs не
пересекаются с публикуемыми файлами самого назначения и активных владельцев,
изменяемая принятая база заменена побайтовым snapshot revN, локальные пути
абсолютны. Хеш входа не является блокировкой от чужой записи. Несовпадение
после assign требует новой базы/назначения, а не пересчёта старых хешей.
Snapshot и preflight хранятся вне .qa-agent-state/ и передаются текстом через
inputs, когда нужны исполнителю; ссылка сама по себе не даёт bare-роли чтение.

Тяжёлые managed-ветки также занимают один согласованный слот; автоматическая
параллельность supervisor не считается выполнением этого правила. Измерения
сборщика не включают интерактивную нагрузку координатора или других сессий.
Ограничения python3/shell у роли не исправляются инструкцией на запуск:
валидатор/хеширование выполняет разрешённый адаптер или координатор с отдельной
квитанцией; роль записывает это в payload.limitations и не заявляет свой запуск.

`prompt.json` содержит `handoff`, `input_contents`, `catalog_validations`,
`source_reports`, `applied_answers` и `recorded_actions`. Для разделённого плана
добавляется `partition_scope`.

UTF-8-входы передаются полностью с исходными переводами строк. Точные текстовые
дубли в одной попытке используют `input_ref` на первое содержимое. Отчёт
зависимости или применённый ответ, уже включённый в inputs, тоже ссылается на
`input_contents`. Путь и SHA256 сохраняются; дедупликация не переносит контекст
между попытками. Непередаваемый как UTF-8 бинарный вход явно отмечается
`unavailable`; для его анализа нужен разрешённый наблюдатель.

Review-cycle формирует inputs reviewer из проверенных `artifact_hashes` результата
автора. Набор включает исходные inputs автора и зарегистрированные выходные
артефакты, а не только итоговый каталог. Первичные `review_sources` заключений
передаются дополнительно. Их хеши и привязка target проверяются. Автоматического
чтения репозитория или внешних URL сборщиком нет.

Входной текст с первым непробельным символом `{` или `[` проверяется как JSON. Для объекта
с `test_cases` сборщик напрямую вызывает `validate_catalog` и сохраняет в
`catalog_validations` путь, SHA256 тех же прочитанных байтов, `kind`, `valid`,
`case_count` и `errors`. Невалидный JSON получает `kind: json` и диагностику;
корректный посторонний JSON не выдаётся за каталог. Это проверка структуры
входа, без shell, сети или выполнения кейсов. Reviewer отдельно оценивает
источники, достижимость, отбор и содержание; успешный `valid` не принимает
результат и не проверяет ещё не созданный выходной каталог.

Авторское исправление получает явно помеченную проекцию `correction_feedback`:
все findings исходной и текущей фазы, непрошедшие checks, conclusion_checks,
execution_checks, combination_checks и ограничения. Дубли удаляются;
исходные blocking сохраняются. Полный feedback остаётся хешированным артефактом
для аудита, но в prompt передаются `projection`, `content`, `source_sha256`.
Поле `correction_feedback` запрещено reviewer.

В независимом повторном ревью зарегистрированный feedback скрывается через
`blind_review_exclusions`, в том числе при ссылках зависимостей. Скрытый feedback
и проекция исправления не анализируются как входные каталоги. При отдельно
назначенном discussion-раунде передаются пакет расхождений и артефакты отзывов;
это обсуждение по REVIEW_DISCUSSION, а не слепое повторное ревью. Первичные
источники и target не сокращаются.

## Контекст групп и объединённого плана

[TEST_PLAN_PARTITION.md](TEST_PLAN_PARTITION.md) задаёт разделение от принятой
общей карты покрытия. `plan_partition` связывает назначение с путём и SHA256
`partition.json`, режимом `group`/`integration` и, для группы, `group_id`.
Review-cycle сохраняет эту привязку автора.

| Участник | Материалы и область проверки |
| --- | --- |
| Автор группы | `partition.json` с общими ID/хешами и `context.json` своей группы: строки покрытия, точные фрагменты требований, открытые вопросы, объявленные общие и групповые условия |
| Reviewer группы | Привязка той же группы, её исходные inputs и зарегистрированные результаты автора; проверка назначенных сценариев |
| Итоговый автор | Объединённый каталог, доказательство сборки и отчёты выбранных принятых групп через зависимости; все сценарии и глобальные критерии |
| Итоговый reviewer | Проверенные артефакты интеграции, первичные источники и результаты/ревью выбранных групп; согласованность всего покрытия |

Групповой `context.json` — именованная проверяемая проекция, а не пересказ моделью.
Объявленные общие и групповые контексты передаются целиком. Локальное требование
без якоря также передаётся целиком; выбор раздела или диапазона строк задаётся
его source. Для внешнего требования необходим объявленный текстовый снимок:
сама HTTP(S)-ссылка не загружает содержимое.

Утилита сверяет проекцию с полными хешами первичных файлов, принятой базой,
назначением и критериями до передачи, submit/review и сборки. Чтение полного
источника для этой проверки не означает передачу его полного текста группе.
Артефакты других групп не добавляются к её prompt автоматически; явно
назначенные зависимости и inputs учитываются обычным способом.

На этапе интеграции область расширяется до всего выбранного покрытия.
Доказательство сборки фиксирует точные request ID групп, хеши их результатов
и отзывов. Его структурная проверка не заменяет финальное содержательное ревью.
Положительное ревью группы не подтверждает всю задачу и не публикует общий HTML.
Итоговый [HTML-план](TEST_PLAN_HTML.md) формируется после принятия интеграции;
он является представлением проверенных артефактов, а не новым источником требований.

`partition_scope` показывает режим, группу и версии базы/плана. Лимит контекста
действует для каждой попытки, включая финальный review. Разделение не запускает
дополнительных авторов автоматически и не отменяет этот лимит.

## Бюджет и превышение

`max_context_characters` — целое 1000..10000000, по умолчанию 200000. Worker
измеряет Unicode-символы в фактическом `system.md` плюс сериализованном
`prompt.json`. Здесь учитываются JSON-оболочка, инструкции и данные, а не только
исходный текст требований. Это не число токенов и не размер окна модели.
Схемы tools, внутренние инструкции CLI, последующая история и ответы gateway
в это измерение не входят.

При превышении сохраняются полный prompt, system и `context-metrics.json`,
после чего запуск модели отклоняется. Автоматического обрезания нет. Координатор
по диагностике пересматривает область, выбирает проверяемую проекцию или делит
план по правилам TEST_PLAN_PARTITION. Если широкий вход необходим для итогового
ревью, задаётся обоснованный бюджет в новом плане. `full` также подчиняется лимиту.

## Телеметрия и чтение сводки

| Файл попытки | Что измеряет |
| --- | --- |
| `context-metrics.json` | `system_characters`, `prompt_characters`, их сумма `explicit_characters`, бюджет и `budget_exceeded`; размеры компонентов prompt и выбранных документов, без копии содержимого |
| `metrics.json` | Backend, exit/category, длительность попытки, доступные метрики контекста, фактические токены и исходные CLI `usage`/`stats`; при наличии — correlation и время начала/окончания |

Размеры `components` измеряются как сериализованные значения полей prompt;
они не включают имена полей и общую JSON-оболочку, поэтому их сумма не равна
`prompt_characters`. Размеры `documents` относятся к выбранным текстам инструкций,
а `system_characters` также включает разделители, имена источников и инструкции
worker. Символы не пересчитываются в токены.

Usage читается из JSON-объекта stdout либо последнего события `type: result`
в списке. Поддержаны `input_tokens`/`prompt_tokens` и
`output_tokens`/`completion_tokens`, только неотрицательные целые.
Отсутствующая или невалидная сторона usage остаётся `null`, доступная сохраняется.
Исходные `reported_usage`/`reported_stats` не означают, что все их поля входят
в агрегат.

Сводки доступны командами:

```bash
python3 scripts/manage_execution.py --state /absolute/path/execution.json show
python3 scripts/manage_review_cycle.py --state /absolute/path/review-cycle.json show
```

В `metrics` учитываются все зарезервированные попытки выбранного execution,
а для review-cycle — попытки его дочерних execution. Повторы, ошибки и
незавершённые попытки входят в `attempts`, даже если `metrics.json` не появился.
Ожидание ответов/ревью видно в состоянии и trace, но не является новой попыткой
модели. Независимые execution групп не объединяются этой сводкой автоматически.

| Поле сводки | Как читать |
| --- | --- |
| `attempts` | Все зарезервированные попытки в выбранной области |
| `measured_context_attempts` | Попытки с сохранёнными метриками контекста внутри `metrics.json` |
| `known_explicit_characters` | Сумма доступных измерений; повторно переданный текст учитывается в каждой попытке |
| `explicit_characters`, `complete_context` | Полная сумма только при измеренном контексте всех попыток; иначе `null` и `false` |
| `measured_usage_attempts` | Попытки, для которых известны обе стороны usage |
| `known_input_tokens`, `known_output_tokens` | Частичные суммы каждой доступной стороны usage |
| `input_tokens`, `output_tokens`, `complete_usage` | Полные суммы только при известном usage всех попыток; иначе обе суммы `null`, полнота `false` |
| `measured_duration_seconds` | Сумма доступных длительностей попыток; не wall-clock задачи и не отдельное время генерации модели |

Например, при двух попытках и usage только одной `attempts: 2`,
`measured_usage_attempts: 1`; известные токены показаны в `known_*`, а итоговые
`input_tokens`/`output_tokens` остаются `null`. Нулевая частичная сумма при
отсутствии измерений не означает бесплатный запуск. При отсутствии попыток
`complete_usage` и `complete_context` также равны `false`.

Trusted command adapters сохраняют длительность и доступный usage stdout,
но не проходят сборку GIGACODE-промпта. Их неизвестный контекст не считается
нулевым. При падении worker до записи итоговых метрик локальный
`context-metrics.json` может быть доступен для диагностики и ещё не войти в сводку.
Интерактивная работа координатора, скрытые provider/cache расходы и денежная
стоимость здесь не измеряются. `/context detail` и данные провайдера проверяются
отдельно. Метрики диагностические; они не заменяют условия приёмки.

## Совместимость и проверка пользы

Сохранённый execution без `context_profile` использует полные тексты по прежним
`instruction_hashes`. Старые состояния и архивы не переписываются автоматически.
Новый план получает текущую сборку; изменение замороженного сборщика или
источников требует нового плана, а не пересчёта старых хешей.

Технические тесты проверяют роли/события/обязательные поля, предметные разделы,
выбор и валидацию примеров, сохранность байтов/хешей, независимость reviewer,
дедупликацию, лимит без обрезки, границы групп и объединение, совместимость
сохранённых планов и учёт попыток. Локальный fixture-процесс проверяет связку
prompt → terminal usage → агрегат. Это не оценка качества живой модели.

Для A/B сохраняйте одинаковые задания, доказательства, модель и условия.
Сравнивайте compact/full или одиночную/разделённую работу с независимым итоговым
ревью: пропуски покрытия, неподтверждённые ожидания, недостижимые сценарии,
лишние отдельные кейсы и неоднозначные шаги. Эти показатели качества оцениваются
в пилоте, автоматически в `metrics.json` они не вычисляются. Экономия символов
подтверждает сокращение явного текста; пользу по токенам, времени и качеству
подтверждают живые запуски по [TEST_CASE_PILOT.md](TEST_CASE_PILOT.md).

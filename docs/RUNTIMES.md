# Среды исполнения QA-пакета

## Общее ядро

Контракты QA, статусы, реестр задач, доказательства, приёмка, метрики и Python-
валидаторы не зависят от выбранной модели. Общие инструкции находятся в
`docs/COORDINATOR.md`. `GIGACODE.md` подключает их для GIGACODE; `AGENTS.md`
содержит общие правила работы с репозиторием.

Основной проверяемый профиль файлов — `.gigacode/agents`, `skills`, `commands`.
При подключении другой среды создайте её профиль из этих инструкций, адаптируйте
имена tools и пути. Автоматический импорт ролей другими CLI не заявляется.

Основной способ распространения — полная проектная копия по
[PROJECT_INSTALLATION.md](PROJECT_INSTALLATION.md), без QA MCP-сервера.
Профиль и скрипты имеют одну версию; `.qa-agent/install.json` переносится через Git.
Контракты изолированных headless-попыток и scoped gateway внешних инструментов
ниже сохраняются; локальная установка сама по себе не выдаёт им shell-полномочия.

## Контракт headless-json-v1

`qa-runtime.json` задаёт backend, executable и protocol. Python-запуски читают
его по умолчанию. `--cli` меняет исполняемый файл, `--runtime-config` задаёт
явный конфиг; override CLI имеет приоритет над config.executable.

```json
{
  "schema_version": 1,
  "backend": "gigacode",
  "executable": "gigacode",
  "protocol": "headless-json-v1"
}
```

Контракт: `-p PROMPT`, `--append-system-prompt SYSTEM`, `--output-format json`.
Обычная автоматизация требует `--approval-mode auto-edit` и `--max-wall-time`.
Изолированный benchmark/reviewer/worker дополнительно требует `--bare`,
`--exclude-tools` и `--max-session-turns`; gateway требует `--mcp-config` и
`--allowed-tools`. Проверка `--help`/`--version` выполняется до задания и
не обращается к модели. Она проверяет наличие флагов, а не их фактическую семантику.

Этот контракт перенесён из прежнего runner. Документация GIGACODE подтверждает
проектные memory/roles/skills/commands/MCP; все headless-флаги и поведение изоляции
должны быть проверены на установленной версии отдельно. Если хотя бы одна
обязательная возможность недоступна, запуск останавливается. Наличие бинарника
с именем gigacode не удостоверяет его происхождение или совместимость.

Ответ: один JSON-объект либо массив событий с последним `type=result`; QA-сообщение
передаётся в `response`, `result` или `structured_result`, либо напрямую в QA-формате.
Ошибки, пустой ответ и отсутствие обязательного исполнения не принимаются.
Неизвестный usage остаётся неизвестным.

## Managed-план

Без adapter используется GIGACODE. Явный адаптер:

```json
{
  "kind": "gigacode",
  "executable": "/absolute/path/to/gigacode",
  "expected_version": "ТОЧНАЯ СТРОКА --version"
}
```

Для другого совместимого CLI допустим `kind=cli` с явными executable/backend.
Для несовместимого CLI используйте существующий `kind=command` с точным argv
доверенного локального адаптера. Он обязан соблюдать назначение, fencing,
доказательность и ограничения gateway; wrapper не делает их автоматическими.
Рабочий subprocess и supervisor ограничивают время и сохраняют попытки отдельно.
Смена executor требует нового плана и контрольного прогона; ранее зафиксированные
хеши и разрешения нельзя автоматически переносить.

## Метрики и история

Запуски сохраняют backend, cli_version и cli_executable_sha256. Сравнение
запрещено при разных runtime или неполной идентификации. Данные прежних форматов
без явного backend и идентичности CLI не принимаются для сравнения.
Для аудита таких данных используйте их исходную версию пакета из истории Git.
Старые архивы, acceptance JSON и журналы не мигрируются заменой строк.

## Приёмка новой среды

Проверьте загрузку memory/ролей/skills и `/qa`; один headless QA-ответ, timeout,
ошибочный/пустой ответ, сбор usage и невозможность запрещённых tool calls.
Для gateway проверьте, что доступны только назначенные scoped tools, работают
отмена и readback неопределённой записи. Зафиксируйте версию CLI и реальные tools.
До этого живой runtime и внешние интеграции остаются непроверенными.

# Управляемое выполнение QA-назначений

Текущий CLI-контракт и ограничения миграции — [RUNTIMES.md](RUNTIMES.md). Примеры с command-адаптером проверяют локальную механику, не GIGACODE.

Второй пакет улучшений добавляет supervisor над существующим реестром. Он запускает заранее согласованные назначения, сохраняет владельца и heartbeat, восстанавливает принятые шаги, останавливает реальные процессы и ограничивает повторы. Код использует Python stdlib и POSIX: macOS/Linux, Windows через WSL. Проверка на этой машине выполнена на macOS; Linux-ветка идентификации процессов пока не проверена живым запуском.

Эта доработка включена в поставку 2.0. Архив `dist/qa-agent-1.9.zip` сохранён. Supervisor не заменяет содержательное ревью, приёмку критериев и окончательный `finish` задачи.

## План и запуск

Минимальный пример — [examples/execution](../examples/execution/README.md). Сначала создаётся реестр задачи с согласованными критериями, затем execution по JSON-плану:

```bash
python3 scripts/manage_execution.py --state .qa-agent-state/tasks/QA-MANAGED/execution.json init --plan examples/execution/plan.json
python3 scripts/manage_execution.py --state .qa-agent-state/tasks/QA-MANAGED/execution.json serve --max-seconds 1200 --answers-poll-seconds 60
python3 scripts/manage_execution.py --state .qa-agent-state/tasks/QA-MANAGED/execution.json show
```

`serve` выполняет цикл supervisor указанное время; новый default — 1200 секунд (20 минут). В waiting_answers опрос пакетов происходит раз в 60 секунд, интервал задаётся --answers-poll-seconds (до 60 секунд). Первая проверка немедленная, последняя выполняется на границе max-seconds. Активные worker и отмена наблюдаются с прежним коротким интервалом. По окончании этого окна состояние ожидания сохраняется; работающий worker продолжает свою попытку. Следующий явно запущенный serve или tick подхватывает состояние. Пока supervisor выключен, новые этапы не запускаются. Worker сам ограничивает свой процесс по времени. Ctrl+C в serve сохраняет отмену и останавливает группу процессов.

План содержит `schema_version: 1`, `task_state`, существующий `workspace`, `adapter`, упорядоченные `steps`. Относительные пути разрешаются от каталога JSON-плана. Каждый шаг содержит:

| Поле | Назначение |
| --- | --- |
| step_id, assignment | Стабильный ID шага и полное назначение по TASK_EXCHANGE.md; зависимости и criterion_ids сохраняются |
| wait_for_questionnaire_ids | Пакеты ответов, без применения которых этот шаг не запускается |
| instruction_paths | Дополнительные документы пакета; роль, CONTRACT.md и SELF_REVIEW.md включаются автоматически |
| max_wall_seconds, max_session_turns | Лимит одной попытки: по умолчанию 300 секунд и 30 ходов GIGACODE |
| retry_safe, retry_on | Автоматический повтор только при явном `true` и разрешённой категории; по умолчанию повтора нет |
| max_attempts, max_identical_failures | Общий предел попыток 1..5, остановка одинаковых ошибок; по умолчанию 1 и 2 |
| retry_backoff_seconds | Пауза между повторами с увеличением вдвое; по умолчанию 1 секунда |
| transient_exit_codes | Явные коды временного сбоя доверенного адаптера; по умолчанию `[75]` |
| gateway_policy | Необязательная фиксированная политика единственного MCP-шлюза |

Общий `max_active_seconds` по умолчанию 1800: сумма времени запущенных попыток. Ожидание ответа, зависимостей, ревью и паузы повтора не расходует этот лимит. `heartbeat_timeout_seconds` по умолчанию 15. `failure_journal` задаёт общий журнал проекта; по умолчанию `<workspace>/artifacts/failures/agent-errors.jsonl`. `scope_kind: synthetic` отделяет учебные инциденты от рабочих; по умолчанию operational.

План, входы и инструкции фиксируются хешами. Для изменения цели, политики или исчерпанного бюджета требуется новый согласованный план с новыми ID и путями результатов. Ручное редактирование execution не является способом продолжения.

## Владение, контрольные точки и сбои

У execution один активный controller с файловой блокировкой. Перед запуском сохраняется намерение; worker атомарно получает попытку и записывает PID, группу и время рождения процесса. Поздний или второй worker не получает право запустить модель. PID сам по себе не считается владельцем: macOS использует `proc_pidinfo` с микросекундами рождения, Linux — `/proc` и boot ID.

Worker запускает модель и MCP-процессы в своей группе, сохраняет stdout, stderr, heartbeat и trace. Неоднозначная группа помещается в `needs_reconciliation`; неизвестный процесс не убивается и рядом с ним не запускается повтор. Истёкший heartbeat означает подозрение, а не доказанную смерть. Лимит попытки проверяется также supervisor, чтобы зависший worker не обходил собственный таймер.

После успешного выхода stdout публикуется эксклюзивно в `result_path`, проходит существующий полный валидатор и `submit`. Execution ждёт `awaiting_review`. Координатор читает отчёт и доказательства и выполняет `manage_task.py review`; только `accepted` создаёт checkpoint. Следующий шаг использует фактический ID принятой попытки, включая `.retry-2`. При продолжении перепроверяются хеши, принятие и источники предыдущих шагов. Успешный код процесса не означает принятие QA-результата.

Неопределённое внешнее действие блокирует даже валидный отчёт. Повторы получают новый request_id, result_path и отдельный каталог; исходное доказательство не перезаписывается. Классификация ошибок: `transient`, `timeout`, `process_lost`, `invalid_result`, `backend_error`, `configuration`, `cancelled`. Последние три не повторяются автоматически. Настройка `retry_on` сама по себе не подтверждает безопасность: координатор задаёт `retry_safe` только после оценки операций и их повторяемости.

Существенные неуспешные попытки получают `failure_incident_id` и запись общего журнала с неизменяемым `failure-observation.json`. Supervisor записывает `cause=unknown`, `recovery=not_attempted`. Он не объявляет восстановление успешным после запуска следующей попытки. Координатор дополняет тот же инцидент проверкой по [FAILURE_JOURNAL.md](FAILURE_JOURNAL.md); повреждённый журнал не считается пустым.

Артефакты исполнения лежат рядом с execution в `<execution.json>.runs/<step>/`: отдельные attempt-N, `handoff.json`, prompt/system/instructions, preflight, stdout/stderr и trace. В handoff есть delivery token: эти файлы предназначены для локального исполнения, не для публичной пересылки. В trace и сводку секреты и текст промпта не копируются; сам prompt может содержать чувствительные входы. Условия хранения определяются проектом.

## Продолжение после HTML-ответов

Форма по [QUESTIONS_UI.md](QUESTIONS_UI.md) отправляет общий ответ в тот же task_state. Шаг заранее связывается через `wait_for_questionnaire_ids`. По умолчанию координатор читает смысл ответов и делает `apply-answers`; затем работающий `serve` запускает этот шаг. Ответы и их хеши входят в handoff.

При пропущенном уведомлении или самостоятельном HTML supervisor обнаруживает
валидный файл по зарегистрированному answers_path и восстанавливает answers_ready.
Для ручного применения координатор запускает questionnaire.py wait: он возвращает
проверенные ответы в течение окна 20 минут с опросом раз в минуту, затем координатор
делает apply-answers. Сам timeout не отменяет задачу и не принимает результат.

`auto_apply_answers: true` означает заранее согласованную передачу полностью отвеченного пакета как контекста для указанного шага. Она не принимает QA-результат, не меняет критерии и не расширяет политику инструментов. `deferred` оставляет выполнение на ожидании. Для ответов, меняющих область действий, используйте ручное применение и новый план. Автоматическое продолжение относится к заранее заданным worker-запускам; завершённый чат GIGACODE не пробуждается.

## Отмена и явное продолжение

```bash
python3 scripts/manage_execution.py --state /absolute/path/execution.json cancel --reason "Пользователь остановил выполнение"
python3 scripts/manage_execution.py --state /absolute/path/execution.json resume --decision "Пользователь разрешил продолжить прежний объём"
```

Флаг отмены сохраняется до сигналов TERM/KILL. Перезапуск supervisor его не снимает. `resume` возможен после подтверждённого остановленного процесса и сверки внешних действий, при оставшемся бюджете. Принятые checkpoints и валидный результат на ревью сохраняются; завершённый отчёт не исполняется повторно. Для неопределённой группы сначала выясните её фактическое состояние и повторите `cancel`; отсутствие вкладок или произвольная правка PID не являются подтверждением.

После сбоя или readback координатор может дать решение:

```bash
python3 scripts/manage_execution.py --state /absolute/path/execution.json retry --step-id env-1 --decision "Внешнее состояние проверено, повтор допустим"
```

Это не снимает отмену или бюджеты. Если процесс уже успешно вернул отчёт, команда продолжает проверку существующего вывода. Иначе создаёт новую попытку. Содержательное отклонение отчёта требует работы координатора; обычный `tick` не переписывает его сам.

## GIGACODE-адаптер и границы исполнения

`adapter: {"kind":"gigacode","executable":"gigacode"}` проверяет CLI и обязательные флаги, записывает доступную версию, запускает отдельную headless-сессию с `--bare`, deny-list встроенных инструментов, лимитами времени/ходов и явными инструкциями. Неизвестные/отсутствующие флаги останавливают запуск; ограничений не ослабляют. При наличии политики добавляется только явный `--mcp-config` со scoped gateway и `alwaysLoadTools`. Полномочия на другие MCP, shell, web, discovery и делегирование не выдаются.

В рабочем плане укажите adapter.expected_version — точную строку `gigacode --version`, сверенную с поддерживаемыми инструментами вашей сборки. Несовпадение останавливает попытку. Deny-list унаследован от прежнего адаптера, включая exec, сессии, cron и media. Его полноту для вашей сборки GIGACODE нужно проверить по фактическому списку tools. Неизвестные будущие встроенные инструменты требуют проверки списка; presence обязательных флагов сам по себе не удостоверяет безопасность произвольной новой сборки. Без expected_version версия записывается, но обновление CLI не блокируется автоматически.

Назначенные входы, принятые отчёты, ответы и прежние подтверждённые действия передаются в prompt. Дополнительные документы надо указать в instruction_paths. Модель возвращает QA JSON; worker сохраняет его. Без разрешённого инструмента создания артефакта/проверки модель сообщает ограничение. Для задач записи кейсов, браузера или изменения кода нужно подключить подходящий scoped MCP-сервер; обычный shell этому адаптеру недоступен.

`adapter.kind=command` запускает доверенную argv-программу с QA_EXECUTION_* контекстом. Это интерфейс для локальных фикстур и собственных адаптеров, а не песочница для произвольной команды. Скрипт может обращаться к файловой системе с правами пользователя. Политика шлюза ограничивает вызовы через него; для недоверенных серверов и процессов необходима изоляция хоста. Не используйте прямой command-адаптер, чтобы обходить согласованный scope.

В этой среде CLI GIGACODE отсутствует: проверены локальные процессы, конкурентные запуски, реальный stdio MCP на фикстурах и состав GIGACODE-команды, но не реальный модельный запуск или качество отчётов. Исторические протоколы доступны в истории Git; они не подтверждают текущую интеграцию GIGACODE. Локальные проверки текущей версии описаны в RELEASE_2.3.0.md.

Контракт и пределы адаптера — [RUNTIMES.md](RUNTIMES.md). Проектные форматы GIGACODE — [официальная документация](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/subagents). Идентификация macOS: [Apple proc_info.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info.h).

Новые планы используют выборочный `context_profile` и лимит `max_context_characters`; исходные документы/сборщик заморожены. Обязательные предметные разделы передаются явно. Context/usage метрики попыток доступны в CLI-сводке; неизвестные расходы остаются null. Подробности и full-режим — [CONTEXT_ASSEMBLY.md](CONTEXT_ASSEMBLY.md).

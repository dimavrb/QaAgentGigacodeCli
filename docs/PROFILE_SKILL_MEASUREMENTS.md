# Развитие профильных skills по измерениям

В исходники добавлены два узких кандидата: [qa-test-data](../.gigacode/skills/qa-test-data/SKILL.md) для `qa-test-data-builder` и [qa-stub-contract](../.gigacode/skills/qa-stub-contract/SKILL.md) для `qa-stub-builder`. Они связывают существующие стандарты с решениями в своей области, не заменяют протоколы и не дают новые инструменты. Польза для GIGACODE пока **не измерена**: доступных оценённых ответов модели нет, preflight 2026-10-09 фиксирует отсутствие CLI.

Это гипотезы из существующих процедур, а не обобщение якобы измеренных ошибок модели. Для данных проверяем, помогает ли связка «запись → обнаруживаемая ошибка → готовность/владелец» избежать слабого набора и ложной готовности. Для заглушек — помогает ли связка «matcher → positive/negative → readback/capture → зависимости» избежать широкого совпадения и устаревшего наблюдения. Проверки Python подтверждают работу измерительного механизма, не пользу инструкций.

## Сравнимый эксперимент

`profile-suite.json` содержит 15 заданий и 60 критериев: по три задания на данные и заглушки плюс девять прежних заданий других ролей для контроля регрессий. Матрица skill/роль хранится в `scripts/profile_skills.py`; каждой целевой роли передаётся только её кандидат. В обеих ветках остаются те же документы, self-review и общий qa-check-quality. Изменяется только добавление профильного skill; инструкции и ответы сохраняются по каждому испытанию. Полные стандарты данных/заглушек переданы явно, потому что reasoning-профиль не может дочитать файлы.

После установки GIGACODE запусти из корня пакета, подставив фактическую модель и новые каталоги:

```bash
python3 scripts/run_agent_benchmark.py --suite examples/benchmark/profile-suite.json --output-dir artifacts/benchmarks/profile-off-01 --model MODEL --repeats 3 --profile-skills off
python3 scripts/run_agent_benchmark.py --suite examples/benchmark/profile-suite.json --output-dir artifacts/benchmarks/profile-on-01 --model MODEL --repeats 3 --profile-skills on
```

Задания и независимая рубрика разделены; runner не выставляет оценки. Проверяющий получает сохранённые ответы, задания и рубрику, но не чужую оценку. Желательно скрыть название ветки при оценке. Заполняются **все** `trial-N/review.json`: `pass/fail/not_checked`, точное место ответа в evidence, идентичные фактические модель/провайдер/настройки и имя проверяющего. Запрошенный `--model` ещё не доказывает фактическую модель: проверь её по доступным данным; если неизвестна, оставь оценки непроверенными. Дополнительные сведения о провайдере/настройках добавь одинаково к configuration обеих веток, сохраняя различие profile_skills.

Проверь каждую ведомость через `check_benchmark_review.py --suite <run>/suite.json --input <run>/trial-N/review.json`, затем:

```bash
python3 scripts/compare_profile_skills.py --baseline artifacts/benchmarks/profile-off-01 --candidate artifacts/benchmarks/profile-on-01 --output artifacts/benchmarks/profile-comparison-01.json
```

Сравнение требует одинаковых заданий/версии пакета/CLI/модели/условий, всех повторов, неизменных общих инструкций, точных хешей и ответов из terminal event. Оно отклоняет пересчитанный хеш подменённого ответа, изменение usage или исключение неудачного повтора. Оценка смысла и честность reviewer остаются его ответственностью: скрипт не может удостоверить их по имени и ссылке.

## Как менять skill после отчёта

1. Выбери `roles[роль].weak_points`: число неудачных повторов, критерий, конкретные evidence. Единичный сбой сначала повтори; проблема интерфейса/доступа не исправляется добавлением предметного правила. `not_checked` и отсутствие CLI не являются ошибкой модели или успехом.
2. Сделай узкую правку соответствующего skill: уточни выбор наблюдения, момент дочитывания документа или условие готовности. Общий дефект нескольких ролей исправляй в общем стандарте, а не копиями в каждом профиле. Запиши исходный отчёт/хеш skill, обнаруженную ошибку и основание правки.
3. Повтори обе ветки в новых каталогах при одинаковых условиях. Добавь самостоятельное задание с другим примером этой ошибки и контроль нормального случая **до** запуска обеих веток; не меняй рубрику после просмотра ответов. Не ограничивай оценку улучшенным примером.
4. `review_for_promotion` допускается только для live, минимум двух полных повторов, всех pass данного профиля, исправления хотя бы одного baseline fail и отсутствия регрессии в других ролях. Это повод проверить подключение кандидата по умолчанию, а не статистическое доказательство или автоматическое изменение маршрута. `no_demonstrated_gain` сохраняет прежнюю маршрутизацию; `revise_candidate` требует пересмотра; `pending_measurement` требует недостающих измерений.

Отчёт сохраняет отдельные улучшения и регрессии по каждому критерию, повторяемые слабые места и затраты только на парных задачах, полностью прошедших обе оценки. Если usage неизвестен хотя бы в одной паре, среднее остаётся null; известно число измеренных пар. Не сравнивай экономию токенов за счёт неправильного ответа. Время/токены интерпретируй после качества, с учётом требуемой пользы и цены дополнительного контекста.

## Подключение и границы

В benchmark `--profile-skills` по умолчанию `off`. Кандидаты доступны для явного пилота; managed-план может передать соответствующий путь через существующий `instruction_paths` вместе с нужными стандартами. Стандартные managed-снимки пока не подключают их автоматически. Обычная discovery GIGACODE зависит от установленной версии; A/B runner использует bare и замороженные инструкции.

`--measurement-kind fixture` обязателен для синтетического CLI-адаптера. Такие результаты получают `fixture_only` и не дают рекомендации о подключении, даже при всех pass. Это явная декларация происхождения: скрипт не может доказать, что произвольный адаптер является живой моделью. Не переименовывай фикстуры в live. Код 0 сравнения означает полученный live-отчёт, а не улучшение; код 1 — отсутствие/неполноту измерений либо fixture, код 2 — несравнимые/повреждённые данные. Выходной отчёт не перезаписывается.

Reasoning-задачи не проверяют выполнение MCP или продукта. Для этих выводов нужен отдельный живой эксперимент с разрешёнными инструментами и свежими квитанциями по [REVIEW_EXECUTION.md](REVIEW_EXECUTION.md). Архив релиза 1.9 не изменён.

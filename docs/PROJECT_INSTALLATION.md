# Проектная установка QA-пакета 2.3.14

Python 3.10+, стандартная библиотека, macOS/Linux или WSL. Первая установка может выполняться командой /qa:init
в GIGACODE; обновление используемого пакета выполняется между сессиями. QA MCP-сервер не требуется
и не поставляется. Внешние подключения браузера/Jira и scoped gateway управляемых
исполнителей настраиваются отдельно; их полномочия этот установщик не меняет.

## Одна команда в GIGACODE

При уже подключённом QA extension выполните `/qa:init` из корня приложения.
GIGACODE самостоятельно выполняет shell-шаги из commands/qa/init.md: Git clone
официального репозитория в уникальную `.qa-agent/bootstrap.local/install.*/source`,
затем локальный `qa_install.py --project-root <project_root> --bootstrap --apply`.
Python из внешнего extension не запускается. Потребуются Git, сеть и shell-tool;
отказ в доступе не обходится. При отсутствии самого extension slash-команды нет:
используйте терминальный способ ниже либо сначала подключите профиль extension.

--bootstrap допускается только из проектной staging-папки и только при отсутствии
install.json и package. Он разрешает открытую сессию GIGACODE для первой установки,
но сохраняет проверки незавершённых QA-задач/планов, конфликтов, pending и блокировок.
Первичная установка не запускает QA-работу. После неё откройте новую сессию,
чтобы клиент загрузил проектный профиль. Живая загрузка CLI не подтверждается
локальными тестами установщика. Повтор /qa:init не скачивает и не обновляет пакет,
а выполняет локальные init и doctor уже установленной версии.

Bootstrap-папка игнорируется Git. При сетевой ошибке установка не продолжается,
целевой пакет не создаётся вручную. Временный исходник не является активным runtime.
Обновление установленного пакета внутри активной сессии запрещено; используйте
терминальный порядок ниже после завершения работы.

## Установка и обновление

Получите проверенный выпуск 2.3.14 в отдельную папку. Для исходной Git-копии
сверьте выбранный commit; для ZIP проверьте checksum и PACKAGE_MANIFEST.json.
Установщик копирует только состав поставки, а не .git, окружения и личные файлы.
При наличии PACKAGE_MANIFEST.json любое расхождение источника отклоняется.

```bash
python3 /path/to/qa-agent/scripts/qa_install.py --project-root /path/to/app
python3 /path/to/qa-agent/scripts/qa_install.py --project-root /path/to/app --apply
```

Первая команда показывает план без записи. Вторая устанавливает либо обновляет
весь комплект. Источник может находиться вне приложения либо в .qa-agent/bootstrap.local;
для обновления используйте установщик из нового выпуска. Нельзя запускать
замену из самой установленной .qa-agent/package или произвольной папки приложения. Повтор неизменённой установки ничего
не заменяет. Закройте GIGACODE и завершите незавершённые QA-задачи и managed-планы;
проверка процессов консервативна и требует закрыть также другие сессии GIGACODE.

В проекте появляются:

- `.qa-agent/package/` — полная копия выпуска с прежней структурой и VERSION;
- `.gigacode/agents/`, `.gigacode/skills/`, `.gigacode/commands/` — профиль,
  включая вложенные references, шаблоны и Python-файлы навыков;
- `.qa-agent/install.json` — переносимый список управляемых файлов/хешей и версии;
- управляемый блок импорта QA в `GIGACODE.md`, без правил разработки самого пакета;
- `.qa-agent/APP_CONTEXT.md`, только если файла ещё нет; правила локального состояния в `.gitignore`.

Существующие настройки GIGACODE, чужие роли/skills, контекст и продуктовые данные
сохраняются. При совпадении чужого файла с будущим QA-файлом установщик требует
разобрать конфликт; весь план проверяется до замены. Для прежних управляемых
ролей используется проверенная база agents.local.json: неизменённые копии
обновляются автоматически, локальные адаптации остаются конфликтами. Неизменённые старые файлы
обновляются, удалённые из выпуска удаляются только при совпадении с прежним хешем.
Изменённые пользователем файлы не перезаписываются. Сначала сохраните адаптацию
отдельно и рассмотрите её перенос в APP_CONTEXT; универсального --force нет. Изменённый блок QA в GIGACODE.md также требует
разбора; инструкции приложения вокруг блока сохраняются.

## Запуск и обновление одной командой

Один раз настройте alias в shell (для новых терминалов сохраните его в shell-профиле):

```bash
alias qa-start='python3 .qa-agent/package/scripts/qa_start.py'
```

Дальше из корня приложения выполняйте `qa-start`. До появления модельной сессии
launcher проверяет установленный комплект, получает main официального репозитория
в проектную bootstrap.local, сравнивает VERSION и проверяет успешный CI нового
коммита. Только после проверки состава и импорта в отдельном интерпретаторе
он вызывает новый установщик. Блокировка проекта передаётся установщику и новому
launcher; после замены launcher перезапускается на новом коде, затем открывает GIGACODE.

| Состояние | Поведение |
| --- | --- |
| Есть проверенная новая версия того же major | Обновить пакет/профиль и запустить новую версию |
| Новая версия отсутствует | Запустить установленную |
| Нет Git/сети или CI ещё не подтверждён | Сообщить причину и запустить установленную |
| QA-задачи/планы незавершены либо уже есть CLI-сессия | Отложить обновление и открыть установленную |
| Есть конфликт/повреждение/незавершённая установка | Остановиться с диагностикой |
| Доступен новый major | Сообщить и оставить установленную версию до ручного перехода |

`qa-start --no-update` запускает установленную копию без сетевой проверки.
`qa-start --update-only` проверяет/применяет обновление без запуска модели; код 1
означает, что обновление отложено/недоступно, код 2 — ошибку. Изменённые собственные
файлы пакета не запускаются даже с --no-update: сначала восстановите целостность.
Проверка процессов консервативна: открытая сессия GIGACODE в другом проекте также
откладывает обновление. Прерванный новый установщик сохраняется в bootstrap.local
для диагностики/восстановления. Успешный/неприменяемый staging удаляется.

В новой сессии проверьте /qa:doctor, /agents manage, /skills, /help и /memory,
затем /qa <цель>. Обычный `gigacode` тоже поддерживается, но не проверяет обновления.
Скрипты разрешаются от .qa-agent/package, cwd и продуктовые файлы — от корня приложения.

## Git и перенос

Коммитьте `.qa-agent/package/`, `.qa-agent/install.json`, установленные файлы
профиля и блок GIGACODE.md одним согласованным изменением. Описание установки
содержит только относительные пути и переносится в другой checkout без rebind.
Абсолютные пути вычисляются при запуске. APP_CONTEXT можно хранить в Git, только
если это общий контекст без секретов; персональные настройки храните отдельно.
Локальные `project.local.json`, `install.local/`, `session.local.lock`, реестры,
доказательства, Python caches и журналы обновления не коммитьте.

После git pull/clone выполните doctor; первый init создаёт лишь недостающий
контекст/правила игнорирования. Git pull не использует блокировки установщика:
обновляйте checkout между сессиями. Старые задачи с абсолютными путями и frozen
хешами не становятся переносимыми от переноса пакета. Перед продолжением проверьте
их прежний план; новая ревизия инструкций требует нового согласованного плана.
Для отдельного репозитория автотестов нужна своя проектная установка.
Общий browser_pool_path остаётся общим, не копируйте состояние пула в каждый проект.

## Прерывание и восстановление

Обновление хранит до/после в игнорируемом `.qa-agent/install.local/` и публикует
install.json последним. При обычной ошибке восстанавливаются прежние файлы.
При аварийной остановке init/doctor отказывают до явного восстановления:

```bash
python3 /path/to/qa-agent/scripts/qa_install.py --project-root /path/to/app --recover --apply
```

Восстановление сначала проверяет весь журнал. Изменённый после прерывания файл
не затирается. Затем повторите обновление. После завершения операции её backup-файлы удаляются. При прерывании подготовки
до записи журнала могут остаться неиспользуемые файлы в игнорируемом install.local;
они не являются рабочей версией пакета.

## Переход с глобального extension

Сохраните адаптации и завершите активную работу. Установите проектный комплект
из нового выпуска; конфликтующие прежние роли/навыки разберите до применения.
Через штатный менеджер вашей сборки отключите прежний глобальный qa-agent,
проверьте отсутствие его MCP-сервера/инструкций в новой сессии. Установщик не
редактирует глобальный registry и настройки пользователя. Прежние local binding
и история ролей остаются локальными историческими файлами; новый режим использует
install.json. Сохранённые задачи, доказательства и хеши не пересчитываются.

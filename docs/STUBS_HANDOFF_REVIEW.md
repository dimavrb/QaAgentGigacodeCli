# Проверка передачи qa-stub-builder

Изменения заглушек из ветки подготовки 2.3.8 входят в текущую поставку вместе
с остальными изменениями пакета. Предметный контракт остаётся schema_version=2;
версии QA-событий не меняются. Основные правила — [STUBS.md](STUBS.md).

Закрыты три пробела локального протокола:

- stub_assignment проверяется при assign и автоматически замораживается до
  handoff. Роль, task/request и сценарии должны совпадать. Пересчёт своих
  assignment_sha256/profile_sha256 не разрешает исполнителю менять намерение;
- будущие issued_at, prepared_at, verification_started_at, resolved_at,
  observed_at и Kafka-интервалы не подтверждают уже выполненные действия;
- новые назначения включают вложенные readback, positive/negative и before-снимок
  updated в artifact_hashes. Они пригодны для assess; изменение файла после
  CLI-проверки до сохранения результата обнаруживается атомарно.

Относительные пути реестра используют artifact_base. Standalone CLI сохраняет
каталог результата по умолчанию и поддерживает --stub-evidence-base. Пути с
пробелами/# не теряют файловую идентичность. Reviewer scope=stubs получает
предметный стандарт, а первичные файлы передаются ему через inputs.

Настройка без проб не открывает продуктовый прогон; partial открывает только
подтверждённые сценарии. Discovery/blocked без scope сохраняются. Новый request_id,
включая retry, требует соответствующего намерения координатора; старый scope
автоматически не переписывается. Исторические реестры без stub_evidence_required
сохраняют прежний набор хешей; вложенные SHA проверяет валидатор v2.

## Проверки

47 проверок заглушек прошли: 27 прежних и 20 новых. Новые случаи охватывают
замороженный scope, несовпадение роли/task/request/сценариев, невалидное намерение,
замену до prepare и resealing до submit, вложенные хеши/критерии, гонку после CLI,
partial/configure_only/discovery/blocked, artifact_base и standalone CLI,
исторические хеши, предметный контекст reviewer, before-снимок и будущие времена.
Отдельно прошли 52 проверки совместимости контрактов, передач и контекста.

При полном прогоне обнаружена зависимость тестового recovery-zipapp от
посторонних процессов на машине: активный CLI выбирал другой корректный отказ
раньше ожидаемой проверки изменённых файлов. Только тестовая фикстура теперь
задаёт результат ps. Отдельный тест проверяет отказ при наблюдаемом активном CLI
и неизменность исходников/установки. Рабочий qa_recover.py не менялся.

Окончательный полный прогон актуального пакета **2.3.9: 943 теста, OK**.
Контрольные суммы кода до и после прогона совпали. Отдельно прошли все 18
проверок восстановления, включая новую изоляцию наблюдения процессов.

```bash
python3 -m unittest discover -s tests -p 'test_stub*.py' -v
python3 -m unittest discover -s tests -v
```

Это синтетические проверки файлов/реестра без sbermock/MCP и живой модели.
Хеш и timestamp не удостоверяют фактическую запись, владение и истинность
наблюдения; координатор проверяет содержание по первичным материалам. Навык
qa-stub-contract есть в поставке, его полезность для модели здесь не измерялась.

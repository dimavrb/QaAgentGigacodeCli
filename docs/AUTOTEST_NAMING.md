# Названия автотестов и Allure-шагов

Автор названий — `qa-test-automation`, независимая проверка — `qa-autotest-reviewer`, принятие — координатор. Применяй к новым и существенно изменённым тестам; массовое переименование не входит в обычную задачу. Это дополнение к `TEST_CASE_STYLE.md` для исполняемых тестов. Отдельный агент не нужен.

## Перед изменением

Прочитай ближайшие тесты и конфигурацию отчётности: язык человекочитаемых названий, адаптер Allure и его установленную версию, параметризацию, правила ссылок на сценарии. По умолчанию используй русский язык; явный стандарт целевого проекта имеет приоритет, отклонение кратко сохрани в материалах ревью. Имена методов, файлов и классов следуют соглашениям кода. Не устанавливай Allure и не меняй зависимости только ради названий. Если Allure отсутствует, используй названия штатного фреймворка и отметь неприменимость проверки Allure.

## Название теста

По `TEST_CASE_STYLE.md`: **`<объект> — <условие или действие> — <ожидаемый результат>`**. Условие должно отличать проверяемый вариант, результат — соответствовать источнику и реальным assert. Отрицания, границы, права и существенный тоггл нельзя убирать ради краткости. Название описывает ожидание, а не утверждает, что тест прошёл.

Сохраняй `scenario_id` отдельно, через принятые ссылки/метаданные или существующую карту покрытия. При наличии каталога используй его название для того же поведения. Для более узкой автоматизированной проверки уточни условие и результат, сохрани ID и объясни границу покрытия; не называй проверку статуса API проверкой всей оплаты или интерфейса.

Параметризованные варианты должны различаться стабильным значимым условием в имени варианта или видимых параметрах отчёта. Используй статус, роль, границу или значение тоггла; случайный UUID заказа, время запуска и секреты в названия не включай. Секреты не передавай в Allure-параметры даже как hidden/masked. Не меняй ID сценария ради редакторской правки. При необходимом переименовании проверь влияние на выбор тестов и сравнимость истории в данном адаптере.

## Allure-шаги

- **Действие:** глагол в неопределённой форме + объект + существенное условие: `Запросить список заказов со статусом «Оплачен»`.
- **Проверка:** `Проверить, что <конкретный наблюдаемый результат>`: `Проверить, что все возвращённые заказы имеют статус «Оплачен»`. Внутри этого шага выполняется соответствующий assert, а не только запись в лог.
- **Подготовка/очистка:** называй отдельно: `Подготовить оплаченный и неоплаченный заказы`, `Удалить созданные заказы`. Не выдавай подготовку за проверку поведения.

Верхний уровень объясняет сценарий; технические вызовы и диагностика могут быть вложенными шагами или вложениями. Не создавай второй ручной шаг вокруг каждого автоматически записанного клика. Не объединяй независимые действия в «Выполнить сценарий». Название должно совпадать с телом шага: если проверяется только HTTP-код, не обещай проверку содержимого. Ошибка assert должна выходить из шага и падать в тесте; не скрывай её исключением или вручную выставленным passed. No-op/log-шаг не является доказательством проверки.

Правило ручного каталога «ожидаемый результат отдельно» сохраняется. Проверочный Allure-шаг — дополнительная исполняемая проверка, он не заменяет и не переписывает ожидаемый результат каталога.

## Как записать название в коде

Используй API установленного адаптера и существующие обёртки проекта. Справочные точки входа:

| Стек | Название теста | Шаг с исполняемым телом |
| --- | --- | --- |
| JUnit Jupiter + Allure | `@DisplayName("…")` | `@Step("…")` на выполняемом методе либо `Allure.step("…", () -> { … })` |
| pytest + Allure | `@allure.title("…")` | `@allure.step("…")` либо `with allure.step("…"):` |
| Playwright Test + Allure | `test("…", async () => { … })` | `await test.step("…", async () => { … })` либо исполняемый `allure.step` |

Проверь подстановку параметров и асинхронное выполнение в используемой версии; аннотация или красивое имя сами по себе не доказывают, что адаптер записал шаг. Справка: [JUnit Jupiter](https://allurereport.org/docs/junit-jupiter-reference/), [pytest](https://allurereport.org/docs/pytest-reference/), [Playwright](https://allurereport.org/docs/playwright-reference/). Учебные примеры и короткое ревью — `examples/autotest-naming/README.md`.

## Проверка и передача на ревью

Автор дополняет существующий артефакт качества: `scenario_id → тест/параметризованный вариант`, источник правила языка, изменение имён (если было), ссылка на результат адресного запуска с записанными названиями и шагами. Для Allure прочитай свежий результат нужного запуска или сформированный отчёт: название, значимые варианты и вложенные шаги должны совпасть с выполненным кодом. Старый отчёт не подтверждает текущую ревизию. Если формирование отчёта недоступно, сохрани ограничение «названия проверены в коде; отображение Allure не проверено».

Ревьюер проверяет: понятен ли сценарий без открытия кода; совпадают ли условие/ожидание с источником и assert; различимы ли параметры; нет ли секретов и лишних технических шагов; действительно ли проверочный шаг содержит проверку и передаёт ошибку. В существующем `checks` укажи основание и результат, в `limitations` — непроверенное отображение. Название, обещающее непроверенное поведение, скрывающий ошибку шаг или утечка секрета требуют исправления; редакторское предпочтение без потери смысла — рекомендация. `review_passed` при ограничениях не означает, что отображение Allure подтверждено; обязательный критерий назначения с недоступным доказательством остаётся незавершённым.

Новые поля QA-событий и JSON-каталога не требуются. Валидатор каталога не проверяет код Allure или фактическое содержание assert; эти проверки выполняет автор и независимый ревьюер.

# Ответы на вопросы агента через HTML

Координатор собирает требующие решения пользователя вопросы в один пакет и показывает HTML-форму. Пользователь отвечает по каждому пункту; в режиме serve кнопка «Отправить все ответы» сохраняет общий ответ в заданный локальный JSON-файл. Самостоятельный build только формирует экспорт для ручной передачи. Есть свободный текст, один или несколько вариантов выбора, общий комментарий и явное «Пока не знаю». Черновик сохраняется в этом браузере отдельно для каждой ревизии вопросов.

## Работа координатора

До открытия формы выбери и запиши канал получения. Если ответ нужен агенту на
диск автоматически, запускай только serve с абсолютным --answers и отдельный
wait с теми же путями/реестром. Wait читает файл, а не создаёт ответ. Проверка
канала проходит после получения валидного файла по назначенному пути; готовый
HTML, localStorage, сообщение браузера или сам адрес сервера этого не доказывают.
Не добавляй --answers к build: у этой команды такого аргумента нет.

1. Сначала ищи ответы в доступных источниках. В форму включай только оставшиеся вопросы, сохраняя `question_id`, зависимости и конкретный контекст. Не спрашивай известное повторно и не выбирай ответ за пользователя.
2. Сохрани пакет в `artifacts/questions/<task>/<request>/questions.json`. Используй новый `request_id` для нового раунда. Формат ниже; существующий результат аналитика с `payload.blocking_questions` или автора плана с `payload.open_questions` также можно передать напрямую. Решённые вопросы пропускаются. Для объединения нескольких отчётов подготовь отдельный пакет с уникальными ID.
3. Запусти локальную форму командой `serve`, сохрани процесс и адрес. Передай пользователю кликабельную ссылку на адрес, выведенный скриптом. При работе на одном компьютере открывай его в доступном браузере. При работе на удалённой машине используй самостоятельный HTML; localhost относится к машине с процессом.
4. Запусти `questionnaire.py wait` в фоне с теми же input/answers и task-state. По умолчанию он ждёт до 20 минут, проверяя файл сразу, затем раз в 60 секунд и на границе таймаута. Сохрани процесс ожидания и продолжай независимую работу; когда она закончится, ожидай результат процесса, не завершая ход только из-за формы. Возврат answers_ready содержит проверенные ответы; прочитай их. timeout оставляет вопросы открытыми: сообщи пользователю, что ответ не получен за 20 минут, не начинай новый цикл автоматически. Не занимай ожиданием единственный инструмент, нужный для независимой работы.
5. Прочитай полный сохранённый ответ: answers[].status, text, selected_options и обязательно overall_comment. Общий комментарий может содержать существенное решение даже при всех deferred; это полученный ответ с открытыми вопросами, а не «ответов нет». Для `answered` оцени смысл ответа и затронутые зависимости; сохрани `resolution` и `decision_source` со ссылкой на JSON и `question_id` в новой ревизии карты. При решении по overall_comment сошлись на это поле и явно сопоставь решение с вопросами; не меняй исходные deferred на answered задним числом. В режиме реестра сначала зафиксируй применение ответа через apply-answers и передай следующему назначению questionnaire_ids; принятый исходный пакет/отчёт сохраняй неизменным. `deferred` оставляет вопрос открытым и не снимает блокер. Форма сама не меняет план, не разрешает внешние действия и не объявляет готовность этапа. Не повторяй готовые независимые проверки.
6. После чтения останови локальный сервер, если он запущен без `--once`. Повтор того же ответа безопасен; иной ответ не перезаписывает отправленный пакет. Уточнения собирай новым пакетом.

HTML не отправляет сообщение в GIGACODE CLI и не возобновляет завершённый ход модели сам по себе. Пока координатор работает, он может прочитать появившийся файл; если он уже ждёт ввода в чате, пользователь пишет один раз «Ответы отправлены», после чего координатор читает сохранённый файл без повторного ввода ответов. Не обещай автоматическое продолжение без поддержки среды запуска.

В текущих исходниках доступен [supervisor](MANAGED_EXECUTION.md): работающий serve может запустить заранее заданный worker-шаг после ответов на связанные wait_for_questionnaire_ids. По умолчанию требуется содержательное apply-answers координатора; заранее согласованный auto_apply_answers передаёт полностью отвеченный пакет как контекст. Полномочия и критерии не меняются, deferred оставляет ожидание. Это продолжение планового исполнения, а не пробуждение завершённого чата; архив 1.9 этого механизма не содержит.

## Локальная форма

Для новой задачи подключай форму к общему реестру параметрами `--task-state` и `--expected-revision` по [TASK_EXCHANGE.md](TASK_EXCHANGE.md). Отправка создаёт `answers_ready`, а работающий координатор получает его через `manage_task.py wait`, читает ответы, обновляет решения и фиксирует `apply-answers`. Принятые ранее ответы восстанавливают уведомление после перезапуска. Без реестра остаётся прежний режим сохранения файла и короткого сообщения в чат; автоматическое пробуждение завершённого чата не добавлено.

```bash
python3 scripts/questionnaire.py serve \
  --input examples/questions/questions.json \
  --answers artifacts/questions/demo/answers.json \
  --open --once
```

Скрипт выводит адрес `http://127.0.0.1:<свободный порт>`. Требуется только Python 3. Сервер обслуживает одну форму и сохраняет только указанный файл; остальные файлы проекта через него недоступны. Принятый ответ содержит ID задачи, назначения, пакета, SHA-256 ревизии, ответы по ID и время сохранения. Старый пакет не принимается после изменения вопросов. Не используй форму для паролей и токенов.

Проверка перед применением:

```bash
python3 scripts/questionnaire.py validate \
  --input examples/questions/questions.json \
  --answers artifacts/questions/demo/answers.json
```

## Ожидание общего ответа до 20 минут

Сервер формы и процесс ожидания запускаются отдельно. После появления адреса формы
запусти команду в фоне и сохрани её process/session ID:

```bash
python3 scripts/questionnaire.py wait \
  --input examples/questions/questions.json \
  --answers artifacts/questions/demo/answers.json \
  --timeout 1200 --poll-seconds 60
```

Передавай те же пути, что при serve. Для режима реестра добавь --task-state с тем же
реестром, что у сервера формы; он должен уже содержать этот пакет вопросов.
Пример выше работает без реестра, как демонстрационный serve. Во время ожидания
можно продолжать другие задания; один вызов инструмента не требуется блокировать
на все 20 минут. Проверяй завершение сохранённого процесса доступными средствами
среды, не запускай дублирующий waiter для той же формы.

Первая проверка выполняется сразу, далее — раз в минуту, последняя — на границе
20 минут. Ответ, отправленный между проверками, возвращается при следующей
проверке. Уже существующий ответ возвращается сразу. JSON результата содержит
status=answers_ready, response, хеш файла и unresolved_question_ids. Код 0 означает
получение валидного ответа, включая deferred; применение бизнес-решения остаётся
за координатором. «Пока не знаю» сохраняет блокер.

Код 1/status=timeout означает отсутствие файла к последней проверке. Форма,
реестр и открытые вопросы сохраняются; поздний ответ можно прочитать новым явно
запущенным ожиданием. Код 2 — ошибка пакета/файла/ревизии, код 130 — остановка
ожидания пользователем. Изменённый или чужой ответ не принимается. В режиме
реестра waiter восстанавливает пропущенный answers_ready, но не выполняет apply-answers.

Чтобы продолжить заранее заданный worker без отдельного waiter, используй
manage_execution.py serve: теперь по умолчанию 1200 секунд, а waiting_answers
проверяется раз в 60 секунд. auto_apply_answers по-прежнему должен быть заранее
разрешён планом; при ручном применении координатор использует waiter и apply-answers.
Техническое наблюдение за активными worker и отменой остаётся частым.

## Самостоятельная HTML-страница

```bash
python3 scripts/questionnaire.py build \
  --input examples/questions/questions.json \
  --output artifacts/questions/demo/questions.html
```

Открой HTML в браузере. Страница работает без сервера и сети: кнопка «Сформировать общий ответ» готовит текст для одного сообщения в чат и JSON для скачивания. В этом режиме она не записывает файл в проект автоматически. Доступ к буферу обмена зависит от браузера; при отказе текст выделяется для обычного копирования.

Вместе с build обязательно передай пользователю явную инструкцию: «Скопируйте
общий ответ в чат либо скачайте qa-answers.json и передайте файл агенту; эта
страница не сохраняет answers.json в проект». Без такого ручного канала build
не является подготовленной анкетой для автономного ожидания. Координатор
сохраняет полученный JSON по согласованному абсолютному пути, запускает validate,
для реестра — notify-answers, затем читает overall_comment и выполняет
содержательное apply-answers. При получении только текста сохрани его первичный
снимок; восстановленный JSON явно проверь с пользователем при неоднозначности,
не выдумывай выбранные варианты, статусы и ревизию. До валидного пакета файл
ответов и ready-событие не считаются полученными.

## Формат пакета

```json
{
  "task_id": "QA-123",
  "request_id": "QA-123-questions-1",
  "questionnaire_id": "QA-123-clarification-1",
  "title": "Уточним правила удаления",
  "description": "Ответ нужен для ожидаемых результатов двух кейсов.",
  "questions": [
    {
      "question_id": "Q-1",
      "question": "Кто может удалять чужие заказы?",
      "context": "В требованиях пока описан только свой заказ.",
      "type": "single",
      "options": ["Только администратор", "Администратор и оператор"],
      "requirement_ids": ["R-2"],
      "scenario_ids": ["TC-007", "TC-008"],
      "blocks": "planning"
    }
  ]
}
```

Обязательны `task_id`, `request_id`, непустой список `questions`, уникальный `question_id` и текст `question`. Типы: `text` без вариантов, `single` с одним выбором, `multiple` с несколькими; при наличии `options` тип по умолчанию — `single`, иначе `text`. Варианты — уникальные непустые строки. Свой ответ доступен при любом типе. Не задавай предвыбранных ответов. `questionnaire_id` по умолчанию состоит из ID задачи и назначения, ревизия вычисляется скриптом. Пример всех трёх типов — `examples/questions/questions.json`.

Это отдельный артефакт взаимодействия с пользователем; оболочка QA-событий и статусы исходных вопросов не меняются. Проверка формата ответа не подтверждает корректность бизнес-решения.

В установленном проекте добавь короткое правило формы из GIGACODE.md в существующий `qa-agent/APP_COORDINATOR.md`, используя префикс `qa-agent/docs/` и `qa-agent/scripts/`. Сохрани настройки и ограничения приложения. Новые инструкции применяются в новой сессии; исходные архивы версии 1.8 не содержат эту ещё не выпущенную доработку.

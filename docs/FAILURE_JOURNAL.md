# Журнал сбоев QA-процесса

Журнал показывает симптом, влияние, причину и результат восстановления. Он хранится локально; данные приложения и доказательства не отправляются во внешние сервисы.

## Когда записывать

Координатор фиксирует неожиданный технический блокер, неверный/невалидный результат, потерю существенного состояния или повтор без основания. Обычный вопрос, корректное unknown и ожидаемая подготовка условий сами по себе не ошибка. Найденный дефект продукта остаётся в отчёте тестирования; он не становится инцидентом агента только потому, что сценарий failed.

Один общий блокер нескольких сценариев — один incident_id. Уточнения и восстановление сохраняют incident_id, но получают новый event_id. Новый независимый сбой другого назначения получает новый incident_id. Повтор того же event_id с тем же содержимым ничего не добавляет; попытка изменить его отклоняется. История не редактируется; одновременную запись защищает файловая блокировка.

## Команды

Из корня QA-пакета:

```bash
python3 scripts/manage_failure_journal.py init --journal .qa-agent-state/failures.jsonl
python3 scripts/manage_failure_journal.py record --journal .qa-agent-state/failures.jsonl --entry /absolute/path/to/incident.json
python3 scripts/manage_failure_journal.py check --journal .qa-agent-state/failures.jsonl
python3 scripts/manage_failure_journal.py summarize --journal .qa-agent-state/failures.jsonl --output-dir artifacts/failures/summary-v1
```

record создаёт отсутствующий журнал сам. init и summarize не перезаписывают существующие файлы/каталоги. В проекте приложения используй `qa-agent/scripts/` и явно заданный общий путь журнала. Скрипты используют stdlib и POSIX-блокировку: macOS/Linux, для Windows — WSL; нативный Windows не проверялся.

## Входной incident.json

Полные примеры — examples/failure-journal/*.json. Каждое обновление содержит полный снимок, а не patch. Время наблюдения имеет timezone и не идёт назад относительно предыдущего снимка инцидента.

| Поле | Содержание |
| --- | --- |
| schema_version | Целое число 1 |
| event_id, incident_id, occurred_at, actor | ID, время наблюдения, автор оценки |
| task_id, request_id, stage, agent, agent_version, scope_kind | Назначение, этап, затронутая роль/версия, operational или synthetic; неизменны внутри инцидента |
| summary, symptom, impact | Суть, наблюдаемый тип проблемы и влияние; неизвестное влияние описывается явно |
| scenario_ids, context, evidence | Затронутые ID, существенные условия и непустой список ссылок; неизвестные условия — null |
| cause | status, category, description, evidence |
| recovery | outcome, action, result, evidence |
| reopens_event_id | Только при повторном открытии: event_id прежнего восстановления |
| regression_case | Необязательно: status, reason, evidence контрольного задания |

Этапы: analysis, planning, environment, test_data, investigation, feature_testing, automation, review, reporting, jira, orchestration.

Симптомы: blocked_execution, tool_error, invalid_result, wrong_conclusion, incomplete_coverage, repeated_action, lost_progress, timeout, other. Timeout не доказывает неисправность сети или модели.

Причины: requirements, verification, environment, test_data, tool, context, coordination, retry, execution, unknown. При cause.status=unknown category=unknown, description=null, evidence=[]. suspected требует конкретной гипотезы и основания. confirmed требует отдельной записанной оценки и локального доказательства: actor отличается от затронутой роли и не равен qa-runner. Строка actor не удостоверяет личность; смысл подтверждения проверяет координатор/независимый проверяющий.

У recovery outcome: not_attempted, in_progress, failed, verified. Для not_attempted action/result равны null, evidence пуст. Для начатой попытки нужен action. failed и verified требуют наблюдаемого result и доказательств; verified дополнительно требует локального доказательства. План перезапуска не подтверждает восстановление. Статус вычисляется как open, recovering или recovered. Повторное открытие требует reopens_event_id; причину нужно пересмотреть. Снятие блокера не означает завершение сценариев или готовность релиза.

Ссылки разрешаются относительно входного файла. Журнал сохраняет абсолютные пути и SHA-256, а не содержимое доказательств. HTTP(S) не читается по сети и остаётся remote_unverified. Доказательства сохраняй неизменяемыми; путь результата не переиспользуй для другого назначения. Промпты, пароли, токены и персональные данные в журнал не копируй. Чувствительные сведения удаляются до записи, без изменения первичного результата.

## Сводка и проверка

summary.md показывает суть, влияние, причину и восстановление; summary.json содержит детали. Последний снимок каждого incident_id считается один раз. Наблюдаемые симптомы, гипотезы и причины с записанным подтверждением учитываются отдельно. Причины с изменёнными/недоступными доказательствами не попадают в счётчик подтверждённых причин с неизменными доказательствами. Если доказательства симптома или восстановления изменены/недоступны, прежнее recovered отображается как recovery_unverifiable. История остаётся; новые независимые записи можно добавлять даже при недоступности старого доказательства.

По умолчанию учитывается только operational. Для учебных записей: `--scope-kind synthetic`, для объединённых — all. Числа показывают зарегистрированные инциденты, а не вероятность сбоя среди всех запусков: полного знаменателя журнал не собирает. Версии сравниваются при одинаковых задачах и условиях.

regression_case имеет status=candidate, added или not_needed и reason. Для added нужен сохранённый артефакт задания; его полезность проверяется содержательно по EVALUATION.md. Автоматического создания/запуска контрольных заданий нет.

check возвращает 0 для корректной истории без ограничений текущих доказательств, 1 при changed/missing/remote, 2 при неверном формате/цепочке или ошибке чтения. Неполный хвост после аварии не отбрасывается автоматически: сохрани повреждённый журнал, восстанови полный префикс в новом файле и разбери утраченную запись. Хеши не защищают от умышленной полной перезаписи или удаления хвоста без внешнего checkpoint. Лимиты — 64 MiB на журнал, 128 KiB на строку; архивируй по периоду/проекту с доказательствами.

## Автоматическая запись из runner

Управляемый supervisor по [MANAGED_EXECUTION.md](MANAGED_EXECUTION.md) также записывает технический сбой, timeout, потерю процесса и невалидный результат. Общий путь задаётся в плане через failure_journal; по умолчанию artifacts/failures/agent-errors.jsonl внутри workspace. Доказательство — отдельный failure-observation.json попытки; stdout/stderr и prompt в запись не копируются. В attempt сохраняется failure_incident_id. Сохраняются cause=unknown, recovery=not_attempted; следующий успешный запуск сам по себе не дописывает verified. Пользовательская отмена не регистрируется как ошибка. Продолжение анализа инцидента — обязанность координатора.

run_test_automation.py записывает наблюдение после timeout, ненулевого завершения GIGACODE, невалидного ответа или валидного blocked. Путь по умолчанию — failures.jsonl рядом с файлом состояния; `--failure-journal /absolute/path/to/failures.jsonl` задаёт общий путь проекта. Журнал и lock находятся вне репозитория автотестов и не пересекаются с файлами запуска.

Runner сохраняет cause=unknown, recovery=not_attempted, ссылку/хеш вывода, код выхода и число ошибок валидации. Промпт и stderr в запись не копируются. needs_* и успех не считаются инцидентами. Проверки параметров до запуска, ручное прерывание и аварии самого runner не охвачены: координатор записывает их по доступным материалам.

В метриках есть failure_incident_id, failure_journal, failure_journal_error. Ошибка записи не маскирует первоначальный сбой и не исправляет повреждённую историю автоматически. Координатор сохраняет вывод и дополняет журнал после ремонта. Автоматический сбор относится к этому runner; остальные маршруты заполняются координатором.

## Использование ошибок и решений в следующих задачах

Журнал служит общей памятью о конкретных случаях. Исполнитель сообщает координатору существенную ошибку процесса, фактические условия, уже выполненные попытки, результат и ссылки на доказательства. Если ошибку обнаружило self_review и автор исправил её до передачи, зафиксируй её, когда она меняла существенный вывод, покрытие, состояние или требовала восстановления. Опечатки и обычное редактирование не требуют инцидента. Самопроверка не подтверждает причину независимо.

Координатор ведёт один incident_id через наблюдение → гипотезу/оценку причины → попытки → проверенное восстановление. Неудачные попытки также остаются в истории с recovery.outcome=failed. После решения в recovery.action опиши реально выполненные действия, в result — наблюдаемый результат и пределы выводов. Context сохраняет важные условия: проект/репозиторий, инструмент и версию, окружение, применимые настройки; неизвестное — null. Не обобщай «в этом случае помогло» до универсального правила.

Перед повтором после сбоя или назначением работы с известным риском координатор ищет похожие случаи. Поиск не нужен перед каждым обычным шагом. Используй конкретные ключевые слова, роль, этап или симптом; при известных условиях передай JSON-контекст:

```bash
python3 scripts/manage_failure_journal.py find --journal /absolute/path/to/failures.jsonl --agent qa-test-automation --symptom invalid_result --query "self_review" --context-file /absolute/path/to/current-context.json --limit 3
```

Контекст — объект с известными значениями, например `{"repo":"/absolute/path/to/tests","cli_version":"observed-version"}`. Имена ключей должны совпадать с записанными условиями. Неизвестные текущие условия опускай; null в поисковом контексте отклоняется. Это явный поиск по словам/фильтрам, не семантическая модель: все слова запроса должны встречаться как подстроки в summary, symptom, причине или восстановлении. Нет совпадения — нет найденного решения; это не доказательство отсутствия похожей проблемы.

`find` возвращает JSON и не меняет журнал. По умолчанию operational, не более пяти кандидатов (максимум 20). Учебные записи доступны только при явном scope-kind synthetic/all. Для каждого incident_id используется последний снимок: открытые, восстанавливаемые и повторно открытые случаи не предлагают старое решение. В выдачу входят только verified-восстановления с неизменными доступными локальными доказательствами симптома, причины и решения; remote_unverified также исключается. Сбой чтения или повреждённый журнал возвращает ошибку, не пустую выдачу.

Известное противоречие текущим условиям исключает кандидат. `context_match` равен matched при совпадении переданных условий, unknown при отсутствии нужных старых условий, not_checked без текущего контекста. Неизвестные условия перечислены в unknown_context_keys. Даже matched требует содержательной проверки: сравни проект, версии, требования и побочные эффекты, которых фильтр не оценивал. Новейшие совпадающие записи идут первыми; процент уверенности не вычисляется.

Каждый кандидат сохраняет incident_id/event_id, исходное назначение, условия, отдельно статус причины и действие/результат восстановления, ссылки и хеши. Рабочее исправление может иметь unknown/suspected причину — она не становится confirmed благодаря успеху. journal_sha256 и checked_at относятся к прочитанному снимку: перед применением перепроверь текущее состояние и доказательства.

После оценки передай исполнителю только относящееся решение и ссылки. При необходимости сохрани неизменяемый снимок выбранных случаев в artifacts/failures/experience-<request_id>.json и включи его в inputs нового назначения; изменяемый общий JSONL не используй как input с обязательной неизменностью. Не копируй всю историю в промпт. При существенном исправленном выводе укажи его в self_review.fixes, оставшуюся неопределённость — в remaining_risks.

Найденное решение не разрешает внешние записи, очистку, перезапуск или увеличение объёма задачи. Сначала проверь актуальные условия и полномочия назначения. Часто повторяющийся подтверждённый случай — кандидат на адресный регрессионный тест или изменение инструкции; это отдельное содержательное решение, а не автоматическая перепись общих правил.

# Пилот навыка написания тест-кейсов

Пилот проверяет отбор полезных сценариев и понятность инструкций на реальной
задаче команды. Структурная валидация и учебные фикстуры проверяют механику
пакета; они не доказывают качество живого GIGACODE и пригодность кейсов для TMS.
Публикация в TestOps не входит в этот пилот.

## Что передать для задачи

Выбери одну функцию, для которой есть подтверждённые требования и доступный
исполнитель ручных тестов. Передай агенту:

1. Задачу, критерии приёмки и источники правил с ревизией или датой. Если
   источники противоречат друг другу, укажи это, не выбирая за автора.
2. Текущие кейсы этой функции и соседнее покрытие. Стабильные ID должны
   сохраниться, если поведение остаётся тем же.
3. [APP_CONTEXT.md](../examples/qa-only/APP_CONTEXT.template.md), заполненный для
   вашего проекта: роли и способ доступа, подготовка состояний и данных,
   доступные UI/API-наблюдения, ограничения и разрешённая имитация сбоев.
   Неизвестное и временно недоступное обозначь раздельно; секреты не передавай.
4. Отдельно 15–20 проблемных кейсов или первоначальных идей, если они есть.
   Добавь несколько редких существенных сценариев и уже хороших кейсов.
   Задание только из плохих примеров провоцирует удаление всего покрытия.
5. Абсолютные `package_root`, `project_root` и назначенные пути выходных
   артефактов. Используй существующие пути проекта; новый общий каталог обычно
   хранится в `test-cases/<feature>/`, карта покрытия — в плане по
   [TASK_STORAGE.md](TASK_STORAGE.md).

Не нужно заранее сообщать агенту, какие кейсы удалить. Для оценки результата
ревьюер отдельно фиксирует защищённое покрытие и ожидаемые решения по спорным
примерам. Часть реальных примеров оставляют для итоговой проверки: их не
используют для настройки инструкций навыка.

## Prompt для реальной задачи

Подставь реальные пути и границы функции; это текст назначения, а не команда
для терминала:

```text
/qa Подготовь ручные тест-кейсы для <функция и границы задачи>.
package_root: <абсолютный путь установленного QA-пакета>
project_root: <абсолютный путь продуктового проекта>
Требования: <пути/ссылки с ревизией>
Контекст и возможности проверки: <путь APP_CONTEXT.md>
Текущий каталог и соседнее покрытие: <пути>
Кандидаты/проблемные кейсы: <путь или «отсутствуют»>
Выход: <путь плана/карты решений> и <путь JSON-каталога>.

Примени qa-test-cases и qa-check-quality. Сначала отбирай сценарии,
потом пиши подробные шаги. Для каждого кандидата зафиксируй источник,
достижимость в выбранном UI/API-режиме, добавленную пользу и решение:
отдельный кейс, включение в другой, предусловие, вопрос либо исключение
с подтверждённой причиной. При объединении укажи, где сохранено покрытие.
Сохрани существенные риски, права, границы и различия уровней проверки.
Временную недоступность данных не называй невозможностью сценария.
Неизвестные правила и способы подготовки не придумывай; задай адресные
вопросы и продолжи части, которым ответы не нужны.

Сохрани существующий schema_version: 1 и стабильные ID. В JSON включи
кейсы, готовые по проектированию: известны ожидание и подтверждённые способы
подготовки и наблюдения. Временная недоступность известного способа не мешает
сохранить такой кейс; зависимость исполнения явно укажи в плане/назначении.
Включение в каталог не означает разрешения запуска. Если неизвестно правило,
способ подготовки или наблюдения, кейс пока не готов по проектированию:
оставь вопрос и связанное покрытие в карте, не включай его в готовый каталог.
Не дублируй подробные шаги каталога в плане. Проверь каталог валидатором,
затем передай результат координатору для независимого содержательного ревью
отдельным назначенным reviewer. Повторная самопроверка автора не заменяет
независимое ревью. Не публикуй в TMS, не запускай продуктовые тесты и не меняй
требования. Передай пути артефактов, итоги отбора, существенные замечания ревью
и вопросы, которые нужно закрыть.
```

Если `/qa` в вашей установке требует отдельно назначить исполнителя, передай
этот же текст координатору через принятый маршрут. Содержательная оценка должна
использовать живой GIGACODE; локальный скрипт не заменяет автора и ревьюера.

Для managed-ревью координатор передаёт reviewer первичные требования, исходное
покрытие, текущий каталог и выбранные сведения APP_CONTEXT через `inputs`.
Задай assignment.test_type и подходящий JSON из examples/test-cases/<type>/INDEX.md
через instruction_paths. При review_target.scope=test_cases стандарты и протокол
[TEST_CASE_REVIEW.md](TEST_CASE_REVIEW.md) включаются автоматически; catalog_validations
подтверждает только структуру текущих байтов. Новые авторские профили получают
те же примеры и стандарты. Review-cycle сохраняет тип и выбор примеров автора,
и зарегистрированные target-файлы, включая inputs автора. Необъявленные первичные
ссылки он не дочитывает: каталог без доступных источников не позволяет независимо
оценить исключения и выдуманные ожидания.

## Как оценить результат

Сначала координатор назначает отдельного ревьюера, который сопоставляет карту
с требованиями и исходным покрытием. Автор может проверить собственный ответ,
но это не считается независимым ревью. Затем тестировщик, не участвовавший в
подготовке, пробует выполнить кейсы на согласованном стенде после закрытия
зависимостей исполнения. До этого проектирование кейса может быть завершено,
а запуск — заблокирован. Считай не только количество кейсов:

| Наблюдение | Как фиксировать |
| --- | --- |
| Ошибочно потерянное покрытие | Источник правила/риска, исходный кандидат, ошибочное решение, какой дефект перестали обнаруживать. |
| Лишний самостоятельный кейс | Что повторяет или почему достаточно наблюдения внутри указанного существующего кейса. |
| Невыполнимые или выдуманные инструкции | Шаг/предусловие, отсутствующий механизм или источник, необходимое исправление. |
| Невнятное ожидание | Какое неверное поведение проходит проверку и какое наблюдение различает его. |
| Уточнения исполнителя | Кейc/шаг, заданный вопрос, был ли ответ уже в переданных источниках. |
| Неизвестное правило или подготовка | Адресный вопрос, кого спросить и какое покрытие зависит от ответа; отдельный класс, не дефект приложения. |
| Нарушение подтверждённого правила | Источник и наблюдение реального прогона; оформить по процессу расследования, не ослаблять ожидание кейса. |

Существенные ошибки — удаление подтверждённого нужного покрытия, выдуманное
ожидание и публикация кейса с неизвестным или недостижимым способом подготовки.
Их нужно устранить до передачи каталога исполнителям. Нет универсальной нормы
«убрать N% кейсов»: сокращение полезно только при сохранении покрытия.

Для сравнения старого и нового навыка используй одну исходную ревизию
требований, одинаковые данные и одинаковый доступ. Не раскрывай автору решения
ревьюера до завершения задания. Сравни замечания и уточнения, затем проверь
исправления на оставленных примерах. Даже удачный пилот на одной функции не
доказывает качество для всех функций проекта.

## Учебная проверка перед пилотом

Можно сначала дать автору только
[input.md](../examples/test-case-quality/input.md), а ревьюеру отдельно
[reviewer-reference.md](../examples/test-case-quality/reviewer-reference.md).
У этого набора 15 синтетических кандидатов; он помогает заметить нарушения
маршрута, а реальный пилот оценивает пользу в условиях вашей команды.
Пример готового JSON и команды структурной проверки находятся в
[README](../examples/test-case-quality/README.md).

Сохрани ответы автора, замечания ревьюера, уточнения исполнителя и точную
версию QA-пакета в локальных артефактах задачи. Результаты и персональные
доступы в поставку пакета не включай. После пилота передай замечания с ссылками
на конкретные источники и кейсы: это основание для следующей доработки навыка.

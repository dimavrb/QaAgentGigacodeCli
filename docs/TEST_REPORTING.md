# Отчёт по бизнес-кейсам и конфигурациям

Роль `qa-test-report-writer` создаёт итоговый или промежуточный снимок из сохранённых материалов. Сборка отчёта не разрешает запуск продукта, изменение тогглов или подготовку данных. Координатор принимает содержание и отдельно применяет критерии готовности релиза. `test_report_ready` означает готовый документ, включая неполное тестирование.

## Входы и владельцы

1. Аналитик/автор плана связывает бизнес-кейсы, требования и сценарии в `scope.json`. Для небольшой задачи это делает координатор по известному источнику. Отдельный полный тест-план не обязателен. Неизвестная связь или требуемое значение остаются вопросом проектирования; reporter возвращает `needs_analysis`.
2. Исполнитель сохраняет прежний `feature_test_complete` либо полную матрицу `blocked` без изменения старой схемы. Условия фиксируются в момент соответствующего исполнения, а не читаются задним числом из изменившегося стенда. Координатор связывает результат, назначение и снимок условий в `runs.json`.
3. Координатор читает источник, фактическое выполнение, условия и доказательства; сохраняет отдельное ревью. Reporter не создаёт запись успешного ревью за него.
4. Reporter проверяет входы и вызывает сборщик; summary объясняет факты и ограничения по MESSAGES.md. Передача истории диалога целиком не требуется.

Для автотестов нужны фактические сценарные результаты и логи исполнения с теми же ID. Написанный тест, `ready_for_review`, discovery или обещание запуска не являются выполненным бизнес-сценарием. Внешние форматы JUnit/Allure не импортируются автоматически: при нормализации результата указывай первичный лог, реальный исполнитель/CI и условия; не объявляй собственный повторный запуск. Нормализованный отчёт проходит содержательное ревью.

## Область проверки — scope.json

Полный учебный пример: `examples/test-reporting/scope.json`. Схема этого артефакта независима от каталога кейсов и QA-событий.

| Поле | Назначение |
| --- | --- |
| `schema_version: 1`, `task_id`, `scope_revision`, `feature` | Задача и фиксированная ревизия согласованной области |
| `scope_kind` | `product` либо `synthetic`; учебные результаты явно маркируются |
| `business_cases` | Объекты `business_case_id`, `title`, `source`, `check_ids`; необязательная `business_goal` — бизнес-цель из `source` |
| `configurations` | Объекты `configuration_id`, `environment_id`, `product_version`, `requirements_revision`, `context`, `feature_flags` |
| `checks` | Объекты `check_id`, `scenario_id`, `configuration_id`, `required` (boolean), `requirement_source`; необязательный `intent` — описание планируемой проверки |

Для понятного отчёта заполняй `business_goal` и `intent` по источникам. `intent` содержит три непустые строки: `action` (действие пользователя), `business_rule` (проверяемое правило), `expected_effect` (наблюдаемый ожидаемый эффект). Основание всех трёх — `requirement_source`; не добавляй правило, которого там нет. Это краткое описание согласованной проверки, не копия шагов каталога и не подтверждение её выполнения. Поля остаются необязательными: старые входы принимаются, а отсутствие деталей показывается прямо в отчёте. Неизвестные подробности не блокируют сборку корректного частичного отчёта.

```json
{
  "intent": {
    "action": "Оплатить свой заказ картой",
    "business_rule": "Покупатель может оплатить свой заказ картой при обоих значениях new_checkout",
    "expected_effect": "Заказ оплачен"
  }
}
```

Единица покрытия — **scenario_id × configuration_id**, а не число попыток или файлов. Один check_id можно использовать в нескольких бизнес-кейсах, без удвоения общего счётчика. Каждый бизнес-кейс содержит хотя бы одну обязательную проверку; все проверки относятся к бизнес-кейсам. Дополнительный непройденный кейс остаётся в матрице, но итог бизнес-кейса вычисляется по обязательному набору. Обязательность задаётся до исполнения; сокращать набор для зелёного отчёта нельзя.

`context` задаёт существенные условия: `role`, `channel`, `browser`, `data_profile`, платформу, организацию/когорту или состояние интеграции, когда это влияет на проверку. Значения могут быть строками, boolean, числами или JSON-структурами. В scope сохраняются только известные требуемые значения. В observed context отсутствие или null означают unknown. Не выдавай один браузер/роль за покрытие остальных. Матрица охватывает согласованную область, не все возможные условия приложения.

`feature_flags` в scope — словарь имя → требуемое значение/вариант. Включай существенные тогглы и согласованные комбинации, включая OFF/альтернативный вариант при необходимости. Используй TEST_DESIGN.md для выбора сочетаний; отчёт сам не расширяет область и не строит тесты.

## Как описывается проверенный функционал

Основная часть Markdown читается без переходов к сценариям: бизнес-цель → целевые условия и тогглы → планируемое действие и правило → ожидание исполнителя → записанные действия → фактическое наблюдение → граница вывода. ID и ссылки расположены после содержания и в технической матрице. Повторы и счётчики по-прежнему считаются по check_id, даже если проверка включена в несколько бизнес-кейсов.

Одинаковое намерение для нескольких конфигураций описывается один раз внутри бизнес-кейса. Если ожидание исполнителя дословно совпадает с expected_effect, отдельная дублирующая строка не выводится; при различии сохраняются оба значения. Одинаковые общие границы выводов также не повторяются у каждой проверки.

Действия берутся только из `scenario_results.steps`, ожидание — из `expected_result`, факт — из `actual_result`. Исполнитель записывает в `steps` фактически выполненные действия, включая просмотр результата, а не копирует весь план; в `actual_result` указывает конкретное наблюдаемое поведение. У частично выполненного заблокированного сценария сохраняются выполненные шаги и причина остановки; его ожидаемый бизнес-эффект остаётся неподтверждённым. Для not_run шаги не выдаются за выполнение. При конфликте повторов reporter не выбирает удобное наблюдение.

Сборщик отображает записи, а не доказывает их смысл. Общее «заказ оплачен» не подтверждает проверку суммы списания, чека или других правил. Они не объявляются обязательными пробелами, если не входили в согласованную область. Пустой `steps`, неизвестные условия, несовпадение конфигурации и незавершённое ревью видны рядом с выводом. Содержательный проверяющий сопоставляет описанные намерения с действиями и доказательствами; `passed` сценария не означает отдельное подтверждение каждого предложения из `business_rule`.

Развёрнутый синтетический пример — `examples/test-reporting/detailed-runs.json`; базовый `runs.json` намеренно сохраняет краткие старые записи. Reporter не исправляет их задним числом ради красивого отчёта.

## Запуски — runs.json

Артефакт содержит `schema_version: 1`, тот же `task_id` и `runs` (допускается пустой список). Каждый прогон:

| Поле | Назначение |
| --- | --- |
| `run_id`, `configuration_id`, `observed_at` | Уникальный прогон, назначенная конфигурация, ISO datetime с timezone |
| `scenario_ids` | Полный набор ID исходного назначения; сверяется с матрицей исполнителя |
| `result_artifact` | Локальный JSON-отчёт `qa-feature-tester`; пути относительны runs.json или абсолютны |
| `requirements_revision` | Фактическая версия требований; отсутствие — unknown |
| `context`, `configuration_evidence` | Фактические условия и ссылки на снимки/логи их проверки |
| `feature_flags` | Имя → `{value, status, source}`; status: confirmed/unknown/fallback |
| `review` | `{status: pending}` либо `{status: passed/changes_requested, source: <review.json>}` |
| `supersedes` | run_id предыдущего прогона или null; задаёт координатор, не reporter |

Значение тоггла фиксируется для фактической роли/организации/когорты и среды в момент теста. Глобальный переключатель не подтверждает применение варианта конкретному пользователю. Для `confirmed` нужны значение и источник; для `unknown` value=null. Возвращённое значение по умолчанию при ошибке провайдера — `fallback`, даже если это boolean false. Unknown/fallback не засчитываются как подтверждение целевой конфигурации. Секреты, токены и персональные данные в профили не переносить.

Полные пути доказательств внутри первичного QA-отчёта разрешаются относительно него. Source тоггла, configuration_evidence и review.source — относительно runs.json. Источник ожидания в scope — относительно scope.json. HTTP(S)-ссылки сохраняются, но сборщик не обращается к сети и помечает их непроверенными. Для проверяемого снимка сохраняй относящийся фрагмент/ответ/скриншот локально с исходным URL и временем; не подменяй это подтверждением смысла источника.

Не редактируй старые результаты и доказательства. Для нового назначения нужны новый request_id и отдельный файл. Для новой ревизии метаданных также сохраняй новый файл runs/scope. Для воспроизводимости прошлых снимков сохраняй также версию сборщика: проверка Markdown использует её правила отображения.

## Ревью и защита от устаревшего принятия

Начальный прогон имеет `review.status=pending`. Сборщик показывает факт выполнения и выдаёт в `report.json.runs` fingerprints для ревью: `result_sha256`, `execution_context_sha256`, `artifact_sha256`. Координатор сначала оценивает материалы, затем переносит эти fingerprints в запись:

```json
{
  "schema_version": 1,
  "task_id": "QA-123",
  "request_id": "feature-1",
  "reviewer": "qa-agent",
  "decision": "passed",
  "result_sha256": "<хеш результата>",
  "execution_context_sha256": "<хеш исходных метаданных прогона без review>",
  "artifact_sha256": {"/absolute/path/to/evidence.txt": "<хеш>"},
  "checks": {
    "expected_source": {"status": "passed", "note": "<основание>"},
    "actual_execution": {"status": "passed", "note": "<основание>"},
    "configuration_context": {"status": "passed", "note": "<основание>"},
    "evidence_support": {"status": "passed", "note": "<основание>"}
  }
}
```

Это шаблон, не готовое принятие. Допустимы passed/failed/unknown в checks и passed/changes_requested в decision. Passed требует все четыре проверки passed с конкретными заметками. Artifact fingerprints охватывают все локальные источники требований, условий, тогглов и доказательств прогона; пути относительно файла review либо абсолютны. Метаданные fingerprint включают также назначение и supersedes. После изменения любого связанного материала нужно новое ревью. Переносить хеш ради обхода замечания нельзя.

Хеши подтверждают неизменность, а не факт выполнения или авторство проверяющего. Поле reviewer не является системой аутентификации. Содержательное решение и соблюдение разделения ролей принадлежат координатору; программная проверка не читает смысл изображений и логов.

## Выбор результата и счётчики

Если одному check соответствуют несколько прогонов, без явной цепочки supersedes результат остаётся conflict. Нельзя выбирать удачный, самый новый по времени или последний в списке. Повтор заменяет только сценарии, которые действительно входят в его назначение. Другие результаты сохраняются. Supersedes не пересекает configuration_id, не идёт назад по времени и не образует цикл. Смена сборки/существенных условий задаёт новую целевую конфигурацию; история остаётся отдельно. Результаты вне области сохраняются без включения в счётчики.

- `planned` — число уникальных checks, `required` — обязательных checks.
- `executed` — выбранные passed/failed, включая не совпавшие с целевыми условиями; факт остаётся виден.
- `target_executed`, `passed`, `failed` — только выбранные результаты при подтверждённых целевых условиях.
- `accepted_passed` — дополнительно прошедшие записанное ревью с локально проверяемыми источниками и доказательствами.

Стенд, сборка, требования, роль/данные/браузер и значения тогглов сопоставляются с конкретной целевой конфигурацией. Unknown и несовпадение сохраняют пробел в покрытии. Статус бизнес-кейса: failed (есть обязательное расхождение), incomplete (есть пробел/блокировка), needs_review (обязательные проверки прошли, принятие не завершено), passed (обязательные проверки прошли и приняты). Failed — расхождение исполнителя; подтверждение продуктового дефекта и Jira по-прежнему требуют процесса INVESTIGATION.md. Report всегда имеет `release_decision=not_assessed`.

## Сборка и проверка

Из корня пакета, в новый каталог:

```bash
python3 scripts/build_test_report.py --scope examples/test-reporting/scope.json --runs examples/test-reporting/runs.json --revision demo-v1 --output-dir /tmp/qa-report-demo-v1
python3 scripts/build_test_report.py --check /tmp/qa-report-demo-v1
```

Скрипт использует только stdlib, не меняет входы и не запускает GIGACODE, браузер, CI или приложение. Новый снимок содержит `report.json` с фактами, источниками/хешами, историей и счётчиками и `report.md` с кратким итогом и таблицами. Существующий каталог не перезаписывается. Проверка заново собирает факты из исходников и обнаруживает изменённые доказательства, числа и Markdown. Большие области явно разделяются: максимум 1000 прогонов, 10000 checks и 50000 строк первичных результатов.

Для handoff верни событие `test_report_ready`: payload содержит `report_artifact`, `summary_artifact`, `report_revision`, `limitations` точно из JSON; оба файла перечислены в artifacts. `validate_qa_result.py` автоматически проверяет пакет отчёта, task_id, ревизию, ограничения и ссылки. Ошибка исходного файла/ревью не превращается в успешный отчёт; исправь вход либо верни конкретный blocked. Корректный неполный отчёт остаётся допустимым документом.

Оценка живой роли отдельно проверяет понятность summary и соответствие выводов источникам. Локальные тесты подтверждают агрегацию и целостность, а не качество GIGACODE или реального тестирования.

# Данные для автотестов

Состав набора и рецепт — `qa-test-data-builder`, реализация в тестовом репозитории — `qa-test-automation`, независимая оценка — `qa-autotest-reviewer`. Координатор принимает готовность. При простой задаче автоматизатор выполняет подготовку сам; отдельное назначение автору данных нужно при недостающих или сложных условиях. Применяй при новой или существенной подготовке, переиспользуя существующие фабрики и фикстуры. Новые обязательные поля QA-событий не вводятся.

Обязательное ядро — TEST_DATA_CHECKLIST.md. Этот документ — справочник: дополнительные разделы загружай по необходимости через `scripts/read_test_data_guide.py --role <имя роли> [--section <ключ>]`. Из другого репозитория используй доступный абсолютный путь к скрипту. Команда печатает чек-лист и начальные разделы роли; полный справочник и примеры в вывод не попадают.

| Роль | Начальные разделы | Дополнительные разделы по задаче |
| --- | --- | --- |
| qa-test-data-builder | composition, profile | recipe при выборе механизма; isolation при общих данных/повторах/времени; cleanup при сложной или частичной подготовке |
| qa-test-automation | recipe | composition при разработке нового набора; isolation при параллельности/повторах/времени; cleanup при изменении подготовки/очистки; profile при отсутствии готового профиля |
| qa-autotest-reviewer | review | composition/recipe для содержательного замечания; isolation/cleanup при риске общих данных, частичного сбоя или недостатке доказательств; profile при проверке передачи готовности |

Ключи соответствуют разделам ниже. Если условия дополнительного чтения есть, раздел обязателен; экономия контекста не отменяет проверку. Примеры читай, только если нужен образец реализации. Для дочитывания используй `--only-sections --section <ключ>`: чек-лист и начальные разделы повторно не печатаются. Не перечитывай уже переданный неизменившийся раздел в той же сессии. При изменении документа/условий обнови нужный фрагмент. По умолчанию координатору достаточно чек-листа и ссылок.

## Состав набора до создания

Начни с scenario_id, источника бизнес-правила и возможной ошибки. Для каждой записи укажи **свойства и связи → зачем нужна → где используется или какой неверный результат позволяет обнаружить**. Не создавай запись без назначения. Нужны как подходящие объекты, так и контрпримеры по существенным условиям: статусу, владельцу, правам или границе. Полноту выбирай по требованиям и рискам, а не числу записей.

Например, для фильтра оплаченных собственных заказов: оплаченный собственный заказ должен попасть в выдачу, неоплаченный собственный — обнаруживает отсутствие фильтрации по статусу, оплаченный чужой — отсутствие ограничения владельца. Требование доступа должно быть подтверждено источником. Сценарий обязан проверять присутствие ожидаемого объекта и отсутствие неподходящих: проверка «все возвращённые оплачены» проходит на пустом списке.

Границы, пустую выдачу и запрещённые состояния оформляй отдельными именованными вариантами, если они проверяют другое правило. Комбинации планируй по TEST_DESIGN.md, сохраняя обязательные критерии и ограничения допустимости; не создавай декартово произведение всех полей без обоснования. Не выдумывай допустимые статусы, связи и ожидаемые результаты. Неясный инвариант — вопрос координатору до подготовки затронутой части.

## Рецепт и фикстура

Фабрика создаёт одну сущность с явными значимыми свойствами и действующими бизнес-инвариантами. Рецепт объединяет фабрики в нужный сценарный набор; фикстура отвечает за жизненный цикл и возвращает тесту именованные объекты/ID, а не позиционный список. Не копируй подготовку между тестами, но и не делай универсальный набор для всех сценариев.

Выбирай механизм из существующих возможностей репозитория:

| Уровень проверки | Способ подготовки |
| --- | --- |
| Unit/компонентный | Фабрики объектов и контролируемые ответы зависимостей; не доказательство живой интеграции |
| Интеграционный в изолированной БД | Штатные миграции + фабрика/seed; SQL допустим при контролируемой схеме и сохранении инвариантов |
| API/UI на общем стенде | Штатный API или тестовый механизм, сохраняющий бизнес-связи; UI, если другого корректного способа нет |
| Проверяется сам процесс создания/перехода | Подготовка только до начала проверяемого действия; это действие выполняет тест |

Не заменяй проверяемую оплату установкой status=paid. В тесте чтения оплаченного заказа такое состояние допустимо только через корректный рецепт: необходимые связи с платёжными сущностями и событиями сохраняются. Testcontainers создаёт инфраструктуру, но не проектирует набор данных. Не вводи зависимость или административную возможность только по названию этого документа.

## Изоляция, повтор и время

Переиспользуй код рецепта; изменяемые сущности создавай отдельно для теста/попытки. Пространство имён должно различать независимые CI-запуски, worker, тест и попытку. При повторе неоднозначно завершившегося создания сначала выясни фактическое состояние по корреляции/идемпотентному ключу, а не создавай дубликат. Новый retry — новая попытка с собственными данными после проверки предыдущей; порядок тестов не является предусловием.

Неизменяемые справочники можно разделять с проверкой нужной версии и свойств. Аккаунт worker допустимо переиспользовать, если каждый тест восстанавливает изменённое состояние; при невозможности восстановления нужна отдельная учётная запись. Изолированный браузер не изолирует записи БД. Не сбрасывай общую БД или организацию ради одного теста.

Статусы, суммы, роли, границы и существенные тогглы задавай явно. Случайные технические идентификаторы допустимы для уникальности и не меняют проверяемое правило. Для исследовательской случайной генерации сохраняй seed **и фактические значения**; seed без версии генератора и входных условий не гарантирует повтор. Для временных границ фиксируй часы при доступной изоляции либо сохраняй согласованный момент/зону и реальные ограничения. Не рассчитывай на произвольный sleep.

## Готовность и очистка

После подготовки проверь все обязательные свойства/связи и видимость для нужной роли в используемом канале. Успешный ответ создания не подтверждает готовность. Для асинхронной подготовки используй наблюдаемый критерий и ограниченное ожидание, затем сохрани причину таймаута; не объявляй данные готовыми. Проверка предусловий не заменяет assert тестируемого действия.

Регистрируй успешно созданные ресурсы для очистки сразу, до следующего потенциально падающего шага. При частичном сбое очисти уже созданные ресурсы в обратном порядке зависимостей. Удаляй только принадлежащие данной попытке объекты по подтверждённым ID; чужие и общие данные не трогай. Очистка запускается и после падения теста. Её ошибка сохраняется отдельно и не маскирует исходную ошибку. При остановке процесса teardown может не выполниться: если нужны TTL/сборщик остатков, они также ограничены владельцем и сроком жизни данных. Если удаление недоступно, заранее опиши безопасный срок жизни/альтернативу и ограничение.

Не используй секреты и реальные персональные данные в рецептах и артефактах. Для синтетических сущностей сохраняй только диагностические свойства и идентификаторы; для чувствительных — безопасные ссылки/псевдонимы. Полные ответы не нужны для объяснения набора.

## Компактный профиль и передача

Профиль по AUTOTEST_QUALITY.md дополни в существующем артефакте, не в длинном сообщении:

- scenario_id, источник/версия правила, окружение/сборка и существенные роль/организация/тогглы;
- таблица «имя записи → свойства и связи → назначение/обнаруживаемая ошибка»;
- ссылка на фабрику/фикстуру и команды подготовки, область изоляции, срок жизни и очистка;
- критерии готовности, фактически проверенные свойства и доказательства либо ограничения;
- для выполненной попытки — корреляция, полученные безопасные ID и результаты очистки; для проектирования — только рецепт, без заявления о готовности.

`data_ready` выдаётся после фактической проверки всех назначенных предусловий. Готовый рецепт без выполнения и доказательств ещё не готовые данные: сохрани непройденные условия и соответствующий blocked/частичный результат по CONTRACT.md. Для `data_partial` готовые и заблокированные ID вместе составляют назначение; независимые сценарии продолжаются. Артефакт передаётся через существующий `artifacts`, подробности готовности/очистки — в существующих verified_properties/cleanup. Не меняй схему событий ради таблицы.

## Ревью данных

Проверь назначение каждой записи, источник ожидания, контрпримеры, отсутствие зависимости от пустого результата, повторяемость, параллельную изоляцию и частичную очистку. Подтверждай адресным повтором/параллельным запуском при риске общих данных и доступном окружении; при недоступности разделяй «проверено в коде» и «проверено запуском» в checks/limitations. Не выдавай синтетический пример за проверку стенда.

# Автообновление перед QA-сессией

С версии 2.1.5 запускайте GIGACODE через `qa-start`: обновление выполняется
до загрузки ролей, skills и MCP, а новая сессия получает согласованную версию.
Нужны Python 3.10+, Git 2.36+, локальная POSIX/macOS/Linux или WSL FS и CLI с поддержкой
`gigacode extensions update qa-agent`. Auth и модель остаются настройками GIGACODE.
Если эта команда требует предварительный uninstall, используйте
[ручную переустановку](EXTENSIONS.md#ручная-переустановка-если-update-требует-uninstall).
В такой сборке `qa-start` не может завершить замену пакета самостоятельно.

## Разовая установка

```bash
mkdir -p "$HOME/qa-tools"
git clone https://github.com/dimavrb/QaAgentGigacodeCli.git "$HOME/qa-tools/qa-agent"
gigacode extensions install "$HOME/qa-tools/qa-agent"
```

Install принимает локальную папку, не Git URL. В интерактивном менеджере тоже
укажите её полный путь. Сохраните этот clone: менеджер обновляет установленную
копию именно из зарегистрированного источника. Используйте один источник для
всех проектов этой пользовательской установки; `qa-start` запускайте из него.
Не используйте link для автообновления: он предназначен для разработки.

Откройте `gigacode` из папки приложения и один раз выполните `/qa:init`,
`/qa:doctor`. Затем закройте сессию. В своём shell задайте:

```bash
alias qa-start='python3 "$HOME/qa-tools/qa-agent/scripts/qa_start.py"'
```

Сохраните строку в своём shell-профиле для следующих терминалов. Агент не меняет
этот профиль автоматически. Дальше запускайте `qa-start` из папки приложения.
При первом запуске появится игнорируемый `.qa-agent/update.local.json` с путями
локального источника и установленной копии; адреса продуктовых систем не нужны.

## Что происходит при запуске

1. Launcher читает локальную привязку проекта и берёт общую блокировку версии.
2. Проверяет активные сессии, процессы GIGACODE и managed-состояния зарегистрированных
   проектов в `.qa-agent-state/`. Незавершённая работа откладывает смену пакета.
3. Для чистого `main` с origin этого репозитория выполняет fetch. Допускается
   только fast-forward и повышение VERSION вместе с версией манифеста. Требуются
   успешный CI точного SHA и полная предвалидация в отдельном каталоге по UPDATE_SAFETY.md.
4. Сохраняет независимый recovery helper, backup установки и намерение, обновляет
   локальный clone и вызывает `gigacode extensions update qa-agent`. Сверяет содержимое,
   проверяет свежий launcher/MCP и синхронизирует файлы до completion markers.
5. Перезапускает собственный код с сохранённой блокировкой, освежает привязку
   новым `qa_project.py init` и открывает GIGACODE из продукта. Общая блокировка
   удерживается до завершения сессии; другие `qa-start` могут работать с той же версией.

`.qa-agent/APP_CONTEXT.md`, продуктовые кейсы, автотесты, auth, managed-состояния
и доказательства сохраняются. При обычном обновлении Git reset/force pull и правка
registry не выполняются. Отдельный явный rollback может отменить только сохранённый
собственный fast-forward, после проверки чистоты и identity. После новых инструкций
нужен новый managed-план. Порядок/пределы — [UPDATE_SAFETY.md](UPDATE_SAFETY.md).
После освежения binding `qa-start` синхронизирует управляемые проектные роли
через установленный `qa_project_agents.py --managed-only`: неизменённые копии
обновляются, адаптации сохраняются, конфликты блокируют новую сессию. При
активных сессиях выполняется только preview. Подключение без истории требует
первого явного `--apply`. Подробности — [PROJECT_AGENT_UPDATES.md](PROJECT_AGENT_UPDATES.md).

## Отказы и управление

- Нет сети: запускается неизменённая установленная версия, выводится `offline_cached`.
- Нет успешного CI точного main SHA: `release_not_verified`, запуск на прежней версии.
- Активна другая сессия/задача: обновление откладывается; новая сессия использует
  прежний пакет. Пока updater держит эксклюзивную блокировку, повторите запуск позже.
- Изменён установленный пакет: локальные правки сохраняются, обновление откладывается.
- Грязный исходный clone, другая ветка/origin или расхождение main: запуск сообщает
  ошибку. Сохраните/разберите изменения; updater не переписывает их.
- Частичная установка или ошибка CLI: новая QA-сессия не открывается. Намерение
  остаётся; следующий запуск сначала читает состояние и восстанавливает применение.
  Для независимого отката после остановки работы используйте внешний recovery zipapp
  по UPDATE_SAFETY.md. Старый pending без snapshot автоматически не мигрирует.
- CLI требует uninstall: выводится исходный ответ и ссылка на порядок ручной
  переустановки в EXTENSIONS.md; автоматического удаления нет. Сохраните pending,
  recovery snapshot и подготовленный commit источника. После install в прежний
  путь повторите `qa-start --update-only` для сверки и завершения активации.
- Изменились пути источника/установки: проверьте новую локальную установку и привязку,
  затем явно пересоздайте update.local.json. Не подменяйте пути автоматически.

```bash
qa-start --no-update
qa-start --update-only
qa-start --project-root /absolute/path/to/app
qa-start -- --model YOUR_CONFIGURED_MODEL
```

`--no-update` использует установленную версию; незавершённую активацию обходить
этим флагом нельзя. `--update-only` проверяет/применяет обновление без открытия
сессии. Статусы выводятся в stderr, код ошибки — 2. Дополнительные аргументы после
`--` передаются CLI без ослабления его режима разрешений.

Общий журнал намерения/список проектов/lock находятся в
`~/.gigacode/qa-agent-updates/`; путь можно явно изменить через `--state-dir`.
Все связанные сессии должны использовать один профиль блокировки. Он не является
источником секретов или новой командой удаления кейсов.
В этом же профиле хранятся qa-recover.pyz, recovery.json и rollback snapshots;
helper не импортирует обновляемый checkout. Снимки не удаляются автоматически.

Контроль охватывает сессии `qa-start`, распознаваемые процессы GIGACODE и managed-
состояния зарегистрированных проектов в стандартном каталоге. Для задач со
состоянием вне этого каталога завершите исполнителей перед обновлением либо
используйте `--no-update`. Нативные install/update и отсутствие интерактивных
запросов менеджера нужно проверить на целевой сборке CLI; локальная фикстура
подтверждает наш протокол, а не поведение установленного GIGACODE.

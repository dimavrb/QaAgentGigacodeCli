# Локальная проверка передачи результатов

Все добавленные ответы и материалы синтетические. Они проверяют протокол, а не работу GIGACODE, продукта, тестового фреймворка или Jira. `review_passed` и `jira_defect_created` в примерах не означают, что реальные ревью или запись выполнены.

`routes.json` связывает четыре маршрута:

| Маршрут | Проверяемая передача |
| --- | --- |
| Анализ → план | Сохранение task_id, ID требований и сценариев, ссылок на источники; чтение плана и JSON-каталога |
| Стенд и данные → проверка | Полный набор ID, непересекающаяся готовность, совпадение окружения/сборки, выполнение только готовой части |
| Автоматизация → ревью | Совпадение ревизии, доступность diff и изменённых файлов |
| Расследование → оформление | Принятый синтетический вывод defect_confirmed, проверенное состояние и перенос ссылок на его доказательства |

Полностью заблокированный набор отдельно представлен в `feature-blocked.json`: результаты сохранены для всех назначенных ID. В отчётах одного маршрута task_id сохраняется, request_id каждого назначения различается. Подтверждённый анализ использует учебные требования из `examples/test-plan`; частичная неизвестность показана отдельно в `examples/analysis/result-partial.json`.

Запуск из корня пакета:

```bash
python3 -m unittest discover -s tests -p test_role_handoffs.py -v
```

Тесты вызывают локальный CLI-валидатор для сохранённых отчётов и проверяют связи между ними. Отрицательные случаи включают пустой анализ, потерянные/дублированные ID, неподтверждённые ожидания без вопросов, пересечение готовых и заблокированных ID, пропущенные результаты и отсутствие назначения при проверке готовности.

Файлы `evidence.txt`, `changes.diff`, `autotest.py` — явные заглушки для проверки чтения ссылок; тесты не принимают их за продуктовые доказательства. Используемое состояние расследования также учебное. Истинность ожиданий, качество assert и фактическое создание задачи этими проверками не устанавливаются. Живые запуски модели не входят в этот этап.

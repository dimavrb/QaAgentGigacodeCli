# Учебные названия автотестов и Allure-шагов

Синтетический пример, не требование приложения. Источник ожидания для примера: фильтр возвращает только заказы выбранного статуса; в наборе есть оплаченный и неоплаченный заказы. Правила — `docs/AUTOTEST_NAMING.md`.

| Неясно или неверно | Содержательное название |
| --- | --- |
| `testFilter`, «Проверка фильтра», «TC-001» | `Список заказов — выбран статус «Оплачен» — возвращены только оплаченные заказы` |
| «Шаг 1», «Отправить запрос» | `Запросить список заказов со статусом «Оплачен»` |
| «Проверить результат», «Всё работает» | `Проверить, что все возвращённые заказы имеют статус «Оплачен»` |
| «Оплата — заказ оплачен — деньги списаны», когда assert проверяет только поле статуса | `Заказ — успешный ответ оплаты — статус изменён на «Оплачен»` (только если именно это требует источник) |

Проверка фильтра должна также подтверждать присутствие ожидаемого заказа: условие «все возвращённые оплачены» само по себе проходит на пустом списке. Название не исправляет слабый assert.

Порядок верхних шагов для этого примера:

1. `Подготовить оплаченный и неоплаченный заказы` — подготовка данных.
2. `Запросить список заказов со статусом «Оплачен»` — выполняемый запрос.
3. `Проверить, что список содержит подготовленный оплаченный заказ` — assert принадлежности.
4. `Проверить, что все возвращённые заказы имеют статус «Оплачен»` — assert по каждому элементу.
5. `Удалить созданные заказы` — очистка, включая случай падения.

## Фрагмент pytest + Allure

Ниже фрагмент интеграции, не самостоятельный исполняемый тест: `orders_api` и `prepared_orders` обозначают существующие фикстуры целевого проекта. API и поля синтетические; не копируй их как контракт приложения.

```python
import allure

@allure.title("Список заказов — выбран статус «Оплачен» — возвращены только оплаченные заказы")
def test_paid_filter(orders_api, prepared_orders):
    with allure.step("Запросить список заказов со статусом «Оплачен»"):
        orders = orders_api.list(status="paid")
    with allure.step("Проверить, что список содержит подготовленный оплаченный заказ"):
        assert prepared_orders.paid_id in {order["id"] for order in orders}
    with allure.step("Проверить, что все возвращённые заказы имеют статус «Оплачен»"):
        assert all(order["status"] == "paid" for order in orders)
```

Подготовку и гарантированную очистку записывает действующая фикстура. Если она не записывает Allure-шаги, автор не утверждает, что они присутствуют в отчёте. Идентификатор подготовленного заказа используется в assert, а не добавляется в название.

## Пример записи ревью

- Связь: `TC-001 → test_paid_filter`; имя сохраняет условие и ожидание учебного сценария.
- Проверено в коде: два проверочных шага содержат assert; пустой список не считается успехом; ошибки не перехватываются.
- Отображение Allure: не проверено, этот пример не запускался с адаптером. Для рабочего задания приложить свежий результат адресного запуска либо сохранить это ограничение.

Плохой вариант: `with allure.step("Проверить, что деньги списаны"):` с единственным assert `order.status == "paid"`. Ревьюер просит исправление: шаг обещает проверку списания, для которой нет ни источника, ни наблюдения.

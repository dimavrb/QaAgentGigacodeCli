# GitVerse → вебхук → Jenkins → ручные кейсы ТестОпс

Переносимый пример для ТестОпс 5.27 из qatools.ru. Канонические сценарии остаются
в JSON по `docs/TEST_CASE_STYLE.md`. Python 3.10+ компилирует их в открытый формат
Allure; Jenkins загружает файлы официальным плагином ТестОпс. Java/JUnit остаётся
стеком настоящих автотестов: для публикации ручного каталога Java не требуется.

Основание — [статья «Тест-кейсы как код»](https://qatools.ru/blog/tpost/tldpbn5vj1-test-keisi-kak-kod-ruchnoe-testirovanie).
В ней используется pytest с ручной меткой. Здесь тот же транспорт Allure,
но без запуска каркасов тестов и без дублирования JSON в Python/JUnit.

Параметры реальных систем не требуются для подготовки этого примера. Агент
собирает URL репозитория/Jenkins/ТестОпс, ветку, ID проекта и ID credentials
при переходе к подготовке инфраструктуры по `docs/TESTOPS_JENKINS.md`.

## Что именно публикуется

Это путь через импорт Allure-результатов, а не API-операция изменения карточки.
Публикация создаёт запуск в ТестОпс с ручными сценариями. Файлы содержат
`ALLURE_MANUAL=true`, `status=unknown`, `stage=pending`; успешного выполнения
генератор не объявляет. Обновление карточек и состояние запуска зависят от
обработки вашей сборкой ТестОпс и закрытия запуска. Их нужно проверить в пилоте.
Не закрывайте автоматически такие запуски до определения процесса ручного выполнения.

Каждое действие сохраняется отдельным шагом. Его `expected_result` представлен
вложенным шагом с префиксом «Ожидаемый результат:». Это текстовое представление,
а не нативный контейнер ожидаемых результатов ТестОпс. Предусловия и источник
сохраняются в HTML-описании с экранированием текста. Если нужны отдельные нативные
секции предусловий/ожиданий, потребуется прямое обновление сценария через API/MCP;
нельзя считать текущий пример полной передачей внутренней модели ТестОпс.

Поддерживается базовая схема каталога: `schema_version`, `test_cases` и пять
обязательных полей кейса. Дополнительные поля, параметры и вложения отвергаются,
чтобы не потерять их молча. Учебные `catalogs/orders.json` не являются тестами
вашего продукта и не должны автоматически отправляться в рабочий проект.
Повторяющиеся JSON-ключи, версия схемы, отличная от целого числа 1, и символические ссылки в
каталоге отвергаются: они могут скрыть часть исходных сценариев или ID.

## Проверка локально

Из корня QA-пакета:

```bash
python3 scripts/build_manual_allure.py \
  --catalog-dir examples/testops-jenkins/catalogs \
  --namespace demo.manual \
  --output artifacts/manual-pilot/allure-results \
  --manifest artifacts/manual-pilot/manifest.json

python3 -m unittest discover -s tests -p 'test_manual_allure.py' -v
```

Команда не обращается к ТестОпс и не выполняет продуктовые действия. Выходная
директория должна быть новой или пустой. Для повторного локального прогона
выберите другой путь. Обе Jenkins-джобы очищают свою рабочую директорию перед
checkout, чтобы сбой не оставил результаты предыдущей сборки для архивирования.
Используйте отдельные рабочие директории джоб без вручную сохранённых файлов.
Manifest лежит вне Allure-директории и содержит локальные ID, идентичность
кейсов, хеш каталога и хеши исходных файлов. Это доказательство подготовки,
а не подтверждение загрузки на сервер.

## Идентичность и связь с JUnit

`fullName = namespace + '::' + scenario_id`; `testCaseId` и `historyId` — SHA256
этого имени. Разделитель `::` не допускается в namespace, поэтому границы
namespace и ID однозначны. Название, шаги и расположение JSON-файла не входят в идентичность.
Namespace фиксируется для одного каталога/проекта и не меняется при переносе
файлов. Один сценарий должен существовать в каталоге ровно один раз.

При первом импорте ТестОпс назначит свои числовые ID. Для существующих карточек
запишите проверенное сопоставление в отдельный файл, аналогичный
`id-map.example.json`, вне директории каталогов:

```json
{
  "schema_version": 1,
  "namespace": "product.manual",
  "endpoint": "https://testops.example.com",
  "project_id": "123",
  "cases": {"TC-001": "1042"}
}
```

Цифры приведены только для формы файла: используйте ID существующей карточки.
Передайте `--id-map`, `--endpoint` и `--project-id`; генератор проверит совпадение
инстанса, проекта и namespace. Проверить существование ID удалённо он не может.
Если ID-карта содержит отсутствующий сценарий, сборка остановится: удаление
кейса из Git не удаляет его в ТестОпс и требует отдельного решения.

После автоматизации свяжите настоящий JUnit-тест через `@AllureId("1042")`.
Одновременно уберите сценарий из ручного публикуемого каталога и его ID-карты,
иначе следующий импорт ручного каталога может конфликтовать с автоматизацией.
Автотестам выделите отдельную Jenkins-джобу и каталог Allure-результатов.

## Две Jenkins-джобы

Потребуются Git, Python 3.10+, Pipeline, Git plugin, Generic Webhook Trigger и
официальный плагин ТестОпс. Агенты Jenkins должны иметь сетевой доступ к GitVerse,
а агент публикации — также к ТестОпс. Версии Jenkins, Java и плагина ТестОпс
согласуйте по [инструкции поставщика](https://docs.qatools.ru/integrations/ci-servers/jenkins/).

Создайте два обычных Pipeline from SCM. Репозиторий, credentials чтения Git
и ветку получения Pipeline задайте в настройках джоб; URL из вебхука не используйте.

В целевом продуктовом репозитории должны находиться директория `scripts/` этого
QA-пакета (генератор использует существующий валидатор и его зависимости),
Jenkins-шаблоны и отдельная директория `test-cases/` с продуктовыми каталогами.
Либо подключите QA-пакет в фиксированном подкаталоге и согласованно измените пути
к скриптам в Pipeline. Все Python-инструменты используют стандартную библиотеку.

| Джоба | Script Path | Ветка Pipeline в SCM | Назначение |
| --- | --- | --- | --- |
| `manual-cases-validate` | `examples/testops-jenkins/Jenkinsfile.validate` | `*/main` | Подготовка каталога из проверяемой ветки; загрузки в ТестОпс нет |
| `manual-cases-publish` | `examples/testops-jenkins/Jenkinsfile.publish` | `*/main` | Подготовка и публикация только основной ветки |

Если основная ветка называется `master`, поменяйте SCM-настройку, `MAIN_BRANCH`
и фильтр вебхука согласованно. Не разрешайте параметризованный выбор SCM-ветки
для джобы публикации. Для обеих джоб Pipeline должен загружаться из защищённой
основной ветки; preview затем переключает только рабочую копию на ветку события.
Preview исполняет Python из этой ветки: выделите ему отдельный агент без токенов
ТестОпс и прочих credentials публикации, а Git-credentials — только на чтение.

В шаблонах замените:

- `REPLACE_OWNER/REPLACE_REPO` в фильтре на точное `owner/repository` GitVerse
  (экранируйте метасимволы регулярного выражения, например точки);
- `CATALOG_DIR` на директорию **только ручных** продуктовых JSON-каталогов;
- `IDENTITY_NAMESPACE` на постоянный namespace вашего каталога;
- метки агентов `qa-python-preview` и `qa-python` на существующие метки Jenkins.

Для публикации настройте сервер ТестОпс через Manage Jenkins и credentials
Secret text `testops-manual-token`. Заполните `TESTOPS_ENDPOINT`,
`TESTOPS_SERVER_ID`, `TESTOPS_PROJECT_ID`, при наличии — `ID_MAP`.
Endpoint должен совпадать с URL сервера выбранного `TESTOPS_SERVER_ID`.
Сгенерируйте `withAllureUpload` через Pipeline Syntax вашей версии плагина и
сверьте аргументы шаблона: Results path — `build/manual-publication/allure-results`,
Index Existing Files — включён, Silent Mode — выключен.
Генерация завершается до входа в блок загрузки; старые файлы предварительно удалены.

По умолчанию `PUBLISH=false`: первый ручной Build with Parameters применяет
конфигурацию триггера и проверяет подготовку без отправки. После пилота измените
в защищённой ветке `defaultValue` на `true`, примените обновлённый Pipeline и
проверьте значение параметра по умолчанию в джобе. Это включит автоматическую
публикацию при вебхуке. Повторная ручная проверка возможна с `PUBLISH=false`.

`disableConcurrentBuilds()` сериализует сборки одной джобы. Несколько разных
джоб публикации в один и тот же каталог ТестОпс не создавайте. Повторная доставка
вебхука не дедуплицируется: она может создать дополнительный запуск с теми же
кейсами. Стабильные ID предназначены для повторного использования карточек,
а не для подавления запусков. Автоматических retry после неопределённого исхода
загрузки нет; сначала проверьте запуск в ТестОпс.

## Вебхуки GitVerse

Используется [Generic Webhook Trigger](https://plugins.jenkins.io/generic-webhook-trigger/):
он принимает POST, извлекает поля через JSONPath и фильтрует события регулярным
выражением. Создайте два независимых Secret text credentials:
`gitverse-manual-validate-webhook` и `gitverse-manual-publish-webhook`.
Это токены запуска джоб, а не токен ТестОпс.

В GitVerse → репозиторий → Настройки → Вебхуки добавьте custom URL для каждой
джобы. Адрес обработчика:

```text
https://jenkins.example.com/generic-webhook-trigger/invoke?token=<ТОКЕН_ЭТОЙ_ДЖОБЫ>
```

Передавайте токен заголовком `token`, если ваша настройка вебхука это позволяет;
параметр URL поддерживается плагином, но URL с токеном не должен попадать в Git,
скриншоты и журналы прокси. Выберите только событие push/сохранения коммитов,
не все события. Merge в основную ветку порождает push; отдельный merge-триггер
не добавляйте, чтобы не запускать публикацию дважды.

Шаблоны **предполагают**, что payload содержит `ref` и
`repository.full_name`. Общая документация GitVerse не фиксирует эту схему для
custom URL. Перед включением загрузки получите тестовую доставку и сверяйте
JSONPath с реальным payload. В плагине используйте `gwt-dry-run: true` для
проверки маршрутизации без запуска сборки. Если формат отличается, измените
JSONPath и фильтр; не убирайте фильтрацию репозитория и основной ветки.

Фильтр публикации ожидает:

```text
REPLACE_OWNER/REPLACE_REPO:refs/heads/main
```

Вебхук нужен только как сигнал. Джоба публикации получает текущую основную
ветку из настроенного SCM и проверяет её commit; присланный URL/SHA не исполняется.
Поздно доставленный вебхук поэтому не заставляет публикацию загружать старую ветку.
На стороне GitVerse защитите основную ветку: прямые push запретите, изменения —
через ревью. Ограничьте доступ к Jenkins endpoint по правилам вашей инфраструктуры.

## Пилот перед рабочим включением

1. В отдельном проекте ТестОпс опубликуйте два учебных кейса с `PUBLISH=true`.
2. Проверьте тип Manual, полный сценарий, описание, предусловия и ожидания,
   статусы без ложного Passed, связи Jenkins ↔ запуск.
3. Определите, когда карточки обновляются и кто закрывает запуск. Закрытие
   незавершённого ручного запуска может менять статусы его результатов.
4. Сверьте назначенные TestOps ID; измените название, шаг и расположение файла,
   опубликуйте снова. Должно остаться две карточки с прежними ID.
5. Отправьте вебхук рабочей ветки: сработает preview, публикация — нет.
6. Отправьте webhook основной ветки: сработает публикация. Проверьте повторную
   доставку и ошибку сети; не считайте отсутствие дублей запусков доказанным.
7. После подтверждения обработки файлов вашей сборкой включите автоматическую
   публикацию для рабочего каталога. Ошибка загрузки должна завершать джобу ошибкой.

Локальная проверка этого примера покрывает генератор и его отказы. Jenkins,
формат живого вебхука и обработка ручных файлов вашим ТестОпс без доступа к
инстансам не проверены. Если требуется только обновить карточки без запуска,
нужна другая джоба с прямым API/MCP-обновлением, а не путь статьи.

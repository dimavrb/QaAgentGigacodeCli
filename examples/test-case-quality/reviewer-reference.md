# Ориентиры независимого ревью

Это **синтетические ожидаемые решения авторов набора**, не результаты работы
живого GIGACODE и не экспертная разметка реального продукта. Формулировки и
число готовых кейсов могут отличаться. Оценивай сохранённые условия, источники
ожиданий и возможность независимого выполнения.

Дай этот файл ревьюеру после получения ответа автора. Для проверки способности
автора к отбору не раскрывай файл заранее. Для реального пилота выдели ещё
примеры своей команды, которых нет в этом учебном наборе.

| Кандидат | Ожидаемое решение и основание |
| --- | --- |
| C-01 | Исходные шаги недостижимы в разрешённом UI-режиме: список не содержит `0`. Не придумывать ввод или обход DOM. Сохранить UI-проверку ограниченного набора и отдельную API-проверку `0 → 400/LIMIT_OUT_OF_RANGE`, без нового задания, по R-3. Отдельный риск серверного допуска не потерять. |
| C-02 | Включить наблюдение доступности кнопки в разрешённый UI-экспорт C-03. Самостоятельный кейс на статическую видимость у той же роли не добавляет отличающего риска. Ролевой запрет C-06 сохранить. |
| C-03 | Принять и переписать конкретно по R-2/`DATA-PAID`: фильтр, данные, скачивание, точные колонки и множество строк. «Всё правильно» не является ожиданием. |
| C-04 | Объединить с C-03: одинаковы роль, канал, фильтр, данные и наблюдаемое поведение. Слабое «файл заполнен» заменить точным составом из R-2. Другой заголовок не делает сценарий новым. |
| C-05 | Сохранить API-разрешение для `analyst`: `202`, `job_id` и факт одного нового задания. UI-сценарий не заменяет прямую проверку API-контракта. Риск зависит от уровня проверки. |
| C-06 | Сохранить отдельные условия запрета `viewer` в UI и API по R-1: отсутствующая кнопка и `403/EXPORT_FORBIDDEN` без нового задания. Не соединять смену ролей и успешный экспорт в последовательный кейс. Для каждого условия независимый доступ и данные. |
| C-07 | Сохранить нижнюю допустимую границу `1` и ровно одну строку данных по R-3. Экспорт обычной выборки из двух счетов границу не покрывает. |
| C-08 | Сохранить верхнюю допустимую границу `1000` и ровно 1000 строк данных. Не растворять в C-07 или в «допустимый лимит». Раздельные кейсы либо независимые, явно различимые наборы параметров допустимы; последовательная зависимость двух экспортов не нужна. |
| C-09 | Сохранить верхнюю недопустимую API-границу `1001`; C-01 проверяет другую сторону диапазона. Допустимы отдельный кейс или независимый именованный набор параметров с собственным ожиданием. |
| C-10 | Сохранить R-4 и спроектировать кейс с известным `DATA-EMPTY` и CSV только с заголовками. В плане указать `blocks=execution`: профиль временно выключен, нужны повторное включение и проверка готовности. Не объявлять состояние невозможным и не считать кейс готовым к запуску. Зависимость не запрещает включить спроектированный кейс в каталог. |
| C-11 | Открыть вопрос о правиле экспорта архивного отчёта, R-8. Предложенный текст не подтверждён. Не публиковать готовый кейс и не называть поведение дефектом без требования. |
| C-12 | Сохранить риск R-6 и спросить подтверждённый способ подмены контрольной суммы. Это неизвестная подготовка при известном ожидании, а не отсутствие требования. Не придумывать SQL, URL, права и текст ошибки. До разрешения вопроса не включать в готовый каталог. |
| C-13 | Сохранить редкий существенный риск по R-5. Прокси предоставляет воспроизводимый механизм: снимок заданий, ключ, первый запрос с потерянным ответом, повтор с тем же JSON/ключом, один новый `job_id`. Два отправления составляют один причинно связанный сценарий; это не независимые действия для сокращения каталога. |
| C-14 | Отделить удаление и отмену удаления от экспорта и друг от друга: разные ветви R-7, независимые свежие данные `DATA-DELETE`. Удаление и затем отмена не проверяют одну и ту же исходную запись. Сокращение количества кейсов не оправдывает зависимость от предыдущего сценария. |
| C-15 | R-2 уже подтверждает ошибку `OBS-1`: чужой ID запрещён. Сохранить сильное ожидание C-03 и связь с наблюдением/расследованием; не дублировать весь кейс и не ослаблять до «файл не пуст». Это нарушение известного правила, в отличие от C-11. Протокол синтетический, нельзя объявлять реальный дефект продукта. |

## Что проверяет ревьюер

- Карта охватывает все 15 кандидатов; у объединения есть целевой кейс или
  строка покрытия, у исключения — подтверждённая причина и способ проверки.
- Сохранились оба направления ролевого правила, различия UI/API, обе допустимые
  границы, обе недопустимые API-границы, идемпотентность, пустая выборка,
  контрольная сумма и две ветви удаления.
- У заблокированной проверки причина конкретна: неизвестное правило,
  неизвестный способ подготовки или временная недоступность известного способа.
- Исполнитель получает роль, независимые данные и нужные настройки; читает
  действие и различающее наблюдение без догадок. Секреты отсутствуют.
- Никакой кейс не утверждает выдуманный текст UI, не использует неизвестный SQL
  и не принимает отсутствие ошибки за достаточное подтверждение результата.
- В карте не дублируются подробные шаги JSON, в JSON не добавляются обязательные
  поля для данного упражнения.

Ошибочное удаление подтверждённого покрытия, выдуманное ожидание и инструкция
с неизвестным/недостижимым способом подготовки — существенные ошибки. Известный
способ с временно недоступным ресурсом допускает проектирование, но не готовность
запуска; зависимость execution должна оставаться явной. Лишний отдельный кейс или
повторное уточнение уже предоставленного сведения — замечания к качеству.
Пустой каталог не считается успешным отбором. Нормальный вариант может
содержать несколько независимых параметризованных кейсов для поддерживающего их
потребителя; перед build_manual_allure.py они должны стать отдельными кейсами
поддерживаемого формата без дополнительных полей. Ориентиром не служит
фиксированное итоговое число кейсов.

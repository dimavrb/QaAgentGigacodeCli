# Примеры API

Выбери один файл по цели текущей проверки. Не загружай все примеры. Контракты, HTTP-коды, тексты, диапазоны и данные здесь учебные: замени их требованиями приложения.

| Цель | Пример |
| --- | --- |
| Создание ресурса, позитивный сценарий | [create.json](create.json) |
| Обязательные поля, ошибка запроса и отсутствие записи | [validation.json](validation.json) |
| Выход за допустимый диапазон | [boundary.json](boundary.json) |
| Доступ к чужому ресурсу | [permissions.json](permissions.json) |
| Пагинация и порядок элементов | [pagination.json](pagination.json) |
| Отказ в отмене чужого заказа и сохранение его состояния в одном кейсе | [cancellation.json](cancellation.json) |

Если точного совпадения нет, используй ближайший пример оформления, не добавляя его сценарий в покрытие. Второй пример читай только для другого существенного аспекта, который не показан первым.

Стандарт API-кейса, как для Kafka: **Шаг — Ожидаемый результат — Тест-дата**. Короткое действие хранится в `name`, конкретные наблюдения — в `expected_result`. Колонка данных формируется из `request` (метод, путь, обязательные headers и тело none/json/text) и `response` (HTTP-статус, нужные headers и JSON-пример). Запрос и ожидаемое тело ответа находятся в строке одного действия. Не копируй их в текстовый test_data; он нужен только для дополнительных данных, SQL или инструкции. Согласованная очистка в `create.json` показана обычным шагом с сохранённым ORDER_ID, без выдуманного endpoint.

Все JSON-ответы в этих примерах имеют `scope: fragment`: это значимая часть ответа, дополнительные поля допустимы в пределах `expected_result`. Состав массива, порядок элементов и отсутствие данных проверяй по явным ожиданиям; пример сам по себе их не задаёт. `scope: exact` применяй только когда контракт требует точного JSON-значения целиком; порядок ключей объекта несущественен. Изменяемые значения не сравнивай с иллюстративными данными дословно.

Обозначения `{{TOKEN_*}}` заменяются значениями тестовых токенов способом из предусловий; реальные секреты в каталог не попадают. `{{ORDER_ID}}` в `create.json` берётся из фактического ответа создания; в примере первого ответа обозначает будущий сохранённый ID, а не строку для дословного сравнения. Учебная панель выдачи токенов, заголовки и поля ответов здесь вымышлены: в продуктовых кейсах нужен подтверждённый источник. Для запросов без тела `Content-Type` в примерах отсутствует согласно этим контрактам.

Сверка полей одного ответа остаётся в ожидании соответствующего вызова. Проверка
состояния отдельным GET относится к тому же причинно связанному кейсу; её не
заменяет статус отказа. Не увеличивай число кейсов или шагов ради каждого поля.

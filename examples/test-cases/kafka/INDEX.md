# Примеры Kafka

Для `test_type: kafka` используй формат **Шаг — Ожидаемый результат — Тест-дата**
по [TEST_CASE_STYLE.md](../../../docs/TEST_CASE_STYLE.md). Прочитай этот индекс и
один подходящий JSON-пример; HTTP-примеры не нужны для оформления Kafka-сообщения.

| Цель | Пример |
| --- | --- |
| Полученное сообщение сохраняется в БД, поля и JSON-тело сохранены | [persistence.json](persistence.json) |

Пример учебный: его cluster, topic, таблица/колонки БД, права, обязательные headers,
уникальность event_id и лимит 5000 мс вымышлены. Они не являются возможностями
подключённого приложения или общими гарантиями Kafka. Замени их подтверждённым
контрактом и доступным средством чтения. Новый бизнес-сценарий из примера не
добавляется в покрытие автоматически.

Короткое действие хранится в `name`, конкретное наблюдение — в `expected_result`,
данные публикации/SQL/ожидаемой записи — в текстовом `test_data`, когда они нужны.
Пустое поле опускается. Kafka не получает вымышленного HTTP-статуса или
request/response. Подтверждение брокера и запись в БД — разные наблюдения.

Сохраняй один причинно связанный кейс. Не делай каждый проверяемый JSON-атрибут
отдельным кейсом; сравнение полей/payload относится к записи этого сообщения.
Отдельное правило, подготовка или обнаруживаемая ошибка могут требовать другого
сценария. Для отсутствия ответа прочитай соответствующую часть стандарта: этот
позитивный пример не устанавливает готовность негативного наблюдения.

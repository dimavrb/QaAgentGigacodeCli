# Модель и комбинации — учебный пример

requirements.md подтверждает правила; model.md показывает решения доступа, пример свойства и неизвестного перехода. Для задачи только о доступе читай таблицу решений, не разворачивай дополнительные модели без основания.

combinations.json содержит конечные строковые классы factors, strength, exclude (частичные назначения), interaction_groups (полное взаимодействие перечисленных факторов) и seeds (обязательные полные назначения со стабильным combination_id). scope_sources — ссылки для содержательного ревью, генератор не проверяет их истинность. Повторный seed с теми же значениями и другим ID сохраняется, если обязателен в модели.

```bash
python3 scripts/generate_combinations.py --model examples/test-design/combinations.json --output /tmp/qa-design-combinations.json
python3 scripts/generate_combinations.py --model examples/test-design/combinations.json --check /tmp/qa-design-combinations.json
```

Генератор не перезаписывает существующий output. При изменении модели используй новый путь/ревизию. Хеш привязывает результат к точной модели. Контроль включает все допустимые взаимодействия и обязательные seeds, не доверяет счётчикам в отчёте. Алгоритм детерминированный жадный, минимальность не гарантирована; предельный полный перебор — 10000 назначений, включая исключаемые. Дополнительно допустимые назначения × число групп взаимодействия не должны превышать 250000; большой набор нужно явно разделить или передать специализированному генератору.

Учебные ready-cases.json и ready-combinations.json показывают один параметризованный
TC-ACCESS с девятью конкретными наборами. Каждый фактор используется в условии,
ожидание различает доступ и отсутствие раскрытия записи. В combinations.json
behavior_rules ссылается на синтетические подтверждённые требования. Проверка:

```bash
python3 scripts/generate_combinations.py --model examples/test-design/combinations.json --check examples/test-design/ready-combinations.json --catalog examples/test-design/ready-cases.json
```

Она проверяет полные назначения кейса/параметров, использование факторов в
условиях/действиях, ссылки на наблюдение и связи всех применимых правил. Пустые
scenario_ids и отсутствие scenario_bindings допустимы только для проектного набора
без --catalog. Ни ожидаемые HTTP-коды, ни реальные кейсы из модели автоматически
не создаются. После изменения наборов сравнивай значения строк: автоматически
созданные COMB-ID могут измениться, scenario_id существующего поведения остаётся стабильным.

Содержательное ревью сверяет факторы каждой строки с preconditions, действиями и
ожиданием связанного кейса. Один TC-ID во всех строках сам по себе не подтверждает
все комбинации. Повторная ссылка допустима только когда кейс действительно
параметризован этими значениями и охватывает соответствующие наблюдения; иначе
набор остаётся неподготовленным. Используй qa-check-quality, сохраняя карту ID и
причину объединения. Успех генератора не заменяет эту оценку.

coverage-criteria.json фиксирует ID bundle, хеш согласованной модели и независимое
направление. В QA-result передай payload.combination_coverage по docs/TEST_DESIGN.md,
reviewer сохраняет отдельный combination_check каждого binding_id. Тесты
test_combination_coverage.py проверяют такой handoff/assess/finish и реальные
worker-процессы ограниченного review-cycle. Учебные записи и fixture-verdict
не подтверждают качество GIGACODE, подготовку реального стенда или выполнение продукта.

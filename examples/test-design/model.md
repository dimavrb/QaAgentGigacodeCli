# Учебная модель поведения

Версия модели M-1; источники — requirements.md. В этой стадии ID кейсов ещё не назначены, сценарии не выполнены.

## Таблица решений доступа

| rule_id | requirement_id | Условия | Ожидаемое поведение | Статус и источник | Покрытие |
| --- | --- | --- | --- | --- | --- |
| RULE-1 | R-1 | user, own | Содержимое доступно | confirmed, requirements.md#access | строки с user/own, scenario_ids ещё не назначены |
| RULE-2 | R-1 | user, other | Чужое содержимое не раскрывается | confirmed, requirements.md#access | C-ACCESS-DENIED и остальные строки user/other |
| RULE-3 | R-2 | admin, own или other | Содержимое доступно | confirmed, requirements.md#access | строки admin, scenario_ids ещё не назначены |

R-3 обосновывает исключения клиентских комбинаций в combinations.json. Запрет просмотра user/other не исключён: это обязательный негативный вход. interaction_groups требует все допустимые сочетания role/owner/channel в дополнение к попарному покрытию; отдельно сохранён seed C-ACCESS-DENIED.

## Другие представления — только при соответствующем задании

RULE-4, R-4: просмотр не изменяет владельца и состояние (confirmed, requirements.md#lifecycle). Для задачи о побочных эффектах это обязательное свойство связывается с отдельной проверкой состояния до/после; комбинации доступа сами по себе его не подтверждают.

RULE-5, R-5: Оплачен + действие отмены → unknown, expected_result=null, source=null. Q-1: разрешена ли отмена оплаченного заказа пользователем и какое состояние/ответ следует ожидать? Q-1 блокирует проектирование этого перехода; ссылка requirements.md#lifecycle объясняет неопределённость, но не подтверждает результат. Задача о переходах потребует этого вопроса и отдельного сценария, не фиктивного кейса в каталоге.

## Контрпримеры для ревью будущего каталога

| Гипотетическая ошибка | Правило/условие | Что должно её обнаружить |
| --- | --- | --- |
| user получает чужой заказ через API | RULE-2, C-ACCESS-DENIED | Проверка отсутствия чужого содержимого; одного HTTP-статуса недостаточно без подтверждённого контракта |
| admin лишён доступа к чужому заказу | RULE-3, admin/other | Проверка доступности именно нужного заказа, а не только непустого ответа |
| UI показывает чужой заказ, API ограничивает корректно | RULE-2, user/other/ui | Отдельная UI-проверка; успех API не подтверждает UI |

До присвоения scenario_ids и проверки конкретных ожиданий эти строки обозначают необходимое покрытие, не принятое ревью. Автор добавляет ID и точный наблюдаемый результат, координатор проверяет соответствие источнику.

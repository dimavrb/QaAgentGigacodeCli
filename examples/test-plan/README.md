# Учебная последовательность тест-плана

Это синтетический пример протокола, не требования реального приложения. Выбор обязательного набора и разбор смысловых дублей показаны отдельно в `scenario-selection.md`. Каждая ревизия сохраняется отдельно для просмотра; в рабочей задаче владелец может обновлять те же файлы с историей в Git.

1. `result-v1.json`: ранняя карта; Q-1 блокирует только R-2. Координатор оценивает карту и запрашивает решение.
2. `result-v2.json`: пока ответ ожидается, каталог содержит TC-001. Частичная готовность не завершает план.
3. `result-v3.json`: ответ Q-1 подтверждён в requirements.md; добавлен TC-002. Проверить TC-002 и его зависимости, сохранить оценку v3 с базой v2. Неизменившийся TC-001 сохраняет оценку только если он действительно был принят в v2.

Проверка каждой ревизии из корня проекта (заменить N на 1, 2 или 3):

```bash
python3 scripts/validate_qa_result.py --input examples/test-plan/result-vN.json --task-id QA-PLAN-1 --request-id QA-PLAN-1-plan-N --agent qa-test-plan-writer
```

Валидатор не подтверждает качество содержания и не сохраняет ревью координатора. Решение по Q-1 здесь имитируется готовым источником; в реальной задаче нельзя подставлять ответ без подтверждения.

# Сократить кейс без потери проверки

Перепиши TC-SEARCH таблицей «Шаг — Ожидаемый результат — Тест-дата» и предусловиями.
ID и объём проверки сохрани. Длина произвольная: текст должен быть коротким и
исполнимым для человека, не читавшего обсуждение. Ниже весь подтверждённый контракт.

Учебная фикстура prepare_search возвращает BASEDOCID и непустой PRESENTED_VALUE
вместе с актуальными LAST/FIRST/MIDDLE. Они сохраняются одним снимком BASE; другие
писатели исключены до окончания кейса. Секретов нет. Данные этой фикстуры валидны.

Исходная формулировка:
«Осуществить подготовку входного сообщения и затем выполнить его отправку в топик
synth.client.search. При подготовке необходимо использовать новое значение evtId
в формате UUID и значение поля basicDocumentId, равное BASEDOCID из BASE.
После этого необходимо выполнить ожидание соответствующего сообщения в топике
synth.client.search.reply и убедиться в получении надлежащего ответа».
Сообщение UTF-8 JSON: {"evtId":"<новый UUID>","basicDocumentId":"<BASEDOCID>"}.

Ожидание автора:
«После отправки следует удостовериться, что не позднее 90 секунд от времени
broker ack получен ответ, в котором header.parentID точно совпадает с новым evtId,
body.statusCode имеет числовое значение 0, body.client.compositeKeyId равен
PRESENTED_VALUE из BASE без trim/смены регистра, а lastName/firstName/middleName
равны LAST/FIRST/MIDDLE того же снимка. Это свидетельствует о корректной работе
соответствующей системы и использовании актуальных клиентских данных».

Проверяется значение декодированных JSON-полей, не сырой текст сериализации.
Чтение ответа начинается с offsets, сохранённых до публикации; сохраняются
фактические UUID, ack со временем и ответ. Других внутренних запретов в контракте нет.

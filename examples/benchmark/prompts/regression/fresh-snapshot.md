# Исправить контрольное чтение

Спроектируй исправленные шаги TC-SNAPSHOT. Это синтетический Kafka-кейс, без запуска.
R-1: обработка evtId создаёт ровно одну строку с тем же evt_id и amount=7.
Поле amount — целое; таблица synth_events имеет ровно колонки evt_id и amount.
Подготовка и очистка выполняются учебной фикстурой только для нового UUID прогона.

Публикация: synth.events, UTF-8 JSON {"evtId":"<UUID>","amount":7}.
Контроль: SELECT evt_id, amount FROM synth_events WHERE evt_id = '<UUID>';
Подтверждённый источник — primary. Ожидание: максимум 5 с от broker ack.
wait_committed(evtId) даёт квитанцию завершения commit обработчика внутри этого
окна; это подтверждённое средство учебного клиента, а не API продукта.

В исходном кейсе SQL-клиент открыл REPEATABLE READ до публикации, прочитал
отсутствие строки и после ответа брокера повторил SELECT в той же транзакции.
Нулевая выдача была объявлена дефектом. Завершение обработчика тогда не ожидалось.

Исправь порядок и режим чтения. Сохрани ключ корреляции и срок; не предлагай
перепубликацию при задержке, лишние блокировки или увеличение SLA. Переменные
и SQL помести в «Тест-дата», условия чтения — рядом с нужным действием/в предусловия.

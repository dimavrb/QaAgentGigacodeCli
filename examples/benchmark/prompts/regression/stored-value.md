# Сохранённый идентификатор

Это синтетическое задание на проектирование; продукт не запускался. Представь один
кейс TC-STORED в JSON-каталоге и короткое основание выбора данных вне шагов.

Контракт rev-3:
- R-1: при непустом stored_key поиск возвращает именно его без пересчёта.
- R-2: lastName ответа берётся из актуального detail.surname.
- R-3: в этой ветке обработчик не фиксирует обновление строки record.
- Формат ключа: region + '/' + surname + '/' + serial слева нулями до 10 знаков.
  Допустимы исторические фамилии; ключ непустой, не маркер, длина <=255.

Подготовленная запись: record_id=R-17, region=EU, serial=7, detail.surname=IVANOV.
Предложен stored_key=EU/IVANOV/0000000007. Оцени различающую силу этих данных и
при необходимости замени stored_key допустимым значением.

Подтверждённые средства будущего ручного прогона:
- seed_record(record_id, stored_key) меняет только свой record, делает commit,
  возвращает исходные поля для restore_record(snapshot). Это полная сигнатура
  учебной фикстуры; её не нужно заменять выдуманным SQL.
- read_record(R-17) читает primary в новом READ COMMITTED снимке; возвращает
  stored_key, xmin, ctid, region, serial и detail.surname.
- Публикация UTF-8 JSON {"evtId":"<новый UUID>","recordId":"R-17"} в synth.search.
  Ответ в synth.search.reply: parentID, statusCode, client.storedKey, client.lastName.
  R-4: ответ с parentID=evtId и statusCode=0 приходит за 90 с от broker ack.
- wait_processed(evtId) возвращает сохранённую квитанцию завершения всех эффектов
  этой обработки, включая commit. В прогоне нет иных писателей и перемещения строк.

В «Тест-дата» укажи сообщение/параметры и происхождение переменных. Сохрани базу
после подготовки, затем ответ и контроль после завершения. Очистка — после
доказательств через restore_record. Ограничения версии строки учитывай по R-3;
запрет попытки незакоммиченного SQL в контракт не добавляй.

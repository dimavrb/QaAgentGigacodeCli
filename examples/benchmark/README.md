Профильные кандидаты для данных/заглушек измеряются через [PROFILE_SKILL_MEASUREMENTS.md](../../docs/PROFILE_SKILL_MEASUREMENTS.md): `profile-suite.json` (15 задач/60 критериев), `--profile-skills off/on`, независимые ведомости каждого повтора и `compare_profile_skills.py`. Отчёт показывает слабые места, исправления и регрессии по ролям, не оценивает смысл сам. Кандидаты по умолчанию выключены в runner; fixture/unavailable не дают доказательства пользы модели.

Актуальная карта Python-проверок — [tests/README.md](../../tests/README.md).

## Автоматический запуск reasoning baseline

Первый пакет добавляет исполняемый runner для этих пяти задач и повторных независимых сессий:

```bash
python3 scripts/run_agent_benchmark.py --output-dir artifacts/benchmarks/baseline-01 --model YOUR_MODEL --repeats 3 --max-wall-time 5m
```

Укажи фактически настроенный model selector или опусти --model, если используется настройка CLI. GIGACODE должен быть установлен и авторизован заранее. Runner проверяет --help/--version и наличие необходимых флагов; при недоступности CLI или несовместимости записывает unavailable и ничего не имитирует. --cli позволяет передать путь к исполняемому адаптеру; тестовый адаптер не является живой моделью.

Профиль reasoning_only передаёт текст одного задания, снимки соответствующей роли и применимых разделов стандартов. Операционные инструкции координатора передаются координаторским заданиям; все документы каждой роли не загружаются. Ответ и требуемые каталоги представляются прямо в окончательном тексте. Рабочий каталог каждой сессии новый и пустой; рубрика и ответы других испытаний не передаются. --bare отключает автоматическое окружение GIGACODE; через --exclude-tools запрещены чтение, запись, shell, веб, делегирование и мосты поиска инструментов. При выявленном tool usage запуск не считается сопоставимым. Несовместимые CLI не получают ослабленный fallback. Это ограниченный baseline рассуждений; полноценные проверки MCP, браузера и восстановления процесса оцениваются отдельно.

Список флагов задаёт контракт [headless-json-v1](../../docs/RUNTIMES.md); его семантика на живом GIGACODE пока не проверена. Preflight не заменяет проверку ограничений конкретной сборки. Профиль не заявляет изоляцию произвольного кода на уровне ОС.

Каталог результатов создаётся эксклюзивно и содержит:

- run.json: профиль, VERSION, хеш набора, версию CLI, запрошенную модель, результаты испытаний и ограничения;
- suite.json и prompts/: снимок рубрики и заданий для последующей независимой оценки; модели не передаётся;
- trace.jsonl: связанные события успешных и ошибочных запусков;
- trial-N/CASE: точные prompt.md/system.md, снимки инструкций, raw.json, stderr.txt, response.md при корректном ответе и execution.json;
- trial-N/review.json: заполненные ссылки, хеши, время и доступные токены, но все смысловые оценки not_checked.

Код runner 0 означает сохранённые ответы всех испытаний, а не прохождение критериев качества. Код 2 означает недоступность CLI, ошибку, таймаут или неверный ответ; остальные задачи после ошибки продолжаются. Ctrl-C сохраняет interrupted и возвращает 130. Отсутствующие usage/model не выводятся из длины текста; необработанный stats сохраняется в execution.json. Проверяющий устанавливает фактическую модель, конфигурацию и reviewer по доступным данным, затем независимо читает ответы и заполняет рубрику:

```bash
python3 scripts/check_benchmark_review.py --suite artifacts/benchmarks/baseline-01/suite.json --input artifacts/benchmarks/baseline-01/trial-1/review.json
```

До оценки этот вызов возвращает 1. Для каждого повторного испытания требуется отдельная оценка; не выбирай только лучший ответ. Все 20 критериев должны пройти в каждом испытании принятого baseline. Если фактическая модель неизвестна, условия не считаются полностью документированными.

Для A/B изменения инструкции self-review повтори запуск в новом каталоге с --self-review off при той же модели, версии CLI, заданиях и числе повторов. on/off меняет явные инструкции; внутренний процесс размышления модели не наблюдается. Память в обоих вариантах отключена для сравнимости. Эти результаты сравнивают между одинаковыми reasoning-профилями; прежний ручной маршрут с инструментами ниже — другая конфигурация.

Это проверка ответов живой модели, а не демонстрация заранее успешных результатов. Все данные синтетические, NDA-материалы не нужны. Источники внутри заданий не описывают реальное приложение. Задания и рубрика разделены: проверяемому агенту передавай только один файл из `prompts/`, проверяющему — `suite.json` и фактический результат.

## Запуск

1. Используй отдельную тестовую установку QA-пакета. Не запускай набор в каталоге рабочего приложения. Сохрани версии пакета, GIGACODE, модель, провайдер и профиль инструментов. Для сравнения разных версий условия одинаковы.
2. Для каждого задания начни новую сессию GIGACODE. Передай `/qa Выполни учебное задание из <абсолютный путь к одному prompts/*.md>. Сохрани результат и артефакты в <каталог этой задачи>.` Не передавай рубрику ожидаемых решений или ответы другой версии. Не загружай весь набор в контекст.
3. Сохрани окончательный ответ, QA-отчёт и созданные артефакты. Для плана проверь отчёт через `validate_qa_result.py` с фактическими task_id/request_id, ролью qa-test-plan-writer. Запуски внешних сервисов этим набором не требуются. Если GIGACODE или модель недоступны, запиши «не выполнялось», без выдуманного результата.
4. Проверяющий читает результат и связанные артефакты, затем вручную оценивает каждый критерий рубрики: `pass`, `fail` или `not_checked`. Запись `pass` требует ссылки на конкретное место фактического ответа/артефакта. Агент не принимает свою работу сам. Сохраняй ограничения; отсутствие проверки не равно успеху.

Создай пустую ведомость из корня QA-пакета:

```bash
python3 scripts/check_benchmark_review.py --init /tmp/qa-benchmark-review.json
```

В `agent_version`, `model`, `configuration` укажи фактические условия, в `reviewer` — проверяющего. Для каждого случая `output_artifact` — путь к сохранённому ответу относительно ведомости либо абсолютный; `output_sha256` — SHA-256 именно этого файла. Если вывод ссылается на дополнительные артефакты, проверяющий читает их и сохраняет их пути/хеши в своём журнале. В `evidence` запиши место, где виден результат критерия. Изменение ответа после оценки требует повторной оценки и нового хеша.

`seconds`, `input_tokens`, `output_tokens` — измеренные неотрицательные значения либо `null`, если данных нет. Не оценивай токены по числу символов. После заполнения:

```bash
python3 scripts/check_benchmark_review.py --input /tmp/qa-benchmark-review.json
```

Код 0: все критерии вручную отмечены pass и ведомость валидна. Код 1: есть fail или not_checked. Код 2: структура/ссылки/хеши ошибочны. Скрипт не оценивает смысл текста и не запускает GIGACODE; он проверяет полноту ведомости и привязку оценки к сохранённому ответу. Пустая ведомость не проходит.

## Решение о качестве

Сначала сравни число правильных решений и неподтверждённых утверждений, затем время и токены только для задач, прошедших содержательную оценку. Все 20 критериев обязательны для принятия этого контрольного набора; задача с неверным решением не компенсируется экономией токенов на другой. Набор охватывает пять типовых ошибок, но не доказывает качество всех маршрутов или браузерной интеграции.

## Общий skill и расширенный набор

`quality-suite.json` расширяет прежние пять заданий четырьмя: недоступная полезная
предпосылка, ненаблюдаемый SQL rollback, конфликт источников, vacuous all на пустой
выдаче. Всего девять задач и 36 независимых критериев; прежний suite.json сохраняет
20 критериев совместимости. Набор включает подтверждённые требования, неизвестное,
дубли, слабый assert, недоступные условия, невозможное наблюдение и частичное исполнение.

```bash
python3 scripts/run_agent_benchmark.py --suite examples/benchmark/quality-suite.json --output-dir artifacts/benchmarks/quality-off --check-quality off --repeats 3
python3 scripts/run_agent_benchmark.py --suite examples/benchmark/quality-suite.json --output-dir artifacts/benchmarks/quality-on --check-quality on --repeats 3
```

Меняй только check-quality при одинаковых модели, CLI, остальных инструкциях,
self-review и условиях. on передаёт полный skill; off отключает его явной инструкцией
и не передаёт текст skill. Это сравнение инструкций reasoning_only, не вызов
нативного инструмента skill. Снимок прежних инструкций отдельно хранится локально
в artifacts/benchmarks/check-quality-instruction-baseline-20261008; он не является
baseline кода и не содержит замера модели. Рубрика не передаётся проверяемому агенту.

Для одного/двух reviewer отдельно оцени один и тот же набор фиксированных ответов
в свежих сессиях. Сначала сохрани их хеши; каждый reviewer получает только задание,
ответ, критерии и первичные доказательства, без чужого verdict. Второе направление
должно дополнять первое (источники/покрытие и сила наблюдения/исполнение). Сравни
обнаруженные пропуски/ложные успехи, спорные блокировки, дополнительные исправления,
время и доступные токены. Не принимай ответ большинством: существенное
противоречащее замечание требует разрешения по источнику или новой ревизии.

`tests/test_check_quality.py` и examples/review-cycle проверяют локальный механизм,
контролируемое падение assert, границы приёмки, бюджет и восстановление. Они не
измеряют качество GIGACODE. До живого запуска/независимой оценки улучшение модели
остаётся не измеренным; unavailable/not_checked не превращаются в pass.

## Обязательная приёмка доказательности после 2.0

Для новых оценок предыдущие ручные команды являются только структурным/цитатным аудитом. Закрытие этапа и сравнение требуют нового маршрута docs/BENCHMARK_EVIDENCE_GATES.md: make_benchmark_grading_pack, check_benchmark_grading_pack, tool-free run_benchmark_grader, приёмка файла accept_benchmark_review и командная сводка build/check_benchmark_summary. Указанное выше ручное evidence-описание места заменено дословными цитатами response.md; note хранит объяснение отдельно. Проверь все критерии выбранного suite в каждом повторении (20 для исходного, 68 для regression-suite), без выбора лучшего trial. Для живого направления сравнения нужен measured dispersion фиксированных ответов; иначе pending_dispersion.

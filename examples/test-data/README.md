# Учебный набор для фильтра заказов

Синтетическое правило: список содержит только оплаченные заказы текущего владельца. Это не контракт приложения. Store хранит объекты в памяти; статусы paid/unpaid и строковый owner — только учебная модель, без платёжных сущностей, API и БД. Для настоящего оплаченного заказа нужен рецепт, сохраняющий инварианты приложения.

| Имя записи | Свойства/связи | Назначение и обнаруживаемая ошибка |
| --- | --- | --- |
| own_paid | paid, текущий владелец | Должен присутствовать; обнаруживает ошибочно пустую выдачу |
| own_unpaid | unpaid, тот же владелец | Не должен присутствовать; обнаруживает отсутствие фильтра по статусу |
| foreign_paid | paid, другой владелец | Не должен присутствовать; обнаруживает отсутствие ограничения владельца |

Рецепт — data_recipe.py, жизненный цикл — prepared_filter_data. Фабрика создаёт запись с явными свойствами; фикстура возвращает именованный FilterData. После каждого создания проверяются ID, owner и status; ID сразу регистрируется для очистки. Частичная подготовка и падение теста очищают ранее созданные объекты. Удаление касается только этих ID, не всех записей хранилища.

Пространство имён передаёт вызывающий тест: оно различает run/worker/test/attempt. Даже владельцы независимых наборов разные. Неизвестный результат создания в реальном API требует проверки фактического состояния; здесь создание синхронное, исключение означает отсутствие новой записи. Очистка памяти не может упасть; в реальном адаптере ошибки очистки нужно сохранять отдельно от первоначального падения. Готовность памяти не доказывает видимость на стенде.

Запуск без внешних зависимостей:

```bash
python3 -m unittest discover -s examples/test-data -v
```

Ожидается один успешный тест с проверкой точного результата и очистки. Дополнительные проверки в tests/test_test_data_example.py подтверждают изоляцию наборов, повтор после очистки, частичный сбой и непригодность пустой/неотфильтрованной выдачи. Это локальная проверка учебного рецепта, не промышленного API или реального параллельного CI.

Для рабочего профиля по docs/TEST_DATA.md добавьте scenario_id, действующий источник требования, окружение/сборку, существенные тогглы, фабрику/фикстуру проекта, критерий видимости и ограничения. Общий «существующий заказ на стенде» без проверки свойств и владельца не заменяет этот профиль.
